# スタンドアロン試作の検証記録

2026-09-26、Apple M5 / 24 GiB、macOS 27.0 (26A428)、arm64 で実施した。
結論は、既存の TypeScript 処理を共有した Tauri アプリで閲覧・編集・書き出しへ接続できたが、今回の測定では Electron に対するメモリ優位を確認できなかった、である。
Tauri の正式採用や製品要件の完了を示す記録ではない。

## 構成と再現性

- 元のリポジトリ: `557f27e960fc1c396d0e8598c3fac9b3fa5da3e3`。
- Tauri 2.11.6、CLI 2.11.5、Monaco 0.57.0、Electron 43.0.0。
- 両ホストは同じ Vite release build の `dist/` を使用した。
- 入力は `scripts/prepare.mjs` が別々の一時ディレクトリへコピーした20サンプルと3運用図。
- 共通の parse / check / format / frontmatter・extends / DOT / Graphviz WASM を使用し、PFD の意味処理を Rust へ再実装していない。
- Tauri は release `.app`、Electron は公式配布ランタイムと比較用ホストで起動した。
- 開発サーバー、開発者ツール、Puppeteer、Tauri の Node 補助プロセスは使用していない。
- Electron の UI 操作に必要なアクセシビリティ情報を得るため、測定時は `--force-renderer-accessibility` を指定した。

## 確認できたこと

両版とも23件すべてで、Node 側の基準と元テキスト・DOT・整形結果・診断の code / severity / message が一致し、SVG を描画できた。
診断の位置や、VS Code 拡張の全コマンド・全操作を比較したものではない。
結果は [Tauri](evidence/tauri-probe.json) と [Electron](evidence/electron-probe.json) に保存した。

Tauri では、単純な図の本文を書き換えるとプレビューが変わり、ディスク上の内容は保存操作まで変わらないことを確認した。
保存後のファイルを読み戻し、テスト前の内容へ戻して保存した。
大きめの図を別タブで開き、元のタブへ戻すと本文・プレビューが組で戻った。
日本語 IME、検索・補完・参照移動、すべての閉じ方や保存競合の実機受入は未実施である。

文書状態管理6件、Electron ホスト12件、Rust ホスト10件の限定テストが通過した。
文書状態管理は、描画完了順の逆転、タブを閉じて開き直した後の古い応答、保存中の別編集、保存失敗、古いディスク読取による上書きを検査する。
ホストのテストは、コーパス外アクセス・シンボリックリンク・保存時点の不一致・出力先・IPC 送信元と PDF 分離を検査する。
ローカルの Biome 検査と Markdown 改行検査も通過した。

## PDF・PNG

日本語ラベル、extends を使う preset、大きめの実装フローの3件を、各版で SVG / PNG / PDF へ書き出した。
PNG の寸法は両版ともそれぞれ 436 × 67、522 × 61、2294 × 2867 pixel だった。
SVG は両版で byte 一致した。
PDFKit で PDF を再描画し、日本語、図の端、大きい図の末尾を PNG と比較した範囲で欠落・クリップ・文字化けを認めなかった。
大きい図は81ノード・112エッジであり、これ以上の負荷や任意の SVG を保証しない。

PDF には方式差が残る。
Tauri は指定サイズがそのまま point、Electron は CSS pixel を96 dpiで解釈するため、物理ページ寸法が約0.75倍になる。
大きい図の「リリース候補版」は両版とも正しく見えるが、Electron の PDFKit テキスト抽出では一部の順序が入れ替わった。
Tauri のラベル一致は 6/6、8/8、202/202、Electron は 6/6、8/8、201/202 だった。
製品でのページ寸法・文字抽出の要件を揃える必要がある。
詳細は [Tauri PDF QA](evidence/tauri-pdf-qa.json) と [Electron PDF QA](evidence/electron-pdf-qa.json) を参照する。

## メモリの探索的測定

macOS `footprint` のプロセス群の total footprint を用い、RSS の単純合算は使っていない。
単位は MiB = 1,048,576 bytes。
各状態について1秒間隔・5秒間を指定し、5〜6点を取得した。
表の幅はその間の最小値〜最大値であり、独立した多数回の起動から得た信頼区間ではない。

| 状態 | Tauri | Electron |
| --- | ---: | ---: |
| 再起動後、単純な図を1タブで表示 | 154.8–154.9 MiB | 148.2 MiB |
| 23件検証と3件の SVG / PNG / PDF 出力後、同じ1タブで待機 | 195.0 MiB | 193.4 MiB |

表示領域は両版とも1280 × 768 CSS pixel、エディタは575 × 605 pixel。
Tauri は PID 67045 と、新規に生じた WebKit GPU / WebContent / Networking の 67061 / 67062 / 67063 を含めた。
Electron は本体 67040 と helper 67041 / 67042 / 67044 を含めた。
起動前から存在した別アプリの WebKit サービスは含めていない。
出力用ウィンドウは処理完了後に閉じた状態で、出力処理中の最大値を測った表ではない。
既存のデスクトップ環境で両アプリを動かした測定であり、OS サービスのすべてをアプリへ帰属させるものでもない。

出力後の測定開始は Tauri の検証完了から約29秒、Electron から約27秒だった。
初期探索では約206 MiB対184 MiBという結果も出たが、検証後の経過時間が約5分42秒対43秒で、エディタ高さにも1 pixelの差があった。
そのデータは `evidence/*-warm-initial.json` に残し、条件を揃え直した表の代用にはしない。
再測定でも Tauri の明確なメモリ優位はなく、「Tauriなら軽い」という前提で選定する根拠にはならない。

測定原票は `evidence/{tauri,electron}-{startup,warm}.json`。
プロセスを現在の起動に属するものへ置き換え、例えば次のように再測定する。

```sh
footprint -p <main-pid> -p <gpu-pid> -p <renderer-pid> -p <network-pid> \
  -j measurement.json --noCategories -f bytes --sample 1 --sample-duration 5
```

起動時間、編集中のピーク、多数タブ、出力中のピーク、開閉を繰り返した後の残留、最低対応 OS、長時間安定性は未測定である。
メモリ上限や採用基準もまだ決めていない。

## 残件と次の判断

試作中に文字や画面が白く見える採取結果があった。
元の描画設定へ戻した後に文字・行番号と実際の編集を確認し、最終の検証レポートには JavaScript / CSP のエラーがなかった。
途中にはウィンドウ移動アニメーションを捉えた画像や、画面操作ツールの `noWindowsAvailable` もあり、描画自体と採取・前面表示のどちらに原因があるかは未特定である。
修正済みと断定せず、製品化前に通常操作と日本語入力を含めて再確認する。

保存はディスクとの比較後に置換するため、その間に別アプリが書き込む競合は残る。
手動保存と外部変更保護の製品要件を満たすには、この競合と解決画面を実装する必要がある。

共通化の次の対象は、core の browser / Node 境界、プレビューの host 接続、エディタの言語支援である。
現在の browser path adapter と VS Code 配下の計算モジュールの直接参照は、共有可能性を見るための試作上の接続である。
Tauri で進める判断には、OS 連携・配布の小ささと、Rust 接続部・OS WebView 差異の保守を併せて評価する。
機能差を増やさない製品方針は [SPEC.md](SPEC.md) のままとする。
