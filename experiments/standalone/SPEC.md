## 1. 合意済みの方針

### 1.1 目的と対象者

VS Code を使わない人が、現在の PFDSL 拡張と同等の PFD 閲覧・編集機能を使えるようにする。
独自機能による差別化を目的にせず、VS Code 版との機能差と保守上の差分を極力なくす。
DSL を使わない図形エディタへの変更は、この目的から要求されていない。

### 1.2 対応環境

正式な対応対象は Apple Silicon 搭載 Mac の macOS とする。
Intel Mac は初版の対応対象に含めない。
最低対応 macOS 版は、Tauri・利用 API・試作結果から確定する。
将来の Windows 対応を視野に入れ、PFD の処理と共通画面に macOS 固有の仕様を持ち込まない。
Windows は継続的に検証・保守する体制を現時点で持たないため、当面の実装・配布・検証・動作保証の対象に含めない。
対応時期は約束せず、将来取り組む段階で保守担当・実機環境・対応範囲を確認する。
OS 固有処理を交換できる境界は保つが、Windows 用の実装や配布機構を先回りして作り込むことは要求しない。

### 1.3 ファイルを開く動作

| 対象 | スタンドアロン版の動作 |
| --- | --- |
| `.pfdsl` | アプリ内で開く |
| Markdown・コード・その他のファイル | OS の既定の外部アプリで開く |
| Web URL | 既定ブラウザで開く |

初版に Markdown ビューアは含めない。
将来必要になった場合は、両版で共有可能な閲覧機能として検討する。
現在の VS Code 版で関連ファイルを VS Code 内に開く動作を、今回の合意だけで外部アプリ起動へ変更しない。
この開き先の違いは、実行環境に合わせた接続部分の差として扱う。

### 1.4 外部変更と保存の保護

開いている `.pfdsl` が外部で変更され、アプリ側に未保存の編集がなければ、自動で読み直す。
アプリ側に未保存の編集があれば、それを上書きせず、外部変更との衝突を知らせる。
利用者が扱いを選ぶ前に、外部変更をアプリ側の内容で黙って上書きすることも防ぐ。

### 1.5 コマンド実行

PFD に書かれた process の command は、利用者の実行操作により、外部ターミナルを開いて実行する。
スタンドアロン版に端末を内蔵することは初版の要件にしない。
初版は Terminal.app を標準とし、Ghostty も利用者が選択できる。
shell、環境変数、実行ディレクトリ等の詳細は、外部実行という方針の中で具体化する。

### 1.6 導入に必要な環境（採用案 A1）

PDF・PNG 出力は、アプリをインストールすれば利用できる。
利用者に Node.js、Puppeteer、ブラウザ等を別途導入させない。
内部でどの描画・出力基盤を使うかは、この利用条件を満たす方式として選定する。

Git は同梱せず、利用者環境にインストールされた Git を利用する。
Git 差分機能は維持し、Git が利用できない場合はその理由と導入方法を案内する。
Git がない環境でも、PFD の閲覧・編集・書き出しと別ファイルとの比較は利用できる。
process command が要求する個別ツールは利用者環境のものを使う。

### 1.7 配布（採用案 B1）

初版は、署名・公証済みの macOS 用 DMG を GitHub Releases で配布する。
初版の配布先に Mac App Store は含めない。
署名・公証に必要な開発者登録や証明書の準備状況は未確認であり、必要な契約や認証情報の利用は具体化した時点で扱う。

### 1.8 更新（採用案 C2）

アプリ内で新しい版を案内し、利用者が配布ページから取得して手動で入れ替える。
初版にはアプリ本体の自動ダウンロード・置換・再起動を含めない。
更新確認のタイミング、通知を見送った場合の扱い、通信失敗時の表示は詳細仕様で定める。

### 1.9 比較した案と採用理由

導入範囲では、PDF・PNG を追加準備なしで使え、Git は既存環境を使う A1 を採用した。
Git も同梱する A2 は利用者の準備を減らせるが、Git 自体の配布・更新も保守対象になるため初版では採らない。
PDF・PNG の実行環境も利用者に導入させる A3 は同梱物を減らせるが、対象者の導入負担を増やすため採らない。

配布では、署名・公証済み DMG を GitHub Releases に置く B1 を採用した。
Mac App Store を使う B2 はストアで導入・更新できる利点があるが、審査・サンドボックスと既存機能の適合確認が加わるため初版では採らない。

更新では、通知から手動で入れ替える C2 を採用した。
完全手動の C1 は更新機構を最小にできるが、新版の存在も利用者が調べる必要がある。
アプリ内で取得・置換・再起動まで行う C3 は利用者の手間を減らせるが、更新処理と失敗時の回復が保守対象になる。
初版は、新版の案内を提供しつつ、アプリ本体の入れ替え処理を持たない C2 とする。

### 1.10 文書タブと保存

複数の PFD はタブで扱い、1つの文書タブが、その文書のエディタとプレビューを必ずセットで持つ。
タブを切り替えると、エディタとプレビューを同じ文書の組へ同時に切り替える。
エディタだけ、またはプレビューだけが別文書へ切り替わる操作モデルは採用しない。
文書タブを閉じると、その組を閉じる。

文書の保存は利用者の明示操作で行う。
初版に文書ファイルの自動保存を含めず、編集後の時間経過やタブ切替によって文書を書き込まない。
未保存内容の自動退避やクラッシュ復旧は、手動保存とは別の検討事項であり、今回の採用事項には含めない。

### 1.11 アプリ基盤と保守範囲

スタンドアロン版には Tauri を採用する。
PFD の言語処理と共通化できるプレビュー・編集計算は VS Code 版と共有し、Rust へ別実装しない。
ファイル操作、PDF 出力、外部アプリ・ターミナル起動等の OS 固有処理は接続部分へ集める。
macOS 用の処理を持つことは認め、Windows でも同じ実装が動くことを採用条件にしない。

採用理由は、既存の TypeScript 処理を共有した試作が成立したこと、配布物を小さくできること、macOS に保守範囲を絞れることの組み合わせである。
macOS では OS の WebKit を利用するため、アプリに Chromium を同梱して更新・再配布する構成を持たない。
一方で、描画環境が利用者の macOS 版に依存すること、Tauri・依存ライブラリ・アプリ自体の更新、独自の OS 接続部分の保守は引き続き必要である。
対応 macOS の下限と、日本語入力・描画・出力の実機確認を省略しない。

Electron は、Chromium の版と PDF API を OS 間で揃えやすい競合案として比較した。
現時点では Windows を積極的に保守せず、TypeScript の主要処理も両案で共有できるため、その利点より macOS での配布サイズと保守範囲を重く見て Tauri を選ぶ。
Deno Desktop は、基盤の成熟過程に伴う不具合対応を保守対象へ加えない方針から、今回の採用候補から外す。
Code-OSS は採用しない。
Electron 比較ハーネスは検証記録として残し、配布製品や機能同等性を維持する対象にはしない。

採用判断の実測根拠と限界は [RESULTS.md](RESULTS.md) に記録する。
今回のメモリ測定では Tauri の優位を確認できておらず、省メモリを採用理由にしない。
採用決定は製品要件の完了や性能保証を意味しない。
起動時間、日本語入力、大きい図の操作感、長時間安定性、署名・公証済み配布物の確認を製品化に向けて進める。

## 2. 機能同等性の範囲案

本節は参照版のソースで確認した機能を整理した案であり、配布済み拡張の実動作を確認した一覧ではない。
実装対象を確定する時点で参照版を更新し、増減した機能だけを照合する。

| 分類 | 同等にする機能 |
| --- | --- |
| テキスト編集 | 構文強調、リアルタイム診断、メタデータの表示、整形、正規化エッジの表示 |
| 構造編集支援 | ノード定義への移動、未定義ノードの定義挿入、コネクタ追加、ノード定義の並べ替え |
| 図の閲覧 | ライブプレビュー、ズーム、パン、ミニマップ、ソースと図の対応箇所への移動、extends による外部プリセットの継承設定の適用 |
| 関連情報 | location・subflow 等から関連 PFD、ファイル、URL を開く。ディレクトリ参照は配下のファイルを列挙し、候補が複数なら選択してから、ファイル種別ごとの開き先ルールを適用する。相対パスや basePath の意味を維持する |
| 差分 | 別ファイルまたは Git の参照先との図差分、その解除 |
| 出力 | DOT・SVG・PDF・PNG・TSV、および現行の一括出力 |
| プロセス操作 | process の command を明示操作で外部ターミナルへ渡して実行する導線。Terminal.app を標準とし、Ghostty も選択可能。実行環境の詳細は未決 |

同じ `.pfdsl` の構文・意味・保存内容を両版で共有する。
スタンドアロン専用の文書形式を追加しない。
アプリの表示状態等を保存する場合も、PFD の意味を環境ごとに変えない。
PFD の機能同等性には、VS Code 本体の全機能や他社拡張の再現までは含めない。
一方、現在 VS Code に依存しているという理由だけで、PFD の既存機能を除外しない。
現行実装の制約や不整合を、そのまま固定することも機能同等性の要件に含めない。
修正が必要なものは、仕様に基づく共通改善として扱い、スタンドアロン版だけの解釈を増やさない。

### 2.1 実行環境に関する確認結果

Git 差分は現在、利用者環境の Git と VS Code の workspace フォルダを使用する。
現在側は未保存の編集内容、比較側は Git 内の内容またはディスク上の別ファイルである。
現行拡張の図差分はノード・エッジ等の構造を比較し、メタデータだけの変更は比較していない。
スタンドアロン版でも利用者環境の Git を使う。
ファイル単独で開いた場合の比較基準と、Git の検出方法は未決とする。

process command は現在、VS Code の対話端末へ送信する。
独自の実行結果管理や、終了コードに基づく PFD の進捗更新は行っていない。
スタンドアロン版では外部ターミナルを使う。
command が必要とするツールをアプリがすべて同梱するとは約束せず、実行に必要な環境条件を利用者へ示す。
実行ディレクトリの扱いには相対・絶対 basePath で現行実装の違いがあるため、言語仕様との照合を経て共通の規則を確定する。

PDF・PNG 出力は現在、Puppeteer と実行可能なブラウザに依存する。
一括出力では PDF・PNG の変換に失敗しても、DOT・SVG・TSV を保存し、警告を返す経路がある。
これらの形式も初版の対象に維持し、追加の開発環境なしで利用可能にすることを初版の利用条件として確定した。
1.11節の Chromium を同梱しない方針の中で、Tauri・macOS の描画・出力機能と共通処理の接続方法を具体化する。
一括出力の部分成功を利用者へどう表示するかは、両版で共通の結果モデルとして定義する。

## 3. 初版の利用体験案

### 3.1 導入と起動

アプリのインストールで、PFD の基本的な閲覧・編集・描画と、対象の各形式への書き出しを始められる。
VS Code、Node.js、Graphviz 等の開発環境を、基本操作や PDF・PNG 出力のために別途準備させない。
Git 差分は利用者環境の Git、任意の command 実行はその command に必要な利用者環境を使う。
既存機能を黙って利用不可にしたまま、全機能が導入だけで使えるとは表示しない。

`.pfdsl` のファイル関連付け、アプリからのファイル選択、フォルダを開く操作、最近開いた対象への再アクセスを提供する案とする。
文書タブごとにテキスト編集とライブプレビューを一体として表示する。
配置の向きや幅の調整等は詳細仕様で定める。
他の PFD への移動は、対応する文書タブを開くか、既に開いている組を選択する動作とする案とする。
カーソル・スクロール・プレビューの表示位置等を文書ごとに保持し、タブ切替で戻せるようにする案とする。
描画完了が遅れて届いた場合も、切替先の文書に別文書のプレビューを表示しない。
構文エラーを表示する場合も、エディタとプレビューの文書対応を維持する。

### 3.2 編集と保存

新規作成、保存、名前を付けて保存、Undo・Redo、検索・置換、日本語入力を、PFD 編集に必要な基本操作として提供する案とする。
整形やコネクタ追加等の支援操作も Undo の対象にする。
不完全な記述や構文エラーを含む編集途中の文書を保持でき、診断やプレビュー更新の失敗で編集内容を失わない。
未保存の文書を閉じるときは、保存・破棄・取消を選べるようにする案とする。
文書ファイルへの自動保存は行わない。
前回セッションの復元、未保存内容の退避、異常終了からの回復範囲は未決とする。

### 3.3 外部変更への対応案

外部変更の検知は、表示の再読込だけでなく保存時にも確認する。
未保存編集と衝突した場合は、アプリ側の内容を保持したまま、ディスク側との差を確認できるようにする案とする。
解決方法は、ディスク側を採用する、アプリ側を別名保存する、明示的に現在のパスを上書きする、の候補から具体化する。
選択中にディスク側が再変更された場合も、古い確認結果で黙って上書きしない。
外部削除・移動・保存失敗でも、編集中の内容を保持する。
自動マージは初版の必須要件とせず、手動で解決できることを優先する案とする。

### 3.4 外部ターミナルの対応範囲と検証点

初版は Terminal.app を標準とし、Ghostty も利用者が選択できる。
任意のターミナルへ共通の方法で実行できることは初版の要件に含めない。
両アプリには AppleScript の操作経路があり、Ghostty では1.3.0以降に作業ディレクトリ・command・環境変数等を渡す API が提供されている。
ここまでの確認は公式資料によるものであり、インストール済みの版や署名済みアプリからの起動動作は未確認である。

対応アプリを絞れば、端末を内蔵する実装を伴わない限定的な連携として進められる見込みである。
保守と検証の中心は、アプリ別の起動処理、作業ディレクトリ、利用者の shell 初期化と PATH、空白・日本語・引用符を含む引数、起動失敗と操作許可の拒否になる。
Ghostty の公式資料は macOS のオートメーション許可が必要になることも明記している。
実行中の既存セッションへ入力することを前提にせず、実行用の新しいタブまたはウィンドウを作り、終了後も結果を読める動作を検証する案とする。
ターミナルへの受け渡し成功と command 自体の成功を区別し、今回の連携だけで終了コード収集や PFD の進捗自動更新を追加しない。

根拠: [Terminal の AppleScript 対応](https://support.apple.com/guide/terminal/trml1003/mac)、[Ghostty の AppleScript API](https://ghostty.org/docs/features/applescript)。

## 4. 保守と共通化の設計要件案

解析・検証・整形・差分・変換等の PFD 処理と、共通化できるプレビュー画面・操作を共有する。
プレビューの複製を両版で別々に修正する運用を避ける。
VS Code API や OS API への依存は、文書の読み書き、編集履歴、ファイル起動、ダイアログ、端末等との接続部分に集める。
PFD の解析・変換・編集計算等、環境から独立させる処理が VS Code の API を直接要求する構成にはしない。
ホストとの接続部分には、VS Code API と Tauri・macOS API それぞれへの依存を認める。
Windows を追加するときに、PFD の意味処理を別実装にしなくてよい境界を保つ。

PFD 機能の追加・修正は、原則として両版に反映する。
共通の入力と期待結果を使って、両版の同等性を確認する。
OS 固有の画面や、合意済みの関連ファイルの開き先について、ピクセル単位の一致を求めない。
リリース日を必ず同期させるかどうかは未決とし、機能の実装共有と配布運用を分けて検討する。

現行では core、graphviz-exporter、preview-engine、metadata-exporter が分離されている。
拡張側の編集バッファ・プレビュー通信・ナビゲーション・端末等には VS Code 依存が残る。
アプリ基盤は1.11節の Tauri とし、既存コードの共有単位と接続方法は小さな動作確認を通じて具体化する。

## 5. 受け入れ確認案

1. 対応する macOS 環境で、VS Code や開発環境を追加せずに基本的な閲覧・編集・描画と PDF・PNG を含む各形式の書き出しを利用できる。
2. 共通の PFD 入力に対し、両版の診断・整形結果・図の意味・差分結果・出力内容が同等になる。入力条件には本文だけでなく、文書の保存場所、extends の参照ファイル、保存前の新規文書かどうかを含める。
3. 構造編集支援を適用して Undo・Redo でき、保存した文書をもう一方の版で編集できる。
4. 未保存の編集をプレビューへ反映でき、構文エラーの発生と修正を往復しても編集内容を保持する。
5. 関連 PFD はアプリ内、その他のファイルは既定アプリ、Web URL は既定ブラウザで開く。ディレクトリ参照では候補がない場合、1件の場合、複数件から選択する場合を確認する。
6. 相対パス・basePath・subflow の参照先が、同じ文書を開いた VS Code 版と一致する。
7. 外部変更時に、未編集なら再読込し、未保存編集があれば双方を黙って上書きしない。
8. 再変更・外部削除・保存失敗・未保存での終了を試し、編集内容を失わず解決操作へ進める。
9. Git 差分・PDF/PNG 出力・command 実行は、決定した依存条件と提供方式を満たす実環境で確認する。command は指定の外部ターミナルで、決定した実行ディレクトリと環境により実行されることを確認する。
10. Git がない場合は導入方法を案内し、それ以外の閲覧・編集・書き出し・別ファイル比較を利用できる。
11. 署名・公証済み DMG を取得した環境でインストールし、起動とファイル関連付けを確認する。
12. 新しい版の通知から正しい配布先を開ける。通知だけでアプリの置換や再起動は起こらず、更新確認の失敗で文書操作を妨げない。
13. 複数の PFD を開き、タブ切替とタブを閉じる操作でエディタ・プレビューが組として切り替わる。描画が遅れた場合や構文エラーを含む文書でも、別文書の組に混ざらない。
14. 編集後の待機・タブ切替では文書ファイルを書き込まず、保存操作で選択中の文書を保存する。

共通処理のテスト成功だけで、インストール、OS のファイル関連付け、日本語入力、保存保護、外部アプリ起動を確認済みとは扱わない。

## 8. 採用前のアプリ基盤比較と検証計画（履歴）

本節は試作開始前にソースと公式資料から整理した方式比較と検証計画の履歴である。
現行の採用方針は1.11節、試作で確認できた範囲と残件は [RESULTS.md](RESULTS.md) を参照する。
本節中の実装・実機に関する未確認事項は、その比較案を作成した時点の状態を表す。
共有率、工数、配布サイズ、性能の実測結果を示す節ではなく、試作の進展だけで候補の採用へ読み替えない。
A1・B1・C2 の採用は、本節の方式の採用を意味しない。

| 候補 | 共通化できる部分 |
| --- | --- |
| Electron と組み込みエディタで専用アプリを作る | 現行の TypeScript / Node.js による PFD 処理、抽出したプレビュー、エディタから独立した編集計算 |
| Tauri と組み込みエディタで専用アプリを作る | 抽出したプレビュー、環境から独立した PFD 処理。Node 処理を補助プロセスとして保持する方法もある |
| Code-OSS に既存拡張を組み込んだ専用配布を作る | 拡張の機能登録・編集処理と、エディタが既に持つ保存・Undo 等 |

上表の保守対象は、順に次のとおりである。

- Electron 案: 文書の開閉・保存と競合保護、組み込みエディタへの診断・hover・編集操作の接続、OS との接続、Electron の更新追従。
- Tauri 案: 文書管理とエディタへの接続に加え、Node 依存処理との橋渡しまたは環境非依存化、PDF・PNG 出力の経路、OS ごとの WebView 差への対応。
- Code-OSS 案: エディタ本体のビルド・更新追従、専用アプリとしての初期画面やメニュー、一般ファイルと端末を外部へ渡す接続、A1 の出力環境の準備。

### 8.1 Electron 案の検討根拠

Electron はアプリのメイン側で Node.js を使えるため、現行の Node 依存処理を保持しやすい。
PDF 出力と画面キャプチャの API があり、A1 を満たす出力経路の候補になる。
この API だけで既存 PDF・PNG と同じ結果になるとは限らず、図全体の寸法、フォント、日本語、大きい図等を共通の期待結果で確認する必要がある。

エディタ部品の候補として Monaco がある。
Monaco は VS Code 由来のエディタだが、VS Code 拡張をそのまま動かす仕組みではない。
診断・hover・整形・コネクタ編集等は、共通の計算処理とエディタ固有の接続に分ける必要がある。
現行の TextMate 文法も、Monaco へ自動的に引き継がれるとは扱わない。

### 8.2 Tauri 案の検討根拠

Tauri は OS の WebView を使うため、ブラウザエンジン自体をアプリに同梱しない構成を選べる。
ただし現行 core の公開入口には Node のパス処理等も含まれ、プレビューだけの再利用と、解析処理全体のブラウザ動作は別に確認する必要がある。
既存 Node 処理を補助プロセスとして同梱する選択肢もあり、採用に Rust への全面書き換えが必須というわけではない。
その場合は、補助プロセスの配布と通信も保守対象になる。
OS の WebView を利用することによる配布サイズの利点と、実行時のメモリ消費は別に評価する。
Tauri も複数プロセスを使うため、メインプロセスだけを測って軽量性を判断しない。
macOS の WKWebView には PDF 生成と画像取得の API があり、独立した Chromium を追加せずに A1 を満たす候補になる。
ただし Tauri からの接続方法、図全体の出力、フォントと描画の同等性は未検証であり、Windows でも同じ実装が使えるとは扱わない。

### 8.3 Code-OSS 案の検討根拠

機能同等性を保つ方法として、既存の拡張ホストと編集環境をそのまま使う案も比較する。
公開ソースの Code-OSS と、Microsoft が配布する VS Code 製品は区別する。
この案でも、非 PFD ファイルを既定アプリで開く動作、外部ターミナル実行、追加準備なしの PDF・PNG 出力は実装・配布側で用意する必要がある。
共通化要件は「既存拡張を変えずに載せれば全要件を満たす」という意味ではない。

### 8.4 試作開始時の提案と検証点

メモリ効率への懸念を受け、既存コードの共有しやすさに加えて、実利用時のメモリ消費を方式比較の軸にする。
比較検証の進め方は Tauri 案を先に検証し、同じ機能・入力を持つ Electron 案を比較対象にする。
これは Tauri の採用やメモリ優位を確認した結論ではない。
Electron 案の既存 Node 処理を保持しやすい利点は維持し、Tauri 案で増える接続処理の保守と、メモリ等の改善が見合うかを確かめる。
Code-OSS 案も既存拡張を広く再利用する比較対象として残すが、エディタ本体を含めた負担を評価する。

Tauri 案でも PFD の解析・整形・検証等を Rust へ別実装することは前提にしない。
共通の TypeScript 処理とプレビューを保ち、ファイル操作・パス解決等の環境依存部分を接続する構成を検証する。
Node の補助プロセスや追加の出力処理が必要になった場合は、それらも配布・保守・メモリの比較対象に含める。

方式を確定する前に、代表的な PFD を使い、次の経路で共有可能性を確かめる。

1. 同じ解析・DOT 生成とプレビュー部品で、図と診断を表示する。
2. コネクタ追加等の既存編集計算を適用し、Undo・Redo と未保存プレビューを往復する。
3. PDF・PNG を追加準備なしで出力し、既存版の期待結果と照合する。
4. 外部変更と未保存編集の衝突を検知し、編集中の内容を保持する。

検証で共有できない部分や追加の保守対象が明らかになった場合は、その事実を使って方式比較を更新する。

### 8.5 メモリ比較の条件案

配布サイズ、起動時間、メモリ消費、操作の応答時間を別々に記録する。
同じ Mac、macOS、PFD と参照ファイル、エディタ部品と設定、表示サイズ、文書数、操作順を使い、配布用ビルドを比較する。
文書タブのエディタとプレビューが組で切り替わる条件を両案でそろえ、開いているタブ数と、非表示タブの処理・保持状態を記録する。
1文書タブを1つの WebView や1つの描画エンジンへ対応させる実装は要件ではなく、文書ごとの状態と表示の対応を保ったうえで資源の共有・遅延生成を検討する。
開発サーバーや開発者ツールを含めた測定と、利用者が実行する構成の測定を混ぜない。
使用したアプリ・WebView・エディタ・描画ライブラリの版を記録する。

起動直後、通常の図の表示、編集中、大きい図または複数文書の表示、PDF・PNG 出力時の最大値、文書の開閉を繰り返した後の残留メモリを確認する。
プレビューだけの最小試作で得た数値を、保存・編集・出力まで備えた製品の数値として扱わない。
WebView・GPU・Node 等の関連プロセスを対象に含め、OS が別サービスとして起動する処理も含めて測定範囲を記録する。
プロセスの RSS の単純合算を総消費量と呼ばず、共有ページの扱いと物理メモリ負荷を比較できる測定方法を先に決める。
複数回の結果とばらつきを残し、特定の1回だけで方式の優位を判断しない。
具体的なメモリ上限や採用に必要な改善幅は、利用対象の図と利用環境を具体化したうえで定める。

基本的な機能同等性の比較には、このリポジトリの `docs/samples/*.pfdsl` を使う。
参照版では20ファイルあり、日本語、メタデータ、グループ、subflow、extends、basePath 等の例を含む。

タブを切り替えてもエディタとプレビューの組が保たれ、非表示の文書へ戻ったときも編集内容が保持されることを確認する。
編集・保存・外部変更の検証には一時コピーを使い、リポジトリの元サンプルを書き換えない。
例示用の外部 URL や command が書かれていることと、外部アプリ・端末の実動作確認が済んだことは区別する。
