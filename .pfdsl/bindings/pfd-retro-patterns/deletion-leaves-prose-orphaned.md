- **成果物の削除が、それを名指す散文を置き去りにする trap**: ファイルを削除するとき、機械的な参照（import・呼び出し・trigger 正規表現・テスト）は検査が拾う。拾わないのは、削除した実体を**名前で説明している散文**である。PFD の `description`・companion の解説・コード冒頭コメントは、名前を書いているだけで参照ではないため、どの検査も落ちない。
  問いの形: 「今削除した名前は、どこかで**説明されて**いないか。`location:` のリンク切れ検査は届かない範囲である」。
  `meta check-links` が見るのは `location:` フィールドのみで、`description` 本文中のパス名は対象外。機械化も一般には難しい — 削除の経緯を記す散文（「〜は削除した」）は削除後も正しく、素朴な実在検査では偽陽性になる。
  具体例: 呼び出し元を失った CLI エントリを削除した際、`pipeline.pfdsl` の `gen_skill` description と sibling companion がそのファイルを「切り出し先」として名指したまま残っていた。全テストと `check-script-imports` は緑（#668、2026-08-05）。
  対策: 削除のコミットでは、削除する名前をリポジトリ全体に grep し、ヒットを「参照」と「説明」に仕分ける。説明側は実体を指し直すか、削除の事実を述べる形に書き換える。
