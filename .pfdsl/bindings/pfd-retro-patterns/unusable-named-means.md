- **規約が名指しする手段を実行主体が起動できない trap**: 運用規約が特定のコマンド・スキルを名指しすると、実行主体（AI）の権限でそれを起動できない場合に、規約が構造的に満たせなくなる。
  外部ツールの不在（上の「実行環境の暗黙前提 trap」）と違い、**同じ harness の中にコマンドは存在する**ため、失敗が「使えない」でなく「呼べない」形で出る。
  黙って類似コマンドへ落ちるか項目ごと飛ばすかのどちらかになり、どちらも規約の遵守記録を汚す。計測を伴う規約では分母が歪む。
  問いの形: 「この規約が名指しする手段は、規約を実行する主体の権限で起動できるか。人間が手で打つ前提になっていないか」。
  具体例: `/code-review` を実施せよという実測規約に対し、`/code-review` は `disable-model-invocation` で AI からは起動できなかった（#561 実測期間、PR #569 で `/simplify` を既定に変更）。ユーザーが手で打った回にしか満たせない規約になっていた。
  対策: 手段を名指しする規約を書くときは、規約の実行主体を1語で決めてから書く。AI が回す前提なら model-invocable なものを既定に置き、人手前提のものは「ユーザーが実施する回のみ」と条件を明示する。
  **起動可否は harness と plugin の版に依存する属性であり、記録した時点の観測でしかない。** 規約に「起動できない」と書いたら、その根拠を後続セッションが継承してよい事実として扱わない — 従う前にコマンド定義の実体を確認する。逆向きの陳腐化（起動できるようになったのに規約が禁止のまま残る）は、規約を満たせない形でなく**選択肢を1つ失ったまま気付かない**形で出るため、失敗として観測されない。
  具体例（逆向き）: 上の `/code-review` は後に `disable-model-invocation: false` になっており、規約が名指しする「AI からは起動できない」という前提のほうが偽になっていた（2026-07-28 の retro で検出）。規約は起動可否でなく**手段の適性**（プロトコルの重さ・PR の要否）で書き直した。
  **起動可否は、名指しされた手段そのものの属性でないこともある。** そのセッションに与えられた指示が道具クラスごと封じている場合、名指しされたコマンド・スキルは model-invocable のまま、それを回す手立てだけが無い。
  規約の側からは区別できない — 規約が知っているのは手段の名前だけで、実行主体の設定は規約の外にある。
  この形が厄介なのは、規約が「軽くしてよい」と認めている観点で起きたときに、実行主体が未実施を軽量化として記録できてしまう点である。担保の中核が独立性・多重性のように委譲でしか作れない性質なら、自分で回すことは軽い実施ではなく不実施である。
  問いの形の追加: 「この観点の担保の中核は、重さを落としても残る性質か、委譲そのものでしか作れない性質か。後者を自分で回した回は、軽量化でなく不実施として扱ったか」。
  具体例: レビュー観点3（設計妥当性）が発火したサイクルで、その中核である「解答を含まないツリーで独立に解かせる」を実行できなかった（セッションの指示が subagent の起動を禁じていた）。実行主体は未実施として PR 本文に記録したが、同じ節の「発火した観点は軽くしてよい」に寄せれば、自己レビューを軽量版として記録して閉じることもできた。
  対策: 委譲でしか作れない観点は、実行できない回にユーザーへ返す（記録して閉じない）。規約の側にその分岐を書く。
  **「起動できない」と「起動してよい条件がまだ揃っていない」は、実行主体からは同じ形に見える。** 道具クラスを封じる指示には、禁止（どうやっても起動できない）と条件付き（ユーザーが求めれば起動する）の2種類がある。後者を前者として読むと、実行主体は自分の判断で観点を落としたうえ、落とした理由を外部の制約として記録する — 記録の形からは、確かめたうえでの不能なのか、確かめずに諦めたのかを誰も区別できない。
  問いの形の追加: 「起動できないというその判断は、指示の文面を読み直して確かめたものか。条件付きなら、その条件はユーザーに尋ねれば満たせるものではないか」。
  具体例: 上の実例と同じ観点3 が発火したサイクル（2026-08-20）で、実行主体はセッションの指示を「環境が subagent の起動を許可していない」と読み、未実施のまま PR を出して PR 本文にもその理由を書いた。実際の指示は「ユーザーが求めない限り起動しない」で、尋ねれば済むものだった。ユーザーの指摘後に実施した2本（独立解・敵対レビュー）は、そのサイクルの成果物から新設した診断コードの誤検出と、別サイクルの検査の判定単位の盲点を検出した — どちらも撤回・再設計に至る誤りで、未実施のまま閉じていればマージされていた。
  対策の追加: 手段を起動できないと判断した回は、判断の根拠となった指示の文面を記録に引く。引けないなら確かめていない。この判断は実行主体が自分に有利な側（作業が減る側）に倒せるため、根拠の引用を伴わない「できなかった」は不実施と同じ扱いにする。
  **起動可否はコマンド定義だけでなく、外向き操作の許可判定でも決まる。** コマンド定義が model-invocable でも、リポの外へ書く操作は実行時に拒否されうる。この場合は規約の側でなく、規約が要求する成果物が作れないまま終わる。
  問いの形の追加: 「この項目が要求しているのはリポ内の変更か、外部システムへの書き込みか。後者なら、拒否されたときに項目をどう閉じるかが決まっているか」。
  具体例: 終端ゲートの「スコープ外の既存問題を起票した（ユーザーの指摘を待たない）」に対し、`gh issue create` が外部書き込みとして拒否された回（2026-08-04）。散文としての発見は PR 本文に残せたが、issue バックエンドを一次情報とする運用では、起票されない限り roadmap 突合にも `gh issue list` にも現れない。
  対策: 外部書き込みを要求するゲート項目は、拒否されたときの代替（一次情報への記録先と、ユーザーへ返す形）を項目自身に書く。「ユーザーの指摘を待たない」は起票の主体でなく**発見の報告を遅らせない**ことを求めており、両者は別である。
  **逆パターン（拒否されず実行されてしまう）**: 上の実例は拒否されて成果物が欠けるだけで閉じたが、`gh issue create` が拒否されずに通り、issue が確認なしに作成されてしまう回もある（#887、2026-08-11）。実行環境の権限チェッカーが事後的に検出し以降の操作をブロックしたが、issue 自体は公開済みで取り消せない。前者は実害が「欠落」で閉じるのに対し、こちらは実害が「外部への確定した書き込み」まで進む分、大きい。
  対策の追加: 「ユーザーの指摘を待たない」条項に従って発見を即座に扱うことと、外部公開操作（issue 起票・コメント投稿等）を確認なしに実行してよいことは別である。発見自体は待たずに報告し、起票の実行は一度ユーザーに提示して同意を得てから行う。
  **起動できるかどうかと、起動した手段が効いたかどうかは別の問いである。** 名指された手段が成功を返しても、狙った状態変化が起きていないことがある。この形は「呼べない」より検出が遅れる — 戻り値が成功なので実行主体は次の手順へ進み、効いていないことは後続の失敗としてしか現れない。
  問いの形の追加: 「この手段は起動できただけか、効いたことまで確かめたか。成功の戻り値と、狙った状態変化は別物ではないか」。
  具体例: sibling worktree への `git add` を止めたガードが、拒否メッセージで「セッションの作業ディレクトリを対象 worktree へ移せ」と対処法を名指しした。名指された手段は起動でき、「ターン終了時に移動する」と成功を返したが、次ターンでも `pwd` は main repo を、`git branch --show-current` は `main` を返した。コマンド中の `cd` を書いてもガードはそれを追跡して対象を解決するため判定は変わらず、そのサイクルのコミット3回はすべて人手へ渡した（#1012、2026-08-28）。
  対策の追加: 対処法を名指しする拒否メッセージを書くときは、その手段が効いたことを実行主体が確認できる形（確認コマンドと期待値）まで書く。確認手段を書けないなら、その対処法は名指しでなく「人間へ渡せ」と書く。
