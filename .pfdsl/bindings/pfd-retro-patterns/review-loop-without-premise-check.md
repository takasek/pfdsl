> 過去事例（保存基準: 33878aeb）。本文の対策・判断は当時の記録であり、現行の指示ではない。現行手順は [pfd-retro binding](../pfd-retro.md) を参照。

- **指摘に対応するだけのレビュー往復が収束しない trap**: レビューを繰り返すとき、各周を「findings を読む → 採否を決める → 直す → 再投入」だけで回すと、周回数が増えても残 findings が減らないことがある。
  レビュアーがずれているのではない。**毎周渡している成果物が変わっている**ため、同じものを複数人が見て合意へ向かう形になっておらず、直前の修正が次の攻撃面を作る。
  この形は findings の件数推移からは読めない。1〜3件が毎周出続けるのは「まだ掘るべきものがある」とも「掘り方が同じところを回っている」とも読めるためで、前者と解釈している限り対応を続ける判断は毎回もっともらしい。
  問いの形: 「今周の指摘は、前周までに自分が入れた修正が作ったものか。同じ類型の指摘が2周続いていないか」。
  指摘そのものへの反論も、決めたうえで**通告**するのと、前提を相手に問い返すのとで効き方が違う。通告は自分の判断が正しい場合にしか働かず、誤っていた却下は検証されないまま残る。
  具体例: `#1174` の実装（PR #1187）で敵対的レビューを23周回した。1〜11周目は完全な一方向ループで、12周目から収束判定・過剰厳密かの判別といったメタな問いを足したが、それは**指摘の系列**についての問いであり、個々の指摘の前提を問い返した回は0だった。異議のある指摘は自分で処分し、次のプロンプトで「反映しない。理由: …」と通告した。自分の修正が次の欠陥を生んだ回は 5→6、6→7、19→21、21→22 で確認できる（2026-09-13）。
  具体例: 同じ23周のうち14〜18周目の6件超は、すべて「CI の失敗マスク、または判定対象の逸脱の、別スコープ・別表記」という単一類型だった（step の `env` を固定すれば job/workflow の `env`、operator を弾けば `{0}` を無視する shell template、options を辞書で読めば重複引数の command substitution）。個別に塞ぎ続け、19周目に workflow 全体を期待ドキュメントと比較する形へ変えたら222行減って既知の変異を全件捕捉した。同じ結論へ14周目で到達できたはずで、遅れた理由は対応モードから議論モードへ切り替わらなかったことにある。
  具体例: 指摘の前提が争える性質であることの裏付けとして、同じ設計点で2人のレビュアーが逆を主張した実例がある。敵対的レビュー5周目は `commitSubjectStep` に checker を注入する seam を足せと言い、`/simplify` の altitude 角度はその seam をテストのためだけの本番表面として落とせと言った。どちらの前提も検証していなかった。
  対策の候補（当時）: 同型の指摘が2周続いたら、個別対応の前に検査設計そのものを議題にする。CLAUDE.md の「同じ検出器から2周続けて欠陥が出たら、直すべきは実装でなく検査設計」は条件としては既にあり、この回は条件成立（5→6周目）から適用（19周目）まで7周かかった。規則の不在ではなく、対応モードに入ると条件の成立自体を見に行かなくなる形。
  **停止条件だけを足しても解にならない。** 打ち切りが早くなるだけで、指摘→対応の形のままなら残 findings は同じ速度でしか減らない。
