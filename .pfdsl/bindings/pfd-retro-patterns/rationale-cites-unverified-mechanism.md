- **採否の理由が、動かして確かめていない他機構の挙動に依拠する trap**: 案を採る・却下する理由として「別の機構がこう振る舞うから」と書いたとき、その振る舞いを実際に起こして見ないまま記録が確定する。理由は選択記録・JSDoc・PR 本文へ同時に写されるので、誤りは1箇所でなく3箇所に定着する。
  問いの形: 「この理由が名指している他機構の振る舞いを、その機構を動かして見たか。読んだのは関数名・JSDoc・コメントだけではないか」。
  **機械検査は全て緑になる。** 選択記録は必須行頭を備え、時点照合を通り、テストも通る — 検査が見ているのは記録の形と、変更した側の挙動であって、理由が引用した側の挙動ではない。理由の真偽を確かめる材料は、どのゲートの入力にも入っていない。
  **関数名・JSDoc・コメントは「何をするつもりか」を述べる器であって、「何を返すか」ではない。** 名前が `classifyDesignRecordContent` で JSDoc が内容検査を語っていても、その戻り値を呼び出し側が判定に使っているとは限らない。読む対象は呼び出し側の分岐である。
  具体例: preflight の閾値を「必須3行が揃っている」へ上げる理由として、着手前の選択記録と JSDoc の両方に「終端ゲートの内容検査が3行を全て要求するので、3行揃わない entry を当選させることは『後で必ず内容不備で FAIL する文章』を確定済みと報告することだ」と書いた（#927）。実際には `gate-check-steps.mjs` は `status: timing.status` を返すだけで、内容検査の FAIL は `WARN:` 付きで detail へ降格されている — #737 案1 が実測（content は true 0 / false 3、timing は true 3 / false 0）に基づいて「content は報告材料であって判定ではない」と決めた結果である。3行揃わない記録は終端ゲートを PASS する。敵対レビューが `designRecordStep` を1行だけの記録で実際に走らせて PASS を再現し、理由が偽であることを示した。採用した閾値そのものは残ったが、理由は実測（直近の設計記録12件に行頭のみの基準を当てて欠落0件、#737 の3件は複合検査の処分トークン側から出ていた）へ差し替えた。
  **却下した案そのものの性能を語る理由は、この trap の中で最も確かめにくい形である。** 名指す機構が既存でなく「その案が作ったはずの実装」なので、走らせる対象も引用する呼び出し側も原理的に存在しない。上の対策はこの形に対して何も要求せず素通しになり、しかも却下した以上は誰もその実装を書かないため、理由が偽であっても反証が生まれる機会が来ない。
  具体例: #953（dispatch のテーブル迂回を塞ぐ）で、起票者が挙げた「dispatch のソースを走査する lint」を却下し、採用した挙動 probe の理由を「lint は構文形を列挙しきれないので、probe が捕まえるものを lint は捕まえられない」と書いた。前半（列挙しきれない）は正しいが、後半の含意（probe が lint を包含する）は偽だった。独立レビューが `if (command.startsWith("graph") && command !== "graph")` を構成し、これが新しい文字列リテラルを一切導入しない — 既にテーブルにある語を再利用する — ため、ソースのリテラルを走査して候補を作る probe には当てる語が生まれないことを示した。実際に注入すると probe は `PASS (59)` を返し、`run(["graphs"])` は `bypass-hit` を返した。lint 側なら `.startsWith` による `command` 比較として即座に挙がる形である。2つの機構は同じ失敗の型に対する別経路であり、どちらも他方を包含しない（`detection-covers-one-path-only` の比較選択への適用）。理由は「両者は別経路を塞ぐ」へ差し替え、probe には第2の候補生成器（既知コマンド名の拡張）を足し、残る経路をコメントと PR 本文に明示した（2026-08-21）。
  対策: 理由に他機構の名前が現れたら、その機構を実際に走らせた出力を理由と一緒に記録へ書く。走らせられない機構なら、呼び出し側の分岐を引用する。どちらも書けない場合、その理由は成立していないので、自分の変更だけで閉じる理由に置き換える。
  却下した案の性能を語る場合は、走らせる代わりに**両案が取り違える具体例を1つ構成する** — 一方だけが捕まえる入力を実際に書く。構成できたなら包含関係は無く、理由を「別経路を塞ぐ」へ書き換える。構成しようとして書けないことを確かめた場合に限り、包含を主張してよい。
