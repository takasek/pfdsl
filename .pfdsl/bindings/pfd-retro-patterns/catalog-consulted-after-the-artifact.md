- **カタログを引く工程が、対策の効く時点より後ろにある trap**: 監査パターンのカタログは retro の工程で引かれる。retro はサイクルの最後にあるので、**サイクルの途中で書かれる成果物（PR 本文の指標・コミットメッセージ・issue コメント）の中身を守るパターンは、その成果物が既に出来上がってからしか照会されない**。
  検出は成立するので緑にはならないが、直しは常に事後の訂正になり、CI もレビューもすでに誤った記述の上を通っている。
  カタログの件数を増やしても、対策の適用時点が前へ来ないかぎりこの遅れは縮まない — パターンを足すほど「書かれているのに間に合わない」ものが増える。
  問いの形: 「このパターンの対策は工程のどの時点で効くか。カタログを引く工程は、その時点より前にあるか」。対策の文が「〜を書く前に」「着手前に」で始まるパターンは全て疑う。
  具体例: `review-baseline-drifts-to-branch-interior`（改善幅の基準がブランチの中間状態へずれる trap）は 2026-08-10 のサイクルで書かれ、その数時間後の次サイクルの PR 本文が同じ誤りを犯した（レビュー指摘で自分が作り込んだ二重計算を直し、`2 → 1` を改善幅として書いた。`origin/main` は元から1回）。カタログには対策として「指標を書く前に `git show origin/<base>:<path>` で基準側を取る」と明記されていたが、カタログを引いたのは PR 作成と CI 完走の後の retro だった。
  対策: 対策が「成果物を書く前」に効くパターンについては、参照点をサイクル内へもう1つ置く。終端ゲートで PR 本文を書く直前にサイクルのタグで `select` を引く、あるいは当該パターン群だけをゲート項目の文面へ引き写す。参照点を1つに保ったまま「retro で気をつける」に翻訳しない — 遅れの原因は注意力でなく工程の順序である。
  具体例: その2つ目の参照点を置いた後も、**それが守れる成果物は PR 本文だけだった**。プリフライトは着手前に `preArtifactPatterns` を全件印字しており（読む契機は最初からあった）、ゲート項目は「PR 本文を書く前に読み直す」と時点を指定している。しかしコード・コメント・テストはその両者の間、レビューより前に書き終わる。`claim-form-invites-restaleness`（`phase: pre-artifact`）はプリフライトの一覧に並んでいたが、実装コメント3ファイルに同じ列挙の形が入るのは止められず、retro が引くまで残った（#929、2026-08-22）。
  問いの形の追加: 「この参照点が間に合う成果物はどれか。そのサイクルが作る成果物のうち、参照点より前に書き終わるものは何か」。
