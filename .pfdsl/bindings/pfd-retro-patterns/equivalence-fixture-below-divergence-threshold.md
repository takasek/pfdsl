- **等価性検査の fixture が、食い違いの現れる規模に届かない trap**: 2つの実装が同じ値を返すことを検査するとき、fixture は「同じ形の値が返る」ことを示せる最小のものが選ばれやすい。
  片方だけが持つ上限・打ち切り・ページングは、その上限を超える入力でしか差として現れない。最小 fixture は上限の手前にあるので、検査は緑のまま両者の一致を主張し続ける。
  検査が非空であることは条件を満たさない — 非空と「差が現れる規模」は別の閾値である。
  問いの形: 「この等価性検査の fixture は、2つの実装が食い違いうる境界を跨いでいるか。片方にだけある上限・打ち切り・件数指定は何で、fixture はその値を超えているか」。
  具体例: #1044 で gh backend と HTTP backend の operation ごとの parity test を書いた。`listLabels` の gh 側は argv に `--limit 100` を持ち、HTTP 側は全ページを走査して打ち切りを持たなかった。fixture はラベル1件で、両者は当然一致した。差が出るのはラベルが100件を超えるリポだけで、検査は9 operation すべてについて緑を返し、モジュール冒頭の「both return the same parsed JS value」という主張もそのまま残った。検出したのは独立解を求めたレビューで、実装ではなく既存コードの `--limit` の扱いを読んで気付いたものだった。
  対策: 両実装が持つ数値パラメータ（上限・ページサイズ・件数指定・タイムアウト）を並べて書き出し、片方にしか無いものを列挙する。列挙が空でなければ、その値を跨ぐ fixture を1本足す。この照合はレビュー時にも効くので、検査を書いた後で気付いた回も同じ手順で足せる。
