- **作業項目が観測と推論を同じ地の文で書く trap**: 使用感プローブや障害報告から起票された作業項目は、観測したこと（agent が同じコマンドを8回叩いた）と、起票者がそこから推論した原因（種別が id から推測できないから）を、どちらも事実の記述として同じ地の文に並べる。
  読み手は症状の再現を確かめると全体を検証したつもりになるが、確かめたのは観測の側だけである。
  推論が誤っていても案は症状を解くので、実装は成功し、解いた原因が違うことは出荷後も表に出ない。
  問いの形: 「本文が原因として述べている1文は、プローブが観測したことか、観測から書き手が推論したことか。推論なら、その主張はデータ構造の不変条件で確かめられるか」。
  観測と推論の見分け方: 観測は「誰が何をした」の形で書かれ、推論は「〜だから」「〜できない」の形で書かれる。後者は起票者の頭の中でしか成立していない可能性がある。
  具体例: #844 項目2 は「`.pfdsl` は artifact と process が交互に並び、隣接の種別は id から推測できない（命名規約に依存しない）」を原因として挙げ、各隣接に `nodeKind` を足す案を出した。
  実際にはエッジは必ず artifact と process の間を走る（`buildGraph` がエッジ種別ごとに端点の種別を割り当て、group id をエッジに書いた図は N002 で弾かれる）ため、隣接の種別は自ノードの種別の逆で常に決まる — 実測は `.pfdsl/` 3図 + `docs/samples/` 全図の 555 エッジで同種端点 0 件。
  「交互に並ぶ」という本文の記述自体が二部性の言い換えであり、そこから「推測できない」は導かれない。
  真の原因は `graph neighbors` が自ノードの種別を出力していなかったこと（`describe` は出していた）で、導出の起点が出力に無かった。
  推論を検証しないまま実装すると、症状（8往復）は消えるが、常に同じ値になるキーを隣接の数だけ並べる契約が残る。
  対策: 本文の原因の1文を、実装に入る前にデータ構造の不変条件へ差し戻して確かめる。「Xできない」と書かれていたら、Xが本当にできないことを実データで数える。
  症状の再現だけでは原因は検証されない点は `stale-root-cause-diagnosis` と同じだが、あちらは起票後にマージされた作業が原因を入れ替える経路で、こちらは起票時点から原因が誤っている経路である。
