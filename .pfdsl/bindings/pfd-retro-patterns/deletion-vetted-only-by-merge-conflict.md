- **削除の妥当性判定を rebase の競合有無に委ねる trap**: 削除してよいかの再検証が rebase の競合有無だけに退化し、base の非競合な変更は判断のやり直しを一度も起こさない。
  呼び出し元ゼロを根拠に死んだコードを消す判断は、その根拠が真であり続ける限り正しい。
  しかし base がサイクル途中で進むと、上流がその同じコードへ直前に投資していることがある。投資は「呼び出し元ゼロ」を偽にしないので、根拠の再確認では現れない。
  現れるのは rebase の競合としてであり、競合するかどうかは変更行が重なったかだけで決まる。上流が隣接する兄弟関数や同ファイルの別箇所を直していれば無競合でマージされ、判断をやり直す契機は生じない。
  問いの形: 「この削除対象について、`git log origin/<base> -- <path>` の直近を見たか。rebase が競合を返さなかったことは、上流の関心と衝突していないことの証拠ではない」。
  具体例: #1044 で呼び出し元ゼロの `fetchCurrentPrView` を削除した。着手時点でその事実は正しく、`grep` でも確認済みだった。作業中に base が2度進み、2度目に入った #1043 の修正が `closingIssuesReferences` を GraphQL から引く変更を、番号指定形と current-branch 形の**両方**に入れていた。所有者は2形を対称に保つ判断を明示的にコメントへ書いており、その10時間後に片方を消すことになっていた。気付いた契機は rebase の競合だけで、判断のやり直し（規約の確認・所有者への確認）はそこから始まった。もし #1043 が `fetchPullRequestView` 側だけを触っていれば、同じ削除が無競合でマージされ、対称性を壊したことは誰にも見えなかった。
  対策: 削除を含むコミットを作る前に、削除対象のパスへ `git log --oneline -5 origin/<base> -- <path>` を実行し、直近の変更が削除対象に触れていないか読む。触れていれば、その変更が何を意図したかを読んでから削除の可否を決める。競合の有無を判断の入力にしない。
