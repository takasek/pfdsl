- **記録の書式検査が投稿後にしか届かず、訂正が別の検査を落とす trap**: 書式を機械検査される記録を外部（issue コメント等）へ投稿する形にすると、検査は投稿済みの実体しか読めない。書式違反は投稿後にしか分からず、しかも訂正の投稿・編集は「記録が着手前に存在したこと」を見る時点検査の側を落とす。片方を満たす操作がもう片方を壊すため、初回に書式を外した時点で、どちらかを犠牲にするか記録の外側（コミットの作り直し等）を動かすかしか残らない。
  雛形を配ることでは直らない。雛形が減らすのは書き間違いの頻度であって、間違えた回の出口ではない。
  問いの形: 「この記録の書式は、投稿する前に手元で検査できるか。できない場合、投稿後に違反が分かった回の訂正手順は、時点を見る検査と両立するか」。
  具体例: `cycle-status.mjs` が `designRecordTemplate` として設計記録の雛形を印字するが、その書式を検査する `parseFormat3DesignRecord` は `scripts/lib/gate-check.mjs` の export であり、下書きファイルへ適用する入口を持たない。#1112 のサイクルで「案の処分」に元候補でない採用案を `元候補外「…」` の形で1行足して投稿したところ、終端ゲートまで違反に気付かなかった。訂正版を投稿・編集すると、今度は `record edited at …, after the first commit at …` で時点検査が落ちた。記録の内容は着手前から変わっておらず、落ちたのは書式訂正の時刻だけだったが、検査は編集時刻しか見ない。未 push だったためコミットを作り直して通したが、これは記録側でなくコミット側を動かす解決であり、ゲート自身も PASS 行に「the commit side is a git author date the runner can set — evidence, not proof」と書いている。
  対策: 投稿前に手元で書式検査を通す。検査器が export だけを持ちファイル入力の入口を持たない場合、入口を足すのが先で、注意深く書くことではない。入口が無いまま投稿する回は、投稿を初回で決めきる必要があることを認識して書く — 訂正の余地がない側の記録だと分かっていれば、書式節を雛形から逐語で組み立てる判断になる。
