- **記録の書式検査が投稿後にしか届かず、訂正が別の検査を落とす trap**: 投稿前の草案を検査する入口がなく、投稿後の訂正も時点制約で拒まれると、記録の書式違反を正規の手順で回復できない。書式を満たすための投稿・編集が「記録が着手前に存在したこと」を見る時点検査を落とし、片方を満たす操作がもう片方を壊す。外部へ記録を投稿すること自体ではなく、草案の検査入口と訂正を受け入れる手順の両方が欠けていることが原因である。
  雛形を配ることでは直らない。雛形が減らすのは書き間違いの頻度であって、間違えた回の出口ではない。
  問いの形: 「この記録の書式は、投稿する前に手元で検査できるか。できない場合、投稿後に違反が分かった回の訂正手順は、時点を見る検査と両立するか」。
  具体例: （旧ゲートの事例）#1112 の当時、`cycle-status.mjs` は `designRecordTemplate` として設計記録の雛形を印字したが、その書式を検査する `parseFormat3DesignRecord` は `scripts/lib/gate-check.mjs` の export だけで、下書きファイルへ適用する入口を持たなかった。「案の処分」に元候補でない採用案を `元候補外「…」` の形で1行足して投稿したところ、終端ゲートまで違反に気付かなかった。訂正版を投稿・編集すると、今度は `record edited at …, after the first commit at …` で時点検査が落ちた。記録の内容は着手前から変わっておらず、落ちたのは書式訂正の時刻だけだったが、検査は編集時刻しか見なかった。未 push だったためコミットを作り直して通したが、これは記録側でなくコミット側を動かす解決だった。当時のゲートも PASS 行に「the commit side is a git author date the runner can set — evidence, not proof」と書いていた。
  対策: 草案にも投稿済み記録と同じ書式検査を適用できる入口を設け、投稿前に検査する。このリポでは `node scripts/check-design-record.mjs --file <草案>` を使う。この予防策が `phase: pre-artifact` の対象であり、投稿後にも可能な補修とは適用時点が異なる。投稿後に不備が分かった場合は同じ記録を補修し、内容の意味が変わる場合は必要な再承認と改訂履歴を残す。投稿・編集時刻と初コミットの比較は撤去済みなので、書式訂正を通すために過去コミットを再作成したり日時を変更したりする必要はない。
