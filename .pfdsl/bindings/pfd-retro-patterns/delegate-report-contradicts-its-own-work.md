> 過去事例（保存基準: 33878aeb）。本文の対策・判断は当時の記録であり、現行の指示ではない。現行手順は [pfd-retro binding](../pfd-retro.md) を参照。

- **委譲先の最終メッセージが自分の作業を反映しない trap**: 委譲先が context を使い切って compaction を通ると、最終メッセージは自分が行った作業でなく、ブリーフを失った後の状態を述べる。
  「依頼の内容を教えてほしい」型の初期応答がそのまま返るので、呼び出し元はそれを「着手しなかった」と読み、同じ作業を別の委譲先へ出し直す。
  作業自体は完了しているため、二重適用も消失も起きず、既存の中断 trap の症状はどれも出ない。
  壊れるのは作者の帰属であり、呼び出し元は成果物の状態を見て、そのとき生きていた別の主体が書いたと述べる。
  問いの形: 「この成果物を誰が書いたかという判断は、委譲先の報告に基づくか、それともツリーの状態と『そのとき動いていたのは誰か』からの推定か」。
  検出: 委譲先の報告が作業内容を述べていない回は、報告の欠落を着手の欠落と読まない。
  各委譲先の transcript を時刻で突き合わせる — Claude subagent は `~/.claude/projects/<project>/<session>/subagents/agent-<id>.jsonl`、Codex は `~/.codex/sessions/<date>/rollout-*-<threadId>.jsonl` にあり、どちらも編集ツールの呼び出しと時刻を持つ。
  ツリーに残った checkpoint やスクラッチの中の見慣れない UUID を、それだけで別セッションの証拠と読まない。
  同じ transcript を grep すれば、それが独立したセッションの ID なのか、1つのセッション内で生成されたメッセージ ID の接頭辞なのかが決まる。
  具体例: #1098 のサイクルで、レビュー指摘14件の修正を Codex へ委譲した。委譲先はブリーフを受け取って44回パッチを当て、全14件を実装したうえで context を使い切り、checkpoint を残して「作業環境とリポジトリの指示を読み込みました。ご依頼の内容をお知らせください。」と返した。呼び出し元はこれを「プロンプトを取り落とした」と読み、同じブリーフを sonnet の実装 agent へ出し直した。sonnet は5分で session limit に当たり、編集を1件も行わずに落ちた。呼び出し元はツリーを調べて全14件が入っていることを確認し、sonnet が完走したとユーザーへ報告した。その後 checkpoint ファイルを開き、そこにあった `Window: <uuid>` を別セッションの ID と読んで、今度は並行セッションの編集だと訂正した。どちらも誤りで、実際の作者は最初の委譲先である。transcript を grep して初めて、その uuid が同じ Codex セッション内の context 枯渇時点のメッセージ ID 接頭辞だと分かった（2026-09-06）。
  対策: 成果物の妥当性と作者の帰属を別々に結論する。
  前者はレビューとテストでツリーから確かめられるが、後者はツリーからは確かめられない。
  帰属を述べる必要が無いなら述べない。
  述べるなら transcript を突き合わせてから述べ、推定であるうちは推定だと書く。
