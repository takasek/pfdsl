- **同意を仰ぐ単位が、findings を束ねた単位を引き継ぐ trap**: 独立した findings を着手単位で1件へ束ねるのは起票側の作法だが（`findings-split-below-triage-unit`）、その束をそのまま1つの可否として同意へ出すと、却下は束に効き、各項目は一度も判断されないまま落ちる。
  束ねる理由は受け手のトリアージ単位に合わせることであり、同意の単位を決める理由ではない。2つの単位が一致するのは偶然で、一致を確かめる工程がどこにも無い。
  差が見えるのは束の一部が外部で解消した回である。片割れが別の PR や別セッションで直ると、残りは「却下された束の残骸」として扱われ、束が別物になったことに気付かないまま単体でも問われない。
  問いの形: 「この可否は項目ごとに取れる形で出しているか。束が却下されたとき、却下されたのは束か、各項目か。束の一部が外部で解消したなら、残りは新しい束なので、改めて可否を問うたか」。
  **却下された側からは、束と項目の区別が付かない。** 同意する側は提示された選択肢しか見ておらず、束の内訳のどれを却下したかを表明する手段を持たない。判断が粗くなったことは提示した側にしか見えないので、提示側が単位を決める時点で分けるほかない。
  具体例: #1050 のサイクルで、`audit-issues-flow` が open な issue #3 を not found と報告する不具合と、`check-roadmap-registration` が audit の非ゼロ終了すべてに同じ remediation 文面を印字する不具合の2件を、「2件まとめて起票する」という1つの選択肢として提示し、選ばれなかった。2件は別のスクリプトの別の欠陥で、独立して着手も却下もできた。その後 #3 側は main の PR #1120 で解消したが、残った文面の不具合を単体で問い直さず、散文の報告へ格下げして終えた。ユーザーの指摘を受けて起票し直している（#1128、2026-09-06）。
  対策: 配布層（pfd-ops `references/work-cycle.md` 手順3 の「記録先: ユーザーへの報告」項目）へ昇格済み — 諾否を項目ごとに取ること、不可分な束はそのままでよいこと、束の一部が外部で解消した時点で残りを新しい束として問い直すことはそちらが一次情報。ここに残すのは問いの形と、この trap を踏んだ実例である。
  分ける基準は「片方だけを採ったとき残りが宙に浮かないか」で、起票時に束ねる基準（同じ回に一緒に着手されるか）とは別に取る。
