- **偽と分かった主張を、同じ形のまま中身だけ差し替える trap**: 規則が外部システムの能力を列挙する形（「Xができるのは A と B」「Xは C 専用」）で書かれていると、その列挙が偽だと判明したときの自然な直し方は「正しい列挙に書き換える」になる。しかし壊れたのは列挙の中身でなく**列挙という形**であり、同じ形で書き直せば次に外部が動いたとき同じ壊れ方をする。
  形を保った修正は、直した本人にも読み手にも「事実誤認を1件直した」として見えるので、再発の予約が入ったことは記録に残らない。
  問いの形: 「この規則が偽になったのは、列挙した中身を間違えたからか、それとも列挙してしまったからか。この規則が答えたい問いを、外部の能力に触れずに書けるか」。
  具体例: 「PreToolUse には advisory チャネルが無いので選択肢は deny と ask の2つ」という規則が偽だと判明した回（PreToolUse も `additionalContext` を運ぶ）。1度目の修正は「実行後の event 専用」へ、2度目は「返せる event は他にあるが PreToolUse は含まれず」へ書き換え、**2度とも別の偽に着地した**。
  閉じたのは3度目に形を変えたとき — 「決定を選ぶ軸は、防ぎたい害が実行そのものか、結果の読み違いか」。advisory は定義上ブロックしないので、この軸は外部が何を実装していても動かない。
  具体例: 同じ主張の4度目が、**規則でなく実装コメントの形で**入りかけた。上の「2度とも別の偽」の中身は「無視されるのは `defer` のときだけ」「注入位置は tool result の隣」で、着手時に一次情報を読み直すとどちらも現行版に存在せず、無視条件は `permissionDecision` が `"allow"` のときだった。そこで3ファイルのコメントへ「PreToolUse は `allow` を返すと `additionalContext` を捨てる」と書いた — 中身は当時正しく、形は列挙のまま。規則の側は既に不変な軸へ閉じていたので、規則を読んでも自分の書いたものが同じ形だとは気付けない。列挙が規則の外へ漏れる経路がある（#929、2026-08-22。retro でカタログを引いて書き換え）。
  対策: 外部の能力に依存する規則は、その能力を列挙せず、**能力が変わっても動かない性質**（定義から出る性質・因果の向き・時点の前後）へ書き換える。書き換えられない場合は、その規則が答えている問いが実は「いまの版で何ができるか」であり、規則でなく調査手順として書くべきものである。
  対策の追加: 規則を不変な形へ閉じた後も、**同じ主張を根拠として引く成果物**（コード・テストのコメント、PR 本文、設計選択記録）は列挙の形で書かれうる。閉じた規則の側に「この列挙をここで書き直すな」と一文を置き、根拠が要る場所からはそこを指す。着手時の調査記録（選択記録・issue コメント）に逐語引用が入るのは正しい — そちらは「いまの版で何ができるか」に答える調査手順であり、規則ではない。
  版依存の断り書き（「時点の観測として扱え」）を添えるのは対策にならない — 断り書きが付いていても、読み手が読むのは列挙のほうである。
