- **検査の入力が、その検査の再実行契機の外にある trap**: 検査が読む状態と、その検査を再実行させるイベントは別物であり、前者が変わっても後者が起きない組み合わせが成立する。
  その形になった検査は、自分が要求した是正が済んだことを観測できない — 直っても赤のまま残り、緑にするには是正と無関係な操作（空コミット・手動 re-run）が要る。
  検査のロジックは正しく、再実行されれば緑を返すため、失敗の側からは何も見えない。
  問いの形: 「この検査が読む状態はどこにあり、それが変わったときに何のイベントが起きるか。そのイベントは、この検査を再実行させる集合に入っているか」。
  問いの形の追加: 「この検査の失敗メッセージが要求する操作を実際に行うと、どのイベントが発火するか」。是正操作そのものを起点に辿ると、入力の在処を経由するより短く答えが出る。
  具体例: `check-closes-reference` は PR 本文（GitHub 側の状態）を読む検査だが、`.github/workflows/check-closes-reference.yml` の trigger は `on: pull_request` のみで `types:` を持たなかった。既定の型集合は `opened` / `synchronize` / `reopened` の3つで、いずれもブランチの変化を報告する — 本文の編集を報告する `edited` は入っていない。この検査の失敗メッセージは「本文を編集して `Closes #<n>` か `no-issue: <理由>` を書け」と指示するので、指示に従った瞬間に発火するイベントだけが集合から漏れていた（#936、2026-08-22）。赤が残り続けた結果、赤の意味が「未対処」から「未 re-run かもしれない」へ薄まった。
  この形は機械検査にしにくい — 「この検査の入力が外部側の状態か」はソースからは判定できず、判定材料が正常な検査と trap を同じ値に落とす（`check-materials-cannot-make-the-distinction` と同じ理由）。母集合も小さく、`.github/workflows/` 全件のうち該当は1件だった。
  対策: 外部側の状態を入力とする検査を新設・変更するとき、`types:`（あるいはその機構における発火条件）を明示的に書く。既定の集合に頼ると、既定が答えているのはツリーの変化であって外部側の変化ではない。明示的に書く場合は、既定の3型を書き戻すことも忘れない — `types:` を書いた時点で既定から opt out するため、書き漏らすと push で再実行されなくなる。
