- **記録の時点照合がブランチを作業単位とみなす trap**: 着手前の記録を求めるゲートは「記録の投稿時刻がブランチの最初のコミットより前か」で照合する。
  この照合はブランチ1本＝作業項目1件を前提にしており、既存ブランチへ2件目の作業項目を積んだ回では、2件目の記録がどれだけ正しく着手前に投稿されていても、最初のコミット（1件目のもの）より後になるため必ず FAIL する。
  逆向きの失敗も同じ前提から出る — 1件目の記録さえあれば、2件目を記録なしで積んでもゲートは1件目について緑を返す（渡した issue の分しか見ないため、渡し忘れた側は判定されない）。
  問いの形: 「このブランチが閉じる作業項目は何件か。2件目以降について、ゲートが着手時刻とみなす点はその項目の着手時刻か」。
  具体例: #829 の PR を出した後、同じブランチへ #844 の2項目を積んだ。#844 の選択記録は実装委譲より前に投稿していたが、gate-check は「記録は 16:20Z、最初のコミットは 15:03Z」と報告して FAIL した。15:03Z のコミットは #829 のもので、#844 の着手時刻ではない（2026-08-11）。
  同じ前提は、作業項目が1件でも記録が改訂された回に現れる。ゲートが時点照合するのは書式適合する記録1件だけなので、着手前に投稿した版が書式に適合しない回は、記録の存在した時刻ではなく適合版を投稿し直した時刻で判定される。
  改訂の原因は2形ある。書式不適合が原因の改訂は着手前の検査で消せるが、実装が前提を崩したことが原因の改訂は着手後にしか出せず、定義上コミットより後になる。
  具体例: #1050 のサイクルで、選択記録を初コミットの約11時間前（08:07Z）に投稿していたが、その版と次の改訂は `案の処分:` の処分トークンを欠くなど書式に適合していなかった。書式に適合した改訂3は初コミットの5分後（19:10Z）になり、gate-check は「record posted at 19:10:01Z, after the first commit at 19:05:09Z」と報告して FAIL した。記録が実装を導いた事実と、ゲートが見た時刻は食い違っている（2026-09-06）。
  対策（改訂が書式不適合に由来する形）: 投稿前に `node scripts/check-design-record.mjs --file <草案>` を通す。終端ゲートと同じ分類器を呼ぶので、書式だけが理由の改訂は投稿前に消える。上の #1050 の記録に当てると改訂1は FAIL、改訂3は PASS を返す。
  設計そのものが実装中に変わった改訂には効かない。その形は時点照合を通せないので、記録の投稿時刻の列と、何が前提を崩したかを PR 本文に開示して人間の判断へ返す。
  対策（作業項目が2件以上の形）: 2件目の作業項目に着手する時点でブランチを分ける。先行ブランチのコードに依存して main から切れない場合は、先行ブランチを base にしたスタックにすれば、その base からの窓が2件目の着手時刻になる。分けたあとのゲートは `--base <先行ブランチ>` で走らせる。
