- **改善幅の基準がブランチの中間状態へずれる trap**: レビューはブランチの差分と作業ツリーを見るため、指摘の一部は**そのブランチ自身が作り込んだ欠陥**を指す。
  それを直すと「レビューで検出し修正した」という正しい記述が残るが、その修正を改善幅として数えると、基準が出荷済みの状態でなくブランチの中間状態になる。
  中間状態は誰も見たことがないので、報告された改善幅は現実の誰に対しても実現しない。
  測定そのものは正しく、記述も嘘ではないため、数字だけを見ても検出できない。
  問いの形: 「この『N → M』の N は `origin/<base>` を実際に測った値か、それともこのブランチの途中で自分が作った状態か」。
  具体例: レビューが「同じ `git log` が1サイクルで2回走る」と指摘し、呼び出しを1回へまとめた。PR 本文には改善として `2 → 1` と書いたが、`origin/main` を測ると元から1回であり、2回になっていたのはこのブランチの中間コミットだけだった（2026-08-10）。
  対策: 指標を書く前に、基準側の値を `git show origin/<base>:<path>` か `git grep <pattern> origin/<base>` で実際に取る。レビュー由来の修正は「レビューで見つけた」欄に書き、改善幅の欄には出荷済みの状態との差だけを書く。
  **同じずれは結果（M 側）にも起きる。** 基準を正しく取っても、M をブランチの途中で測ってそのまま最終結果として報告すれば、報告値はやはり誰も見ていない状態のものになる。N 側と違い `origin/<base>` との突合では検出できない — 測定コマンドも対象のツリーも正しく、ずれているのは時点だけである。
  問いの形の追加: 「この報告値は最終状態を測ったものか、ブランチの途中で測って以後測り直していないものか。測ってから最後のコミットまでの間に、測定対象を変えた編集はあるか」。
  具体例: 生成物の drift 検査（`make gen-plugin` が差分ゼロであること）を1本目の編集直後に測り、レビュー由来の修正を2本目のコミットで入れたあと測り直さないまま、サイクルの結果として報告した。結論は同じだったが、報告時点の測定は最終状態を見ていない。気付いたのはユーザーに問われたときで、終端ゲートも CI も緑のままだった（#974 のサイクル、2026-08-28）。
