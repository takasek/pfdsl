- **ゲートが記録を同定する条件と、規約が記録を定義する条件がずれる trap**: 記録の提出を求めるゲートは、まず「記録がどれか」を選び、次に「内容が要件を満たすか」を見る。規約が語るのは後者だけのことがあり、その場合、規約どおりに書いた記録が前段で落ちる。落ち方は「内容不備」ではなく「記録なし」であり、規約遵守者ほど原因に辿り着けない。
  問いの形: 「このゲートは記録をどうやって見つけているか。その条件は、規約が記録の要件として挙げているものと同じか」。
  規約側を読んでも検出できない — 同定条件はゲートの実装にしか書かれていないため、実装を読むまで存在しない条件に見える。
  兆候は**回復手段が規約の禁じ手になること**である。提出済みの記録を後から書式に合わせる操作（コメントの編集等）を規約自身が「記録の真正性を壊す」として戒めている場合、規約遵守者だけがその操作へ追い込まれる構図になっている。
  具体例: 着手前の選択記録ゲートが、記録エントリを行頭 `決定: 案N` 行の有無で同定していた。一次情報側の reference はこの行を「起票者が書く設計確定の証拠」と定義し、実行主体が書く選択記録（`前提:` / `否定案:` / `却下理由:`）とは**別物**だと明記している。必須3行を完備し初コミット前に投稿した記録が「記録なし」で FAIL し、回復は投稿済みコメントの編集になった（2026-08-05）。同じ reference は実行主体が書いた `決定:` 行を無効と定めてもおり、ゲートを通す作業がゲートの守る区別を崩す形にもなっていた（#727 で同定条件を必須3行側へ移して解消）。
  具体例: ずれは逆向きにも出る。同じ選択記録ゲートの同定が「必須3行のうち最も多く当たった entry」を選ぶ形になっており、下限が無いため1行でも当たれば当選する。issue 本文に議論として書かれた `**前提**:` / `**否定案**:` の2行が、強調記号を剥がされて行頭一致し、記録として選ばれた（#879 の着手時、#927 で起票）。規約は記録をコメントとして投稿するものと定めているので、本文は原理的に記録たりえない。プリフライトはこれを「設計対話も記録も不要」と報告し、実行主体が issue を自分で読んでいなければ、記録なしで着手する側へ倒れていた。前段の同定が緩い側へ外れると、内容条件を持つ終端ゲートまで誤りが出てこない。
  対策: ゲートの実装を読み、同定条件と内容条件を分けて規約に書く。同定条件は緩い側にも厳しい側にも外れうるので、規約が「記録はどこに置くか」を定めているなら、その置き場の外にある候補を同定の対象から外せているかを実装で確かめる。両者を一致させられない期間は、運用 companion 側に暫定の書式指示を置いて規約と実装の差を吸収する。
