- **不在判定の探索範囲 trap**: 「これは存在しない」と判断するとき、探索範囲が**それが本来ありそうな場所**に限定され、**実際にありうる場所**を含んでいないことがある。
  不在の証明は探索範囲がすべてであり、範囲を誤ると偽陽性が出る。
  存在の確認（1件見つければ足りる）と違って、不在の確認は範囲の網羅性そのものが結論を決める。
  この trap は「捏造の疑い」だけでなく、**ゲート項目を N/A と判断する場面全般**に効く。
  問いの形: 「『無い』と判断した検索範囲は、それがありうる場所を含んでいるか。名前で検索したなら、名前が違うだけの同じものを取りこぼしていないか」。
  具体例1（識別子）: テストが `artifactKey: "ops_checkers"` を使っているのを見て、実在しない artifact キーの捏造と判断しかけた。
  `.pfdsl/` と `docs/` を grep して0件だったことを根拠にしたが、実際は同じテストファイル内に12箇所の既存フィクスチャとして存在しており、委譲先はファイルの既存慣行を正しく踏襲していた。
  全置換を実行していれば、既存テスト6件がフィクスチャとアサーションの不一致で落ちるところだった（コミット前に気付いて revert）。
  具体例2（ゲートの N/A 判断）: 「変換コンポーネントを PFD に反映したか」のゲートを N/A と判断する際、`.pfdsl/*.pfdsl` を対象スクリプト名の文字列で grep して0件だったことを根拠にした。
  正しい探索軸は名前ではなく `location:` であり、それで引き直すと同種の運用スクリプトが4件モデル化されていた（結論の N/A 自体は成立したが、根拠は成立していなかった）。
  対策: 探索を**名前でなく性質**で行う。artifact の不在を言うなら `location:` を、識別子の不在を言うならその文字列が由来しうるファイル自身を、探索軸にする。
  「あるべき場所に無い」と「どこにも無い」を区別し、後者を主張するときだけ N/A と書く。
  **軸を性質に直しても、母集合をディレクトリで絞れば同じ結論が出る。** 探索は軸と母集合の2つで決まり、対策文が扱っているのは軸だけである。正しい性質で探しても、探した先が「ありそうなディレクトリ」に限られていれば、そこに無いものは最初から候補に入らない。
  問いの形の追加: 「この探索の母集合は何で決めたか。ディレクトリ名で絞ったなら、その境界は探している性質と関係があるか」。
  具体例: #648 の同型カウントで、フラグ探索という性質を軸に `grep -rn 'indexOf("--\|includes("--' scripts .claude/skills` を回し「スコープ外に同型は残らない」と結論した。軸は正しかったが母集合が2ディレクトリで、`packages/vscode-extension/esbuild.config.mjs` の `process.argv.includes("--watch")` が候補に入らなかった。同サイクルで作った検査（追跡下の `.mjs` 全件を走査）が拾って発覚した。
  **軸と母集合が正しくても、軸の上で見る関係が1種類だと同じ取りこぼしが出る。** 「同じ実体を指すノードが図をまたいで食い違う」件数を数えるとき、`location:` を軸にし3図すべてを母集合にしてもなお、比べる関係を前置（ディレクトリ包含 = 粒度差）だけに取ると、同一 `location`・別 id の組（粒度は揃っていて名前だけが違う形）が最初から候補に入らない。
  取りこぼした側は「同型はスコープ外に18組」という具体的な数として出るため、数が出ていること自体が網羅の証拠に見える。
  問いの形の追加: 「この軸の上で、同型が成立しうる関係は何種類あるか。数えたのはそのうち何種類か」。
  対策の追加: 不在を主張する探索は、母集合を性質側の条件（追跡下の全 `.mjs` 等）で決める。ディレクトリ列挙は「検査対象を手列挙で指定する trap」と同じ形であり、探索にも同じく効く。
  **検査を広げた回の「偽陽性は無い」も同じ形の不在の主張であり、母集合はその検査が返した全件である。** 返った件数が目視できない規模だと標本で代用することになるが、標本の選び方が偏っていれば、偏りと相関する偽陽性の型だけが丸ごと候補から外れる。
  **母集合を、その事象が二次的に写される場所で決めると、写されなかった分がまるごと候補から外れる。** 事象そのものの一次情報（履歴・レジストリ）でなく、それを人が記録した器（作業項目・台帳）を数えると、器へ写す工程を経なかった事象は最初から存在しないことになる。器の側は網羅的に読めるので、読み切ったこと自体が網羅の証拠に見える。
  問いの形の追加: 「数えた対象は、その事象の一次情報か、事象を人が写した器か。器なら、写されなかった分をどう数えるか」。
  具体例: ある機構が実際に働いた回数を「その機構を出自として起票された作業項目」で数え1件と結論した報告があったが、機構の産物は配布層と companion を同一コミットで触る形で git 履歴に残っており、そちらを母集合にすると4件だった。作業項目に写されたのはそのうち3件で、残る1件は起票を経ずに直接実施されていた。
  問いの形の追加: 「標本を何で選んだか。その選択基準は、探している性質と相関していないか」。
  **不在の主張の母集合を先行する作業項目の分類から継承すると、その分類の外は最初から候補に入らない。** 継承した母集合が保証するのは「誰かが以前その軸で数えた」ことだけで、軸そのものの妥当性は引き継がれない。
  問いの形の追加: 「この件数の母集合は誰がどの軸で決めたか。自分はその軸を導き直したか、受け取っただけか」。
  **母集合はゲート自身の報告材料からも継承される。** ゲートが項目のすぐ隣に一覧を印字していると、その一覧が項目の問いに答えたものとして読まれるが、報告材料が立てている軸は項目の軸と一致しているとは限らない。自分で範囲を狭めた回と違い、狭めた覚えが無いので疑う契機も無い。
  問いの形の追加: 「この一覧はどの軸で作られているか。ゲート項目が問うている軸と同じか」。
  具体例: 終端ゲートが「変更したパスのうち、採用済み PFD の `location:` がモデル化しているもの／していないもの」を印字する。#879 のサイクルではモデル化側が0件だったので、PFD 反映のゲート項目を N/A と確定させた。だが pfd-ops プロトコル5が求めるのは**新しい種類の成果物**への producer・consumer の登録であり、そのサイクルは repo-local スキルと release ゲートの記録という新種を2つ作っていた。パス軸の一覧はこの問いに答えていない — 新種は既存のどの `location:` にも載らないので、必ずモデル化されていない側に並ぶ（別セッションの retro が検出し `workflow.pfdsl` へ登録して解消）。
  具体例: #906 で「判定できない criteria 28件」を直したのち、残存0件をフレーズ（「期待通り」「網羅」等）の grep で確認した。母集合は #867 が同じフレーズ軸で分類した集合であり、判定手段を名指さないがそのフレーズを含まない criteria は変更前も変更後も候補に入らない。別の軸（criteria が手段語を含むか）で150件を引き直すと43件が引っかかり、そのうち何件が真の残存かは #867 の分類を導き直さない限り言えない。
  具体例: 図と実装の対応の穴を数えるサイクルで、外部 URL を `location:` に持つ artifact を `workflow.pfdsl` だけで5件と数えた。作業項目の本文がその5件を挙げていたためで、`pipeline.pfdsl` にも同じ形が1件あり実際は6件だった（結論は変わらなかったが、母集合の数字を PR 本文に書いた時点では気付いていない）。同じサイクルで新設した診断コードの発火数を `.pfdsl/` と `docs/samples/` と `docs/examples/` の全ファイルで0件と数えたが、`docs/spec/spec.md` 内の fenced `pfdsl` ブロックが数えられていなかった — そこは `check-doc-examples.mjs` が各ブロックを単独ファイルとして検査する母集合であり、仕様書自身の例が1件その診断に当たっていた。どちらも独立解の subagent が別の数え方をして出した（#930 / #938、2026-08-20）。
  問いの形の追加: 「軸を引き直す作業で、新しい軸の定義に使った文は、作業項目が書いた**予測**ではないか」。作業項目は分類をやり直せと言いながら、結果の見積りを本文に添えていることがある。見積りは検証対象であって定義ではない — 定義として採ると、母集合を継承する代わりに軸を継承する形になり、同じ trap をもう一段上で踏む。
  具体例: 上の #906 の件を受けた #925 で、軸を「criteria が判定手段を名指しているか」へ引き直した。その本文は「43件の大半は真の残存ではない（`動作確認済み` `統合済み` は観察・grep で判定できる）」と添えており、これを分類の定義として採って真の残存を7件と見積もった。母集合（155件）は正しく取っていたので、狭かったのは軸のほうである。独立解と敵対レビューが独立に「`動作確認済み` は何を起動して何が見えれば真かを書かないので自己申告と区別できない」と判定し、所有者確認を経て55件になった。起票者の予測を定義に採った時点で、その予測が偽である可能性は検査の外へ出ていた（#925、2026-08-21）。
  **母集合の食い違いは、探す側だけでなく外す側にも出る。** 「これは対象外」と決めた集合は、他の機構が母集合として拾う範囲と交差しうる。外す理由に使った性質をその機構が見ないなら、その機構にとって除外は成立していない。
  問いの形の追加: 「対象から外すと決めた集合は、どの機構の母集合と交差するか。外す理由に使った性質を、その機構は見るか」。
  具体例: 委譲ブリーフで `.pfdsl` の除外集合を「歴史記録か」で切ったが、`check-docs` は `find docs -name "*.pfdsl"` を母集合にしており記録性を見ない。除外したはずの実験記録の図が改名後の列挙値検査で落ち、委譲先が差し戻した（#670、2026-08-29）。除外の理由は人間向けの分類で、機械の母集合はパスの形だけで決まっていた。
  **母集合は空間だけでなく時点でも狭まる。** 一覧を返すコマンドは、その時点で存在するものだけを返す。あとから生成されるものを含む主張へそのまま使うと、返り値の網羅性が主張の網羅性に見える。
  問いの形の追加: 「この一覧はいつ生成されたものを含むか。まだ生成されていないものを含む主張に使っていないか」。
  具体例: `gh pr checks` が「Passed: 9, Failed: 0」を返したので CI 全通過と断定したが、その直後の本文編集を契機に走る job がまだ生成されておらず、後から別の job が失敗した（#670、2026-08-29）。失敗0という数字は、数えた時点の job 集合についてだけ真だった。
  具体例: 広げた検査が返した149件について「偽陽性0件」と報告したが、実際に目視したのは件数の少ない9ファイル分の34件だけで、件数の多い3ファイル（115件）は開いていなかった。件数が多いのは長い貼り付け（過去の spec を丸ごと写した ADR）だからで、フェンスの無いコードスニペットが集中するのもまったく同じ理由だった — 標本から外した基準が、外した偽陽性の型そのものの原因だった。実際には30件が散文でなくコードで、対処も行の結合ではなくフェンスの追加という別のものになった（#770。全件を機械的に分類し直して発覚）。
