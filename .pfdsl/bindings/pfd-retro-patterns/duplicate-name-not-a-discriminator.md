- **同名の実体が2つあるとき、名前は判別子にならない trap**: バージョン番号・タグ・識別子が一致していても中身が一致しているとは限らない。公開済みの成果物とローカルのビルドが同じ番号を名乗ったまま挙動が違う状態は、番号を見比べる限り検出できない。
  問いの形: 「この番号は、比べている2つの実体のどちらから来たか。番号が同じなら中身も同じだと、何が保証しているか」。
  この trap の兆候は**些細な食い違いとして現れる**。決定的な失敗ではなく「あれ、と思ったが実害がなさそうなので流した」の形を取るため、想起ステップ（C 層の「保留した違和感」）を通さないと拾えない。
  具体例: `pfdsl --version` が 0.0.23 を返す一方 `packages/cli/package.json` は 0.0.24 だった。その場では「ビルドが古いだけ」と流したが、実体は公開版 0.0.24 と main の 0.0.24 が別物という食い違いで、配布散文が未公開の CLI 挙動を前提にしていた最大の finding の最初の兆候だった（2026-08-04）。
  対策: 番号の食い違いを見たら、その場で「どの実体が何を返したか」を確定させる。確定は数秒で済み、流したときの発見の遅れはサイクル単位になる。
  **番号が一致する変種では、上の兆候も対策も働かない。** 公開版とローカルビルドが同じ番号を名乗り、かつ実際に同じ番号である（公開後に main が進んだだけ）場合、食い違いは一切表に出ないため「流した違和感」すら発生しない。
  この変種を拾える経路は1つで、**道具の出力がその道具の本文の記述と食い違うこと**である（上の「本文の記述と食い違うこの出力は、図の異常か、版の挙動か」と同じ問い）。したがって番号照合ではなく、実体を固定する規約でしか塞げない。
  具体例: 上流リポで `npx pfdsl graph orphans` が、フィードバックエッジのみで繋がるノードを配線忘れとして報告した（2026-08-05）。スキル本文は「`>>?` だけで繋がるノードは配線済みとして扱われる」と述べており、この食い違いだけが兆候だった。両者の `--version` はともに 0.0.25。実体は公開 0.0.25 が #676 の修正前で、main のビルドでは再現しない（`.pfdsl/bindings/pfd-ops.md` に CLI もローカルビルドを正とする規約を追加）。
