- **検査の材料が、規範の要求する区別を作れない trap**: 規範が「この形は正当、この形は負債」と分けているとき、検査がその判定に使える材料は、その2つを別々の値へ落とすとは限らない。材料が返す分類の粒度が規範より粗いと、検査は正当な形をそのまま誤検出する。
  対象を絞ることでは直らない。絞れるのは対象の集合であって、材料が返す分類の粒度ではないからである。
  問いの形: 「この検査が判定に使う材料は、何種類の値を返すか。規範が正当と呼ぶ形と、報告したい形は、その値の上で別々になるか」。
  具体例: `>>?` の誤用（subflow の境界配線を怠って `>>?` で代替した辺）を検出する W009 を新設した。判定材料は Primary Graph の到達可能性で、feedback 辺を「下流」「上流」「非連結」の3つに分ける。仕様が正当と認めるのは下流（`>>` は V010 の循環になるため取れない）と非連結（別系統からの補助入力）で、報告したかった配線の手抜きも非連結に落ちる。対象を subflow 展開プロセスへ絞ったが、絞ったのは対象プロセスの種類であって分類の粒度ではなく、subflow プロセスへの非連結フィードバックを合成すると仕様が明示的に許容する形をそのまま警告した。さらに上流の場合は V011（error、逆循環）と同一辺で共発火し、V010 の循環になる修正を勧めた。同じ PR の仕様本文に「非連結は許容」と書いておきながら実装がそれに反した状態で、観点3 の敵対レビューが合成例で示すまで気付かなかった（#938、2026-08-20 に撤回）。
  具体例: 設計選択記録の雛形が、`optionCount` 件それぞれに `採用 / 却下 / 保留` のいずれかを書くよう `案の処分:` 行自身で説明していたため、未記入の雛形と実際に各案を処分した記録が、検査の材料である処分語数の上で同じ値へ落ちた。`optionCount` 1〜3 で未記入雛形が PASS し、記入を促す説明が記入済みの証拠に化けた。処分宣言を `案の処分 N: <処分語> — <対象案と理由>` の番号付き構文にし、番号集合が重複なしの `1..optionCount` であることと未記入雛形の FAIL を統合テストで固定して解消した（#987）。
  具体例: 委譲の受け入れ基準にも同じ形が出る。#1112 のブリーフは「canonical source へ実質的な変更を加え生成物を更新していない場合の drift 検出をテストで固定する」ことを受け入れ基準に据えたが、その充足を判定する材料は「そのテストが現在のツリーで通ること」だった。この材料は「production の変更を反証できるテスト」と「コミット済みの生成物の性質を写しただけのテスト」を同じ値へ落とす。委譲先が返した3件は生成済みの `.agents` を `cpSync` でコピーして検査するだけで、`gen-plugin.mjs` を revert しても3件とも緑のままだった。反証可能性を要求する受け入れ基準（production 側を一時 revert し、落ちる出力を報告に貼る）へ書き換えて差し戻し、`assembleCodexAssets` を実際に駆動するテストへ置き換わった。
  具体例: 同じ形が #1114 のブリーフにも出た。受け入れ基準は「投稿済みコメントを検査する既存経路と同じ判定を返す（同じ本文に対して結論が一致することをテストで固定する）」で、充足の判定材料は「その一致テストが通ること」だった。この材料は「入口と既存経路が食い違えば落ちるテスト」と「妥当な本文1件だけを両者へ通すテスト」を同じ値へ落とす。委譲先が返した一致テストは PASS する本文1件だけを対象にしており、スクリプトが判定を捨てて PASS を印字するだけでも緑のままだった。受け入れ基準は「一致すること」しか要求せず、一致が非自明になる入力を要求していなかった。呼び出し元のレビューが検出し、valid と malformed の両方を回す table 駆動へ差し戻した。この中間状態はコミットされていないため履歴には現れず、`scripts/check-design-record.test.mjs` は最初のコミットの時点で既に table 駆動になっている。
  対策: 検査を書く前に、判定材料が返す値を全部列挙し、規範が正当と呼ぶ形と報告したい形がそれぞれどの値に落ちるかを書き出す。同じ値に落ちるなら、その材料では検査を作れない — 規範は散文として残し、機械検査が無い理由を規範の側に書く。
  **材料の粒度が粗いと、安全側へ倒した既定がその道具の主目的の動線ごと巻き込む。** 誤検出の被害が「余計な警告」で済むとは限らず、判定が操作の可否を決めている場合は、正当な形が機能を丸ごと失う。
  問いの形の追加: 「この材料が同じ値へ落とす2つの形のうち、片方は安全側の扱いを受けて何を失うか。失うものは、この道具が本来奉仕する動線ではないか」。
  具体例: 自己点検器が target を上流リポと採用リポに分ける判定材料を、`scripts/gen-install.mjs` 等のパスの実在だけに置いた。この材料は「上流リポの部分チェックアウト」と「同名のファイルをたまたま持つ無関係な採用リポ」を同じ値へ落とす。前者を安全側（`--deploy` 拒否）へ倒したので、後者はファイル名の衝突だけで導入そのものができなくなった — このツールが存在する第一の理由である動線が塞がる形だった。材料をパスの実在から内容の一致（そのファイルが `.claude/skills/pfd-ops/install` に言及しているか）へ変えて、偶然一致の類を丸ごと消した（#971、観点2 の敵対レビューが実際の採用リポ相当の fixture で示した）。
  **導入時の発火0件は、この trap について何も言わない。** 0件は「対象になりうる形がリポに1件も無かった」の言い換えでありうる。実際 W009 は導入時に全ファイルで0件だったが、それは自リポに subflow プロセスと feedback 辺を同時に持つファイルが1つも無かったためで、本体ロジックは一度も行使されていなかった。誤検出の有無は、発火数でなく合成例で確かめる。
