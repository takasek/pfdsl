- **先例のスタイルを性質確認せずに踏襲する trap**: 既存の先例のスタイルをそのまま踏襲すると、先例と今回で性質が違う場合を個別に検討し損ねる。踏襲される対象は散文・コード・委譲ブリーフの指示のいずれでも起こり、踏襲する主体も実装者とは限らない。以下は同じ主題の3つの軸で、順に「散文のポインタ化」「模倣元のリスク受容注記」「委譲ブリーフの倣う対象の列挙」を扱う。
  frontmatter の `phase: pre-artifact` を主張しているのは第3の軸だけである。第1・第2の軸の対策はレビュー時にも retro 時にも効くので、着手前の一覧でこのファイルを見た読者は第3の軸を読めばよい。`phase` はファイル単位のフラグで軸ごとの時点差を表現できないため、ここで断っておく。

  **第1の軸: 散文を hook へのポインタに置き換えるとき。** 既存の先例（例: #647 stale-dist-guard）のスタイルを踏襲すると、先例と今回の hook で性質が違う場合（例: advisory の hook が対処法まで含むか否か）を個別に検討し損ねる。
  問いの形: 「この散文が伝える情報は、hook の deny/advisory メッセージ自体に既に含まれているか。含まれているなら、ポインタ化でなく完全削除が正しいのではないか」。
  具体例: #650 で worktree-write-guard・md-write-check 候補の散文を hook へのポインタに書き換えたが、両 hook とも対処法まで含めて deny/advisory メッセージに全情報を持っており、散文には残す情報が無かった。#647 の stale-dist-guard スタイル（対処法を hook 外の散文にも残す）を無批判に踏襲した結果、完全削除できる箇所をポインタ化に留めて見落とした（ユーザー指摘で気付き、追加コミットで削除。同時に workflow.md「知見の振り分け」に散文追記前の機械化検討ステップを追加した）。
  対策: hook へのポインタ化を検討するときは、hook が実際に出力する文言と付き合わせ、散文に残る情報の有無を確認してから「ポインタ化」か「完全削除」かを選ぶ。
  具体例（不作為の側）: 新しい PreToolUse ガードを `workflow.pfdsl` に artifact として登録するかを、既登録2件・未登録1件という先例から「登録しない」と決めた回（#840）。
  未登録側が意図的な判断の結果か単なる漏れかは確認しておらず、後で `git log -S` を引くとその実体（`worktree-write-guard`）は `workflow.pfdsl` に一度も現れていなかった — 先例は判断ではなく空白だった。
  踏襲は作為だけでなく不作為の側にも起こる。「先例が無いから書かない」は、先例の不在が判断だったのか記録漏れだったのかを確かめない限り、同じ trap の別の向きである。

  **同じ主題の第2の軸: 写されない性質がリスク受容の注記であるとき。** 散文でなくコードを模倣する場合も、コピーされるのは構造（関数の形・フィールド名）だけで、模倣元が過去のふりかえりで蓄積した「既知の弱点をあえて塞がない」という判断の注記までは自動でコピーされない。
  模倣元の完成度（防御的コーディング済み・テストが揃っている）がそのまま模倣先の安全さの証拠に見えてしまい、両者が共有しているはずのリスク受容判断が模倣先にだけ欠けていることに気づきにくい。
  問いの形の追加: 「この新規メカニズムが模倣した既存メカニズムには、過去の issue で明示的に受容したトレードオフの注記があるか。あるなら同じ注記を新規側にも書いたか」。
  具体例: `scripts/lib/review-record.mjs` の `Review: tool=<name>` trailer は `scripts/lib/gate-check.mjs` の design-selection record（前提/否定案/却下理由の issue コメント）と同じ「実行主体の自己申告に依存し、検査は申告内容の真偽を検証できない」構造を持つ。design-record 側には #824 の検討を踏まえ「forgeable だが検出器は意図的に追加しない」という JSDoc 注記があるが、review-record 側には長らく同種の注記が無かった（#869 で追加して解消。注記は #824 の判断を写したが根拠は写していない — design-record のラベルは PR diff と矛盾するのに対し、findings ゼロのレビューは正当に痕跡を残さないため diff では skip と clean を区別できず、残る担保は work-cycle.md の「機械が守らない範囲」に帰す）。#809 でこの trailer 用の雛形関数（`buildReviewRecordTemplate`、`buildDesignRecordTemplate` を明示的に模倣）を書いた際、実装者自身が実際にはツールを起動せず `Review: tool=simplify` trailer だけをコミットに書きかけた——trailer が形式的に有効である以上、この操作を機械は区別できない。注記の不在に気づいたのは模倣先を書いている最中に自分がまさにその弱点を踏んだ瞬間であり、模倣元を読み直して初めて気づいたわけではない（#869）。
  対策の追加: 既存メカニズムを明示的に模倣するコミットでは、模倣元の JSDoc/コメントに「意図的に検出しない」「forgeable だが受容する」等のリスク受容の言明が無いか確認し、あれば模倣先にも同じ言明を複製する。無い場合も、模倣先が同じ自己申告構造を持つなら新たに一言添える。

  **同じ主題の第3の軸: 踏襲を委譲する側が、倣う対象を列挙しないとき。** 先例を名指して「同じ形にせよ」と書くブリーフは、倣う範囲を決めていない。委譲先が写した性質と写さなかった性質の両方について「同じ形にした」は等しく真になるため、指示の充足からは欠落を判別できない。
  問いの形の追加: 「先例を名指すブリーフで、倣う対象として何を列挙したか。列挙しなかった性質のうち、先例が持っていて新実装が持たなくても『同じ形にした』と言えてしまうものはどれか」。
  具体例: #1114 の実装委譲ブリーフは `scripts/check-review-record.mjs` を先例として名指し、倣う対象に strict な `parseArgs`・出力の書式・終了コードの割り当て・終端ゲートと同一関数への委譲の4点を挙げた。挙げなかったのは先例が持つ入出力失敗の扱いで、返ってきた実装は `readFileSync` を裸で呼び、存在しないパスで未捕捉の ENOENT が終了コード1へ落ちた — 書式違反に予約されていた値である。呼び出し元のレビューが差し戻し、読み込み失敗を終了コード2へ分離して解消した。この中間状態はコミットされていないため履歴には現れず、`scripts/check-design-record.mjs` は最初のコミットの時点で既に修正後の形をしている。
  対策の追加: 先例の名指しは列挙の代わりにならない。失敗経路の扱い（不正入力・対象の不在・権限）は、正常系の shape とは別の項目として列挙する。
