- **共有ヘルパーの絞り込みが最初の消費者の都合で決まっている trap**: 「この集合を返す」という名前のヘルパーが、実装では最初の消費者の都合で一部を除いていることがある。
  除外の理由はその消費者の側にしかなく、名前にもシグネチャにも現れない。
  次の消費者は名前を信じて再利用し、除かれた分については何も報告しないまま完成する — 出力は正しく見え、欠けているものは出力に現れないので、差分を読んでも気付けない。
  問いの形: 「このヘルパーが返さないものは何か。その除外は集合の定義から来ているか、それとも最初の呼び出し側の都合か」。実装のフィルタ引数を読み、除外理由のコメントが自分の用途にも当てはまるかを確かめる。
  具体例: `changedFilesSince` は `--diff-filter=d` で削除パスを落としている。理由は既存の消費者の側にあり、削除された `.pfdsl` / `.md` に対して `pfdsl check` や linebreak 検査を走らせると存在しないファイルで落ちるため。#778 でサイクルの変更パスを PFD の `location:` と突合する報告材料を書いた際、この名前をそのまま再利用した。突合が答えるべきゲート項目は「変換コンポーネントを追加・変更・**削除**した場合」と書いており、削除こそモデル化側が実体を失ったまま残りやすい経路だったが、削除はどちらの側（モデル化・モデル化外）にも現れず、報告そのものが存在しなかった（レビューが検出。`deletedFilesSince` を別に足して解消）。
  対策: 共有ヘルパーを新しい用途へ引くときは、名前でなくフィルタ引数を読む。除外があれば、その除外理由のコメントを自分の用途に読み替えて成立するかを1行で書く。書けないなら、その用途にはヘルパーを分ける。
