- **区間を列挙せずに書いた移行ガイドが、自分の区間の項目を落とす trap**: 版ごとの移行ガイドは「前回の公開版から今回の公開対象までに、採用先の作業を要する変更」を網羅する必要がある。
  書き手が記憶や直近の作業から項目を拾うと、書き手が関わらなかった変更や、採用先への影響が件名から読めない変更が落ちる。
  落ちたことはガイドの側からは見えない — 載っている項目はどれも正しく、欠けている項目は読み手の更新後に初めて表に出る。
  コミットの印（Conventional Commits の `!` 等）だけで絞ると、印を付けなかった変更がそのまま落ちる。
  問いの形: 「ガイドの対象区間のコミットを配布物のパスで全件列挙したとき、採用先の作業を要するものがすべて項目になっているか」。

  観測（2026-09-30、PR #1317 のレビュー）: PR の初版は `docs/migration-guide.md` の「Unreleased — after v0.0.26」節を、変更 PR ごとに未公開項目を書く運用とともに新設した。
  その節は、同じ区間に入っていた2件を落としていた。
  1件は GitHub Issues backend の採用先へ新たに配置される `pfdsl-sweep-completed-chains.yml`、もう1件は #1314 より前の installer が壊した `.claude/pfd-ops-install-manifest.json` の回復である。
  後者の回復手順は、通常の更新経路から辿れない一度きりの点検表にだけ置かれていた。

  証拠: レビューで `git diff --name-status v0.0.26 dc94909e -- plugin/pfdsl/skills …` を取ると、sweep workflow が追加（`A`）として現れた。
  `git log --no-merges v0.0.26..dc94909e` のうち `!` 付きのコミットに絞ると、D 層の opt-in 化（`1ecbbb24`）と installer の修正（`5685f158`）はどちらも `!` を持たず、候補に入らなかった。
  配布物のルート・`packages/`・`docs/spec/` に触れたコミットを全件列挙する形（164件）では、区間内で採用先の作業を要すると分かっていた6件（`1ecbbb24`、`5685f158`、`47fdc6b7`、`29883428`、`8a84b139`、`313c490f`）がすべて含まれた。
  ファイル単位の差分では installer の修正が `M check-install-sync.mjs` としか現れず、移行が要ることは読み取れなかった。
  コミット単位で件名を読むと読み取れた。

  採用した対策: PR #1317 で、ガイドの保守を変更 PR ごとの記載義務から、公開準備でのコミット単位の全件列挙と振り分けへ移した（`.pfdsl/workflow.md`「採用先への移行案内」）。

  原因の仮説（未検証）: 変更 PR の作者に採用先への影響の記載を課す運用は、作者が影響に気づいた変更しか拾えない。
  同じ区間を後から機械的に列挙する手段が無ければ、気づかなかった変更は誰の担当にもならない。

  未解決: 振り分けそのものは人か agent の判断であり、列挙が全件でも分類で落ちうる。
  分類の誤りを検出する手段は無い。
