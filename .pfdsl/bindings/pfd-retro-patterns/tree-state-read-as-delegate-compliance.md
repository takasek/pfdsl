- **作業ツリーの状態を、委譲先が指示に従った証拠として読む trap**: 委譲先が無応答で終わった回、呼び出し元は作業ツリーを見て残作業を判定するが、そこで得られるのは「何があるか」であって「誰が書いたか」ではない。
  同じツリーへ書く主体がもう1つあると、この2つは黙って乖離する。
  ツリーは正しく、テストも緑で、二重適用も消失も起きないため、既存の trap の症状はどれも出ない。
  壊れるのは報告だけで、呼び出し元は自分の委譲が成功したと述べ、その根拠として成果物の状態を挙げる。
  問いの形: 「委譲先が完走したというこの判断は、委譲先の報告に基づくか、それともツリーの状態からの推定か。推定なら、このツリーへ書ける主体は委譲先だけだと確かめたか」。
  検出: 委譲先が報告を返さずに終わった回は、判定の根拠が推定であることを先に確定させる。
  そのうえで `git status --short` の untracked を含む全行を開く — 並行して動く主体は自分の checkpoint やスクラッチをツリーへ残しており、それが唯一の在席証拠になる。
  セッション開始時点の `git status` に既にあったファイルを「前のセッションの残骸」と分類して読まずに置くと、この証拠を最初に捨てることになる。
  具体例: #1098 のサイクルで修正を委譲した agent が session limit で停止し、報告は「F12 を確認しよう」という途中の一文だけだった。呼び出し元はツリーを調べ、F1 から F14 までの修正がすべて入っていることを確認して「エージェントは最後の確認中に落ちただけで完走していた」とユーザーへ報告した。実際にはこの worktree で別のセッションが同じ issue を並行して進めており、その checkpoint ファイルがサイクル開始時から untracked で置かれていた。呼び出し元はそのファイルを2度「前のセッションの残骸」として分類し、終端ゲート後に `cycle-status` が dirty tree で停止して初めて開いた。中身には並行セッションが行った修正が列挙されており、コミット済みの差分の一部はその主体の編集だった（2026-09-06）。
  対策: 委譲先が報告を返さなかった回は、成果物の妥当性（レビューとテスト）と作者の帰属を別々に結論する。
  前者はツリーから確かめられるが、後者は確かめられない。
  帰属を述べる必要が無いなら述べない — 述べるなら、報告のどこから来た情報かを書く。
