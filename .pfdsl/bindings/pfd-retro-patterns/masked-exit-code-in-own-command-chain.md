> 過去事例（保存基準: 33878aeb）。本文の対策・判断は当時の記録であり、現行の指示ではない。現行手順は [pfd-retro binding](../pfd-retro.md) を参照。

- **自分のコマンド連結が終了コードを隠す trap**: 検査・整形・コミットを `;` で1行に連結して実行すると、途中で拒否されたステップの失敗が他のステップの成功出力に紛れる。
  パイプライン全体の終了コードは最後のコマンドのものになり、途中の hook が止めたコミットは「実行された」ように読める。
  出力を人が読んで判断している限り、この誤読は成功の形で現れる — 弾かれたコミットは作られていないので、次に走る `--amend` は**手前のコミットを書き換える**。結果として2つの論理単位が1つへ畳まれ、しかも畳まれたことはコミットメッセージからは分からない。
  問いの形: 「この連結のどこかが失敗しても、私は気づく形になっているか。各ステップの終了コードを見ているか、それとも出力の文字列を見ているか」。
  具体例: pre-commit の biome 検査に弾かれたコミットを成功と誤読し、`git commit --amend` で回復しようとして、共有関数の追加コミットとその委譲リファクタが1コミットへ畳まれた。後から `git reset --soft` して割り直している（2026-09-13、PR #1187 のサイクル）。
  当時の条件: hook は `make setup` が `.git/hooks/pre-commit` へ置いた shim 経由で `scripts/pre-commit` を実行する構成で、検査は `node scripts/check-biome.mjs --staged`。連結の形は `pnpm biome …; node scripts/check-biome.mjs .; git add -A && git commit -m …` で、`;` 区切りのため前段の非ゼロ終了がコミットの実行を止めていない。
  観測できたのは、コミット後に `git log` が期待した2件でなく1件を返したこと。hook の拒否メッセージ自体は他ステップの出力に紛れて読み落としている。
  原因の仮説: 出力の文字列を見て成否を判断しており、各ステップの終了コードを見ていなかった。仮説であって、同じ連結を再現して確かめてはいない。
  この回の皮肉は、同じサイクルの CI 検査が23周かけて塞いでいた欠陥が「終了コードのマスク」そのものだったこと（`|| true`、`continue-on-error`、`{0}` を無視する shell template）。**検査対象の中に探していた失敗の型を、自分の操作手順の側では探していない。**
  対策の候補（当時）: 検査と確定操作を同じ連結に入れない。確定操作の前段に検査を置くなら `&&` で繋ぎ、`;` は独立した観測にだけ使う。コミット後は件数（`git rev-list --count`）で確かめ、出力の文字列を根拠にしない。
  未解決: この候補は採用した操作手順へ反映していない。連結の形は実行のたびに組み立てるもので、`;` と `&&` の選択を判定できる入力が既存の検査のどれにも入っていないため、機械化の可否も見ていない。
