- **遅れたツリーの間に外部へ出した成果物は rebase で直らない trap**: base がサイクル途中で進むと、遅れに気付くまでの間ツリーは旧版の規約を現行の見本として提示し続ける。
  ツリーそのものは rebase で復旧するが、その窓の間に**リポジトリの外へ出した成果物**（起票した issue の本文、投稿したコメント、PR 本文）は rebase の対象でないため、旧規約の転写を抱えたまま残る。
  検査も CI もブランチのツリーしか見ないので、残った転写を指す機構が1つも無い。
  問いの形: 「遅れに気付いてから rebase するまでの間に、ツリーの外へ出した成果物はあるか。その本文は、いま rebase で取り込んだ側の規約に照らしても正しいか」。
  具体例: #828 のサイクルで、着手時 `behindBase: 0` だったツリーが作業中に10コミット以上遅れた（PR #830 のマージ）。その窓の中でスコープ外の発見を #831 として起票し、チェックリストに「方針決定（`決定: 案N`）」と書いた。`決定:` 行はまさに #830 が retire した規約であり、遅れたツリー側の companion を現行の見本として読んだ結果だった。rebase・再ビルド・全ゲート再実行はいずれも緑で、#831 の本文はどれの検査対象にもならなかった（retro の C 層で気付き本文を修正）。
  対策: 窓そのものは終端ゲートが報告材料として印字する（`gate-check.mjs` の Cycle window）ので、時刻範囲を手で求めるところから始めない。印字された窓の中の外向き操作を数え、`gh issue list --search "involves:@me" --json number,createdAt` と `gh api` のコメント一覧で窓に入るものを列挙し、取り込んだコミットが規約文書（companion・reference・スキル本文）を触っていれば、その本文を読み直す。窓が空だったなら1行そう記録する。
  窓の印字は rebase 後も残るが、rebase 後は「ブランチ作成 〜 最初のコミット」の区間だけ落ちる — その区間に外向き操作をしていれば、そこは手で補う。
  **同じ主題の第2の軸: 窓が改訂したのが、自分が見本に使った兄弟成果物であるとき。** この場合の被害はツリーの外に出ない。窓の中で書いた新しい成果物はツリーの中にあり、rebase は競合なくマージされ、以降の検査もすべて緑を返す — 写した先の版が改訂前だったことを指す機構が1つも無いのは、外向き成果物のときと同じである。
  問いの形の追加: 「窓が取り込んだコミットは、自分がこのサイクルで見本にした成果物を触っているか。触っているなら、その改訂は自分の写しにも当たるか」。
  具体例: `prose-mechanization-audit` スキルを兄弟の `retro-pattern-sweep` スキルを見本に書いた（#915）。着手時 `behindBase: 0` だったツリーが作業中に10コミット遅れ、その窓に兄弟スキルの**初回実行レビュー**（#934・#935）が入っていた。そのレビューが塞いだ3点（記録ファイル不在時に読み取りコマンドがクラッシュする・記録を1コミットに畳むと `commit` フィールドが自己言及になる・検査を最後にまとめると切り分けの手戻りが出る）は、写した側にもそのまま入っていた。写した時点の見本は誰にも欠陥が知られておらず、写す前にどれだけ精査しても出なかった — 出したのは見本の初回実行だけである。
  対策の追加: 窓が触ったファイルを `git diff --name-only <旧base> <新base>` で列挙したら、規約文書かどうかだけでなく、**このサイクルで見本にした成果物が含まれるか**も見る。含まれていればその差分を読み、自分の写しへ当たる分を同じサイクルで反映する。見本がまだ一度も実行されていない設計であった場合、写した側の欠陥は精査ではなく初回実行でしか出ないので、見本側の初回実行は自分の写しの検証を兼ねる。
