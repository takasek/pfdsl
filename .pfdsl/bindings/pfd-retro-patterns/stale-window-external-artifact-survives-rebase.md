- **遅れたツリーの間に外部へ出した成果物は rebase で直らない trap**: base がサイクル途中で進むと、遅れに気付くまでの間ツリーは旧版の規約を現行の見本として提示し続ける。
  ツリーそのものは rebase で復旧するが、その窓の間に**リポジトリの外へ出した成果物**（起票した issue の本文、投稿したコメント、PR 本文）は rebase の対象でないため、旧規約の転写を抱えたまま残る。
  検査も CI もブランチのツリーしか見ないので、残った転写を指す機構が1つも無い。
  問いの形: 「遅れた窓の間に外部へ転送または兄弟成果物から写したものはあるか。あるなら、その全ては現行の規約・差分・再導出した値に照らしてなお正しいか」。
  具体例: #828 のサイクルで、着手時 `behindBase: 0` だったツリーが作業中に10コミット以上遅れた（PR #830 のマージ）。その窓の中でスコープ外の発見を #831 として起票し、チェックリストに「方針決定（`決定: 案N`）」と書いた。`決定:` 行はまさに #830 が retire した規約であり、遅れたツリー側の companion を現行の見本として読んだ結果だった。rebase・再ビルド・全ゲート再実行はいずれも緑で、#831 の本文はどれの検査対象にもならなかった（retro の C 層で気付き本文を修正）。
  **同じ主題の第2の軸: 窓が改訂したのが、自分が見本に使った兄弟成果物であるとき。** この場合の被害はツリーの外に出ない。窓の中で書いた新しい成果物はツリーの中にあり、rebase は競合なくマージされ、以降の検査もすべて緑を返す — 写した先の版が改訂前だったことを指す機構が1つも無いのは、外向き成果物のときと同じである。
  具体例: `prose-mechanization-audit` スキルを兄弟の `retro-pattern-sweep` スキルを見本に書いた（#915）。着手時 `behindBase: 0` だったツリーが作業中に10コミット遅れ、その窓に兄弟スキルの**初回実行レビュー**（#934・#935）が入っていた。そのレビューが塞いだ3点（記録ファイル不在時に読み取りコマンドがクラッシュする・記録を1コミットに畳むと `commit` フィールドが自己言及になる・検査を最後にまとめると切り分けの手戻りが出る）は、写した側にもそのまま入っていた。写した時点の見本は誰にも欠陥が知られておらず、写す前にどれだけ精査しても出なかった — 出したのは見本の初回実行だけである。
  **同じ窓は handoff prompt にも残る。** PR #966 の rebase 後、Claude distribution-review 用の外部 prompt が rebase 前の approval interval と `inScope` file count を保持していた。branch の gate は current tree を検査するため、外部へ渡した本文を訂正しない。
  **例外は、外へ出した成果物がゲートの入力でもある場合。** 窓の中で書いた外向き成果物のうち、機械が読むもの（設計選択記録のように終端ゲートが形式を検査するもの）は、rebase 後のゲート再実行で捕まる。この経路がある成果物は上の「指す機構が1つも無い」に当たらない — ただし捕まるのは機械が見る面だけで、同じ成果物の散文部分に入った旧規約の転写は依然として誰も指さない。
  具体例: 着手時 `behindBase: 0` だったツリーが作業中に11コミット遅れ、その窓に設計選択記録の処分行を番号付き形式へ変える規約変更が入っていた（#974 のサイクル、2026-08-27）。窓の中で投稿した記録は旧形式で書かれており、rebase 後にゲートの内容検査が `numbered dispositions must cover exactly 1..3; missing: 1, 2, 3` を返して判明した。窓の存在に気付いた契機は別の作業（レビュー用の detached worktree を `origin/main` から切ったときに HEAD が想定と違ったこと）で、ゲートはその後の確認だった — 機械が捕まえる面があっても、気付きが先行しないと投稿済みの成果物は旧形式のまま残る。
  対策: 窓そのものは終端ゲートが報告材料として印字する（`gate-check.mjs` の Cycle window）ので、時刻範囲を手で求めるところから始めない。印字された窓の中の外向き操作を数え、`gh issue list --search "involves:@me" --json number,createdAt` と `gh api` のコメント一覧で窓に入るものを列挙し、取り込んだコミットが規約文書（companion・reference・スキル本文）を触っていれば、その本文を読み直す。窓が空だったなら1行そう記録する。窓の印字は rebase 後も残るが、rebase 後は「ブランチ作成 〜 最初のコミット」の区間だけ落ちる — その区間に外向き操作をしていれば、そこは手で補う。窓が触ったファイルを `git diff --name-only <旧base> <新base>` で列挙したら、規約文書かどうかだけでなく、**このサイクルで見本にした成果物が含まれるか**も見る。含まれていればその差分を読み、自分の写しへ当たる分を同じサイクルで反映する。見本がまだ一度も実行されていない設計であった場合、写した側の欠陥は精査ではなく初回実行でしか出ないので、見本側の初回実行は自分の写しの検証を兼ねる。handoff の直前に gate と同じ判定から current approval interval と `inScope` 集合を再導出し、その出力を prompt へ転記する。手で数えた file count や rebase 前の range を再利用しない。
