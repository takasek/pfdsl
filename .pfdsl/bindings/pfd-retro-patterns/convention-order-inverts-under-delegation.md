- **規約の作業順が委譲で反転し、集約単位のゲートがそれを見ない trap**: 「A を B の前に行う」型の規約は、A も B も同じ主体が行うことを暗黙の前提にしている。B を委譲すると委譲先が B まで済ませて戻るため、呼び出し元が行う A は必ず B の後になる。規約の求める順序は構造的に満たせない。
  ゲートが A の痕跡をブランチ・PR のような集約単位で数えていると、順序が反転していても「A は在る」で PASS する。反転は緑の中に隠れ、規約違反としては一度も観測されない。
  問いの形: 「この規約が求める順序の両端を、同じ主体が行うか。片方を委譲したとき順序は保てるか。保てないなら、ゲートは何を見て PASS しているか」。
  具体例: （旧規約の事例）当時の `.pfdsl/roadmap.md` は「レビューはコミットの前に回す」と定めていた — 記録が commit message の trailer であり後から追記できないため。#944 のサイクルは実装を `pfd-implementer` へ委譲し、委譲先はコミットまで済ませて戻った。呼び出し元のレビュー（`/simplify` 4角度・独立解）はその2コミットの後に走り、trailer は後続の修正コミットに付いた。`gate-check.mjs` の Review record 項目はブランチ内の trailer を数えるので `2 record(s)` で PASS し、先行2コミットが未レビューのままコミットされた事実はどこにも出なかった（2026-08-22）。
  対策: 配布層（pfd-ops `references/work-cycle.md` 手順2 適用点3）へ昇格済み。必要な作業順と記録形式を分け、最終差分をレビューする。記録漏れの補修だけを理由に過去コミットを再作成しない。
  過去には、最後のレビュー記録とコミットの順序を見る検査を61ブランチへ試し、6本で発火した（2026-08-22）。この発火率だけでは、レビューの実施を検証できることや、履歴の作り直しを求める運用の妥当性を示せない。trailer 専用ゲートの撤去後は、この検査案を現行の回復手順として使わない。
