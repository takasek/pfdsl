- **規約の作業順が委譲で反転し、集約単位のゲートがそれを見ない trap**: 「A を B の前に行う」型の規約は、A も B も同じ主体が行うことを暗黙の前提にしている。B を委譲すると委譲先が B まで済ませて戻るため、呼び出し元が行う A は必ず B の後になる。規約の求める順序は構造的に満たせない。
  ゲートが A の痕跡をブランチ・PR のような集約単位で数えていると、順序が反転していても「A は在る」で PASS する。反転は緑の中に隠れ、規約違反としては一度も観測されない。
  問いの形: 「この規約が求める順序の両端を、同じ主体が行うか。片方を委譲したとき順序は保てるか。保てないなら、ゲートは何を見て PASS しているか」。
  具体例: `.pfdsl/roadmap.md` は「レビューはコミットの前に回す」と定める — 記録が commit message の trailer であり後から追記できないため。#944 のサイクルは実装を `pfd-implementer` へ委譲し、委譲先はコミットまで済ませて戻った。呼び出し元のレビュー（`/simplify` 4角度・独立解）はその2コミットの後に走り、trailer は後続の修正コミットに付いた。`gate-check.mjs` の Review record 項目はブランチ内の trailer を数えるので `2 record(s)` で PASS し、先行2コミットが未レビューのままコミットされた事実はどこにも出なかった（2026-08-22）。
  対策: 配布層（pfd-ops `references/work-cycle.md` 手順2 適用点3）へ昇格済み — 順序の相手側を委譲前に決めること、痕跡の存在だけを見るゲートが反転を通すこと、順序を見る検査が何をどこまで分けるかはそちらが一次情報。ここに残すのは問いの形と、この trap を踏んだ実例である。
  なお「順序を見る検査は作れない」と書くのは誤り。「最後に記録された A より後ろに B が積まれた」を見る検査を実履歴に当てると、現行ゲートを PASS した61ブランチ中6本（9.8%）でしか発火しない — 運用に耐える。素朴な強化（B ごとに記録を要求する）が過半を叩くのと桁が違う。数え方は、main の各 merge コミットの `M^1..M^2` を1ブランチとみなし、trailer を `review-record.mjs` の `parseReviewRecords` と `GATE_TOOLS` で解析し、`CODE_PATH` を触るブランチのうち現行ゲートを PASS するものを母数に取る。この誤りは、1種類の検出器を測っただけで検出器というクラス全体を却下した回に実際に書かれ、独立解が反証した（2026-08-22）。
