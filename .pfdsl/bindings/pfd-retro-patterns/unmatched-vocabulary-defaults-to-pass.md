- **語彙に当たらなかった入力が「異常なし」の既定に落ちる trap**: 条件の発火を語句の allowlist（見出しの語・キーワード・接頭辞の一覧）で決める判定器は、allowlist に無い書き方をされた入力に対して「判定できなかった」ではなく「条件は成立しない」を返す。
  検査対象の集合が漏れる形（手列挙 trap）と違い、こちらは対象を正しく受け取っており、走ってもいる — 落ちているのは対象でなく**判定の語彙**であり、その漏れが判定結果の側では「確認済み・問題なし」という積極的な緑として出てくる。
  問いの形: 「この判定器が語彙に当たらなかったとき、返るのは『不明』か『異常なし』か。後者なら、その既定を選んだ根拠は何か」。判定関数の分岐を末尾から読み、どの分岐が catch-all になっているかを見る。
  具体例: `scripts/lib/cycle-status.mjs` の `detectEnumeratedOptions` は、かつて候補列挙の起点になる見出しを語彙の allowlist（`対応案` / `方針案` / `選択肢` / `検討したい方向`）で探していた。#774 の本文は候補2件を `## 対応の方向` の下に並べていたためどれにも当たらず、`classifyDesignSettlement` の catch-all である `no-enumerated-options` に落ちて `unsettled: false`（設計確定済み）が返った（#800、2026-08-07）。人手で本文を読んだから設計対話に入れたのであって、機械判定を信用する運用なら素通りしていた。
  具体例（同じ catch-all の2度目）: #828 の本文は候補を見出しの下に並べておらず、「現行の flat 配列を壊すか、別キーにするかは互換性判断」という散文の二者択一として書いていた。見出し語彙の問題ですらなく、列挙という形を取らない案の提示であり、`detectEnumeratedOptions` の模型の外にある。判定はやはり `no-enumerated-options` へ落ち、`unsettled: false` を返した（2026-08-10）。**語彙を足す方向の修正では届かない位置に2度目が出た**ことが、catch-all の既定値そのものを選び直す根拠になった。
  この2件については語彙 allowlist 自体が撤廃済みで、`detectEnumeratedOptions` は markdown 見出し行なら語彙を問わず起点として扱う（#800。偽陽性の許容と引き換えに偽陰性を潰す判断）。catch-all の分岐そのものは残っており、列挙という形を取らない案の提示は依然この既定へ落ちる。
  具体例（カタログを引く道具自身がこの形を持つ）: `scripts/retro-patterns.mjs select` の `--tag` に存在しないタグを渡すと、`tagged (0 of 64)` を警告なしで返す。
  0件は「今サイクルに当たるパターンは無い」と読めるため、監査そのものが素通りする。
  同じリポの `pfdsl meta list` は、どのノードも使っていないセレクタ値に対して stderr へ typo の警告を出す — 正しい形は既にリポ内にあり、`retro-patterns` 側だけが持っていない（カンマ区切りを1つの未知タグとして扱っていた変種は解消済みで、`--tag a,b,c` は分割されて和集合になる）。
  対策: 語彙による判定器を書くとき、catch-all の分岐が返す値を「不明」と「異常なし」のどちらにするかを明示的に選び、選んだ理由を1行書く。判定が真偽2値で「不明」を表現できない場合、値の追加が要るかどうかもその時点で決まる。

  **入力 schema のフィールド名を推測した場合も、未知の語彙が0件へ落ちる。** 同じ処理の別集計が正しい値を返すと、出力全体が schema に適合しているように見え、0件の系列だけが疑われない。
  問いの形の追加: 「0件を返した系列が読むフィールド名は、schema や実データの1件から確かめたか。同じ出力の別系列が正しいことを、その系列の正しさへ流用していないか」。
  具体例: PR #1036 のレビューサイクルで `graph edges --json` の edge を `{from, to}` と推測して集計し、`retro_findings edges: 0` を得た。実際のフィールドは `{kind, artifact, process}` であり、実ファイルの grep では22本あった。同じスクリプトの total と feedback 集計は正しく動いていたため、部分的に正しい出力が0件を「該当なし」と読む根拠になりかけた（#1037 で記録）。

  **同じ主題の第2の軸: 潰れるのが判定の既定でなく、表示の減算であるとき。** 別の経路が既に拾った分を引いてから件数を出す表示は、引く前が0だった回と、引かれて0になった回を同じ0で表す。
  0 は「何も無い」と読まれるが、そこには「元から無かった」と「あったが他方が既に持っていた」の2つが潰れている。
  取るべき次手は両者で逆になる — 前者は探し方を変える必要があり、後者は探し方が既に当たっている。
  減算は表示を簡潔にするために入るので、書いた側は情報を削った自覚を持たない。
  問いの形の追加: 「この数は何から何を引いた結果か。引く前の数は同じ出力のどこかに出ているか」。
  具体例: `scripts/retro-patterns.mjs select` の word-only 節は、語が当てたパターンからタグが既に選んだ分を引いた件数を出していた。`--tag target:check-script --word allowlist` は `word-only (0)` を返し、どのパターンにも当たらない `--word zzznothing` も同じ `word-only (0)` を返した。語が1件当てていた回と1件も当てなかった回が同じ表示になっており、語の選び直しが要るかどうかが出力から判定できなかった（#803 検出3）。
  対策の追加: 減算後の数を出す箇所には、減算前の数を同じ出力に並べる。別の表示へ分けると、読み手が2つを突き合わせる工程が要るぶん潰れたままになる。既定値の側（上の catch-all）と直し方が違う点に注意する — こちらは分岐の選び直しでなく、出力へ minuend を戻すことでしか解けない。
