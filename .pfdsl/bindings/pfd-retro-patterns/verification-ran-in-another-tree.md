- **検証が別のツリーで走り、その緑が自分の変更の緑として読まれる trap**: worktree でサイクルを回していても、Bash の作業ディレクトリはセッション既定（main repo）へ戻ることがある。
  戻った状態で走らせたテスト・ビルドは、当該サイクルの変更を持たないツリーを検査するので緑になる。
  緑は「自分の変更が通った」証拠として読まれるが、実際にはその差分は一度も検査されていない。
  書き込み側には guard があっても（別 worktree への Edit は拒否される）、検証コマンドの実行場所を見る機構は無い。
  問いの形: 「いま緑を返したこのコマンドは、どのツリーで走ったか。出力の中に、自分がこのサイクルで足したものの痕跡（テスト件数の増分・新しい項目名）があるか」。
  具体例: 実装を委譲した subagent のセッションが、直前に main thread が別の worktree へ `cd` していたせいでそちらに紐づき、対象 worktree へ書けずに停止した（この回は書き込み guard が deny したので事故にならなかった）。同じセッションで後に `make test` が main repo で走り `pass 1333 / fail 0` を返した。worktree で走らせ直すと `pass 1346` で、差の13件はそのサイクルで追加したテストだった — 1回目はそれらを1件も実行していない。exit code は両方 0（#834 のサイクル、機構化は #840）。
  具体例: 同じ cwd の戻りが、緑でなく「機能が無い」の形で出ることもある。新設した3サブコマンドの help を読もうとして `node packages/cli/dist/cli.js graph locate --help` を相対パスで叩いたところ、main repo の古いビルドが走り `unknown graph subcommand: locate` を返した。直前の数回は同じ相対パスで新コマンドが動いていたので、出力はコマンドの実装が壊れた証拠に見えた（2026-08-11。worktree の絶対パスで叩き直して解消）。
  具体例: 読むだけでなく書く回にも同じ戻りが起きる。worktree で走らせたつもりの `node scripts/gen-plugin.mjs` が main repo で走り、そのツリーの古いビルドから配布スキル本文を再生成して、後から追加されたサブコマンド3つが消えた版を main の作業ツリーへ書き込んだ。気付いたのは、続けて叩いた `git add` を main ブランチのガードが拒否したときで、生成物の中身ではなくガードの拒否が症状だった（2026-08-11。main のツリーは `git checkout --` で戻し、worktree の絶対パスで再生成した）。
  具体例: `pwd` を置いて確かめても、確かめたのはその呼び出し1回分でしかない。同じサイクルの前半で `pwd &&` を先頭に付けた呼び出しが worktree を印字しており、その確認を根拠に以降を相対パスで走らせたところ、途中から cwd が戻っていた。症状は緑ではなく「自分の作業が消えた」形で出た — 単体テストの件数が 28 から 16 へ減り、`git status --short` が空を返し、変更したはずのファイルを `tail` すると変更前の内容が出た。実際には worktree 側は無傷で、3つの出力すべてが main repo のものだった。`git -C <worktree> status --short` で照らして判明（2026-08-11）。
  対策: 検証コマンドの出力は件数で読む。**実行場所の確認は1回では持続しない** — 前の呼び出しで `pwd` が正しかったことは次の呼び出しの根拠にならないので、測るたびに確かめるか、そもそもパスを毎回書く（`make -C <worktree>`・`node <worktree>/scripts/x.mjs`・`git -C <worktree>`）。件数の減少や「変更が消えた」に見える出力も同じ疑いの対象で、消失を疑う前に実行場所を疑う。生成コマンドは出力を持たないので件数で読めない — 走らせた後に `git -C <対象ツリー> status --short` と、意図していないツリーの `status` の両方を見る。前回との差が自分の変更の増分と合わない回は、値を疑う前に実行場所を疑う。コマンドの冒頭に `pwd` を置くか、ディレクトリ変更を別の呼び出しに分けて確定させてから測る。委譲の直前も同じで、subagent は呼び出し元の cwd を継ぐため、spawn 前に cwd が対象 worktree であることを確かめる。
