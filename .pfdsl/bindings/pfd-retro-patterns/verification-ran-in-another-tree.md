- **検証が別のツリーで走り、その緑が自分の変更の緑として読まれる trap**: worktree でサイクルを回していても、Bash の作業ディレクトリはセッション既定（main repo）へ戻ることがある。
  戻った状態で走らせたテスト・ビルドは、当該サイクルの変更を持たないツリーを検査するので緑になる。
  緑は「自分の変更が通った」証拠として読まれるが、実際にはその差分は一度も検査されていない。
  書き込み側には guard があっても（別 worktree への Edit は拒否される）、検証コマンドの実行場所を見る機構は無い。
  問いの形: 「いま緑を返したこのコマンドは、どのツリーで走ったか。出力の中に、自分がこのサイクルで足したものの痕跡（テスト件数の増分・新しい項目名）があるか」。
  具体例: 実装を委譲した subagent のセッションが、直前に main thread が別の worktree へ `cd` していたせいでそちらに紐づき、対象 worktree へ書けずに停止した（この回は書き込み guard が deny したので事故にならなかった）。同じセッションで後に `make test` が main repo で走り `pass 1333 / fail 0` を返した。worktree で走らせ直すと `pass 1346` で、差の13件はそのサイクルで追加したテストだった — 1回目はそれらを1件も実行していない。exit code は両方 0（#834 のサイクル、機構化は #840）。
  対策: 検証コマンドの出力は件数で読む。前回との差が自分の変更の増分と合わない回は、値を疑う前に実行場所を疑う。コマンドの冒頭に `pwd` を置くか、ディレクトリ変更を別の呼び出しに分けて確定させてから測る。委譲の直前も同じで、subagent は呼び出し元の cwd を継ぐため、spawn 前に cwd が対象 worktree であることを確かめる。
