- **型が許す形の幅と、消費側が仮定した幅がずれる trap**: 型や仕様がスカラーと配列、ASCII と非 ASCII のように広い形を許していても、消費側のコードはリポに実在する狭い形だけを想定して書かれることがある。
  広い形の最初の実例が現れるまで欠陥は潜伏し、現れた瞬間にたまたま最初に走った消費者がクラッシュする形で出る。
  設計レビューでは見つからない。仕様も型定義も正しく、消費側も現存データに対しては正しく動いているため、どちらを読んでも異常が無い。
  問いの形: 「この型が許す形のうち、いま実在しているのはどれか。実在していない形が来たとき、この消費側は何をするか」。
  具体例（3件、すべて #659 のサイクルで同時に顕在化した）:
  具体例1: `git ls-files` は非 ASCII を含むパスを quote してエスケープする。10箇所が改行 split で受けており、非 ASCII のファイル名が37件入った時点で2箇所が ENOENT でクラッシュした。残る8箇所は pathspec が新ディレクトリに届いていなかっただけで同じ欠陥を持っていた。
  具体例2: 同型が `git diff --name-only` にも3箇所あった。**`ls-files` の10箇所を直した直後に見落としており**、レビューが拾った。塞いだのは型でなく経路の一つだった。
  具体例3: `location:` は spec §15.8 と `packages/core` の型がスカラーと配列の両方を許すが、`skill-wiring-check` がスカラー前提で `location.replace()` を呼んでいた。`workflow.pfdsl` 側で初めて配列を使った時点でクラッシュした。
  「検出フィールドが失敗の型の一経路しか塞いでいない trap」は検出側の網羅性を問うが、こちらは生産側と消費側が想定する**値の形の幅**のずれを問う。
  対策: 型定義や仕様が「A または B」と書いている箇所を見つけたら、リポに実在するのがどちらかを数える。片方が0件なら、その形を受ける消費側は全て未検証である。
  消費側を直すときは型の定義から呼び出し箇所を機械的に列挙する（名前で grep しない）。
