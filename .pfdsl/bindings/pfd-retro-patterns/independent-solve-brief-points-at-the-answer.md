> 過去事例（保存基準: 33878aeb）。本文の対策・判断は当時の記録であり、現行の指示ではない。現行手順は [pfd-retro binding](../pfd-retro.md) を参照。

- **独立解を求めるブリーフが解答の在処を名指しする trap**: 委譲先に「結論を伏せて同じ問題を独立に解け」と求めるとき、問題の説明はどうしても変更対象のファイル名を含む。委譲先の作業ツリーがそのサイクルの実装を含んでいれば、委譲先は禁止コマンドを一切使わずに、通常の探索の中で解答へ到達する。
問いの形: 「この委譲が求めているのは独立解か。独立性を担保しているのは禁止事項の列挙か、それとも解答を含まないツリーか」。禁止の列挙で担保している場合、列挙にない経路が何本あるかは誰も数えていない。
この trap の出力は**完全な一致**である。独立解が採用案と細部まで揃うことは、設計が正しいときに期待される唯一の結果でもあるため、汚染された回と成功した回は成果物からは区別できない。委譲先が自己申告しない限り、呼び出し元には強い裏付けが返ってきたようにしか見えない。
具体例: #671 のサイクルで、観点3（設計妥当性）の独立解 agent へ渡したブリーフが `scripts/gate-check.mjs` を問題の所在として名指しした。ブリーフは issue 本文・`git diff`・companion の該当行を読むことを明示的に禁じていたが、実装はその時点で未コミットのまま当該ファイルに適用済みであり、agent は名指しされたファイルを普通に読んで `(#671)` と書かれたコメントごと解答に到達した。禁止された経路は1本も通っていない。agent 自身が汚染を申告したため撮り直せたが、申告は agent の裁量であって機構ではない。
対策: 独立性はツリーと文面の両方で担保する — 解答を含まないツリーを `git worktree add --detach <path> origin/<base>` で用意し、そのうえでブリーフから現状への評価語を除く。ブリーフには「このパスのみを読む」と書き、禁止事項の列挙はツリー分離の補助であって代替ではない。ブリーフを書く前に、名指しする予定のパスを自分で開き、そこに解答が書かれていないことを確かめる。
評価語の除き方: 下書きから評価語（無駄・過剰・二度手間・行数）を含む文を洗い出し、各文を「その機構が在る」という中立記述へ置き換える。置き換えても問題が成立するなら評価語は不要だったので消す。置き換えると問題が成立しなくなるなら、その評価語が解を決めているので、ブリーフでなく制約として書く — 「この機構は消してよい」ではなく「満たすべき性質はこれである」と書き、どの機構が残るかは委譲先に決めさせる。それも書けない場合、その回の一致は独立の証拠として数えない旨を報告に書く。
**第2の軸: ツリーが清潔でも、ブリーフが現状の欠点を論評すると解の形が渡る。** 分離したツリーは解答を含まないが、問題を説明する散文は書き手が書く。現状のどこが無駄か・どの機構が過剰かを列挙した時点で、残る設計空間は「その機構を消す案」に狭まる。委譲先が採用案へ到達しても、それは独立に到達したのか、渡された論評を実装しただけなのかを区別できない — ツリーの清潔さは前者の証拠にならない。
具体例: #1044 のサイクルで、独立解 agent へ `origin/main` から切った detached worktree を渡した（実装は含まれない）。しかしブリーフ本文は「argv を組む→逆翻訳する→呼ぶ、という往復を持ち、さらに AST・代表値・shape identity という機構を coverage のために抱えている」と現状を論評し、削除対象の機構を名指しで列挙していた。返ってきた設計は採用案と一致し、呼び出し元ゼロの経路2件も独立に検出されたが、一致のうちどこまでが独立かは判定できない。PR 本文には当初「独立に到達した」と書き、retro で「ブリーフが機構を列挙していた」旨の限定を付けて書き直した。
問いの形の追加: 「このブリーフから現状への評価語（無駄・過剰・二度手間・行数）を全部消しても、同じ問題を解けるか。消せないなら、その評価語が解の形を決めていないか」。
**第3の軸: 作業項目の受け入れ条件をそのまま転記すると、条件に紛れた既決事項が解になる。** 独立解のブリーフは問題を成立させるために要件を書き写す必要があり、その要件は作業項目の本文から採る。だが作業項目は要件だけを書いているとは限らず、所有者が既に決めた事項を要件と同じ節に並べていることがある。転記した側にはどれが要件でどれが決定かの区別が無いので、決定を含む軸は独立に解かれない。前2軸と違って混入源は書き手の論評でなく一次資料であり、「一次資料に忠実に書いた」ほど強く混入する。
具体例: #1229 のサイクルで、観点3(a) の独立解 agent へ `origin/main` と同一のツリー（採用案は GitHub のコメントにしか無く、`gh` を禁止したのでツリーからは到達できない）を渡した。ブリーフは5軸を問うたが、そのうち「本サイクルで配布層を修正するか」の軸について、要件節に issue 本文の「本 issue の成果は findings の列挙であり、修正は件数と規模を見てから別 issue / 別ブランチへ割る」をそのまま転記していた。返ってきた解はこの軸で採用案と一致したが、答えは渡した文そのものであり、独立の証拠として数えられない。判断材料として `.pfdsl/bindings/pfd-ops.md`「適用点 3 と 3 層制御」を名指した点も、委譲の可否を問う軸を委譲側へ寄せている。一方で「findings の記録先」の軸では解が割れた（agent は新規 issue、採用案は対象 issue のコメント）ので、全軸が汚染されたわけではない。
問いの形の追加: 「ブリーフの要件節は、作業項目のどの文から来ているか。その文は要件か、所有者が既に下した決定か。決定なら、その軸は独立に解かれていない」。
対策の追加: 軸ごとに、その軸の答えがブリーフ本文に文字列として現れていないかを投げる前に確かめる。現れている軸は問いから外すか、外せない（問題が成立しない）なら、その軸の一致は独立の証拠として数えない旨を報告に書く。
