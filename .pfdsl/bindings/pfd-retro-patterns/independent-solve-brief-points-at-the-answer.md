- **独立解を求めるブリーフが解答の在処を名指しする trap**: 委譲先に「結論を伏せて同じ問題を独立に解け」と求めるとき、問題の説明はどうしても変更対象のファイル名を含む。委譲先の作業ツリーがそのサイクルの実装を含んでいれば、委譲先は禁止コマンドを一切使わずに、通常の探索の中で解答へ到達する。
問いの形: 「この委譲が求めているのは独立解か。独立性を担保しているのは禁止事項の列挙か、それとも解答を含まないツリーか」。禁止の列挙で担保している場合、列挙にない経路が何本あるかは誰も数えていない。
この trap の出力は**完全な一致**である。独立解が採用案と細部まで揃うことは、設計が正しいときに期待される唯一の結果でもあるため、汚染された回と成功した回は成果物からは区別できない。委譲先が自己申告しない限り、呼び出し元には強い裏付けが返ってきたようにしか見えない。
具体例: #671 のサイクルで、観点3（設計妥当性）の独立解 agent へ渡したブリーフが `scripts/gate-check.mjs` を問題の所在として名指しした。ブリーフは issue 本文・`git diff`・companion の該当行を読むことを明示的に禁じていたが、実装はその時点で未コミットのまま当該ファイルに適用済みであり、agent は名指しされたファイルを普通に読んで `(#671)` と書かれたコメントごと解答に到達した。禁止された経路は1本も通っていない。agent 自身が汚染を申告したため撮り直せたが、申告は agent の裁量であって機構ではない。
対策: 独立性はツリーで担保する。`git worktree add --detach <path> origin/<base>` で解答を含まないツリーを用意し、ブリーフには「このパスのみを読む」と書く。禁止事項の列挙はツリー分離の補助であって代替ではない。ブリーフを書く前に、名指しする予定のパスを自分で開き、そこに解答が書かれていないことを確かめる。
**第2の軸: ツリーが清潔でも、ブリーフが現状の欠点を論評すると解の形が渡る。** 分離したツリーは解答を含まないが、問題を説明する散文は書き手が書く。現状のどこが無駄か・どの機構が過剰かを列挙した時点で、残る設計空間は「その機構を消す案」に狭まる。委譲先が採用案へ到達しても、それは独立に到達したのか、渡された論評を実装しただけなのかを区別できない — ツリーの清潔さは前者の証拠にならない。
具体例: #1044 のサイクルで、独立解 agent へ `origin/main` から切った detached worktree を渡した（実装は含まれない）。しかしブリーフ本文は「argv を組む→逆翻訳する→呼ぶ、という往復を持ち、さらに AST・代表値・shape identity という機構を coverage のために抱えている」と現状を論評し、削除対象の機構を名指しで列挙していた。返ってきた設計は採用案と一致し、呼び出し元ゼロの経路2件も独立に検出されたが、一致のうちどこまでが独立かは判定できない。PR 本文には当初「独立に到達した」と書き、retro で「ブリーフが機構を列挙していた」旨の限定を付けて書き直した。
問いの形の追加: 「このブリーフから現状への評価語（無駄・過剰・二度手間・行数）を全部消しても、同じ問題を解けるか。消せないなら、その評価語が解の形を決めていないか」。
