- **委譲ブリーフが未検証のデータ構造を前提にする trap**: 委譲ブリーフを書く実行主体が、対象データファイル（`.pfdsl` の他に roadmap.pfdsl のような内部フォーマットを含む）の実際の構文を確認せず、既存コードの類推や記憶から前提を記述すると、その前提が実データと食い違ったまま委譲される。issue 本文自体は症状と実装位置しか述べておらず、食い違った前提はブリーフ作成者が実装詳細として独自に補ったものである点で、issue 本文の記述を無批判に信用する trap とは経路が異なる。
  対象は構造だけではない。既存出力を再現させる委譲では、桁数・列幅・区切り文字のような数値仕様が同じ位置を占める。
  問いの形: 「このブリーフが述べる対象データの構造（フィールド名・キーの単複・ネスト形状）や数値仕様（桁・幅・件数）は、実ファイル・実出力を測って確認したものか、それとも読んだ印象からの類推か」。
  具体例: #794（gateCheckCommand の artifact 誤解決）の委譲ブリーフで、「roadmap.pfdsl の process ブロックに `outputs:` フィールドがあり、トップレベルキーは `processes:`（複数形）」と記述したが、実ファイルは `outputs:` フィールドを持たず、トップレベルキーも `process:`（単数形）だった。outputs は `>> processId -> artifact` というフロー矢印記法から導出される別セクションの記法であり、`findIssueNumberForProcess` が読む `location:` フィールドと同じブロックにあるだろうという類推で書いた誤りだった（2026-08-09）。
  具体例: #902（dispatcher と help 列挙のテーブル化）の委譲ブリーフに、既存 help を再現するための列幅を「meta は 48」と書いた。実測値は単行エントリ 47・折返し行 50 で、旧・手書き本文が1つの幅では再現できない不揃いを持っていた。委譲先はブリーフどおりに実装し、単行6本が1桁ずれた状態でコミットされた。ブリーフが受け入れ基準に据えた `make check-readme-cli` は help を表へ組み直すため列揃えを見ず、緑を返した。呼び出し元が `origin/main` を別ツリーでビルドして41通りの呼び出しを直接突合するまで検出されなかった（2026-08-21）。
  対策: **差し戻し条件は、委譲先が食い違いに気付ける場合にしか効かない。** 上の #794 は実ファイルを開けば分かる形だったので止まったが、#902 は「ブリーフの数値」と「受け入れ基準が見る範囲」が両方とも誤りを通したため、委譲先からは正常な完了と区別できなかった。ブリーフに数値仕様を書くときは、その値を出した実測コマンドと出力をブリーフに併記し、受け入れ基準がその数値を実際に判定するかを渡す前に確かめる（一般形は work-cycle.md 適用点2 の「流用する既存機構の作用域を実測で確認する」）。
  以下は #794 についての記録: pfd-implementer は差し戻し条件（work-cycle.md 適用点3「前提が事実でないと判明した場合は実装を止めて設計者へ返す」）に従って実装前に実ファイルを確認し、食い違いを検出した時点で止まって報告した。機構は意図通り機能した実例であり、追加の機構は不要。ブリーフ作成時点で実データを読む習慣そのものは変わらず要る（CLAUDE.md「一次情報は自分で読んでから指示する」の対象は issue・spec に限らず、ブリーフが名指しする実装対象データの構造にも及ぶ）。
