- **検出フィールドが失敗の型の一経路しか塞いでいない trap**: ある失敗の型に対して機械検出が既に存在すると、その型は「対策済み」として監査の対象から外れる。
  検出フィールドが名指すのは実際には**その型に至る一つの経路**であり、同じ型に別経路で到達できるかは検出の存在からは分からない。
  フィールド名が経路でなく型の名前で読まれること（「持ち越し検出がある」）がこの盲点を作る。
  問いの形: 「このフィールドが検出しているのは失敗の型か、それとも型に至る経路の一つか。同じ型に到達する他の経路はどれか、それぞれ何が見ているか」。
  検出の網羅性は各機構が**いつ動くか**で決まるため、経路を列挙したら機構ごとの発火時点と突き合わせる。着手時点を見る機構が無ければ、その時点を通る経路は全部素通しになる。
  具体例: 前サイクルの差分が次サイクルへ持ち越される型に対し、プリフライトは `commitsAheadOfBase` を持つ（#629）。塞いでいるのはコミット経由の経路だけで、未コミットの作業ツリー変更という経路は誰も見ていなかった。`gate-check.mjs` はコミット済み差分、pre-commit hook は staged 分を見るため、どちらも着手時点のツリーの汚れを判定する位置にいない（#744、2026-08-05）。
  具体例: `release-status.mjs` の終了コードは版比較と skill bundle のコミット数だけから決まっていたが、`make release` はそれに加えて distribution review の陳腐化と spec-history の未追随でも拒否する。この終了コードを `releasePending.needsAction` としてプリフライトへ再輸出したとき、フィールド名は型（公開の backlog があるか）を名乗り、実際に塞いでいるのは経路の一つだった — 版がすべて公開済みで `plugin/pfdsl/` だけが未レビューの状態では `needsAction: false` が返り、`make release` は即座に拒否した（#814 のサイクルのレビューが検出。読むべき行は `report` の側だと doc に明記し、終了コード自体の食い違いは #880 として切り出して解消した）。是正は「残り経路を全部畳み込む」でなく「畳み込む範囲を実測で決める」形をとった — release の拒否条件のうち CI・pre-commit がどこでも見ていないものだけを数え、それがちょうど2件だと確かめてから足している。
  他所の判定を自分のフィールド名で再輸出する形は、名前が型を名乗り実装が経路を塞ぐ状態を最も作りやすい — 再輸出元の判定条件を読まずに名前だけを引き継げるため。
  対策: 検出フィールドを追加・参照するときは、それが塞ぐ経路を1語で書く。書けない場合は型の名前で呼んでおり、経路の列挙が済んでいない。
