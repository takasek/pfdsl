- **検査と push を同じ命令に並べても、検査が push を止めない trap**: 検査を走らせた直後に push する命令を1つにまとめると、検査の終了コードは出力に表示されるだけで push の条件にならない。
  積み上げた PR の下のブランチを上へ取り込む merge は、自分の変更が無いので検査を省いて push されやすい。
  原因の見立てが外れていても、修正を push すれば CI が答えるので、見立てを確かめる前に push してしまいやすい。
  どの形でも、失敗を見つけるのは CI か人になり、push した側は「直した」と報告できてしまう。
  問いの形: 「この push は、同じ tree で検査が成功したことを条件にしているか。終了コードを表示しているだけではないか」。

  観測（2026-10-20、PR #1471〜#1473 を積み上げた cycle）: main に入った V036（#1470）は、同じ組を `>>` と `>>?` で接続した文書を error にした。
  B1（#1471）経由でそれを取り込んだ B2（#1472）では、そうした文書を使っていた Connections のテスト5件が失敗した。
  その merge の push は `make build …; make test … ; echo "test=$?"; make typecheck …; git push` の形で、`;` で連結していたため、テストが失敗したまま push された。
  それより前の B1→B2→C の merge の push は `git merge … && git push` の形で、検査を1つも走らせていなかった。
  C（#1473）の vscode-smoke の失敗には、途中で切れた CI ログから「ステータスバーの文字列に含まれる CSS の selected」が原因だと推定し、確かめないまま修正を push した（`c43cc02f`）。
  smoke はそれでも失敗し、失敗を解消したのは別の原因だった。Monaco は表示行の空白の一部を U+00A0 で描き、`label: ""` の照合が一致していなかった。CI ログの生のバイト列（`302 240`）から分かり、`d411ca6a` で直した。
  `c43cc02f` の推定が当たっていたかは確かめておらず、その変更は害がないので残した。
  その間の報告では、#1471・#1472 の smoke は通るようになったと書いた。これは merge を push する前の head の結果で、push 後の head は確かめていなかった。
  #1471 以降のテストが通っていないことは、利用者の指摘で分かった。

  証拠: `cee986e5`（B2 のテストを V036 にならない文書へ書き直した）、`47904d6e`（B1 の vscode-smoke が見つけた、閉じたソースをプレビューのグループに開き直す不具合の修正）、`c43cc02f`（C の推定にもとづく修正）、`d411ca6a`（C の smoke を通した修正）。
  検査と確定操作を `;` で連結せず `&&` で繋ぐ規則は、作業者向けの散文として既にあった。

  採用した対策: 以後の push は `make test && make typecheck && make lint && git push` の形にした。3本とも最終 head の vscode-smoke は通過した。
  同じ形を機械的に止める検査は、別の作業項目として起票する案にした。

  原因の仮説（未検証）: 検査の結果を後でまとめて読むつもりで `echo "X=$?"` を並べると、命令の形が「観測」になり、push が検査の後ろにあっても条件にならない。
  merge の push は「上流は CI を通っている」という前提で検査を省きやすい。ただしこの回は、取り込んだ側の仕様変更が下流のテストの前提を崩していた。

  対応方針: 必須 check と `make push` で対処する（#1499）。
  機械的な事前停止は作らない。
  main の ruleset への `test`・`vscode-smoke` の必須化は所有者が設定し、適用の確認までは未検証とする。
