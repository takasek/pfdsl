## 監査の追加パターン（このリポで検出）

パターンは1件1ファイルで `.pfdsl/bindings/pfd-retro-patterns/` に置く。
このファイルを全読しても本文は出てこない — 引くのはスクリプトである。

```bash
node scripts/retro-patterns.mjs tags                                  # 語彙を prefix ごとに列挙する（タグの下に、それを持つパターンの名前とパスが並ぶ）
node scripts/retro-patterns.mjs select --tag <tag> --word <word>      # 今サイクルで読むべきものを出す
node scripts/retro-patterns.mjs near --word <word>                    # 語が触れた行数の多い順に、既存パターンとの近さを見る
node scripts/retro-patterns.mjs list                                  # 全件を名前と一文で並べる
node scripts/retro-patterns.mjs check                                 # 全ファイルの解析可否・ファイル名の書式・タグ有無・往復一致に加え、この bash ブロックの例が実サブコマンド・実オプションと一致するかも検査する（make check-docs から自動実行、手動は書式直後の確認用）
```

`tags` の出力が語彙の実体である。
正準リストはどこにも無いので、乖離する相手が存在しない。
prefix は3つ立っている — `target:`（trap が起きる対象物）・`method:`（そのサイクルで行った行為）・`context:`（行為でなく成立していた周辺条件）。
prefix も値も宣言されておらず、新しいものを弾く機構も無い。
見慣れない軸や件数1のタグは `tags` の出力に見えるので、そこで気付く。

`--tag` に積を取る手段は用意していない（実測で14件が3件へ落ちる操作であり、落ちた分は黙って読まれないため）。
`select` が返す節の別・各節が何を含むか・どのタグが当てたか・語ごとの reach はここに列挙しない — 見出しとその直下の行が出力自身で述べ、並び順（一致タグ数の降順・同着はカタログ順）は `scripts/lib/retro-patterns.mjs` の `select` の JSDoc が述べる（#913）。

タグが N 件返した回ほど危ない。
0件は目立つので立ち止まるが、N件は「絞れた・読んだ・終わり」で止まる。
和集合は成立タグが増えるほど単調に増え、実測ではタグ1個あたり平均 +2.9 件、13タグ成立したサイクルでは 38/43 が返った（#819）。
このリポのサイクルは1回で scripts と companion と issue を触る形が大半なので、これは例外でなく通常ケースである。
母数の半分を超えた回は `select` 自身が「絞り込みではない」と出力に書くが、書かれたあとに何を読むかは読み手が決める — 上から順に読み、リストの終わりを監査の終わりと見なさない。
細分化で選択性が戻らないことは実測済みで、最大タグ `target:check-script`（10件）を丸ごと消しても 38 は 31 にしか下がらない。
`--word` には今サイクルの diff にある具体的な語（変更したファイル名・触ったフラグ・エラー文言）を渡す。
タグは付けた人が予期できた軸しか答えないが、本文の `具体例:` にはタグには載らない固有名詞が入っている。

### パターンを追記するとき

- 書く前に `near --word <草案の固有語>` を叩き、上位数件を実際に開いて草案との差を判定する。タグ軸の重複は `tags` の出力に並ぶパターン一覧で見る。
  **渡すのは草案そのものの語であって、草案が属する分野の一般語ではない。**
  順位は語の選び方に依存する — 実測では、草案の固有語（`語彙` `allowlist` `既定`）で4件に絞られ真の近傍が1位になった同じ草案が、一般語（`列挙` `検査対象`）では16件に広がり近傍の1件が9位まで沈んだ。
  一般語を渡した回は、上位数件を開く運用のほうが先に尽きる
- ファイル名はパターン名そのもの。本文は `- **パターン名**: ` で始める（この bullet 形式は、分割前のカタログとバイト単位で一致させるために保っている）
- **冒頭の一文が定義文になるように書く。** 要約は frontmatter に持たず、この一文から導出される。二文目以降に `問いの形:`・`具体例:`・`対策:` を置く
- frontmatter は `tags` のみ。既存の語彙を `tags` で見てから選ぶ
- タグは**そのパターンが発火するサイクルの条件**を表す。具体例が起きた場所でも、打った対策でもない。
  判定テスト: そのタグを持つサイクルを1つ思い浮かべ、そのサイクルでこのパターンを読むべきかを問う。読むべきでないなら、そのタグは発火条件ではなく別のものを表している。
  誤りは取りこぼす向きに出る（該当するサイクルで出ず、該当しないサイクルで出る）ため、緑のまま気付けない。
- 迷ったら3軸それぞれを埋められないか考える。1軸しか思いつかないパターンもある（`always` の2件は軸を持たない）
- frontmatter に `phase: pre-artifact` を付けるかは、対策の効く時点で判定する。対策がこのサイクルの成果物（コミットメッセージ・issue コメント・PR 本文・委譲ブリーフ等）を書く前、あるいは着手前にしか効かないなら付ける。実装後・レビュー時・retro 時にも直せる対策には付けない
- `phase: pre-artifact` を付けた回は、カタログへの追記だけで終えない。対策が本来効くはずだった工程（issue の書き方・委譲ブリーフの様式・着手前の確認手順等）の規約自体を同じサイクルで直す。カタログの追記は次にその工程を読む契機を作るだけで、工程そのものが古い記述のままなら次のサイクルも同じ trap を踏む

### パターンを改訂・統合・廃止するとき

- **統合を既定にする。** `near --word <草案の固有語>` が近いパターンを返したら、新規追加でなく既存パターンへ具体例を足す。1パターンが太ることは受け入れる — 太る痛みより、同じ問いの構造が2ファイルに分かれて片方だけ読まれる痛みのほうが大きい
- **廃止条件は「対策が機械化され、その trap が構造的に起こり得なくなったこと」。** 記録が古くなった・件数が減った・しばらく踏んでいない、では廃止しない。人手の注意力に戻る余地が残っている限り、カタログから消してよい理由にはならない
- **廃止の契機は、対策を機械化したサイクル自身。** 定期棚卸しでその日を待たない — 機械化した回とパターンを消す回を同じサイクルにする。分けると、機械化は完了したのに古いパターンだけが残って読み手を迷わせる期間ができる
- **廃止の方法はファイルごと削除する。** tombstone ファイル（廃止の記録だけを残す空ファイル）は作らない。廃止の記録は git 履歴とそのコミットメッセージに残る。カタログは「いま効く問い」の集合であって、効かなくなった問いの記念碑ではない
- **上の3項目が取りこぼした分は、集合としての棚卸しが拾う。** 統合は追記の時点にしか働かず、廃止は機械化したサイクルが気付いた分にしか働かないので、どちらの契機も来ないまま残るものがある。その棚卸しの手順は `retro-pattern-sweep` スキルが、起動の引き金は `scripts/lib/asset-sweep.mjs` の `SWEEP_TARGETS` が持つ（閾値も発火条件もそちらが一次情報）

### 変更時の意味レビュー

新規パターン、既存パターンへの `具体例:` の追記、パターンの統合・分割は、書式検査とは別に diff-scoped な意味レビューを行う。
まず次の2コマンドの和集合で、base から working tree までの追加・変更・削除・rename と untracked の新規ファイルを列挙する。

```bash
git diff --name-only --diff-filter=ACMRD origin/<base> -- .pfdsl/bindings/pfd-retro-patterns/
git ls-files --others --exclude-standard -- .pfdsl/bindings/pfd-retro-patterns/
```

列挙した各対象について `retro-pattern-sweep` スキルを起動し、「6. 所属と内部論理を監査する」を正準とする9観点をすべて適用する。
観点表と各問いはここへ複製せず、変更時レビューでも同スキルの正準表を参照する。

変更者とは独立した reviewer に対象 diff を渡し、finding ごとに再現可能な concrete failure scenario と `file:line` の根拠を必須とする。
finding を修正した後は同じ reviewer が同じ観点で再検証し、解消または残存を報告する。
`node scripts/retro-patterns.mjs check` が証明するのは解析可能性・ファイル名・タグ有無・往復一致等の構造だけであり、所属や論理的一貫性の合格ではない。
`near` 等の語彙類似は近傍を開く補助には使えるが、意味分類を自動決定してはならない。
