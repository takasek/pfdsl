## 監査の追加パターン（このリポで検出）

- **並行委譲の接合部**: 複数 subagent へ並行委譲した成果物同士の整合は、各委譲の受け入れ基準では検証されない。
  検収では成果物ペアの接合部（一方が定める規約 × 他方が生成する内容）を突合する。
  問いの形: 「委譲 A の出力は、委譲 B が実装した検査・規約の除外条件に収まっているか」。
  具体例: ADR の構文例引用（double-backtick span）と lint の inline-code 除外（当時 single-backtick のみ対応）の組で、構文例が実マーカーとして検出され、定義例と参照例が相互解決して lint が偶然 PASS した（#328。除外は #398 で backtick run 対応に修正済み）。
  検査 PASS は接合部の健全性を保証しない — 例示が実データ化していないかを実マッチ列挙（検出関数の直接実行）で確認する。
  **同じ形は委譲を伴わない単独の編集でも起きる。** 例示として書いた文字列が、それを囲む記法のエスケープ規則と衝突すると、例示のつもりのものが実データとして解釈される。
  具体例: JSDoc のブロックコメント内に再帰 glob の例を書いたところ、そのパターンに含まれる星と区切りの並びがコメント終端記号を作り、以降の散文が構文として解釈されてファイルが壊れた（#582 のサイクル）。
  問いの形: 「この例示は、それを囲む記法にとってただの文字列か、それとも意味を持つ並びを含むか」。
  対策: 例示を書いたら、囲みの記法でパースし直す（コメントならファイルを実行・import する、lint なら検出関数を直接走らせる）。目視では終端記号は読み飛ばされる。

- **並行リファクタの死角**: 同じ主題（例: edge集合からのグルーピング）を扱う複数の並行 issue/PR が、互いのスコープ外に同型の重複コードを残すことがある。各 issue は自分のスコープ内でしか重複を見ないため、相手側のリファクタが通った後も気付かれない。
  問いの形: 「このリファクタが対象にしなかった箇所に、同種のループ/パターンがもう一方の並行リファクタの後にも残っていないか」。
  検出の機会: 2つの並行ブランチを rebase/merge で合流させるとき。コンフリクトした箇所だけでなく、双方の diff で「同じ処理を別名の変数で書いている箇所」を横断 grep する。
  具体例: `computeOpenInputs`（multifile.ts）に externalInputs 計算を委譲するリファクタと、edges グルーピングを共有ヘルパーに統合するリファクタが並行して走り、audit.ts 内の produced/consumed Set 構築（前者の対象外）が後者のヘルパーからも漏れて残った（takasek/pfdsl #460）。

- **検査の自己参照 trap**: 「生成器を再実行し出力を既存生成物と diff する」形の drift 検査は、生成器の入力（ビルド成果物・キャッシュ等）自体が古い場合、古い入力から再生成した出力を古い生成物と比較するため一致してしまい、検査が自己無矛盾のまま PASS する。
  問いの形: 「この検査の『再生成』は、検査対象と同じ古い入力を使っていないか」。
  具体例: pre-commit の `check_drift`（regenerate-then-diff 方式）が dist ファイルの**存在**のみを前提条件にしており鮮度を見ていなかったため、worktree に残った stale な CLI dist から `gen-plugin` を再生成すると、stale dist 由来の誤った内容同士が一致して PASS した。CI は fresh checkout から都度ビルドするため唯一そこでだけ drift が検出された（#450）。`scripts/lib/dist-freshness.mjs` で dist の mtime を sibling `src/` の最新 mtime と比較し、存在しないときと同様に古いときも検査を skip する形に修正（#452）。
  対策: 「存在すれば検査可能」でなく「入力より新しければ検査可能」を前提条件にする。

- **フラグの意味範囲 trap**: フラグ名が示唆する狭い意味範囲（「今触っている検査の厳格版」）を信じて未検証のまま既存ゲートに組み込むと、そのフラグが実際に束ねる無関係な検査群が一斉に error 化し、意図しない大量破壊を CI で初めて知ることになる。
  問いの形: 「このフラグは名前が示す範囲だけを制御しているか、他の無関係な検査も同時に束ねていないか」。
  具体例: `--strict` は V011（feedback 到達性）のみを制御すると読める名前だが、実装は W002/W005 の warning→error 昇格も同時に束ねていた（#480 派生作業）。既存リポ資産（`docs/*.pfdsl`・`.pfdsl/*.pfdsl`）に対して素の `--strict` を先に検証せず CI 設定へ組み込もうとし、無関係な既存 W002/V011 所見 170 件超が一斉 FAIL するところだった。
  対策: 新しいフラグを既存ゲートに組み込む前に、そのフラグを対象コーパス全体に対して単体実行し、意図した検査以外の所見件数を数えてから採否を判断する。
  **束ねられた対象が不可逆操作の場合、この trap は顕在化しない形で出る。** 上の例は CI が一斉 FAIL したので気付けたが、破壊系フラグでは束ねが黙って実行され、失われたものを知っている人間しか異常に気付けない。
  具体例: `check-install-sync.mjs --deploy --force` の `force` が「ローカル編集済みファイルの上書き」と「orphan の削除」の2箇所で使い回されており、旧パスの掃除だけを意図して渡したところ、直前に新パスへ再適用したばかりのカスタマイズも canonical へ巻き戻された（#603）。
  出力は成功で、終了コードも変わらない。
  問いの形の追加: 「このフラグが束ねている操作は、間違って発動したときに出力から気付けるか。気付けないなら、意図の数だけフラグを割るべきではないか」。
  **分割しただけでは半分しか直らない。分割後の名前が動作の主語を取り違えていると、同じ誤読がそのまま生き残る。** 上の例を最初 `--force-overwrite` / `--force-remove-orphans` に割ったが、後者は「orphan を削除するフラグ」と読める一方、実装が制御していたのは「ローカル編集を抱えた orphan も削除するか」だけで、編集の無い orphan はフラグ無しで既に削除されていた。つまり掃除が目的の人には**そもそも不要なフラグ**である。
  `--overwrite-local-edits` / `--delete-edited-orphans` に改名して、フラグが決めるのは操作の有無ではなく「立ちはだかるローカル編集を捨てるか」だと名前に出した。
  問いの形の追加: 「このフラグを外したら、その操作は本当に起きなくなるか。起きるなら、フラグ名は操作でなく**それが破棄するもの**を名乗るべきではないか」。
  **命名の当否は、文脈を持たない executor に実出力とタスクを与えて行動を観測すれば測れる。ただし何を見せるかで測れるものが変わる。** 旧名・新名・別案（`--discard-orphan-edits` 系）の3アームに実 CLI 出力を見せて操作させたところ全アームが全問正解で、差は出なかった — 出力に「編集なし orphan は Removed、編集ありは要フラグ」の対比が並んで出ており、名前を読まずとも規則が読めたためである。
  usage 行だけを見せて推測させると旧名アームだけが「素の `--deploy` は orphan を消さない」「このフラグは対象集合そのものを広げる」と誤答し、#603 と同じ選択に至った。
  新名アームが正答した根拠は「`edited` をわざわざ名指ししている以上、非 edited は既定で処理されるはずだ。そうでなければ `--delete-orphans` で足りる」であり、**名前に含まれる限定詞が既定動作を逆算させている**。別案（限定詞が対象側に付く `--discard-orphan-edits`）にはこの効果が無かった。
  したがって命名が効くのは**出力を精読せずフラグ名から推測する場面**に限る。ドキュメントや出力の改善で代替できると考えず、逆に「出力が良いから名前は何でもよい」とも考えない。

- **出力の動詞が主語を取り違える trap**: 処理の報告に使う動詞が、読み手にとっての主語（自分のファイル）と実装にとっての主語（canonical の内容）を取り違えていると、状態を正反対に受け取らせる。
  フラグ名と違い出力は毎回目に入るため安全だと見なされがちだが、目に入ることと正しく読まれることは別である。
  問いの形: 「この行の動詞は、読み手が自分の持ち物に起きたことだと解釈しないか。実際に動いたのは canonical 側ではないか」。
  具体例: リネーム検出直後の `Copied: <新パス>` を、文脈を持たない executor 3体が3体とも「自分のファイルが新パスへ引き継がれた」と読み、「その解釈で進めば旧パスを消してカスタマイズを失う」と自ら指摘した（#603 の被害はまさにこの経路）。実際には canonical の素の内容が新パスに書かれただけである。
  対策: rename 候補の宛先に限り `(canonical content only — the edit at <旧パス> is not in it)` を付し、動詞の曖昧さを行内で打ち消した。。

- **自己点検器が二重に実在する trap**: 配布物の上流リポでは、同じ検査スクリプトが canonical（リポ内）と配布スナップショット（plugin cache 等）の2箇所に実在し、**同じ対象に対して矛盾する答えを返しうる**。
  スキル本文の指示が「どちらのロード元で走らせるか」しか決めていないと、実行者はどちらか一方の出力だけを見て判断し、それが古い側だったことに気付かない。
  「検査の自己参照 trap」が**入力**の陳腐化であるのに対し、こちらは**検査器そのもの**が複数版で併存する形である。
  問いの形: 「この検査スクリプトは、いま実行した実体のほかに、同じ対象を見る別の実体がリポ内に存在しないか。存在するなら、どちらが正かを規約が決めているか」。
  具体例: pfd-ops 発火時の鮮度セルフチェックで、plugin cache 0.0.21 版が `missing` 10件 + `orphaned` 10件を報告する一方、repo-local 版は in sync を報告した。差分の実体は #358 のリネームであり、drift ではなく plugin の陳腐化だった。SKILL.md の判定規則はコマンド行のパス置換有無しか見ておらず、上流リポで両方が実在する状況を扱っていない（`.pfdsl/bindings/pfd-ops.md` に repo-local を正とする規約を追加）。
  対策: 上流リポでは正とする実体を companion で1つに固定する。両者が食い違ったときの解釈（版差であって drift ではない）と、してはならない対応（古い側へ `--deploy` で追随する）も併せて書く。

- **実行環境の暗黙前提 trap**: リポの運用スクリプトが特定の CLI ツール（`gh` 等）の存在を暗黙の前提にしていると、そのツールを持たない実行環境（Claude Code Remote 等、GitHub 操作が MCP server 経由に限定されるセッション）では preflight/gate-check の一部〜全部がエラーで止まる。
  問いの形: 「このスクリプトが前提にしている外部 CLI は、全ての起動元セッション種別で利用可能か」。
  具体例: `scripts/cycle-status.mjs` / `scripts/gate-check.mjs`（内部の `audit-issues-flow.mjs`）が `gh` に `execSync`/`execFileSync` で依存しており、`gh` 不在の Claude Code Remote セッションで `audit-issues-flow.mjs` が `spawnSync gh ENOENT` でクラッシュし、gate-check の残り項目の出力ごと失われた（#482 セッション、#489 で追跡）。
  対策: 該当ステップは GitHub MCP のツール呼び出しで個別に代替できる（`.pfdsl/roadmap.md`「自動生成 PR」節に代替手順を記録）。恒久対策（`gh` 依存の解消・try/catch 化）は #489。

- **検査対象を手列挙で指定する trap**: 検査・テストの対象集合をディレクトリやパスの手書きリストで指定すると、対象が増えたときに無言で漏れる。
  漏れた対象は「検査を通っている」のでなく「検査が走っていない」が、出力はどちらも同じ（緑）になる。
  列挙ドリフト（同じリストが2箇所にあって乖離する）と違い、こちらは**照合相手のリストが存在しない** — 比較対象がないので目視でも気付けない。
  問いの形: 「この検査が実際に拾った対象の集合と、リポジトリに実在する対象の集合は一致するか」。列挙を読むのでなく**両方を数えて突き合わせる**。
  具体例: `node --test` の対象が `scripts/lib/` と `scripts/pfdsl/lib/` をディレクトリ名で列挙していたため、`scripts/*.test.mjs` に置いたテスト4件（shell injection のガードを含む）が一度も実行されていなかった。
  対策: 列挙をやめるか、**実在集合との突合を検査に組み込む**。このリポは後者を採り、`scripts/lib/test-glob-coverage.mjs` が Makefile と CI の `node --test` glob を読んで、tracked な `*.test.mjs` に到達しないものを列挙する。
  前者（`"scripts/*.test.mjs" "scripts/**/*.test.mjs"` の2パターン化）も `node --test` 側は成立するが、突合検査があれば列挙のままで安全なので採らなかった。

- **対策の適用漏れ（trap を1箇所だけ直す）**: trap を検出して対策の道具まで作っても、同じ形をした他の箇所を横断で掃かなければ、道具の存在が「もう安全だ」という誤った完了感だけを残す。
  パターンが binding に記録済みであることは、そのパターンが残っていないことを意味しない — 記録は再発時の**診断**を速くするが、既存箇所の**掃き出し**は別作業である。
  問いの形: 「この trap の対策を入れたとき、同じ判定を書いている他の箇所を grep したか。道具を作って終わりにしていないか」。
  具体例: 「検査の自己参照 trap」への対策として `scripts/lib/dist-freshness.mjs` を導入した際（#452、2026-07-11）、pre-commit の `check_drift` だけを鮮度判定に切り替えた。同じ `existsSync(dist)` だけを条件にしていた `packages/cli/src/cli-smoke.test.ts`（2026-06-12 から存在）は掃かれず、stale な bundle に対して緑を返し続けた（PR #579 で修正）。
  対策: trap の対策を入れる PR では、置き換える前の判定式（この例では `existsSync` と dist パスの組）でリポジトリ全体を grep し、ヒットした全箇所の採否をその PR 内で決める。掃かない箇所があるなら理由を残す。

- **間接テストの入力偏りが分岐を隠す trap**: 下位モジュールに直接テストがなく上位経由でのみ到達している場合、上位テストの入力が偏っていると、その偏りがそのまま未到達分岐になる。
  カバレッジが測れない状況では「テストがある」ことと「分岐が検証されている」ことの差が見えない — ファイル単位の空白は目視でも見えるが、到達しているファイルの中の未到達分岐は見えない。
  問いの形: 「このモジュールに直接テストはあるか。上位経由だけなら、上位テストの入力は下位の分岐を張っているか」。
  具体例: `packages/graphviz-exporter/src/label.ts` の折り返しは `exportDot` 経由の4ケースでのみ検証されており、その全てが日本語の読点を区切り文字に使っていた。半角記号を通る分岐に一度も到達せず、区切り文字が消える欠陥（`仕様書 v0.0.8` → `仕様書 v0.0` + `8`、`(#97)` → `#97)`）を運用中の 25 ラベルが踏んだまま残った（PR #579 で直接テストを追加して発覚・修正）。
  対策: テストを持たないモジュールを列挙するときは、ファイル単位の有無だけでなく「上位経由で何が張られているか」を見る。上位テストの入力集合が下位の場合分け（記号の種別・文字クラス等）を張っていなければ、下位に直接テストを置く。

- **規約が名指しする手段を実行主体が起動できない trap**: 運用規約が特定のコマンド・スキルを名指しすると、実行主体（AI）の権限でそれを起動できない場合に、規約が構造的に満たせなくなる。
  外部ツールの不在（上の「実行環境の暗黙前提 trap」）と違い、**同じ harness の中にコマンドは存在する**ため、失敗が「使えない」でなく「呼べない」形で出る。
  黙って類似コマンドへ落ちるか項目ごと飛ばすかのどちらかになり、どちらも規約の遵守記録を汚す。計測を伴う規約では分母が歪む。
  問いの形: 「この規約が名指しする手段は、規約を実行する主体の権限で起動できるか。人間が手で打つ前提になっていないか」。
  具体例: `/code-review` を実施せよという実測規約に対し、`/code-review` は `disable-model-invocation` で AI からは起動できなかった（#561 実測期間、PR #569 で `/simplify` を既定に変更）。ユーザーが手で打った回にしか満たせない規約になっていた。
  対策: 手段を名指しする規約を書くときは、規約の実行主体を1語で決めてから書く。AI が回す前提なら model-invocable なものを既定に置き、人手前提のものは「ユーザーが実施する回のみ」と条件を明示する。
  **起動可否は harness と plugin の版に依存する属性であり、記録した時点の観測でしかない。** 規約に「起動できない」と書いたら、その根拠を後続セッションが継承してよい事実として扱わない — 従う前にコマンド定義の実体を確認する。逆向きの陳腐化（起動できるようになったのに規約が禁止のまま残る）は、規約を満たせない形でなく**選択肢を1つ失ったまま気付かない**形で出るため、失敗として観測されない。
  具体例（逆向き）: 上の `/code-review` は後に `disable-model-invocation: false` になっており、規約が名指しする「AI からは起動できない」という前提のほうが偽になっていた（2026-07-28 の retro で検出）。規約は起動可否でなく**手段の適性**（プロトコルの重さ・PR の要否）で書き直した。

- **同型を数える単位の取り違え**: 「同じ形の構造がほかに何個あるか」を数えるとき、数えやすい単位（スクリプト・ファイル・コンポーネント）で代用すると、1単位の内部に同型が複数あってもまとめて1と数える。
  対策は出力の単位で効くのに、数え上げは生成器の単位で行う、という食い違いが典型である。
  結論は「同型は残らない」という形で出るため、結論だけを読んでも誤りが見えない。
  問いの形: 「この数え方の単位は、対策が実際に作用する単位と同じか」。
  具体例: `gen-skill.mjs` の drift 検査が dist 鮮度で丸ごと skip される問題（#586）で、同型を「dist を要求する check_drift の本数」= 生成器の粒度で4本と数え、references を切り出せば同型は残らないと結論した。
  実際には `gen-plugin.mjs` の出力のうち dist を要するのは `skills/pfdsl/SKILL.md` 1つだけで、pfd-* スキル・commands・agents・hooks・plugin.json はすべて純コピーでありながら同じ dist ゲートに束ねられたまま残っていた（`/simplify` の altitude 角度が検出、#593 として切り出し）。
  対策: 数える前に「対策はどの単位で効くか」を1語で決め、その単位で数える。生成器を1と数えたくなったら、その生成器の出力を列挙して単位を割り直す。

- **委譲ブリーフの片肺 trap**: companion `.md` の記述更新を委譲するとき、同じ事実を述べる sibling `.pfdsl` のノード description をブリーフに含めないと、委譲先は指示された `.md` 側だけを直して戻る。
  委譲先に落ち度はない — ブリーフが片肺だったのであり、成果物レビューでも「指示通り」に見える。
  問いの形: 「このブリーフが更新を指示している散文は、同じ事実を述べるノードの description・criteria を図の側にも持っていないか」。
  具体例: `.svg` のドリフト検査機構を変えた回で、ブリーフは `.pfdsl/roadmap.md` と `.pfdsl/workflow.md` の該当記述を名指ししたが、同じ検査機構を述べる `workflow.pfdsl` の `sample_previews.description` を含めていなかった（終端ゲートの「変換コンポーネント反映」項目で捕捉、#588）。
  対策: 委譲ブリーフに companion `.md` の編集が含まれる場合、sibling `.pfdsl` を `graph neighbors` で引いて該当ノードをブリーフに列挙する。ゲート側は既に捕捉できるので機構の追加は不要 — ブリーフ作成時の手順として持つ。

- **companion 追記手順の見落とし**: SKILL.md 本文の自己点検セクションが1つのスクリプトしか名指ししていないと、同じ契機で実行すべき binding 側の追加ステップ（companion にのみ書かれている）を読み飛ばしたまま作業を始めてしまう。
  問いの形: 「このセルフチェック手順は、binding に追記された継続ステップの存在を保証しているか、それとも読み手が binding 全文を読む前提に依存しているか」。
  具体例: `.pfdsl/bindings/pfd-ops.md` に「配置ファイルの鮮度セルフチェックに続けて `check-scaffold-sync.mjs` も実行する」という追加ステップがあったが、SKILL.md 側の該当セクションはそれへの参照を持たず、セッション開始時に見落とした（retro で気付き実行、drift は無し）。
  対策: SKILL.md のセルフチェックセクションに「同じタイミングで binding の追加ステップも確認する」という一般化した誘導文を追記した（本コミット）。

- **単一メタ項目が N 個のサブ項目を隠す trap**: 終端ゲートの MANUAL チェックリストが「companion（roadmap.md 等）が定義するリポ固有の追加ゲート項目を確認した」という1行のメタ項目であるため、companion 側に列挙された十数個の個別サブ項目（例: PR 本文の `Closes` キーワード）を実際に1つずつ確認しなくても、メタ項目1行にチェックを入れて先へ進めてしまう。特に PR 作成はサイクル序盤の companion 読了から時間が経った終盤の作業であり、序盤で読んだ内容の再確認が漏れやすい。
  問いの形: 「このメタ項目にチェックを入れた瞬間、companion の個別サブ項目を実際に1つずつ再読したか、それとも『前に読んだから大丈夫』で済ませていないか」。
  具体例: PR #497（#476）作成時に `.pfdsl/roadmap.md` の「PR 本文の `Closes` キーワード確認」項目を実行し忘れ、`Closes #476` を欠いたまま PR を作成した（pfd-retro の C 層監査で気付き、PR 本文を更新して修正）。
  対策: PR 作成・issue クローズ等、companion のサブ項目が集中するタイミングでは、メタ項目にチェックする前に companion の該当セクションを Read し直し、列挙された個別項目を上から順に照合する。
  **サブ項目が集中するタイミングは終盤だけではない。** 着手時にも同じ密度で集中しており（出力 artifact の wip 更新・複数方針を列挙した issue の選択記録）、そちらは終端ゲートのチェックリストが読み上げられる契機そのものが無い分、見落としても最後まで気付かない。
  具体例: #644 のサイクルで、issue 本文が対応方針を2案列挙していたにもかかわらず、選択の記録を issue コメントに残したのは実装完了後だった（`.pfdsl/roadmap.md` は「実装着手前に」と定めている）。着手前に issue 本文とコメントは読んでおり、2案あることも認識していたが、記録のタイミング規約は companion 側にあり、その時点で読み直さなかった。
  対策の追加: work-cycle 手順1 で issue を読んだ直後、companion の「着手時」項目を読み直す。終端ゲートで拾えるのは終盤の項目だけである。

- **issue クローズ漏れ trap（別 PR 経由の偶発解決）**: あるレビュー対応 PR が別 issue のスコープを偶発的に解決すると、その別 issue 自体は誰も見ていないため open のまま残り続ける。着手前に issue 本文の再現手順を現行コードに当てて「まだ再現するか」を確認しないと、既に解決済みの issue に無駄な実装差分を積みかねない。
  問いの形: 「この issue が指す症状は、現行コードでまだ再現するか（既存の別 PR が偶発的に解決していないか）」。
  具体例: #494（def-insertion.ts のフルドキュメント置換問題）は、#491 のレビュー対応コミット 31b16c1（fix(core,vscode-extension): use a minimal insert edit ...）で既に解決済みだったが、issue 自体は open のまま1日残った。#490/#493/#498 のバッチ処理着手前に現行コードを確認したことで発覚し、実装差分なしでクローズできた。
  対策: 着手前の issue 本文再読（work-cycle 手順1）に「本文の再現手順・コード引用を現行の該当ファイルと突合する」を含める。

- **自動ステージの巻き込み trap**: hook が生成物を再生成して `git add` するとき、生成器が「作業ツリー全体から」再生成する型だと、staged された変更に由来しない出力まで一緒にステージされる。
  未 staged の編集が、人間のレビュー機会なしにコミットへ入る。
  クリーンな作業ツリーで踏む end-to-end テストでは**構造上再現しない** — 巻き込み元となる無関係な未 staged 編集が存在しないため、テストは PASS する。
  問いの形: 「この `git add` の範囲は、今回の変更が影響しうる部分木に限定されているか。生成器の出力全体を無条件にステージしていないか」。
  具体例: install/ の同期後に `gen-plugin.mjs` を再実行して `git add plugin` と広くステージしていた（#547 の初回実装、PR #549。同 PR は別方針で作り直され close）。
  `gen-plugin.mjs` は `plugin/pfdsl/` 全体を作業ツリーから再生成するため、`.claude/skills/**` に未 staged の編集があるとその生成物まで staged された。
  影響しうる唯一の部分木に絞って解消し、無関係な生成物は未 staged で残して後続の drift 検査が止める形にした。
  対策: auto-stage を伴う hook のレビューでは、クリーンツリーの正常系に加えて「無関係な未 staged 編集がある状態」を必ず踏む。
  委譲する場合はこの敵対的ケースを受け入れ基準に明記する（正常系の e2e だけを指示すると委譲先はそれしか踏まない）。

- **解空間の継承 trap**: 作業項目が対応案を列挙していると、その集合をそのまま設計空間として受け取り、集合の外にある「問題自体が発生しない形」を誰も生成しない。
  列挙した案がすべて「乖離・競合・例外をうまく捌く」型なら、起票者の枠組みを継承した兆候である。
  ユーザーに選択肢を提示して選ばせても検証にならない — 集合を作ったのは自分であり、承認が担保するのは集合内部での選好順位だけで、網羅性ではない。
  問いの形: 「列挙された全案が共有している前提は何か。その前提を否定した案はどうなるか」。
  具体例: 同一内容が3箇所に存在する問題で、1箇所は既に生成物として自動化済みという比較表が作業項目本文にあったにもかかわらず、提示した3案すべてが「残り2箇所の乖離をどう捌くか」の変種だった（#547、PR #549 は実装完遂後に棄却）。
  「その1箇所を生成物に降格する」という別クラスの案は、レビュー後にユーザーから問われて初めて出た。
  **信号は3回出ていて3回とも検出されていた**（既存慣行への例外が要る・曖昧ケースの新設が要る・対称であるべき2方向の片方だけ挙動が違う）が、いずれも受容すべきコストとして分類された。
  記録を精査した結果、別解を思いついて捨てた形跡は無い。
  分岐点は判断の甘さではなく、比較対象となる別解がその場に存在しなかったことである。
  コストは単独では評価できず、常に対案との差でしか評価できない。
  対策と根拠は ADR-0033（比較対象を生成する）。
  プロトコル本体には work-cycle 手順1・手順2 の3適用点として反映済み。

- **原因診断の陳腐化 trap**: issue 本文が「症状 → 原因 → 対応案」の形で書かれているとき、症状が現在も再現することを確認しただけで、原因診断まで有効だと受け取ってしまう。
  症状の再現は原因診断の正しさを保証しない。
  起票から着手までの間にマージされた作業が、本文の想定する欠落を既に埋めていることがある。
  この場合、症状は同じ見た目で残り続けるが原因は別のものに入れ替わっており、本文の対応案は「すでにあるものをもう一度作る」指示になる。
  問いの形: 「本文が『無い』と述べている機構は、現行コードに本当に無いか。症状が残っていることを、原因診断が有効な証拠として使っていないか」。
  具体例: #553 は gate-check の2項目が毎回 FAIL することを症状として挙げ、対応案に「`audit-issues-flow` を理由つき SKIP に分ける」を含めていた。
  着手前に実コードを読むと `classifyAuditIssuesFlowResult` として既に実装済みで（#489 / #492 由来、テスト3件つき）、当該 FAIL は機構の不備ではなく本物の drift（`#542 missing_process`）だった。
  症状（FAIL が出続ける）は真、原因診断（SKIP 機構が無いから）は偽、という組み合わせである。
  対策: 本文が名指しする「欠けている機構」を、着手前に実体で grep する。issue の起票日と、関連領域に入ったコミットの日付を突き合わせる。

- **不在判定の探索範囲 trap**: 「これは存在しない」と判断するとき、探索範囲が**それが本来ありそうな場所**に限定され、**実際にありうる場所**を含んでいないことがある。
  不在の証明は探索範囲がすべてであり、範囲を誤ると偽陽性が出る。
  存在の確認（1件見つければ足りる）と違って、不在の確認は範囲の網羅性そのものが結論を決める。
  この trap は「捏造の疑い」だけでなく、**ゲート項目を N/A と判断する場面全般**に効く。
  問いの形: 「『無い』と判断した検索範囲は、それがありうる場所を含んでいるか。名前で検索したなら、名前が違うだけの同じものを取りこぼしていないか」。
  具体例1（識別子）: テストが `artifactKey: "ops_checkers"` を使っているのを見て、実在しない artifact キーの捏造と判断しかけた。
  `.pfdsl/` と `docs/` を grep して0件だったことを根拠にしたが、実際は同じテストファイル内に12箇所の既存フィクスチャとして存在しており、委譲先はファイルの既存慣行を正しく踏襲していた。
  全置換を実行していれば、既存テスト6件がフィクスチャとアサーションの不一致で落ちるところだった（コミット前に気付いて revert）。
  具体例2（ゲートの N/A 判断）: 「変換コンポーネントを PFD に反映したか」のゲートを N/A と判断する際、`.pfdsl/*.pfdsl` を対象スクリプト名の文字列で grep して0件だったことを根拠にした。
  正しい探索軸は名前ではなく `location:` であり、それで引き直すと同種の運用スクリプトが4件モデル化されていた（結論の N/A 自体は成立したが、根拠は成立していなかった）。
  対策: 探索を**名前でなく性質**で行う。artifact の不在を言うなら `location:` を、識別子の不在を言うならその文字列が由来しうるファイル自身を、探索軸にする。
  「あるべき場所に無い」と「どこにも無い」を区別し、後者を主張するときだけ N/A と書く。

- **同型コマンド群の安全策が実装ごとにバラつく trap**: 複数の類似コマンドを同じ設計判断（例: 同じ内部表現への移行）で書き換えるとき、既存コマンドが個別に持っていた安全策（不正入力時の早期リターン等）は移行先の設計にまとめて明文化されない限り、一部の実装だけが踏襲し他は落ちる。
  各コマンドの実装作業（TDD で機能テストは通す）は独立に green になるため、テストは通っていても、テストが踏んだ入力の集合（正常系＋既知の壊れ方）が実装ごとに揃っていなければ、揃っていない箇所は緑のまま漏れる。
  問いの形: 「この設計判断が対象にする複数コマンドのうち、既存実装の一部だけが持っていた安全策を、移行後の全実装が同じ形で持っているか」。
  具体例: ADR-0034（frontmatter 書き込みを yaml CST に統一）で、`sort`/`reindex`/`meta set` は既存実装の時点で `analyze(source)` の error 診断を事前ゲートに持っていたが、`fmt`（`format()`）と `insert-definition` にはそのゲートがそもそも無かった。CST 化の実装委譲ブリーフは「既存の書き込み4コマンドを CST 化する」と対象範囲だけを指定し、既存ゲートパターンの横展開は明示しなかった。結果、`sort`/`reindex` の実装（別 subagent、既存コードを読んで模倣）は自発的にゲートを踏襲したが、`fmt`/`insert-definition` は持たないまま実装され、fence は正しいが YAML 内容が不正な入力で `Document#toString()` が未捕捉例外を投げてクラッシュした（`pfdsl fmt` と VS Code の insert-definition quick-fix の両方で再現。#598 の `/code-review` で検出、TDD で修正）。
  対策: 複数コマンドを同一設計判断で書き換える委譲ブリーフには、対象範囲だけでなく「既存実装のうち一部だけが持つ安全策」を明示的に横展開の対象として列挙する。書き手（委譲元）が把握していない既存の非対称は、委譲先の模倣にも実装ごとの独立作業にも期待できない。

- **測った水準を超えて書く**: 実測で確かめたのは挙動の一致なのに、成果物には実装内部が同一であるかのように書いてしまうことがある。
  一段強い主張のほうが読み手に届く説明になるため、書いている側は補強のつもりでいる。
  コメントや設計記録に残ると、後続の読み手はその強い主張を前提に検証を省く。根拠の水準が落ちたことは文面からは見えない。
  問いの形: 「この1文が主張している水準は、実際に走らせて確かめた水準と同じか」。
  具体例: glob 判定を Node の API へ委譲した際、実測したのは `fs.globSync` との**挙動の一致**だったが、JSDoc には「`node --test` が引数解決に使うのと同じエンジン」と書いた（#582。実装内部は確認していない。検証した内容の記述へ差し替えた）。
  対策: 主張を書いたら、その根拠として走らせたコマンドを1つ思い出せるか確認する。思い出せない語（同一・常に・原理的に等）が入っていたら、測った内容の記述へ落とす。

- **指摘は正しいが修正案が指摘を解かない trap**: レビュー（`/simplify`・`/code-review`・agent）が返す finding は「診断」と「修正案」の2部からなるが、検証されているのは診断だけであることがある。
  診断が実測付きで正しいと、その正しさが修正案の正しさへ横滑りし、案の側は誰も試さないまま採用される。
  適用しても finding が残ったまま「対応済み」になるため、レビューを回した記録だけが残って穴は塞がらない。
  問いの形: 「この修正案は、指摘が挙げた入力そのもので走らせて確かめたか。診断が正しいことを、案が正しい根拠に使っていないか」。
  具体例: `/simplify` の altitude 角度が「`--force` の pre-check が `--force=value` を取りこぼす」と正しく指摘し（実測付き）、修正案として「`force: { type: "boolean" }` を options に宣言して post-parse で移行メッセージを raise せよ」と書いた。
  実際には boolean 宣言だと strict parse が先に「does not take an argument」で弾くため post-parse に到達せず、移行メッセージは出ない — 提案どおり実装すれば finding はそのまま残っていた（#631 のサイクル。`--force=` 前方一致を pre-check に加える形で解消）。
  対策: finding を採用するときは、案の形でなく **finding が挙げた入力を先にテストへ落とす**（Red を作る）。提案どおりの実装で緑にならなければ、提案でなく finding のほうを信じる。

- **確認の観測範囲が症状を映さない trap**: 同型の他箇所を「確認した」と記録していても、そのとき見た指標が症状の出る場所を映していなければ、掃いていないのに掃いたことになる。
  「対策の適用漏れ trap」は他箇所を**見に行かなかった**型だが、こちらは**見に行って、無事だと結論した**型である。記録に「確認済み」と残る分、次に疑われる可能性が低くなる。
  問いの形: 「無事だと確認したとき、見た指標は症状が現れる場所を含んでいたか。自分が触った対象だけを見て、触っていない周辺を見ずに済ませていないか」。
  具体例: 読み側（`frontmatter.ts`）の `\r` 混入を直した #636 で、書き側（`frontmatter-cst.ts`）も確認して「CST パーサが `\r` を吸収する」と結論し、その旨をテストのコメントにも残した。
  実際に見ていたのは**書き換えた当のフィールド**の値だけで、`\r` が実際に焼き付くのは**同じノードの最終行にある別フィールド**だった。書き換え対象の値は CST の別スライスから来るため無事に見える。
  結果、同じ欠陥が書き側に1リリース分残り、CRLF ファイルを1回書き換えると触っていない `criteria` の値が `"approved\r"` になった（#644）。
  対策: 「他箇所も確認した」と書くときは、見た指標を1語で書く（この例なら「書き換えたフィールドの値」）。その語が症状の記述（この例なら「frontmatter の最終行の値」）と一致しなければ、確認になっていない。
  独立した二重実装を持つ箇所では、両者に同じ入力を通して**出力全体**を突き合わせるテストを置く（片方だけを直したことが次回は失敗として出る）。

- **否定案を生存させたまま出荷する trap**: 比較対象生成の原則（ADR-0033）に従って否定案を作り、一部の領域では却下理由が効かないと正しく気付いたあと、その領域だけを別の作業項目へ切り出して実装を確定してしまうことがある。
  原則は「却下理由が書けなければ否定案を生存候補として残す」までを定めており、**生存候補を残したまま出荷してよいか**は扱っていない。そのため切り出しは手続き上は正しく見える。
  出荷される成果物は、前提が一部の経路にしか適用されていない状態になる。同じリリースに載る同種の変換群であれば、利用者から見た挙動はそこで割れる。
  問いの形: 「否定案が生存している領域を別作業へ切り出したとき、残りの経路だけで前提を適用した成果物を出荷することになっていないか。前提は全経路に同時に適用するか、全経路で適用しないかのどちらかであるべきではないか」。
  具体例: #644 で「改行スタイルはユーザーの所有物」という前提のもと書き戻し4経路を改行保存に揃え、`fmt` については「整形コマンドなので同じ却下理由が効かない」と正しく認識したうえで #656 へ切り出して PR を出した。
  ユーザーから「今やるべきではないか」と指摘され、方向を確定して同 PR に統合した（結果として `fmt --check` が CRLF リポで初めて使えるようになるという副次効果も同時に得られた）。
  対策: 否定案が一部領域でのみ生存する形になったら、切り出す前に「その領域を未決のまま出荷したとき、利用者から見て挙動が割れるか」を判断する。割れるなら同じ作業のうちに方向を決める（方向の決定自体は所有者に聞けば済む — 切り出しの理由が「判断が要るから」であれば、それはその場で聞ける判断である）。

- **先例のスタイルを性質確認せずに踏襲する trap**: 散文を hook へのポインタに置き換える際、既存の先例（例: #647 stale-dist-guard）のスタイルをそのまま踏襲すると、先例と今回の hook で性質が違う場合（例: advisory の hook が対処法まで含むか否か）を個別に検討し損ねる。
  問いの形: 「この散文が伝える情報は、hook の deny/advisory メッセージ自体に既に含まれているか。含まれているなら、ポインタ化でなく完全削除が正しいのではないか」。
  具体例: #650 で worktree-write-guard・md-write-check 候補の散文を hook へのポインタに書き換えたが、両 hook とも対処法まで含めて deny/advisory メッセージに全情報を持っており、散文には残す情報が無かった。#647 の stale-dist-guard スタイル（対処法を hook 外の散文にも残す）を無批判に踏襲した結果、完全削除できる箇所をポインタ化に留めて見落とした（ユーザー指摘で気付き、追加コミットで削除。同時に workflow.md「知見の振り分け」に散文追記前の機械化検討ステップを追加した）。
  対策: hook へのポインタ化を検討するときは、hook が実際に出力する文言と付き合わせ、散文に残る情報の有無を確認してから「ポインタ化」か「完全削除」かを選ぶ。

- **issue 間の列挙ドリフト**: ある issue に列挙した候補群を、別の issue が別の軸で仕分け直すとき、候補の集合が2箇所に転記される。
  「issue は単体で自己完結する」という運用規約と、「同じリストを2箇所に置かない」という列挙ドリフト回避が正面から衝突する場面であり、どちらかが自動的に勝つわけではない。
  問いの形: 「元の列挙に項目が増えたとき、こちらの仕分けは更新されるか。されないなら何が気付かせるか」。
  解き方は転記の削除ではなく、**一次情報がどちらかを明示し、追加時に見直す対象としてもう一方を名指しする**こと。仕分け軸が違う以上、転記自体は情報の重複ではなく別の判断の記録である。

- **PR 作成後のスコープ拡張**: PR を出した後に同じブランチへ別の主題を足し、タイトルと本文を書き換えると、レビュー中の相手が見ていたものと別物になる。
  終端ゲートの「変更束を PR にまとめた」は作成時点の話で、作成後の拡張を扱っていない。
  問いの形: 「この追加は、既にレビューを始めた人の前提を壊すか」。壊すなら別 PR にするか、少なくとも拡張した旨を PR にコメントで残して相手が読み直す契機を作る。
  未レビューであれば実害はないが、実害の有無はこちらからは見えない — 相手がいつ読み始めたかを知らないため。

## 配布物への finding 反映

誰が配布層を編集できるかの一般ルールは pfd-retro SKILL.md「出力」節の「上流変更ルール」が一次情報（ADR-0028）。
このリポは pfd-* bundle の上流であるため、そのルールの「自リポが上流である場合」に当たり、配布物への finding 反映をその場での編集として実施してよい（採用リポにこの経路は無い）。
配布スキル本文（SKILL.md）に取り込めるのは L1（固有名詞ゼロの汎用プロトコル — 層定義は `pfd-ops/references/architecture.md`）に一般化できる記述のみ: リポ固有の固有名詞・issue 番号・ファイルパス・ADR 番号は禁止、配布 bundle 内のスキル・reference への相互参照は可。
一般化できない具体例は companion に残す。
