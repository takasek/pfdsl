# pfd-ops バインディング

pfd-ops 運用に紐づく、Claude へ恒常的に届けたい指示（PR 本文規約等）はこのファイルに置く（命名規則は `.claude/skills/pfd-ops/references/architecture.md` の「バインディングファイルの命名規則」参照）。読まれる契機は pfd-ops SKILL.md の該当行が保証する。サイクル外でも常時届けたい指示は root `CLAUDE.md` からこのファイルへポインタを張る。

新しい指示が生まれたら、配布層へ載せるかを `.claude/skills/pfd-ops/references/architecture.md`「昇格先の判定ルール」で判定する。昇格候補は0段目の区分 i・ii に入るものだけで、配布先リポでも一般に役立つことはその根拠にならない（workflow.md「知見の振り分け（3経路）」の経路1も同じ判定を通る）。
候補にならない指示のうち、このリポの開発で必要なものはこのファイルに追記する。宛先がこのファイルであることは同 architecture.md の「companion への書き分けルール」表が定める。

## 配置ファイル鮮度セルフチェックをこのリポでは repo-local 版で実行する

このリポは pfd-ops スキルの上流であり、`.claude/skills/pfd-ops/` が canonical、plugin cache 配下（`~/.claude/plugins/cache/pfdsl/pfdsl/<version>/`）はそこから配布された過去のスナップショットである。
両方が実在して食い違う状況を SKILL.md のロード元判定が扱わないこと、古い側の報告が drift でなく陳腐化であること、`--deploy` で追随してはならないことは `.pfdsl/bindings/pfd-retro-patterns/duplicate-name-not-a-discriminator.md` が一次情報。

したがってこのリポでは、pfd-ops 発火時のセルフチェックは `node .claude/skills/pfd-ops/scripts/check-install-sync.mjs --upstream` で実行する。
#971 以降、向きの判定はスクリプト側が持つ — このリポを target とした実行は上流と分類され、どちらの実体から起動しても `--deploy` は案内されず明示指定でも停止する。したがってこの規約が残す指示は「repo-local 版を使う」だけで、`--deploy` を避ける判断を読み手に委ねてはいない。

pfd-ops 発火時、SKILL.md の配置ファイル鮮度セルフチェックに続けて次を実行する:

```bash
node scripts/check-scaffold-sync.mjs
```

`.claude/skills/pfd-ops/references/scaffold/`（`gen-plugin.mjs` のコピー元）と `plugin/pfdsl/skills/pfd-ops/references/scaffold/`（配布用ミラー）の drift を検知する。警告が出たら `node scripts/gen-plugin.mjs` で反映してからコミットする。`install/` と異なり `scaffold/` に `--deploy` 相当の機構はない（scaffold は `/pfd-init` がコピー後にユーザーが値を埋めるテンプレートのため、実配置先は用途的に別物になる）。

## このリポの CLI をローカルビルドから実行する

`pfdsl` / `npx pfdsl` は npm 公開版の `@pfdsl/cli` を走らせる。
このリポは上流であり、公開版は main より必ず遅れているため、公開版で `.pfdsl` を検査すると main で既に直っている欠陥を実在の所見として拾う。
同じ番号を名乗る2実体を番号では判別できない形は `.pfdsl/bindings/pfd-retro-patterns/duplicate-name-not-a-discriminator.md` が一次情報。

したがって手で CLI を叩く場合も `node packages/cli/dist/cli.js <cmd>` を使う（`cycle-status.mjs` / `gate-check.mjs` および `.pfdsl` の `command:` フィールドが既にこの形を使っている — 手打ちだけが例外になっていた）。
worktree では先に `pnpm install && pnpm -r build` を済ませる。
pfdsl スキル本文の CLI プリフライトは採用リポ向けに `pfdsl` / `npx pfdsl` を指示するが、上流であるこのリポではこの規約が優先する。

`check-install-sync.mjs` を repo-local 版で走らせる上の規約と同じ形（上流リポでは正とする実体を1つに固定する）であり、適用先が検査スクリプトから CLI 本体へ広がったもの。

## spec 参照では get-by-ID で必要な節だけ読む

`docs/` 内の `(SPEC_xxx)` 定義済みブロックを参照する際は、ファイル全文を Read せず `node scripts/get-spec-id.mjs SPEC_xxx` で該当ブロックのみ取得する（レンジ規則は ADR-0027）。
参照先が `[[SPEC_xxx]]` / `[[SPEC_xxx?]]` で書かれている本文を追うときが起動契機。

## 新しい仕様 ID を確認して採番する

新規 ID を採番する前に slug の既出を確認する（ADR-0027「ID の性質」）。機械列挙は `node scripts/mint-check.mjs <slug>` を使う（定義・strict 参照・forward-ref の全出現を file:line で列挙し、既出ありなら exit 1。tombstone 次元は初 ID 削除まで据え置き #405）。
採番しようとした slug が既存 forward-ref（`[[SPEC_xxx?]]`）と一致した場合、その forward-ref が予約した概念と同一かを確認し、別概念なら slug を変える。
削除された ID は再利用しない。

## 削除を確定する前に上流の意図を確認する

削除を確定する前に、対象と関連する consumer・兄弟実装・正本や生成・配送境界について、削除判断に関わる未確認の意図や変更がないか確認する。
呼び出し元ゼロだけで不要と判断する場合、並行した上流変更がある場合、正本や生成・配送境界を削る場合は、判断に必要な履歴と差分を読み、所有者の意図と削除後の影響を確かめる。
確認済みの対象・削除理由・関連範囲が変わらず、その範囲に新しい変更がなければ結果を再利用し、削除コミットごとに同じ履歴を読み直さない。
同じセッションで作成した使い捨ての一時ファイルの片付けや、上記を確認済みの削除には、追加の履歴確認を課さない。
対象・関連実装・consumer・生成や配送の規約に変更が入った場合、または削除範囲や理由が変わった場合は、影響する部分を再確認する。
base が無関係な変更で進んだことだけでは再確認せず、固定件数の履歴や merge conflict の有無を、意図を確認した証拠にしない。

## サイクル中の下書きをリポジトリの外へ置く

設計選択記録・PR 本文・委譲ブリーフ等の下書きは `/tmp` へ置き、ファイル名にセッション固有の要素（worktree 名等）を含める。
リポジトリの内側へ置く必要がある場合は、そのパスが今サイクルで触っている検査の列挙対象に入らないことを、検査自身の列挙範囲で確かめる。
`.claude/` 直下は consumer fixture のコピー元であり、置いた時点で output closure 検査が undeclared surface として数える。
worktree 配下であることは他セッションとの衝突だけに答えるもので、このリポの検査に入るかには答えない。

## ワークサイクルの追加手順

pfd-ops の `references/work-cycle.md` が持つ手順1〜3の各段で、この節の該当小見出しに従う。配布層が持つのは PFD 固有の契約と骨格で、このリポの git 衛生・委譲規律・設計記録と人間確認・汎用の終端ゲート項目はここが一次情報である（ADR-0039）。

### 原則として採用案と対案を比較して判断する

**貫く原則: 比較対象を生成する。** コストは単独では評価できず、常に対案との差でしか評価できない。「立ち止まれ」「慎重に判断しろ」型の規則は原理的に効かない — 信号が既に見えているのに受容すべきコストとして分類される、というのが失敗の形だからである。本節の「適用点 1 で採用案と対案を比較して設計を決める」「適用点 2 で新概念と対象範囲を確認する」「適用点 3 と 3 層制御で実装を委譲し外向き操作を制御する」にある3つの適用点は独立した3規則ではなく、この1原則の適用点である（独立3規則にすると3つとも忘れられる）。比較対象生成を省略しない条件は本節末尾の「対案生成を省略しない条件を適用する」にまとめる。

### 再発防止を手順へ反映し機械化を判断する

再発防止は、問題が起きる操作の既存手順・必要な入力・道具・テストへ反映する。適用例と非適用例、確認済み結果を再利用できる条件、再確認を要する変更をその適用点で示す。事例集への追記を、その操作を変えた証拠にしない。
機械化するのは、入力や状態から実際に判定でき、既存検査と重複せず、実装・維持・誤発火の費用に見合う性質である。自然言語の意味や承認の実質をコマンド文字列から推測しない。機械化しない場合も、必要な時点の入力と検証を具体化する。観測・原因の仮説は既存の事例置き場へ、採用済みの規約は操作の手順へ置き、両者を混同しない。

hook の決定を選ぶ軸は害の発生点である。実行自体が害なら advisory は選ばない。対処法を message に書けば1回の retry で自己修復し、対処済みかを rule 側から判定できる場合は deny を使う。対処済みかが payload から見えず人間判断が必要な場合は ask を使い、deny による同じ retry の再拒否を避ける。結果の読み違いだけが害なら advisory を使える。event と channel の対応は harness の版で変わるため列挙せず、実装時に一次情報を確認する。

既存の Node テストへ一時的な文字列変異を当てて検出能力を確認する場合は、分離した作業場所で `node scripts/mutation-check.mjs --config <json-file>` を使う。
Linux / macOS のプロセスグループを使い、タイムアウト時も子テストの終了を確認してから復元する。Windows では変異を適用する前に未対応として拒否する。
JSON のパスは実行時の cwd を基準とし、対象とテストファイルはその配下に限る。
`expected.name` は suite から個別テストまでの名前を順に並べる完全一致の配列で、期待する失敗は1テストだけ指定する。

```json
{
  "target": ".claude/skills/pfd-ops/references/file-based-tracker-backend.md",
  "from": "binding が定める現行の書式を使い",
  "to": "常に Format 3 を使い",
  "tests": ["scripts/lib/pfd-ops-applicability.test.mjs"],
  "expected": {
    "file": "scripts/lib/pfd-ops-applicability.test.mjs",
    "name": ["pfd-ops applicability contract", "keeps placement and readback distributed while record policy belongs to the binding"]
  },
  "timeoutMs": 30000
}
```

ヘルパーは変異前の緑、1箇所の実置換、指定テストだけの失敗、原文復元、復元後の緑を確認し、各段のテスト名と結果を JSON に残す。
A（指定テストが変異で落ちた）は `detected` / exit 0、B（元から赤）は `baseline-failed` / exit 2、C（置換不成立・期待名の非一致や重複・期待テストの skip/todo・変異を検出しない）は `ineffective` / exit 3 とする。
巻き添え失敗、実行テスト集合の変化、実行・復元エラーは `error` / exit 1 とし、成功に含めない。
失敗件数や `--test-name-pattern` の終了コードだけで代用しない。
エラー時も原文のバイト列へ戻すが、独立した書換えを検出した場合は上書きせず、復元用の `<target>.mutation-check-backup` を残す。
強制終了など自動復元できない場合もこのバックアップを使い、残ったテストプロセスを終了させてから対象との差分を確認して復旧する。
既存バックアップがある場合は別実行の復元資料として保護し、自動で上書き・削除しない。
テスト自身の副作用やビルド生成物の復元は対象外なので、副作用を持つ検査は使い捨ての環境で実行する。
fixture で正常版・欠陥版を既に比較している検査には重ねて要求しない。
結果を再利用できるのは対象ファイル、置換、テストとその依存、Node と実行条件が同じ場合だけで、いずれかを変えたら再実行する。

### 手順 1 の追加で worktree と upstream を確認する

- **このサイクル用の worktree を作り、ブランチはその中に切る。既定であり、宣言も確認も要らない。** 同じ作業ツリーで別のセッションが同時に動くと、双方の未コミット変更が同じファイルに混ざって現れ、どちらが書いたかを git の状態から区別できない。ブランチの切り替えは相手の HEAD ごと動かすため、相手が読んでいるファイルの内容が黙って入れ替わる。どちらも「自分の変更だけを見ている」限り検出できない形で壊れる。現在の作業ツリーでそのまま進めてよいのは、ユーザーがそう指示した場合と、リポの構成上 worktree を作れない場合に限る。前セッションから継続する worktree があるならそれを使う（新規作成は不要）。worktree の置き場・命名・セットアップ（依存・ビルド生成物・hook はいずれも引き継がれない）は companion が定義する。
**共有ツリーで編集が消えた場合、探すときは `git stash list` を先に見る。** `git stash` は内部で reset を行うため reflog 上は `reset: moving to HEAD` として現れ、`git reset` と区別がつかない — reflog だけを見ると、他セッションの stash を自分の操作の痕跡と読み違える。
- **companion（roadmap.md 等）がサイクル・プリフライトの集約スクリプトを指す場合**、`git fetch origin` の後に `origin/<base>` を起点としてこのサイクルのブランチを切り、**そのうえで**集約スクリプトを実行する。出力（fetch 実施有無・base への遅れ・open PR の一覧・着手可能プロセス一覧・best 推薦。集約スクリプトが追加で返す付随情報があればそれも従う対象に含む）に従う。**プリフライトは作業ツリー内のスクリプトなので、遅れたツリーではその古い版が走る** — 出力は「どの判定が存在するか」からして古い版のものになり、上流で追加された判定の不在が「走って異常なし」と区別できない。実際に起きた形は、スクリプトが印字したコマンド行に上流で足されたフラグが無く、そのコマンドをそのまま使った結果、そのフラグでしか有効にならない検査がサイクル全体で一度も走らなかった、というものである。集約スクリプトが base への遅れを検出して実行を拒否する場合はその指示に従い、ツリーを更新してから再実行する。**拒否は拒否する版へ更新されて初めて効く**ので、古い版のツリーでは自分で `git log --oneline HEAD..origin/<base>` を見る。指していない場合は以下を手動で行う。**以下3項目は「選択判断はすべて origin の現在状態を前提にする」という1原則の各論である** — fetch 漏れ・stale な base・競合しうる未統合の open PR は、いずれも選択判断の前提を確認する対象になる:
  - まず `git fetch origin` でリモートの最新状態を取得する。新規ブランチは `origin/<base>` を起点に作成する — fetch は remote-tracking ref のみ更新し local ブランチは更新しないため、local 経由で切ると stale なまま気づかず作業してしまう
  - **既存ブランチ（前セッションから継続する worktree 等）で作業を再開する場合**、`git log --oneline HEAD..origin/<base>` で base が先行していないか確認し、先行していれば rebase してから続行する。stale なまま進めると無関係な PR diff（他 PR で先行 merge された変更の revert に見える差分）が混入する。**再開時に限らずサイクルの途中でも起こる** — ゲート集約チェッカーやツールが内部で `git fetch` を実行すると、着手時は最新だった base がその場で先行しうる。
差分の混入だけが害ではない。
遅れたツリーから読んだコードは現行の規約の見本として働くため、既に retire された書き方をそこから新規コードへ写してしまう。
判定を読むためだけでなく、実装の前提を作るためにも、進めてから読む。
**この転写がツリーの外へ出た分は rebase では戻らない。** 遅れに気付くまでの窓の中で確定した作業項目・外向きの作業記録・PR 本文は、ツリーを直しても旧規約を抱えたまま残り、以降の検査はいずれもブランチのツリーしか見ないため誰も指さない。rebase の直後に、その窓の間の外向き操作を数え、取り込んだコミットが規約文書を触っていればそれらの内容を読み直す。窓が空だったなら1行そう記録する
  - **自分の変更を確認する差分は三点（`origin/<base>...HEAD`）で取る。** 二点（`origin/<base>..HEAD`）は base 側の先行分も差分に含めるため、他者が追加したファイルが自分のブランチによる削除として現れる。上の遅れが生じている間、二点で見た差分は「身に覚えのない大量削除」の形で出るので、削除を疑う前に差分の取り方を疑う
  - **同一セッションで続けてサイクルを回す場合も、着手時に `origin/<base>` から新しいブランチを切る。** 前サイクルのブランチに続けてコミットすると、前サイクルの差分が次サイクルの PR に混入する。前サイクルの PR が未マージであれば必ずこの形になる。検出は着手時に `git log --oneline origin/<base>..HEAD` が空であることの確認、または終端ゲートのコミット数が想定と合っているかの照合で行う（コミット数はサイクル完了時に初めて見るため、混入に気付くのは PR 作成後になりやすい）
  - **open PR が今回の作業と重なるか、前提を変えるかを確認する。** 競合する作業は、解消方法か影響の扱いを決めてから選択へ進む。リポ固有の判断基準は companion の roadmap.md に記載する

### 適用点 1 で採用案と対案を比較して設計を決める

着手前に、その作業項目の一次記録と設計判断履歴を確認し、現行のコード・仕様と照合する。取得手段・記録先は roadmap.md が指すバックエンドの L3 reference に従い、承認根拠の確認は本 binding の「GitHub Issues バックエンドの設計記録を確認する」に従う。記録が無いことは未記録を意味し、追加承認が必要かは依頼内容から別に判断する。方式が確定した小さな修正や既に許可された作業は、必要な記録を整えて進める。結果を大きく変える未決事項、実質的な前提の不一致、ユーザーが明示した設計レビュー待機点がある場合だけ、具体案を示して確認する。記録の不足を理由に既存の承認を取り直さず、ほかの機械検査の PASS を設計や承認の確認済みの証明にもしない。公開記録への書込みには既存の承認範囲を適用する。

着手前の確認は、`--issue` で明示した各 issue と、指定なしで best プロセスから解決した issue の双方が対象である。プリフライトは対象と取得失敗を報告するだけなので、終了コードが成功でも実行主体が本文・コメント・現行コードと仕様を照合し、未決の方針と必要な承認を解消する。対象未解決や取得失敗を確認済みとは扱わない。

既存の設計記録を再利用する場合も、採用案と競合する別クラスの実装案が含まれるか、着手前に本文を目視で確認する。「何もしない」「現状維持」だけが比較対象なら、下の適用点1に戻って競合実装案を加え、処分を再検討する。

**サイクルの範囲は、選んだ作業項目の設計が確定するまで確定しない。** 複数の作業項目を一度に指定されたとき、着手前の見た目の小ささで1サイクルに畳まない — 設計対話で方針が決まった時点で規模と種類が変わることがあり、そこで初めて別クラスの変更だと分かる。畳んだまま進めると、性質の違う変更が1つの差分に混ざってレビューの信号が埋もれ、片方が他方の前提を動かす（検査を厳しくする変更を同じブランチに入れると、以降のコミットが全てその厳しさを前提にする）。設計確定の直後に範囲を見直し、分けるなら分ける。

- **適用点1 — 作業項目が列挙する案の集合を、設計空間とみなさない。** 起票者が挙げた案は入力の一部であり、網羅性は保証されていない。設計を確定させる前に次を行う。
  **ユーザーへの設計提示と着手前の公開記録は、今回確定する判断と理由を先に示す構成を推奨する。** 決定した範囲、理由、元候補の扱い、共有前提とそれを外した案の検討、決定の変更と必要な承認を、後から追える記録にする。固定見出し・項目順・列挙値は必須にせず、対話で承認された内容と記録の意味を一致させる。
  判断が複数の軸に分かれる場合は各軸の決定と理由を対応させる。例えば「決定」「理由」「候補の扱い」「前提の検討」「変更履歴」に分けると読みやすいが、表や散文でもよい。候補の一部を採る場合は採用部分と残部の扱いを示し、保留する条件や却下する理由を残す。検討中の案を決定済みと読ませない。
  決定を変えた場合は、変更前後・理由・必要な承認の根拠と対象変更の対応を記録する。表示上の分類は、ファイル変更、外部書き込み、認証情報の利用、費用発生の権限を付与しない。調査や待機の判断を実装の許可に読み替えない。
  1. **前提を1文で書く。** 例えば「本案は〈○○という状態が存在し続けること〉を前提にする」と表せる。列挙された全案が共有している前提を書く（案が1つしかない場合はその案の前提を書く）。表現を固定せず、各案に共通する前提を具体的に説明する。
  2. **その前提を否定した案を1つ作り、同じ粒度で集合に加える。** 起票者が挙げていなくても作る。**作った否定案が列挙済みの案のいずれかと一致したら、集合の外へ出られたことの証拠にはならない** — 否定したのが全案の共有前提でなく採用しかけていた1案の前提だった場合と、起票者の列挙がもともと網羅的だった場合の両方がこの形になる。列挙と読み比べて一致に気付いたら、どちらなのかを既存候補との差分として記録する。**後者だと述べる場合は、もう一段上の前提を否定した案も既に列挙内にあることを示す。示せなければ前者として扱い、もう一段上の前提へ遡ってやり直す** — 網羅性は機械照合できない側の性質なので、自己申告だけで免除にすると、遡り直しを避けたい回が必ず後者を名乗る。この一致は記録を読んで確認する。
  **前提を否定した結果が「何もしない」「現状維持」に帰着する場合、それは前提を試す案として残してよいが、採用案と競合する別クラスの実装案をもう1つ加える。** 対策の有無だけでは採用した手段の対立仮説にならないため、設計記録を確定する前に両案の処分を明示する。
  3. 否定案または追加した競合実装案の却下理由は、外部制約か所有者に帰着させる。
     **「手間がかかる」「大がかり」「今回のスコープ外」は却下理由として無効。**
     **述語への分解、各述語の根拠検証、不成立の除去、処分の順で進め、全述語の除去処理が終わるまで処分を確定しない。**
     述語は根拠と対象範囲を個別に判定できる主張として記録し、分解が一意に定まらない部分は未確定とする。
     各述語には、該当する次の検査をすべて適用する。
     - **決定の引用**: 既存の設計決定・規約・制約を引く場合、再読できる版や出典と具体的な条項を示し、「その条項が案を禁じる条件」と「実際に処分する案がその条件を満たす箇所」を1文で書く。
       別案の該当、適用範囲の一致、具体的な禁止条件のない原則・選好・意図だけでは却下の根拠にならない。
       外部仕様・法規・他者所有の規約も同様に扱い、実装のない規範述語は文面で検証する。
       引用に対象リポジトリの機構が実現する挙動述語が含まれるなら、その述語には次の挙動検査も適用し、一方の根拠を他方へ流用しない。
     - **挙動の引用・機構の名指し**: 既存の挙動を引く場合、今回の変更対象を含め、その挙動を起こしたコマンドと出力を書く。
       自分の変更の外にある機構を名指す場合も実行出力を示し、走らせられない場合に限り、挙動を決める呼び出し側の分岐を引用する。
       関数名・JSDoc・コメントだけでは挙動の根拠にならない。
     - **却下案そのものの未実装機構**: 名指す機構が却下案そのもので未実装の場合は、実行・呼び出し側の引用に代えて両案を具体的な入力で比較する。
       採用案が却下案を包含すると主張するなら、却下案だけが扱える入力を構成して両案に当てる。
       見つかれば包含の主張を除去対象とし、採用案が扱えない経路を成果物に明示する。
       見つからないことだけでは根拠にせず、却下案の対象入力・条件を採用案が覆う対応を示す。
     **除去するのは、未確定または根拠を書けない引用・述語と、それに依存する主張である。**
     独立した有効な述語は残し、除去後の理由だけで案を採れないと示せる場合に限り `却下` とする。
     有効な理由が残らない場合は `保留` とし、再検討条件を書く。
     残る理由が案の一部しか禁じない場合は案全体を落とさず、禁止部分を外した縮小案を生存候補として残す。
     生存候補であることは `採用` を意味しない。
     **縮小案の `部分採用` は、採用部分が単独で案の目的を満たす成果物として分離でき、残部の処分と、`却下` なら理由、`保留` なら再検討条件が確定した場合に限る。**
     ファイルや面を分割できるだけでは足りず、条件を満たさなければ `保留` として再検討条件を書く。
     縮小元の候補との対応が追える位置に、採用部分と残部の扱いを記す。
  対話の要否は案の本数でなく、ユーザーが判断すべき未決事項が残るかで決める。通常の実装詳細は依頼範囲内で判断し、工程が移るたびに同じ内容の承認を求めない。選択肢を提示する場合は、決定を変えうる前提と理由を併記する。
  **記録先**: 判断、理由、候補の扱い、前提を外した案の検討、決定の変更と必要な承認は、そのサイクルについて後から読み返せる作業記録に残す。**方針と必要な承認は実装着手前に確定する。** 配置と投稿・編集直後の exact-write readback はバックエンドの L3 reference に従う。記録の不足に気付いたら経緯を補記し、必要な承認が未了なら依存する実装を進めず判断を受ける。記録不足だけを理由に承認済み事項の再承認を求めない。
  **人間レビューは、記録の存在と正本を確認し、issue 由来の候補をすべて扱ったか、決定と候補の扱いが意味的に整合するか、複数採用・部分採用・組合せの境界と軸分割が実際の独立性を反映するかを確認する。** 調査や待機を実装の黙示的な許可にしていないこと、保留の再検討条件が実行可能なこと、却下理由、共有前提、前提を外した案の粒度、一致時の上位前提検査、決定変更と承認根拠の正確さも確認する。承認根拠への参照先を実際に読み、必要な承認が実在し、対象変更を覆うかを確認する。複数の変更が同じ承認を参照する場合も、それぞれの対応を確認する。
  記録漏れや正本の曖昧さ、必要な承認の未確認は、実行主体が補修・確認してから終端の人間レビューへ渡す。補修を理由に過去コミットの再作成や記録・コミットの日時変更を要求しない。

### 適用点 2 で新概念と対象範囲を確認する

- **適用点2 — 既存の不整合・重複・drift・手作業の機械化を目的とする作業では、着手前に次も確認する。**
  - **導入する新概念を列挙する。** 規則・状態・例外・分岐・向き・停止条件を数える。既存の慣行に対する例外は必ず含める。
  - **同じ形の構造がほかに何個あり、今回のスコープは何個かを数える。** スコープ外に同型が残る場合、それらが使っている機構を1語ずつ書き出す。**数える単位は、対策が作用する単位に合わせる。** 対策が出力単位で効くなら同型も出力単位で数える。スクリプト・ファイル・コンポーネントなど数えやすい単位で代用すると、1単位の内部に同型が複数あってもまとめて1と数えてしまい、スコープ外の残存を過小に見積もる。この誤りは「同型は残らない」という結論の形で出るため、結論だけを見ても検出できない。
  - 今回の案の機構がその語彙に無ければ、**「なぜ今回だけ既存機構が使えないのか」を1文で書く。** その1文に現れる性質を、制約でなく設計変数として扱う案を1つ作る。
  - 新概念ゼロを主張する場合、流用する既存機構の作用域を**実測で**確認した旨を1行添える。名前が示唆する範囲を信じない。**この実測は案をユーザーへ提示する前に済ませる。** 提示は選択を確定させる行為なので、提示の後で実測して前提が崩れれば、確定した決定を差し戻すことになる。既存機構への委譲は「その機構が現に何を拾っているか」で成否が決まり、規約や README が述べる範囲とは別物である — 委譲先を実データに当てて、いま拾えているものが拾えなくなる件数を数えてから提示する。適用点1 が記録の時点を着手前に固定しているのと同じ理由で、この実測にも時点がある。
**この実測は、既存機構を受け入れ基準として名指しするときにも要る。** 案の一部として流用する場合だけでなく、「この検査が緑なら目的の性質は保たれている」と宣言する場合が同じ形であり、こちらのほうが誤りが露見しにくい — 流用した機構が拾い漏らせば実装が壊れて見えるが、受け入れ基準が性質を見ていない場合は緑が返るだけで、壊れたことは出力のどこにも現れない。判定したい性質を1つ挙げ、その機構の入力にその性質が入っているかを、機構を実際に走らせた出力の上で確かめる。実装を委譲する回はこの確認を委譲先に任せられない — 委譲先は与えられた基準が緑になったことしか見えず、基準が見ていない範囲の食い違いを正常な完了と区別できない。
  判定物は新概念の数ではなく、この1文の質である。数が多い案を採ってもよいが、その場合は理由を書く。「もう実装したから」は理由にならない。概念数は生成器の内部へ押し込めば操作できるため、数そのものを勝敗判定に使わない。

### 手順 2 の追加で worktree 上の変更を検証する

ブランチを切って作業する（main 直コミットしない）。ビルド・生成・全量 check 系のコマンドは出力が数百行に及ぶことがある — 結果確認は `git status --short <対象パス>` / `git diff --stat` で変更有無を先に見る（詳細ログが要る場合のみファイルにリダイレクトして絞る）。**その出力が、いま実装しているツリーのものかを毎回確かめる。** worktree で作業していても、実行環境がコマンドの作業ディレクトリをセッション既定の場所へ戻すことがあり、そうなるとビルドもテストも別ツリー（多くの場合 base ブランチ）で走る。そこは変更前の状態なので緑になり、緑は「自分の変更が通った」証拠として読まれる — 実際にはこのサイクルの差分は一度も検査されていない。実測すべきは出力でなく実行場所で、コマンドの冒頭に `pwd` を置くか、ディレクトリ変更を別の呼び出しに分けて確定させてから測る（同じ理由で、`cd <dir> && <cmd>` の形はツール呼び出し前に発火する検査の目には `cd` 前のディレクトリしか見えない）。**この確認は1回では持続しない** — 戻りはサイクルの途中で起きるので、前の呼び出しで確かめた実行場所は次の呼び出しの根拠にならない。測るたびに確かめるか、そもそも対象ツリーの絶対パスを毎回書く。戻った状態は緑としてだけでなく「自分の変更が消えた」形でも出る（テスト件数が減る・作業ツリーが clean に見える・変更したはずのファイルが変更前の内容を返す）ため、消失を疑う前に実行場所を疑う。**GUI・エディタ拡張等の UI 変更は、ビルド後にユーザーと実際に操作して動作確認する。verify が BLOCKED になった場合も「確認手順をユーザーに渡す」で終わらず、ユーザーの確認結果を受け取るまで完了とみなさない。**
**変更前後を報告する作業では、変更前に比較対象と測り方を決める。** 基準は作業開始前の版を commit ID 等で固定し、測定対象・条件と一緒に既存の作業記録へ残す。ブランチ内で自分が作った不具合とその修正幅を、基準からの改善幅にしない。
履歴から同じ条件で復元できる静的な指標は、固定した版から後で測ってよい。未コミットの状態・外部データ・実行時の性能など、後から復元できない対象は変更前に取得する。取得を逃したら比較不能の理由と確認できる範囲を報告し、現在値を before として補わない。
after も測った版と条件に結び付ける。計測後に HEAD・未コミット差分・入力・設定が変わったら、その変更が指標へ影響するかを確認し、影響する測定だけをやり直す。影響しない根拠があれば既存結果を再利用できる。履歴のない実行時指標の代わりに静的な件数を示す場合は代理指標と明記し、効果の実証と区別する。比較を目的にしない通常作業へ新しい計測や報告書を課さない。
**そのサイクルで新設した agent が同じセッションから起動できるかは、確かめるまで分からない。** harness が定義の追加を検出して即座に使える場合と、セッションを開き直すまで見えない場合があり、どちらになるかは追加のしかた（既存のディレクトリへ足したか、ディレクトリごと新設したか）や起動時の設定で変わる。
**「できない」を前提に検証を次セッションへ送る前に、実際に1回呼んでみる** — 呼べないことを前提にすると、呼べる回でも検証が先送りされ、そのサイクルは自分の成果物を一度も動かさずに閉じる。
呼べなかった場合は、壊した状態を作って呼び報告を生ログと照合する型の受け入れ基準はそのサイクル内では満たせない — 検証を次セッションへ渡し、未了である旨を作業記録に明示して閉じる。
別 agent に同じ指示を与えて代用しない。検証対象は agent 定義そのものであり、別の定義の挙動はその代理にならない。
**渡す検証手順には、壊れたことの確認を手順そのものに含める。** 作業ツリーの差分を前提にする壊し方（`git stash push -- <file>` 等）は、その差分をコミットした後は空振りし、以降の検査は健全なツリーに対して走って緑を返す。
空振りは失敗でなく緑として出るため、確認を挟まない限り検証者からは成功と区別できない。

**develop 中に見つけたスコープ外バグの扱い。** 作業中の issue とは無関係な既存問題を偶然見つけた場合は原則どおり別途起票する。ただし、**当該 PR のテストを green にするために不可避な既存バグ**（例: 新規追加したテストの実行方式が、テスト対象と無関係な既存コードの欠陥を顕在化させた場合）は、同一 PR 内で直接修正してよい — 別 issue に切り出すと当の PR が green にならず着地しない。判定テスト: 「このバグを直さずに今の PR のテストを green にできるか」。できない場合のみ同一 PR 内で直す。修正理由・原因は PR 本文に明記する（発見経緯でなく、何が壊れていて何を直したかの事実）。この規律は作業項目バックエンドの種類に依存しないため、配布層の GitHub Issues プリセットでなくここが持つ（ADR-0039 の区分 iii）。

### 適用点 3 と 3 層制御で実装を委譲し外向き操作を制御する

- **適用点3 — 実装を別エージェント・別セッションへ渡す場合、前提の1文・却下した案とその理由・新概念の列挙、の3点をブリーフに含める。** 差し戻し条件を列挙型で明記する。列挙に無い概念が実装に必要になった場合、前提が事実でないと判明した場合、却下理由に事実誤認があった場合、**仕様が作業項目の目的に反する例外を含んでいる場合**（設計者が書いた仕様そのものの誤りは、実装者が忠実であるほど検出されない）は、実装を止めて設計者へ返す。**無条件の「決定済み・再設計禁止」は書かない。** 凍結してよいのは実装詳細であり、前提ではない。実装者に自由な代案探索をさせることは要求しない（二重設計になりコストが合わない） — 差し戻し条件を列挙型に限定することで churn を抑えつつ、最後の検出機会だけを開けておく。委譲先が留保作業（push・PR 作成・作業項目バックエンドへの書き込み）を実行していないかの戻り時照合は本原則の管轄外であり、委譲の範囲制御として次項で別に扱う。
  **手書きの成果物を生成へ置き換える委譲では、渡す前にその生成器が書き込む先を全部列挙し、受け入れ基準がその全部を固定しているかを確かめる。** 列挙の単位は生成器の出力先であって、ブリーフが名前を挙げた出力ではない。一部だけを固定した受け入れ基準は、固定した出力については最後まで緑を返すため、同じ宣言から作られる他の出力が崩れても委譲先からも呼び出し元からも正常な完了と区別できない。
  **生成物が適合すべき既存構造は、実物から読んで入力に明示する。** 出力が既存の構造（設定ファイルのキー・仕様の節番号・データの形）へ適合しなければならない委譲では、その構造を委譲先に読ませるか、抽出した現物をブリーフへ書く。渡さないと委譲先は存在しない構造を捏造し、戻り後のレビューでしか検出できない — 入力として渡せば捏造そのものが起きない。前提の1文と違いこれは実物を読む工程であり、構造の名前が示唆する形からの推測では代用できない。
  **先例を使う委譲では、先例と今回の入出力を実物で比べる。** 呼び出し元は目的・編集範囲・先例の版と入口・今回の期待結果を渡し、正常系に加えて不正入力、対象不在、権限等の失敗時の扱いを示す。先例の前処理・除外・別枠の分岐のうち、引き継ぐものと今回には当てはまらないものを区別する。「同じ形で」の一言や、パターン名を渡すだけでは入力にならない。
  ブリーフが足りなければ、委譲先は一次資料を読んで補い、目的や権限に関わる未決事項だけを呼び出し元へ返す。調べられる内容の再承認は求めない。先例を使わない単独作業にはこの比較を課さない。
  戻りのレビューにも目的・最終差分・一次資料への入口を渡す。reviewer は依頼に列挙された条件を探索の上限にせず、先例と実消費者から今回の scope を点検し、正常・失敗時の期待結果を実物へ当てる。既に検証した結果は、対象版・条件が今回も一致すると確認できれば再利用し、変更で根拠が崩れる範囲だけ再確認する。
  **必要な作業順と記録形式を分ける。** 承認やレビューなど、委譲の前後で誰が何を確認するかをブリーフに明示する。記録をコミットへ載せる都合だけで実施時点を縛らない。戻り後のレビューで見つけた問題は通常の追加コミットで直し、記録漏れの補修に過去コミットの再作成を要求しない。
  **記録の存在や時刻だけでは、承認・レビューの実施を証明できない。** 内容と対象差分の対応は人間レビューで確認する。未実施の確認は実施し、判断が変わった場合は必要な承認を得てから反映する。
- **委譲先の外向き操作の制御 — 3層で機構化する。** 実装を委譲するとき、push・PR 作成・作業項目バックエンドへの書き込みは呼び出し元が持つ。ブリーフに「push するな」と明示しても破られることが実測されているため、指示でなく機構で制御する（同一サイクルで範囲指定が2回破られ、2回目は明示的な禁止に反して PR が作成された事例がある）。
  1. **agent の選択。** 外向きツール面（GitHub 連携等）を `tools:` に持たない実装専用 agent を使う。全ツールを持つ汎用 agent は実装委譲に使わない。本スキルに同梱の `pfd-implementer` がこれに当たる（worktree 作成から PR 作成までを一気通貫でやらせる場合は、その範囲を持つ別の agent を使う）。
     委譲先のセッションは呼び出し元のその時点の作業ディレクトリを継ぐ。
     別のツリーへ移動した直後に委譲すると、委譲先は対象ツリーへ書けずに停止するか、書き込みガードが無ければ誤ったツリーへ書く。
     委譲前に作業ディレクトリを確認し、ブリーフには対象ツリーの絶対パスを書く。
     委譲するフローが worktree の作成を含む場合、「既存の分離ワークスペースがあれば再利用する」型の手順を素通しにしない。
     委譲先は呼び出し元が使用中の worktree の中で起動されることがあり、その場合その手順は共有中の worktree を既存の分離ワークスペースと誤認識して乗っ取る。
     agent 定義側に、その再利用判定を迂回して常に新規 worktree を作る旨を明記する。
  2. **PreToolUse ガード。** allowlist 外の subagent による `git push` と変更系コマンドを、ツール呼び出しの時点で拒否する。subagent の hook payload には `agent_id` が入り呼び出し元の payload には入らない — この差が判別子になる。**agent 名を運ぶフィールド（`agent_type` 等）を判別子に流用しないこと** — harness の契約はそれを「subagent 内で発火したとき」に加えて「セッションが `--agent` を使うとき」にも入れると定めており、後者に当たる呼び出し元が subagent と誤判定されて自分の push を止められる。`agent_id` の側にこの追加条件は無い。`session_id` / `transcript_path` は親子で共通のため使えない。デフォルト拒否にすれば、agent を新設しても黙って push 権を得ることはない。プロジェクト全体に効く permission deny を使わないのは、呼び出し元と一気通貫型 agent まで巻き込むためである。実装はリポ固有のため本スキルは配布しない — 置き場は companion に書く。
  3. **戻り時の検出。** 委譲から戻ったら `git log origin/<branch>..HEAD` と open PR 一覧を確認する。上2層をすり抜ける経路（生 `curl`・スクリプト経由の間接実行）は塞げないため、この層が最後の網になる。将来ツール面が増えても効き続けるのはここだけである。

### 終端ゲートの追加項目を検査して完了を確認する

work-cycle.md 手順3 の終端ゲートに、次の項目を同じ扱いで加える。

- [ ] **記録先: ユーザーへの報告**: 作業中に偶発的に見つけたスコープ外の既存問題（バグ等）を、発見した時点でユーザーへ報告した（ユーザーの指摘を待たない、が指すのは発見の報告を遅らせないことであり、新しい作業項目を外部サービスへ公開する同意を省略してよい意味ではない。公開書き込みは実行環境の権限モデルによって拒否される、または確認なしに確定してしまう — いずれの場合も報告と別に、公開の可否はユーザーに諾否を仰いでから実行する）。**独立して着手・却下できる発見は、諾否も項目ごとに取る** — 束ねて1つの可否として出すと、却下は束に効き、各項目は一度も判断されない。不可分な発見を束のまま出すのは正しいが、その束の一部が外部で解消したら残りは新しい束なので、その時点で改めて諾否を仰ぐ
- [ ] 適用点1の方針と必要な承認が確定され、対象とする各 issue コメントの記録の存在・正本・判断の根拠・承認参照と対象変更の対応を人間が確認する。元候補の扱い、採用案と競合する別クラスの実装案、前提を外した案とその理由を読む。「何もしない」「現状維持」だけが対案になっている場合や、無効な理由で案を除外した場合は適用点1から再検討する。既存の記録は書式を揃えるために変換しない
- [ ] 本節「手順 2 の追加で worktree 上の変更を検証する」で変更前後の比較が対象となる作業では、固定した基準・対象版・条件に対応する結果を確認した。測れない範囲は理由と確認できる範囲を残し、代理指標を示す場合は効果の実証と区別した。比較を目的にしない通常作業はこの項目の対象外。数値の書き込み先は下の「PR 作成後」の項目
- [ ] コミット粒度（論理単位ごとの分割）が規約（CLAUDE.md または companion で定義）に従っている。**生成元と生成物は同一コミットに入れる** — 作業ツリー全体から再生成して staged 分と突き合わせる型の drift 検査を持つリポでは、両者を別コミットに割ると生成元だけを staged にした時点で不一致になり弾かれる。論理単位が2つ以上あってもこの境界では割れない — 割れない理由の書き込み先は下の「PR 作成後」の項目
- [ ] コミット subject が Conventional Commits 形式に従う
- [ ] **記録先: PR 本文**: 利用中のハーネス・モデルと companion の規約に従って最終差分をレビューし、確認した影響先と検証根拠、未確認範囲、未解決の指摘をまとめた（レビューコマンド・チェックリスト等の具体的な手段は companion で定義。定まっていなければ最低限、差分を自分で読み直す。省略する場合はその理由を PR 本文に書く）。**レビューの重さは diff の規模に合わせる** — 数十行・1〜2ファイル中心の scoped な修正に多角度 finder × 候補ごと検証 agent のような高効度設定をかけると diff に対して過剰になる。角度を絞るか、そもそも委譲せず自分で読む。重量級の構成は大規模 diff 向け。
レビューを取りまとめる実行主体（委譲した場合は呼び出し元）は、今回影響する経路とレビューの確認範囲・根拠を照合し、追加確認の結果または不要と判断した根拠、残る未確認範囲を PR 本文へまとめてから終了を判断する。レビューの実行回数、指摘なし、CI 成功から未確認範囲まで問題なしと推定しない。必要な経路が未確認なら、その経路を追加確認する。
**ただし担保の中核が委譲でしか作れない観点は、重さを落とす対象に入らない。** 独立性（解答を知らない主体が解くこと）や多重性のように、別主体を立てることでしか成立しない性質を自分で回すのは、軽量な実施ではなく不実施である。
その委譲を起動できない回は、記録して閉じずにユーザーへ返す。
**起動できないというその判断も、指示の文面を確かめてから下す** — 「禁止されている」と「まだ求められていない」は実行主体からは同じ形に見え、後者を前者と読めば作業が減る側に倒れる。根拠として引ける文面が無いなら、確かめていない。
**起動可否は harness と plugin の版に依存することがあり、規約に書かれた「起動できない」はそれを書いた時点の観測でしかない。** 過去にそう記録された手段でも、その記録に従う前にその回の実体（コマンド定義の起動可否フィールド）を確認する。逆向きの陳腐化（起動できるようになったのに規約が禁止のまま残る）は、規約を満たせない形ではなく選択肢を1つ失ったまま気付かない形で出るため、失敗としては観測されない
- [ ] 両ホストとも workflow.md の番号付きレビュー観点を、「どの手段を選ぶか」の優先順ではなく「どの観点が担保されたか」で確認した。観点ごとにブリーフ要件を課し、その観点をどの手段で満たすかは workflow.md のホスト別の節が定める。複数の観点を同じ reviewer が担ってよいが、独立解が必要な観点3(a) は採用案を読む最終差分 reviewer と兼ねない。
最終差分のレビューでは、変更目的・差分・変更対象の成果物を渡し、reviewer が影響先を自分でも探す。実装がある場合はその入口も渡すが、文書・設定だけの変更でも、その読み手や参照先を調べる。指定ファイル一覧を探索範囲の上限にしない。条件や機能を撤去する場合は、旧識別子・出力文言・条件を手掛かりに、未変更の利用側コードと説明・回復手順を確認し、過去の事例と現行の指示を区別する。探索は今回変えた契約に依存する経路に絞る。
機械が読む文書・設定の抽出対象を変える場合は、編集した実ファイルを読み手の処理に渡し、期待する内容が最終出力へ届くか確認する。構造検査や見本データのテストだけを、この経路の確認済みという根拠にしない。
- [ ] finding には具体的な failure scenario（入力・状態 → 誤出力・誤誘導）を伴わせ、構成できない指摘は報告しない。敵対的な指示は「何か見つけねば」という圧で false positive を量産するため、scenario を構成できることを報告の条件にする
- [ ] **記録先: PR 本文**: 両ホストとも workflow.md の番号付き観点ごとに、発火して実施されたか、条件を満たさず非発火だったか、発火したが未実施かを区別する。発火条件と実施時の重さは別軸であり、軽量化した回は観点名と理由を、非発火の回は条件を満たさない理由を、未実施の回はその旨と理由を PR 本文へ書く。独立性や多重性を自分の読直しで代替できない範囲は上の規則に従う。確認範囲・根拠・未確認も上の最終差分レビュー項目に従って記録する
- [ ] 変更束を PR にまとめた（PR 作成後にローカルで追加コミットした場合、push し忘れていないか `git log origin/<branch>..<branch>` で確認する — CI は push 済みの内容にしか反応しない）
- [ ] **PR 作成後**: 本節「手順 2 の追加で worktree 上の変更を検証する」で変更前後の比較が対象となる作業では、固定した基準・対象版・条件と結果を PR 本文に書いた。測れない範囲は理由を示し、代理指標を使った場合はその旨を書いた。比較を目的にしない通常作業に、数値や代理指標の記載を要求しない
- [ ] **PR 作成後**: 生成元と生成物を同一コミットに入れたために論理単位が割れなかった場合、割れない理由を PR 本文に書いた
- [ ] **PR 作成後**: サイクルの途中で前提が変わった箇所を、PR 本文（最初に読まれる正本）にも書き戻した。訂正を別の記録媒体へ書いた回は、その場で正本の該当箇所も直す — 正本だけを読む人は訂正の存在を知る手がかりを持たないため、両方を読んだ者にしか食い違いが見えない。サイクルの終わりにまとめて見直す形にしない（その時点では、どの文がいつ書かれたかがもう分からない）。**この項目だけは実施の時点がここではない** — 実施は訂正を書いた各時点であり、ここで確認するのはその実施の有無である。ここへ来て初めて全訂正を見直す運用にすると、項目文自身が禁じている形になる
- 上3項目がここに置かれているのは、書き込み先が PR 本文だからである。**書いた内容そのもの**（指標の数値・割れない理由・書き戻した訂正）を読むのは PR をレビューする人間だけで、それを判定に使う機械は無い — したがって PR 本文が置き場として適格であり、誤っていたのは確認を求める時点のほうだった（チェックリストの上の方に置くと、書き込み先がまだ存在しない時点で確認を求めることになる）。並べ替えないこと。ゲート集約チェッカーはこの正本の本文や印を解析せず、PR 作成前後の固定案内だけを出す。実行主体は PR 作成後にこの位置へ戻り、行頭に `**PR 作成後**` を持つ項目を直接確認する。`**記録先: …**` は時点でなく記録先を宣言する別の印である

### 機械判定の外にある事項を人間が確認する

設計記録の実在・正本・承認根拠への参照と対応は、人間の必須確認である。書式・候補数・旧形式の cutoff・独自の再承認時間窓を機械判定しない。委譲先の外向き操作は本節「適用点 3 と 3 層制御で実装を委譲し外向き操作を制御する」の3層ガードで制御する。最終差分の独立レビューと人間のマージ判断を維持する。
記録の内容が実質を伴うか、案を網羅しているか、必要な承認が実在し対象の変更を覆うか、最終差分をレビューしたかは人間レビューの責務である。
投稿・編集時刻と初コミットの比較では、判断やレビューの実施を証明できない。記録補修を理由に履歴を作り直すことも、その代わりにはならない。

### 対案生成を省略しない条件を適用する

適用点1〜3 に共通する、比較対象生成を省略しない条件。書式を自由にしても、判断・理由・候補の扱い・前提を外した案の検討・決定変更と必要な承認を追跡できる記録を残す義務は変わらない。

- 同型の先例が0件と確認できた場合は、その0件を1行記録する。0件は比較対象を生成しない根拠にせず、前提を外した案とその検査案の処分を前提検査に含める。
- 前提が他者所有・後方互換・法規等の外部制約に帰着する場合も、前提を外した案を先に生成する。外部制約または所有者名は、生成後にその案を採らない検査案の処分として記録する根拠であり、対案生成の免除にはならない。
- 緊急修正でも比較記録を省略しない。緊急性だけを理由に記録なしを選ばない。

## GitHub Issues バックエンドの設計記録を確認する

このリポは #1208 の[採用済み方針 B](https://github.com/takasek/pfdsl/issues/1208#issuecomment-5755227472)に従い、設計記録を残して確認を人間レビューへ移す。配布層の `references/github-issues-backend.md`「設計確定の証拠」が定める配置と exact-write readback の契約は変えない。

**対象と時点**: 着手前は `--issue` で明示した各 issue と、指定なしで best プロセスから解決した issue の双方を扱う。候補が何件あるかに関係なく、実行主体は一次資料と現行コード・仕様を照合し、未決の方針と必要な承認を解消する。終端は明示した各 `--issue` が対象であり、省略した issue を人間確認済みとは扱わない。対象未解決や取得失敗は解消してから進む。

**正本と補修**: issue 本文は依頼内容、設計選択記録の正本は当該 issue のコメントとする。人間はコメントの内容と経緯から正本を同定し、存在・判断の理由・候補の扱い・前提を外した案の検討・決定変更を確認する。正本が曖昧なら推測せず、実行主体が既存の記録を確認し、承認範囲内で同じコメントを補修してからレビューへ渡す。正本が分からなくなる別コメントでの置換や、旧コメントの一括変換・削除・日時変更は行わない。

**承認の追跡**: 決定を変える場合は必要な承認を得て、変更前後と理由、根拠への参照、承認が覆う対象変更を同じ記録に残し、既存実装との整合を確認する。根拠は当該コメントや元の対話などを再読できる参照で示す。URL の独自字句や秒単位の時間窓を要求せず、人間が参照先の実在・承認内容・対象変更との対応を読む。記録不足を承認の不在と同一視せず、承認済み事項を再承認させない。公開記録の補修にも既存の外部書込みの承認境界を適用する。

**確認の分担**: 投稿・編集直後は送った本文と保存された本文を exact-write readback で照合する。記録の確認は上の「適用点 1 で採用案と対案を比較して設計を決める」と「終端ゲートの追加項目を検査して完了を確認する」へ統合し、確認済みを証明する機械状態や記録欄を追加しない。Format-3 構造分類器と投稿前の書式検査を廃止し、JSON schema や承認レジストリでは置き換えない。記録欠落・正本重複・参照不整合の自動検出を失うため、人間がこれらも読む。従来の機械検査と同じ保証や、総費用・見落とし率の優位は主張しない。通常の issue 読取と取得失敗の扱い、PFD・生成物等の検査、事前チェック8本は維持する。記録の投稿・編集時刻と初コミットの比較は行わない。

**適用開始**: この方針を実装した版の運用文書を使うサイクルから適用する。旧版の worktree は旧検査を持ち続けるので、新方針を使う場合は通常の手続きで実装済みの版を取り込む。既存コメントの内容は必要に応じて読み直すが、書式を揃えるための変換はしない。
