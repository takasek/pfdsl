# ワークサイクル（選択・実行・終端ゲート・報告）

作業項目に着手する回はこの4手順に従う。起動口は問わない。
コンテキストのないセッションでも1サイクル回せる自己完結手順（`.pfdsl/` 配下の各ファイルと sibling companion を読めば動ける）。範囲規則: **1サイクル = 1プロセス**。大きすぎる場合は粒度ルールで分割を `.pfdsl/roadmap.pfdsl` に反映してから着手する。PFD の読み書きが生じたら `pfdsl` スキルを invoke する。

**貫く原則: 比較対象を生成する。** コストは単独では評価できず、常に対案との差でしか評価できない。「立ち止まれ」「慎重に判断しろ」型の規則は原理的に効かない — 信号が既に見えているのに受容すべきコストとして分類される、というのが失敗の形だからである。以下の手順1・手順2 にある3つの適用点は独立した3規則ではなく、この1原則の適用点である（独立3規則にすると3つとも忘れられる）。免除条項は末尾にまとめる。

1. **選択**:
   - **このサイクル用の worktree を作り、ブランチはその中に切る。既定であり、宣言も確認も要らない。** 同じ作業ツリーで別のセッションが同時に動くと、双方の未コミット変更が同じファイルに混ざって現れ、どちらが書いたかを git の状態から区別できない。ブランチの切り替えは相手の HEAD ごと動かすため、相手が読んでいるファイルの内容が黙って入れ替わる。どちらも「自分の変更だけを見ている」限り検出できない形で壊れる。現在の作業ツリーでそのまま進めてよいのは、ユーザーがそう指示した場合と、リポの構成上 worktree を作れない場合に限る。前セッションから継続する worktree があるならそれを使う（新規作成は不要）。worktree の置き場・命名・セットアップ（依存・ビルド生成物・hook はいずれも引き継がれない）は companion が定義する。
**共有ツリーで編集が消えた場合、探すときは `git stash list` を先に見る。** `git stash` は内部で reset を行うため reflog 上は `reset: moving to HEAD` として現れ、`git reset` と区別がつかない — reflog だけを見ると、他セッションの stash を自分の操作の痕跡と読み違える。
   - **companion（roadmap.md 等）がサイクル・プリフライトの集約スクリプトを指す場合**、`git fetch origin` の後に `origin/<base>` を起点としてこのサイクルのブランチを切り、**そのうえで**集約スクリプトを実行する。出力（fetch 実施有無・base への遅れ・自動生成 PR の open 有無・着手可能プロセス一覧・best 推薦。集約スクリプトが追加で返す付随情報があればそれも従う対象に含む）に従う。**プリフライトは作業ツリー内のスクリプトなので、遅れたツリーではその古い版が走る** — 出力は「どの判定が存在するか」からして古い版のものになり、上流で追加された判定の不在が「走って異常なし」と区別できない。実際に起きた形は、スクリプトが印字したコマンド行に上流で足されたフラグが無く、そのコマンドをそのまま使った結果、そのフラグでしか有効にならない検査がサイクル全体で一度も走らなかった、というものである。集約スクリプトが base への遅れを検出して実行を拒否する場合はその指示に従い、ツリーを更新してから再実行する。**拒否は拒否する版へ更新されて初めて効く**ので、古い版のツリーでは自分で `git log --oneline HEAD..origin/<base>` を見る。指していない場合は以下を手動で行う。**以下3項目は「選択判断はすべて origin の現在状態を前提にする」という1原則の各論である** — fetch 漏れ・stale な base・未マージの自動生成 PR は、いずれもこの原則からの逸脱として検出する:
     - まず `git fetch origin` でリモートの最新状態を取得する。新規ブランチは `origin/<base>` を起点に作成する — fetch は remote-tracking ref のみ更新し local ブランチは更新しないため、local 経由で切ると stale なまま気づかず作業してしまう
     - **既存ブランチ（前セッションから継続する worktree 等）で作業を再開する場合**、`git log --oneline HEAD..origin/<base>` で base が先行していないか確認し、先行していれば rebase してから続行する。stale なまま進めると無関係な PR diff（他 PR で先行 merge された変更の revert に見える差分）が混入する。**再開時に限らずサイクルの途中でも起こる** — ゲート集約チェッカーやツールが内部で `git fetch` を実行すると、着手時は最新だった base がその場で先行しうる。
差分の混入だけが害ではない。
遅れたツリーから読んだコードは現行の規約の見本として働くため、既に retire された書き方をそこから新規コードへ写してしまう。
判定を読むためだけでなく、実装の前提を作るためにも、進めてから読む。
**この転写がツリーの外へ出た分は rebase では戻らない。** 遅れに気付くまでの窓の中で起票した作業項目・投稿したコメント・書いた PR 本文は、ツリーを直しても旧規約を抱えたまま残り、以降の検査はいずれもブランチのツリーしか見ないため誰も指さない。rebase の直後に、その窓の間の外向き操作を数え、取り込んだコミットが規約文書を触っていればそれらの本文を読み直す。窓が空だったなら1行そう記録する
     - **自分の変更を確認する差分は三点（`origin/<base>...HEAD`）で取る。** 二点（`origin/<base>..HEAD`）は base 側の先行分も差分に含めるため、他者が追加したファイルが自分のブランチによる削除として現れる。上の遅れが生じている間、二点で見た差分は「身に覚えのない大量削除」の形で出るので、削除を疑う前に差分の取り方を疑う
     - **同一セッションで続けてサイクルを回す場合も、着手時に `origin/<base>` から新しいブランチを切る。** 前サイクルのブランチに続けてコミットすると、前サイクルの差分が次サイクルの PR に混入する。前サイクルの PR が未マージであれば必ずこの形になる。検出は着手時に `git log --oneline origin/<base>..HEAD` が空であることの確認、または終端ゲートのコミット数が想定と合っているかの照合で行う（コミット数はサイクル完了時に初めて見るため、混入に気付くのは PR 作成後になりやすい）
     - **CI やツールが自動生成した PR が open のままであれば、新規作業より先にマージを確認する** — open のまま作業を始めると選択判断が stale な状態に基づく（どのような PR が自動生成されるかはリポ固有 — companion の roadmap.md に記載する）
     - `.pfdsl/roadmap.pfdsl` の着手可能プロセスを列挙する。`pfdsl status ready <roadmap.pfdsl> --best --json` で、入力 artifact が全て done のプロセス一覧と `--best` 推薦（合流点を解放するもの＝後続プロセスの最後の未完入力になっているもの）が JSON で得られる。着手可能集合が薄く「何が止めているか」を知りたい場合は `status blocked <roadmap.pfdsl>` で各未着手プロセスの未達入力 artifact を一覧できる（`graph stats` の fan-out と併せればボトルネックの優先度づけもできる）
   - **サイクルの範囲は、選んだ作業項目の設計が確定するまで確定しない。** 複数の作業項目を一度に指定されたとき、着手前の見た目の小ささで1サイクルに畳まない — 設計対話で方針が決まった時点で規模と種類が変わることがあり、そこで初めて別クラスの変更だと分かる。畳んだまま進めると、性質の違う変更が1つの差分に混ざってレビューの信号が埋もれ、片方が他方の前提を動かす（検査を厳しくする変更を同じブランチに入れると、以降のコミットが全てその厳しさを前提にする）。設計確定の直後に範囲を見直し、分けるなら分ける。
   - ユーザー指定があればそれを、なければ `best` の推薦を優先して1つ選ぶ。roadmap 非管理の作業項目（exempt 等）を番号指定された場合も本手順で処理する — ready 列挙に出ないことは cycle を通さない理由にならない（プリフライト・終端ゲート・retro は変更内容と独立に有効）。**ユーザー指定で入力 artifact が done でないプロセスを選んだ場合、「前提条件未達で着手する」とその理由を記録してから実行する**
   - 選択後、そのプロセスの issue 本文とコメント（一次情報。`gh issue view` はデフォルトで本文のみ、`--comments` はコメントのみを返す — `--json body,comments` で本文とコメントを両取得する）を読む。判定は fail-close で、着手前の設計選択記録（本文・コメントから機械的に同定できる記録）が見つからない限りすべて設計対話が必要と扱う — 該当するのは「design TBD」「設計未確定」等の設計未合意フレーズがヒットした場合、候補が2件以上列挙されているのに記録が無い場合、候補列挙構造自体を検出できなかった場合の3ケースで、いずれでも実装に進まず設計対話を行って方針を確定させる（列挙未検出を対話省略可の既定にすると検出漏れが素通りするため、既定を対話要求側に倒してある）。**確定の証拠はこの記録の実在のみとする** — 「本命はこちら」「〜が安全」「順序を示唆している」等のヘッジ語は確定の証拠にならない。この判定は機械化されており、companion が指すプリフライト集約スクリプトが対象 issue について報告する（記録の投稿先・時点照合の詳細はバックエンドの L3 reference が定義する）。設計確定がコメントとして事後投稿されていることがある — 本文のみで判断し着手すると見落とす。逆に、設計を記した本文・コメントが起票後にマージされた依存や仕様・決定記録の更新で陳腐化していることもある — issue が関連作業より前に書かれている場合、設計メモを鵜呑みにせず現行のコード・仕様・決定記録と突き合わせてから実装する（メモは一次情報だが最新とは限らない）
   - **適用点1 — 作業項目が列挙する案の集合を、設計空間とみなさない。** 起票者が挙げた案は入力の一部であり、網羅性は保証されていない。設計を確定させる前に次を行う。
     1. **前提を1文で書く。** 書式は「本案は〈○○という状態が存在し続けること〉を前提にする」。列挙された全案が共有している前提を書く（案が1つしかない場合はその案の前提を書く）。この書式に嵌らない場合、案が複数ある意味を説明できていないので書き直す。
     2. **その前提を否定した案を1つ作り、同じ粒度で集合に加える。** 起票者が挙げていなくても作る。**作った否定案が列挙済みの案のいずれかと一致したら、集合の外へ出られたことの証拠にはならない** — 否定したのが全案の共有前提でなく採用しかけていた1案の前提だった場合と、起票者の列挙がもともと網羅的だった場合の両方がこの形になる。列挙と読み比べて一致に気付いたら、どちらなのかを1行で述べる。**後者だと述べる場合は、もう一段上の前提を否定した案も既に列挙内にあることを示す。示せなければ前者として扱い、もう一段上の前提へ遡ってやり直す** — 網羅性は機械照合できない側の性質なので、自己申告だけで免除にすると、遡り直しを避けたい回が必ず後者を名乗る。記録の形（行頭 `否定案:` の有無）からはこの一致は見えないので、機械照合は通ってしまう。
     3. 否定案を却下する場合、却下理由を外部制約か所有者に帰着させる。**「手間がかかる」「大がかり」「今回のスコープ外」は却下理由として無効。** これらしか書けない場合、否定案は生存候補として残す。
     **理由が自分の変更の外にある機構の振る舞いを名指しする場合、その機構を実際に走らせた出力を理由と一緒に書く。** 関数名・JSDoc・コメントは「何をするつもりか」を述べる器であって「何を返すか」ではないので、それらを読んだだけでは確かめたことにならない。走らせられない機構なら、その振る舞いを決めている呼び出し側の分岐を引用する。どちらも書けない理由は成立していない — 理由の真偽を確かめる材料はどのゲートの入力にも入っておらず、記録は必須行頭も時点照合もテストも通ったまま誤った理由を3箇所（記録・実装のコメント・PR 本文）へ同時に定着させる。
     **名指す機構が却下する案そのものの実装である場合、走らせる対象も引用する呼び出し側も存在しない。** 却下した以上その実装は誰も書かないため、理由が偽でも反証の機会が来ない。この形に限り、走らせる代わりに**両案が取り違える入力を1つ構成する** — 一方だけが捕まえる入力を実際に書いて、両案に当てる。構成できたなら一方が他方を包含するという主張は偽であり、理由を「両案は別の経路を塞ぐ」へ書き換えたうえで、採用案が塞がない経路を成果物に明示する。構成しようとして書けないことを確かめた場合に限り、包含を主張してよい。**包含の主張は却下理由の中で最も検査に掛からない形である** — 採用案が現に動いていることは、それが他案の守備範囲を覆っていることの証拠にならない。
     対話を省略してよいのは、上記を経てなお選択が1案に絞られる場合のみ。ユーザーに選択肢を提示する場合、承認が担保するのは提示集合の内部での選好順位だけであり、集合の網羅性ではない。提示時に前提の1文を併記し、ユーザーが案でなく前提を却下できるようにする。
     **記録先**: 前提の1文・否定案・却下理由は、そのサイクルの作業記録（PR 本文・作業項目のコメント等、後から読み返せる場所）に残す。頭の中だけで済ませない — 残さないと、後から「前提を疑ったか」を第三者が判定できず、原則が効いているかの点検自体ができなくなる。**記録は着手前に投稿する** — 実装を終えてから書いた記録は、選択を導いた形跡ではなく事後の辻褄合わせであり、外形上は区別がつかない。区別は投稿時点と初コミット時点の前後で機械照合する（判定は終端ゲートの担当。記録先がリポ内ファイルであるバックエンドでは「投稿」がコミットになるため前後をコミット順で見る — 具体はバックエンドの L3 reference が定義する）。**記録には行頭 `前提:` / `否定案:` / `却下理由:` の3行を含め、列挙された各案の処分（採用・却下・保留）を明示する** — 処分されずに残った案は、却下理由テストの対象外に逃げた案である。
   - **適用点2 — 既存の不整合・重複・drift・手作業の機械化を目的とする作業では、着手前に次も確認する。**
     - **導入する新概念を列挙する。** 規則・状態・例外・分岐・向き・停止条件を数える。既存の慣行に対する例外は必ず含める。
     - **同じ形の構造がほかに何個あり、今回のスコープは何個かを数える。** スコープ外に同型が残る場合、それらが使っている機構を1語ずつ書き出す。**数える単位は、対策が作用する単位に合わせる。** 対策が出力単位で効くなら同型も出力単位で数える。スクリプト・ファイル・コンポーネントなど数えやすい単位で代用すると、1単位の内部に同型が複数あってもまとめて1と数えてしまい、スコープ外の残存を過小に見積もる。この誤りは「同型は残らない」という結論の形で出るため、結論だけを見ても検出できない。
     - 今回の案の機構がその語彙に無ければ、**「なぜ今回だけ既存機構が使えないのか」を1文で書く。** その1文に現れる性質を、制約でなく設計変数として扱う案を1つ作る。
     - 新概念ゼロを主張する場合、流用する既存機構の作用域を**実測で**確認した旨を1行添える。名前が示唆する範囲を信じない。**この実測は案をユーザーへ提示する前に済ませる。** 提示は選択を確定させる行為なので、提示の後で実測して前提が崩れれば、確定した決定を差し戻すことになる。既存機構への委譲は「その機構が現に何を拾っているか」で成否が決まり、規約や README が述べる範囲とは別物である — 委譲先を実データに当てて、いま拾えているものが拾えなくなる件数を数えてから提示する。適用点1 が記録の時点を着手前に固定しているのと同じ理由で、この実測にも時点がある。
**この実測は、既存機構を受け入れ基準として名指しするときにも要る。** 案の一部として流用する場合だけでなく、「この検査が緑なら目的の性質は保たれている」と宣言する場合が同じ形であり、こちらのほうが誤りが露見しにくい — 流用した機構が拾い漏らせば実装が壊れて見えるが、受け入れ基準が性質を見ていない場合は緑が返るだけで、壊れたことは出力のどこにも現れない。判定したい性質を1つ挙げ、その機構の入力にその性質が入っているかを、機構を実際に走らせた出力の上で確かめる。実装を委譲する回はこの確認を委譲先に任せられない — 委譲先は与えられた基準が緑になったことしか見えず、基準が見ていない範囲の食い違いを正常な完了と区別できない。
     判定物は新概念の数ではなく、この1文の質である。数が多い案を採ってもよいが、その場合は理由を書く。「もう実装したから」は理由にならない。概念数は生成器の内部へ押し込めば操作できるため、数そのものを勝敗判定に使わない。
2. **実行**: 作業項目の一次情報は roadmap.md が指すバックエンド。ブランチを切って作業する（main 直コミットしない）。`.pfdsl/runtime-pipeline.pfdsl` が存在する場合は着手前に変換境界を確認し、実装スコープが境界を越えないか確かめる。PFD の読み書きは pfdsl スキルの品質ガイドに従う。ビルド・生成・全量 check 系のコマンドは出力が数百行に及ぶことがある — 結果確認は `git status --short <対象パス>` / `git diff --stat` で変更有無を先に見る（詳細ログが要る場合のみファイルにリダイレクトして絞る）。**その出力が、いま実装しているツリーのものかを毎回確かめる。** worktree で作業していても、実行環境がコマンドの作業ディレクトリをセッション既定の場所へ戻すことがあり、そうなるとビルドもテストも別ツリー（多くの場合 base ブランチ）で走る。そこは変更前の状態なので緑になり、緑は「自分の変更が通った」証拠として読まれる — 実際にはこのサイクルの差分は一度も検査されていない。実測すべきは出力でなく実行場所で、コマンドの冒頭に `pwd` を置くか、ディレクトリ変更を別の呼び出しに分けて確定させてから測る（同じ理由で、`cd <dir> && <cmd>` の形はツール呼び出し前に発火する検査の目には `cd` 前のディレクトリしか見えない）。**この確認は1回では持続しない** — 戻りはサイクルの途中で起きるので、前の呼び出しで確かめた実行場所は次の呼び出しの根拠にならない。測るたびに確かめるか、そもそも対象ツリーの絶対パスを毎回書く。戻った状態は緑としてだけでなく「自分の変更が消えた」形でも出る（テスト件数が減る・作業ツリーが clean に見える・変更したはずのファイルが変更前の内容を返す）ため、消失を疑う前に実行場所を疑う。**GUI・エディタ拡張等の UI 変更は、ビルド後にユーザーと実際に操作して動作確認する。verify が BLOCKED になった場合も「確認手順をユーザーに渡す」で終わらず、ユーザーの確認結果を受け取るまで完了とみなさない。**
**症状の指標の baseline は着手時に取る。** 手順3 はその指標を変更前後で測ることを求めるが、実行時のレイテンシや自分の diff が既に書き換えた出現件数のように、着手後は遡って測れない指標がある。
`git show origin/<base>:<path>` や `git grep <pattern> origin/<base>` で事後にも取れる種類なら、着手時に測るのは省いてよい。
**そのサイクルで新設した agent が同じセッションから起動できるかは、確かめるまで分からない。** harness が定義の追加を検出して即座に使える場合と、セッションを開き直すまで見えない場合があり、どちらになるかは追加のしかた（既存のディレクトリへ足したか、ディレクトリごと新設したか）や起動時の設定で変わる。
**「できない」を前提に検証を次セッションへ送る前に、実際に1回呼んでみる** — 呼べないことを前提にすると、呼べる回でも検証が先送りされ、そのサイクルは自分の成果物を一度も動かさずに閉じる。
呼べなかった場合は、壊した状態を作って呼び報告を生ログと照合する型の受け入れ基準はそのサイクル内では満たせない — 検証を次セッションへ渡し、未了である旨を作業記録に明示して閉じる。
別 agent に同じ指示を与えて代用しない。検証対象は agent 定義そのものであり、別の定義の挙動はその代理にならない。
**渡す検証手順には、壊れたことの確認を手順そのものに含める。** 作業ツリーの差分を前提にする壊し方（`git stash push -- <file>` 等）は、その差分をコミットした後は空振りし、以降の検査は健全なツリーに対して走って緑を返す。
空振りは失敗でなく緑として出るため、確認を挟まない限り検証者からは成功と区別できない。
   - **このサイクルで最初の成果物を書く前に、`phase: pre-artifact` を宣言する監査パターンを読み直す。** 参照点は3つあり、到達範囲が違う — どれも他の2つを代替しない。置く前に到達範囲を数えること自体がこの手当ての本体であり、参照点の個数ではない。
     - P1 プリフライトの一覧印字（手順1の集約スクリプト）: 時点としてはこのサイクルの全成果物に間に合うが、着手前に一度きりで、書く瞬間から最も遠い。
     - P2 手順3 のチェックリスト項目（PR 本文を書く前）: PR 本文・issue コメント・それ以降に書くものにだけ間に合う。その時点で既に書き終わっているコード・コメント・テスト・`.pfdsl`・コミットメッセージには間に合わない。
     - P3 ここ（実装成果物を書く直前）: P1 と P2 の間に落ちる実装成果物を受け持つ。
     **参照点を足しても「印字されたことと読まれたこと」の差は消えない。** 差を消せるのは書く瞬間に発火する機構（該当パスへの書き込みを検出する hook）だけで、それはリポ固有のため本スキルは配布しない — 置き場は companion に書く。機構を持たないリポではこの参照点が最後の手当てになる。
     **到達範囲は成果物の種類だけでなく、それを書く主体でも切れる。** 実装を委譲する回の書き手は委譲先であり、上の3点はいずれも呼び出し元の工程に置かれている — P3 を自分で読んでも、コードを書くのは読んでいない主体になる。委譲する回は、読み直しの結果をブリーフへ書き写すか、委譲先自身が引ける形にする。機構で補う場合、その機構が「1回だけ」を何の単位で数えているかを確かめる — 呼び出し元と委譲先が同じ単位に畳まれていると、先に書いたほうが発火を使い切り、もう一方は何も受け取らない。
   - **適用点3 — 実装を別エージェント・別セッションへ渡す場合、前提の1文・却下した案とその理由・新概念の列挙、の3点をブリーフに含める。** 差し戻し条件を列挙型で明記する。列挙に無い概念が実装に必要になった場合、前提が事実でないと判明した場合、却下理由に事実誤認があった場合、**仕様が作業項目の目的に反する例外を含んでいる場合**（設計者が書いた仕様そのものの誤りは、実装者が忠実であるほど検出されない）は、実装を止めて設計者へ返す。**無条件の「決定済み・再設計禁止」は書かない。** 凍結してよいのは実装詳細であり、前提ではない。実装者に自由な代案探索をさせることは要求しない（二重設計になりコストが合わない） — 差し戻し条件を列挙型に限定することで churn を抑えつつ、最後の検出機会だけを開けておく。委譲先が留保作業（push・PR 作成・issue 操作）を実行していないかの戻り時照合は本原則の管轄外であり、委譲の範囲制御として次項で別に扱う。
     **生成物が適合すべき既存構造は、実物から読んで入力に明示する。** 出力が既存の構造（設定ファイルのキー・仕様の節番号・データの形）へ適合しなければならない委譲では、その構造を委譲先に読ませるか、抽出した現物をブリーフへ書く。渡さないと委譲先は存在しない構造を捏造し、戻り後のレビューでしか検出できない — 入力として渡せば捏造そのものが起きない。前提の1文と違いこれは実物を読む工程であり、構造の名前が示唆する形からの推測では代用できない。
   - **委譲先の外向き操作の制御 — 3層で機構化する。** 実装を委譲するとき、push・PR 作成・issue 操作は呼び出し元が持つ。ブリーフに「push するな」と明示しても破られることが実測されているため、指示でなく機構で制御する（同一サイクルで範囲指定が2回破られ、2回目は明示的な禁止に反して PR が作成された事例がある）。
     1. **agent の選択。** 外向きツール面（GitHub 連携等）を `tools:` に持たない実装専用 agent を使う。全ツールを持つ汎用 agent は実装委譲に使わない。本スキルに同梱の `pfd-implementer` がこれに当たる（worktree 作成から PR 作成までを一気通貫でやらせる場合は、その範囲を持つ別の agent を使う）。
        委譲先のセッションは呼び出し元のその時点の作業ディレクトリを継ぐ。
        別のツリーへ移動した直後に委譲すると、委譲先は対象ツリーへ書けずに停止するか、書き込みガードが無ければ誤ったツリーへ書く。
        委譲前に作業ディレクトリを確認し、ブリーフには対象ツリーの絶対パスを書く。
        委譲するフローが worktree の作成を含む場合、「既存の分離ワークスペースがあれば再利用する」型の手順を素通しにしない。
        委譲先は呼び出し元が使用中の worktree の中で起動されることがあり、その場合その手順は共有中の worktree を既存の分離ワークスペースと誤認識して乗っ取る。
        agent 定義側に、その再利用判定を迂回して常に新規 worktree を作る旨を明記する。
     2. **PreToolUse ガード。** allowlist 外の subagent による `git push` と変更系コマンドを、ツール呼び出しの時点で拒否する。subagent の hook payload には `agent_id` が入り呼び出し元の payload には入らない — この差が判別子になる。**agent 名を運ぶフィールド（`agent_type` 等）を判別子に流用しないこと** — harness の契約はそれを「subagent 内で発火したとき」に加えて「セッションが `--agent` を使うとき」にも入れると定めており、後者に当たる呼び出し元が subagent と誤判定されて自分の push を止められる。`agent_id` の側にこの追加条件は無い。`session_id` / `transcript_path` は親子で共通のため使えない。デフォルト拒否にすれば、agent を新設しても黙って push 権を得ることはない。プロジェクト全体に効く permission deny を使わないのは、呼び出し元と一気通貫型 agent まで巻き込むためである。実装はリポ固有のため本スキルは配布しない — 置き場は companion に書く。
     3. **戻り時の検出。** 委譲から戻ったら `git log origin/<branch>..HEAD` と open PR 一覧を確認する。上2層をすり抜ける経路（生 `curl`・スクリプト経由の間接実行）は塞げないため、この層が最後の網になる。将来ツール面が増えても効き続けるのはここだけである。
3. **反映 — 終端ゲート（全項目を明示的に確認する。「該当なし」も判断として確認の対象に入る）**:
   - **記録を要求するのは行頭に `**記録先: …**` または `**PR 作成後**` を持つ項目だけで、印の無い項目は確認で足りる。** 線引きは行頭の印だけで決まる — 本文が記録先らしき語に触れていても印が無ければ確認で足り、逆に印のある項目は本文を読まずに記録要求と分かる。項目ごとに本文を読んで記録先の有無を判定する形にしないのは、その照合コストが読み手側にしか現れず、迷った回と迷わなかった回が記録から区別できないためである。記録先を持たない項目の確認結果には読み手がいない — 集約チェッカーが読むのはチェックリストの行そのものであって確認結果ではなく、人間レビューが読むのは差分と PR 本文である。読まれない書き込み先を全項目に用意しても書き捨てになる。判別せずに「該当なし」と書いた回の検出は、下の「機械が守らない範囲」が人間レビューへ割り当てている
   - **companion がゲート集約チェッカーを指す場合**、まずそれを実行する。PASS/FAIL 判定が出た項目はその結果に従い、`MANUAL:` 表示・チェッカーが存在しない項目のみ以下を個別に確認する。**companion に到達できない場合は「チェッカーなし」へ倒し、以下を全項目個別に確認する。** companion は採用リポの `.pfdsl/` 配下に置かれた sibling の `.md` なので、そこが見えない読み手（配布バンドルだけを渡された等）は指しているかどうかを確かめる手段を持たない — その状態がこの既定に当たる。倒す向きが非対称なのは、冗長な個別確認は結論を変えないが、PASS を仮定して飛ばした項目は誰も見ないためである

**ただし担保の中核が委譲でしか作れない観点は、重さを落とす対象に入らない。** 独立性（解答を知らない主体が解くこと）や多重性のように、別主体を立てることでしか成立しない性質を自分で回すのは、軽量な実施ではなく不実施である。
その委譲を起動できない回は、記録して閉じずにユーザーへ返す。
**起動できないというその判断も、指示の文面を確かめてから下す** — 「禁止されている」と「まだ求められていない」は実行主体からは同じ形に見え、後者を前者と読めば作業が減る側に倒れる。根拠として引ける文面が無いなら、確かめていない。
**起動可否は harness と plugin の版に依存することがあり、規約に書かれた「起動できない」はそれを書いた時点の観測でしかない。** 過去にそう記録された手段でも、その記録に従う前にその回の実体（コマンド定義の起動可否フィールド）を確認する。逆向きの陳腐化（起動できるようになったのに規約が禁止のまま残る）は、規約を満たせない形ではなく選択肢を1つ失ったまま気付かない形で出るため、失敗としては観測されない
   - [ ] レビューの menu を「どの手段を選ぶか」の優先順ではなく「どの観点が担保されたか」で組んだ。手段を1つに固定すると、その手段が探さない型の欠陥だけが常に無担当になる — 簡素化のみを見るレビューが findings なしを返した回に、別観点のレビューが採用案の成立根拠の不備と JSDoc の事実誤認を検出した実測がある。観点ごとにブリーフ要件を課し、その観点をどの手段で満たすかは companion が定める
   - [ ] finding には具体的な failure scenario（入力・状態 → 誤出力・誤誘導）を伴わせ、構成できない指摘は報告しない。敵対的な指示は「何か見つけねば」という圧で false positive を量産するため、scenario を構成できることを報告の条件にする
   - [ ] **記録先: PR 本文**: 発火した観点を軽くしてよいが、消してはならない。 観点の発火条件（何を担保するか）と、その観点にかける重さ（別主体へ委譲するか自分で読むか）は別軸である。規約が両方を1つの文で決めていると、重さを落とす判断が観点そのものを消す判断に化ける — 「小さい回は軽くてよい」と「この条件を満たす回は対象」が同時に成立する回に優先関係が書かれていないと、実行主体は軽いほうへ畳んで観点を1つも回さずに終わり、その事実はどこにも残らない。重さを落とした回は、落とした観点の名前と落とした理由を成果物（PR 本文等）へ書く — 名前を書かせない限り、軽く回した回と一度も回さなかった回は記録から区別できない
   - [ ] 監査パターンのカタログが「対策は成果物を書く前に効く」と宣言しているものを、PR 本文を書く前に読み直した（宣言の書式と、それを列挙する手段は companion が定める。プリフライトの集約スクリプトを持つリポではその出力に並ぶ）— retro でカタログを引くのはこの後になるため、成果物を書く前にしか効かない対策はここでしか間に合わない。カタログがこの宣言を持たないリポでは該当なし
   - [ ] 変更束を PR にまとめた（PR 作成後にローカルで追加コミットした場合、push し忘れていないか `git log origin/<branch>..<branch>` で確認する — CI は push 済みの内容にしか反応しない）
   - [ ] デフォルトブランチへ直接マージする PR に issue を閉じるキーワード（`Closes #<issue番号>` 等、バックエンドの L3 reference が定義する書式）を含めた（feature branch への中間 PR では使わない）。閉じる issue が無い場合は、バックエンドの L3 reference が定義する免除宣言（`no-issue: <理由>` 等）を代わりに含めた
   - [ ] **PR 作成後**: 上で測った症状の指標の数値を PR 本文に書いた（測れなかった場合はその理由と代理指標を書いた）
   - [ ] **PR 作成後**: 生成元と生成物を同一コミットに入れたために論理単位が割れなかった場合、割れない理由を PR 本文に書いた
   - [ ] **PR 作成後**: サイクルの途中で前提が変わった箇所を、PR 本文（最初に読まれる正本）にも書き戻した。訂正をコメント等の別の器へ書いた回は、その場で正本の該当箇所も直す — 正本だけを読む人は訂正の存在を知る手がかりを持たないため、両方を読んだ者にしか食い違いが見えない。サイクルの終わりにまとめて見直す形にしない（その時点では、どの文がいつ書かれたかがもう分からない）。**この項目だけは実施の時点がここではない** — 実施は訂正を書いた各時点であり、ここで確認するのはその実施の有無である。ここへ来て初めて全訂正を見直す運用にすると、項目文自身が禁じている形になる
   - 上3項目がここに置かれているのは、書き込み先が PR 本文だからである。**書いた内容そのもの**（指標の数値・割れない理由・書き戻した訂正）を読むのは PR をレビューする人間だけで、それを判定に使う機械は無い — したがって PR 本文が置き場として適格であり、誤っていたのは確認を求める時点のほうだった（チェックリストの上の方に置くと、書き込み先がまだ存在しない時点で確認を求めることになる）。並べ替えないこと。**チェックリストの行そのものは機械が読む** — ゲート集約チェッカーを持つリポでは、この行が MANUAL 一覧へ写されるので、行頭の `**PR 作成後**` を段の区切りとして扱わせる（区切りを持たないと、PR がまだ無い時点で一覧の全項目が同時に提示され、順序の意味が消える）。`**記録先: …**` は時点でなく記録先を宣言する別の印で、段の区切りには使わない — 印を2種に分けているのは、記録先が PR 本文でない項目（ユーザーへの報告等）が PR 作成後の段へ紛れ込まないようにするためである
4. **報告**: 完了したプロセス、それにより解放された後続プロセス、更新後の着手可能集合。特定 status の全体像（例: 残 wip 一覧）が要る場合は都度 `status list <roadmap.pfdsl> --status wip,waiting --json` 等で機械的に絞り込む — 全文 Read や個別 `meta get` の積み上げに頼らない
5. **retro**: `/pfd-cycle` コマンド経由の場合、プロトコル7の (a)(b) 両条件を確認する（定義は SKILL.md 本文が一次情報 — ここには複製しない）。このサイクル手順自体に最終ステップとして組み込み、報告を出して終わりにしない。**バックストップ**（(a) について）: plugin を導入したリポでは、`roadmap.pfdsl` に `status: done` を追加するコミットの後、同梱の PostToolUse hook（`hooks/`、`hooks/hooks.json` で配線済み）が advisory reminder を返す（非ブロッキング）。セッション記憶が抜けても done 付与コミットの Bash tool result 経由で気付ける。(b) にはバックストップがない — セッション記憶のみに依存する既知の弱点

## 機械が守らない範囲

適用点1〜3 を支える層は4つある — タイミング照合（記録の投稿・編集それぞれが着手前かを機械照合する。具体の証拠はバックエンドの L3 reference が定義する）、編集検出（タイミング照合と同じ機構で着手後の改変を検出する）、3層ガード（委譲先の外向き操作を止める。定義は手順2「委譲先の外向き操作の制御」）、人間レビュー+マージ（最終の網。機械化しない）。
4層が立つ証拠のうち、実行主体が偽造できないのはバックエンドが持つ記録・権限機構・人間の判断そのものである。
**ただしタイミング照合はこれで閉じていない** — 比較の2入力のうち記録側（コメントの投稿時刻・編集時刻）はバックエンドが記録するが、コミット側は git の author date であり実行主体が設定できる（コミット時のオプション・環境変数・初コミットに届く rebase の3経路）。
author date を使うこと自体は選択の結果で、committer date は rebase のたびに全コミットが書き換わりサイクルの窓が消えるため使えない。
したがって時点の真正性は「機械が保証する」側ではなく、この非対称を承知したうえで人間が見る側に属する。
この4層が守らないものは4つ残る — 記録の内容が実質を伴うか、案の網羅性、実行主体が人間の判断を経たかどうか、そして時点の真正性である。
これらは機械照合できる証拠を持たないため、人間レビューが担う。

## 免除条項（比較対象生成の原則）

適用点1〜3 に共通の免除条項。

- 同型の先例が0件と確認できた場合は1行記録して免除する。
- 前提が他者所有・後方互換・法規等の外部制約に1行で帰着する場合、否定案の生成は免除し所有者名の記載のみでよい。
- 緊急修正は免除する。ただし事後に「前提を疑わずに入れた」ことを作業項目として残す。
