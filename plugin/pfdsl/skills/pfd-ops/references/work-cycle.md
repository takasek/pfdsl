# ワークサイクル（選択・実行・終端ゲート・報告）

## 運用契約

### 着手可能性と受け入れ

入力 artifact が全て done の process を着手可能とし、並列着手集合は `pfdsl status ready <roadmap.pfdsl> --best --json` で機械的に導出する。roadmap 全文の目視で代用せず、優先順位の議論より先に列挙する。作業項目に着手する回は、この判断より先に下の4手順へ入り、起動口にかかわらず手順1の一部として判断する。

新規作業は、成果物を生み他作業の着手をゲートする場合だけ依存グラフへ1チェーン追加する。他作業をゲートしないバグ修正、CI・build・tooling、図や文書の bookkeeping は載せない。backend 固有の分類は採用した L3 reference に従う。並列性・接点・合流点を確定し、方針の合否基準を下流作業なしで書けない相互依存は分割しない。

### 進捗と完了根拠

着手と同時に出力 artifact を todo から wip へ更新し、PR 作成や merge を待たない。作業完了時の status 更新は完了コミットと同時に行い、done の根拠が言えない場合は出力成果物の定義を疑う。criteria 未達を文言変更で done に帳尻合わせせず、wip を維持して未達部分を独立した後続作業へ切り出す。基準自体が原理的に達成不能と実測できた場合だけ、不能の証拠と元の意図を別手段で満たす代替基準を示し、人間の承認を得てから差し替える。

### 成果物の門番

終端監査は消費者側と後続側の両向きに行う。消費者を書けない成果物は作らない。終端を名乗れるのは公開物、外部提出物、運用される成果物などの真の納品物だけで、仕様・設計・計画・提案などの手段成果物には、それを消費する後続 process を todo でも登録する。終端は `pfdsl graph io <file> --json` で機械列挙し、`terminals` と `externalTerminals` の両方を見る。

版 artifact を起こす契機は2つに限る。(1) その版が後続 process をゲートする、(2) その版自体が納品物で、管理下の実装 artifact を消費する publish process の出力である。どちらにも当たらない版は実体が公開されていても起こさない。手段成果物の版は (1) にしか該当せず、版が上がったこと自体を理由にしない。`status blocked` と `status ready` で版待ちの process の実在を測る。図の版チェーンが実体の現行版より古いこと自体は欠陥でなく、`revises:` は起こした版同士を繋ぐため版番号が飛んでも線形性違反ではない。既存図に (1)(2) のどちらでもない版が残る場合は後続側の門番違反として扱う。版 criteria は、公開対象の版の状態を公開後に再確認できる形で書く。

新しい種類の成果物は `.pfdsl/workflow.pfdsl` に producer と consumer を登録してから作る。ただし workflow が未採用または scaffold なら登録は該当なしで、対象操作に対応する採用済み PFD で消費者を示せばよい。roadmap が実データでも workflow が scaffold なら workflow への登録は非適用なので、登録先を探す前に対象 PFD の採用状態を確かめる。

hook、guard、agent、script 等の道具は、図の process がその道具を要求するか、図の artifact を生産または消費する場合だけ参加者として登録する。個別の事故への対処やリポ開発上の都合で追加しただけの道具は、実在しても参加者ではない。生成・外化 process が同種の道具をまとめて出力すること、配布物への包含、規約からの参照は参加者性の代理にすぎず、基準にしない。道具の種類ごとに別基準を立てない。

変換 component の追加・変更・削除、成果物の格納先・生成方式・配送経路の変更では、その変換をモデル化する採用済み PFD の description、criteria、edge、location を同じ変更束で更新する。`pipeline.pfdsl` が存在しないだけで該当なしにせず、`workflow.pfdsl` など別の PFD が同じ変換を表現していないか横断確認する。

### 知見と機械化

実践・review の知見のうち、構造的事実は対応する PFD の node、edge、description、criteria に、グラフで運べない手続き散文は sibling companion に置く。両方に該当する変更は両方を更新する。
再発防止の反映先・機械化の判定・hook の決定軸は、リポ固有の規律として `.pfdsl/bindings/pfd-ops.md` 等の binding が持つ。

### 定期監査

`/pfd-cycle` では、done 付与時の pfd-retro 自動実行と、サイクル終結時の能動的な締め確認を独立に適用する。前者は対象 process の出力 artifact に done を付けた時点で実行し、直接 pfd-ops を呼んで done event がない回には適用しない。後者は done の有無にかかわらず必須で、一方の非該当は他方を免除しない。findings は上の「知見と機械化」に従って振り分ける。

## 前提条件

`.pfdsl/roadmap.pfdsl` が存在しない場合、本ワークサイクルは非適用として呼び出し元の通常フローへ戻る。roadmap が scaffold のままかは次のコマンドで判定し、該当する場合も本ワークサイクルは非適用とする。

```bash
grep -q 'に置き換える)' .pfdsl/roadmap.pfdsl && echo "scaffold のまま"
```

bare GitHub Issue 番号や一般的な issue 作業の依頼だけを根拠に PFD の初期構築を提案したり、作業を終了したりしない。ユーザーが明示的に PFD の導入または既存 scaffold の実データ化を依頼した場合に限り、pfd-ecosystem スキル（`/pfd-init`）を案内する。

作業項目に着手する回はこの4手順に従う。起動口は問わない。
コンテキストのないセッションでも1サイクル回せる自己完結手順（`.pfdsl/` 配下の各ファイルと sibling companion を読めば動ける）。範囲規則: **1サイクル = 1プロセス**。大きすぎる場合は粒度ルールで分割を `.pfdsl/roadmap.pfdsl` に反映してから着手する。PFD の読み書きが生じたら `pfdsl` スキルを invoke する。
binding（`.pfdsl/bindings/pfd-ops.md`）に「ワークサイクルの追加手順」節がある場合、手順 1〜3 の各段でその追加手順に従う。無ければ本文の手順だけで足りる。

1. **選択**:
   - `.pfdsl/roadmap.pfdsl` の着手可能プロセスを列挙する。`pfdsl status ready <roadmap.pfdsl> --best --json` で、入力 artifact が全て done のプロセス一覧と `--best` 推薦（合流点を解放するもの＝後続プロセスの最後の未完入力になっているもの）が JSON で得られる。着手可能集合が薄く「何が止めているか」を知りたい場合は `status blocked <roadmap.pfdsl>` で各未着手プロセスの未達入力 artifact を一覧できる（`graph stats` の fan-out と併せればボトルネックの優先度づけもできる）
   - ユーザー指定があればそれを、なければ `best` の推薦を優先して1つ選ぶ。roadmap 非管理の作業項目（exempt 等）を識別子で指定された場合も本手順で処理する — ready 列挙に出ないことは cycle を通さない理由にならない（プリフライト・終端ゲート・retro は変更内容と独立に有効）。**ユーザー指定で入力 artifact が done でないプロセスを選んだ場合、「前提条件未達で着手する」とその理由を記録してから実行する**
   - binding の追加手順（手順 1）があればここで従う。
2. **実行**: 作業項目の一次情報は roadmap.md が指すバックエンド。`.pfdsl/pipeline.pfdsl` が採用済み（scaffold のままでない）なら着手前に変換境界を確認し、実装スコープが境界を越えないか確かめる。scaffold のままなら該当なしとする — ファイルの実在と採用は別で、判定は上の「前提条件」と同じ scaffold 判定で行う。PFD の読み書きは pfdsl スキルの品質ガイドに従う。
   - binding の追加手順（手順 2）があればここで従う。
3. **反映 — 終端ゲート（全項目を明示的に確認する。「該当なし」も判断として確認の対象に入る）**:
   - **記録を要求するのは行頭に `**記録先: …**` または `**PR 作成後**` を持つ項目だけで、印の無い項目は確認で足りる。** 線引きは行頭の印だけで決まる — 本文が記録先らしき語に触れていても印が無ければ確認で足り、逆に印のある項目は本文を読まずに記録要求と分かる。項目ごとに本文を読んで記録先の有無を判定する形にしないのは、その照合コストが読み手側にしか現れず、迷った回と迷わなかった回が記録から区別できないためである。記録先を持たない項目の確認結果には読み手がいない — 人間レビューが読むのは差分と PR 本文であり、機械結果に含まれない判断は実行主体がこの正本の節を直接確認する。読まれない書き込み先を全項目に用意しても書き捨てになる。判別せずに「該当なし」と書いた回の検出は人間レビューが持つ — この配分を明文化した節を binding が持つ場合はそれに従う
   - **companion がゲート集約チェッカーを指す場合**、まずそれを実行する。PASS/FAIL 判定が出た項目はその結果に従い、それ以外はこの正本の節を直接読んで個別に確認する。集約チェッカーは本文を解析・再印字せず、PR 作成前にこの節を確認する案内と、PR 作成後に `PR 作成後` 項目を確認する案内だけを固定表示する。**companion に到達できない場合は「チェッカーなし」へ倒し、以下を全項目個別に確認する。** companion は採用リポの `.pfdsl/` 配下に置かれた sibling の `.md` なので、そこが見えない読み手（配布バンドルだけを渡された等）は指しているかどうかを確かめる手段を持たない — その状態がこの既定に当たる。倒す向きが非対称なのは、冗長な個別確認は結論を変えないが、PASS を仮定して飛ばした項目は誰も見ないためである
   - [ ] companion（roadmap.md 等）が定義するリポ固有の追加ゲート項目を確認した（**タイミング規約があれば以降の項目より優先**）
   - [ ] 出力 artifact の status を更新した（タイミングは companion の規約が最優先。無ければ上の運用契約のデフォルト — 着手時に wip・完了コミットと同時に done）
   - [ ] 知見を `.pfdsl/workflow.pfdsl` の sibling companion の振り分け手続きに従って振り分けた
   - [ ] 実行中に発見した新プロセス・成果物を `.pfdsl/roadmap.pfdsl` に追記した（消費者を明示できないものは作らない）
   - [ ] 変更した `.pfdsl` に対して `pfdsl graph io <file> --json` を実行し、`terminals`（消費者が疑わしい終端）と `externalTerminals`（`externalStakeholders` 宣言による終端 — 別枠に入る条件と見方は pfdsl スキルの「読解と点検」が一次情報）の両方を確認した。片方だけ見ると監査対象が丸ごと落ちる。今サイクルの出力 artifact が `terminals` に現れ、かつ手段（仕様・設計・計画・提案）なら、それを消費する後続プロセスがグラフに在るか確認した。無ければ todo プレースホルダで登録した（上の運用契約にある後続門番。真の納品物のみ終端を許す）。`externalTerminals` に現れる場合は、その宣言が妥当か（手段成果物に誤って `externalStakeholders` を付けていないか）を確認した。companion がゲート集約チェッカーを指す場合はその差分報告を使ってよい
   - [ ] 変換コンポーネントを追加・変更・削除した場合、または成果物の格納先・生成方式・配送経路を変えた場合、それをモデル化している採用済み PFD（`.pfdsl/pipeline.pfdsl` または `.pfdsl/workflow.pfdsl` の該当箇所）へ同一 PR で反映した（該当なしもここでの確認に含める。pipeline.pfdsl 未採用は自動的に N/A にならない — workflow.pfdsl 側を確認）。**「どの PFD もモデル化していない領域を触った」という N/A と、「見て判断した結果の」N/A は、どちらも同じ「該当なし」として記録されるため、記録からは区別できない** — 変更したパスが採用済み PFD の `location:` に載っているかを先に見て、どちらの N/A かを言えるようにする。
**その突合には process の `location:` も入れる** — 成果物の実体が外部（レジストリ・別リポ・外部サービス）にある場合、artifact の `location:` はその外部を指すため、生産・配送を実装しているファイルはどの artifact の `location:` にも載りえない。
artifact 側だけで突合すると、その実装を変えた回が「どの PFD もモデル化していない領域」の N/A として通過し、実際には description・criteria・location が揃って陳腐化する。companion がゲート集約チェッカーを指す場合はその突合材料を使ってよい。影響範囲の特定には `pfdsl graph impact <file> <id>`（下流の消費者全て）・`graph depends-on <file> <id>`（上流の生産者全て）が使える — 変更対象ノードを grep で手繰るより網羅的
   - [ ] 変更した全 .pfdsl が `check` を通過する
   - [ ] バックエンドの L3 が完了契約を定義する場合、その契約と終端ゲート証拠を満たした
   - binding の追加手順（手順 3）があればここで従う。
4. **報告**: 完了したプロセス、それにより解放された後続プロセス、更新後の着手可能集合。特定 status の全体像（例: 残 wip 一覧）が要る場合は都度 `status list <roadmap.pfdsl> --status wip,waiting --json` 等で機械的に絞り込む — 全文 Read や個別 `meta get` の積み上げに頼らない
5. **retro**: 上の「定期監査」に従い、done 付与時とサイクル終結時をそれぞれ確認する。報告を出して終わりにしない。hook の通知や事例の一覧を、この実行の代わりにしない。採用リポ独自の reminder があれば、その到達範囲は companion で確認する。
