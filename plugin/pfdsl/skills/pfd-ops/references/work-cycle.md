# ワークサイクル（選択・実行・終端ゲート・報告）

## 運用契約

### 着手可能性と受け入れ

入力 artifact が全て done の process を着手可能とし、並列着手集合は `pfdsl status ready <roadmap.pfdsl> --best --json` で機械的に導出する。roadmap 全文の目視で代用せず、優先順位の議論より先に列挙する。作業項目に着手する回は、この判断より先に下の4手順へ入り、起動口にかかわらず手順1の一部として判断する。

新規作業は、成果物を生み他作業の着手をゲートする場合だけ依存グラフへ1チェーン追加する。他作業をゲートしないバグ修正、CI・build・tooling、図や文書の bookkeeping は載せない。backend 固有の分類は採用した L3 reference に従う。並列性・接点・合流点を確定し、方針の合否基準を下流作業なしで書けない相互依存は分割しない。

### 進捗と完了根拠

着手と同時に出力 artifact を todo から wip へ更新し、PR 作成や merge を待たない。作業完了時の status 更新は完了コミットと同時に行い、done の根拠が言えない場合は出力成果物の定義を疑う。criteria 未達を文言変更で done に帳尻合わせせず、wip を維持して未達部分を独立した後続作業へ切り出す。基準自体が原理的に達成不能と実測できた場合だけ、不能の証拠と元の意図を別手段で満たす代替基準を示し、人間の承認を得てから差し替える。

### 成果物の門番

終端監査は消費者側と後続側の両向きに行う。消費者を書けない成果物は作らない。終端を名乗れるのは公開物、外部提出物、運用される成果物などの真の納品物だけで、仕様・設計・計画・提案などの手段成果物には、それを消費する後続 process を todo でも登録する。終端は `pfdsl graph io <file> --json` で機械列挙し、`terminals` と `externalTerminals` の両方を見る。

版 artifact を起こす契機は2つに限る。(1) その版が後続 process をゲートする、(2) その版自体が納品物で、管理下の実装 artifact を消費する publish process の出力である。どちらにも当たらない版は実体が公開されていても起こさない。手段成果物の版は (1) にしか該当せず、版が上がったこと自体を理由にしない。`status blocked` と `status ready` で版待ちの process の実在を測る。図の版チェーンが実体の現行版より古いこと自体は欠陥でなく、`revises:` は起こした版同士を繋ぐため版番号が飛んでも線形性違反ではない。既存図に (1)(2) のどちらでもない版が残る場合は後続側の門番違反として扱う。版 criteria は、公開対象の版の状態を公開後に再確認できる形で書く。

新しい種類の成果物は `.pfdsl/workflow.pfdsl` に producer と consumer を登録してから作る。ただし workflow が未採用または scaffold なら登録は該当なしで、対象操作に対応する採用済み PFD で消費者を示せばよい。roadmap が実データでも workflow が scaffold なら workflow への登録は非適用なので、登録先を探す前に対象 PFD の採用状態を確かめる。

hook、guard、agent、script 等の道具は、図の process がその道具を要求するか、図の artifact を生産または消費する場合だけ参加者として登録する。個別の事故への対処やリポ開発上の都合で追加しただけの道具は、実在しても参加者ではない。生成・外化 process が同種の道具をまとめて出力すること、配布物への包含、規約からの参照は参加者性の代理にすぎず、基準にしない。道具の種類ごとに別基準を立てない。

変換 component の追加・変更・削除、成果物の格納先・生成方式・配送経路の変更では、その変換をモデル化する採用済み PFD の description、criteria、edge、location を同じ変更束で更新する。`pipeline.pfdsl` が存在しないだけで該当なしにせず、`workflow.pfdsl` など別の PFD が同じ変換を表現していないか横断確認する。

### 知見と機械化

実践・review の知見のうち、構造的事実は対応する PFD の node、edge、description、criteria に、グラフで運べない手続き散文は sibling companion に置く。両方に該当する変更は両方を更新する。

再発防止は、問題が起きる操作の既存手順・必要な入力・道具・テストへ反映する。適用例と非適用例、確認済み結果を再利用できる条件、再確認を要する変更をその適用点で示す。事例集への追記を、その操作を変えた証拠にしない。
機械化するのは、入力や状態から実際に判定でき、既存検査と重複せず、実装・維持・誤発火の費用に見合う性質である。自然言語の意味や承認の実質をコマンド文字列から推測しない。機械化しない場合も、必要な時点の入力と検証を具体化する。観測・原因の仮説は既存の事例置き場へ、採用済みの規約は操作の手順へ置き、両者を混同しない。

hook の決定を選ぶ軸は害の発生点である。実行自体が害なら advisory は選ばない。対処法を message に書けば1回の retry で自己修復し、対処済みかを rule 側から判定できる場合は deny を使う。対処済みかが payload から見えず人間判断が必要な場合は ask を使い、deny による同じ retry の再拒否を避ける。結果の読み違いだけが害なら advisory を使える。event と channel の対応は harness の版で変わるため列挙せず、実装時に一次情報を確認する。

### 定期監査

`/pfd-cycle` では、done 付与時の pfd-retro 自動実行と、サイクル終結時の能動的な締め確認を独立に適用する。前者は対象 process の出力 artifact に done を付けた時点で実行し、直接 pfd-ops を呼んで done event がない回には適用しない。後者は done の有無にかかわらず必須で、一方の非該当は他方を免除しない。findings は上の「知見と機械化」に従って振り分ける。

## 前提条件

`.pfdsl/roadmap.pfdsl` が存在しない場合、本ワークサイクルは非適用として呼び出し元の通常フローへ戻る。roadmap が scaffold のままかは次のコマンドで判定し、該当する場合も本ワークサイクルは非適用とする。

```bash
grep -q 'に置き換える)' .pfdsl/roadmap.pfdsl && echo "scaffold のまま"
```

bare GitHub Issue 番号や一般的な issue 作業の依頼だけを根拠に PFD の初期構築を提案したり、作業を終了したりしない。ユーザーが明示的に PFD の導入または既存 scaffold の実データ化を依頼した場合に限り、pfd-ecosystem スキル（`/pfd-init`）を案内する。

作業項目に着手する回はこの4手順に従う。起動口は問わない。
コンテキストのないセッションでも1サイクル回せる自己完結手順（`.pfdsl/` 配下の各ファイルと sibling companion を読めば動ける）。範囲規則: **1サイクル = 1プロセス**。大きすぎる場合は粒度ルールで分割を `.pfdsl/roadmap.pfdsl` に反映してから着手する。PFD の読み書きが生じたら `pfdsl` スキルを invoke する。

**貫く原則: 比較対象を生成する。** コストは単独では評価できず、常に対案との差でしか評価できない。「立ち止まれ」「慎重に判断しろ」型の規則は原理的に効かない — 信号が既に見えているのに受容すべきコストとして分類される、というのが失敗の形だからである。以下の手順1・手順2 にある3つの適用点は独立した3規則ではなく、この1原則の適用点である（独立3規則にすると3つとも忘れられる）。比較対象生成を省略しない条件は末尾にまとめる。

1. **選択**:
   - **このサイクル用の worktree を作り、ブランチはその中に切る。既定であり、宣言も確認も要らない。** 同じ作業ツリーで別のセッションが同時に動くと、双方の未コミット変更が同じファイルに混ざって現れ、どちらが書いたかを git の状態から区別できない。ブランチの切り替えは相手の HEAD ごと動かすため、相手が読んでいるファイルの内容が黙って入れ替わる。どちらも「自分の変更だけを見ている」限り検出できない形で壊れる。現在の作業ツリーでそのまま進めてよいのは、ユーザーがそう指示した場合と、リポの構成上 worktree を作れない場合に限る。前セッションから継続する worktree があるならそれを使う（新規作成は不要）。worktree の置き場・命名・セットアップ（依存・ビルド生成物・hook はいずれも引き継がれない）は companion が定義する。
**共有ツリーで編集が消えた場合、探すときは `git stash list` を先に見る。** `git stash` は内部で reset を行うため reflog 上は `reset: moving to HEAD` として現れ、`git reset` と区別がつかない — reflog だけを見ると、他セッションの stash を自分の操作の痕跡と読み違える。
   - **companion（roadmap.md 等）がサイクル・プリフライトの集約スクリプトを指す場合**、`git fetch origin` の後に `origin/<base>` を起点としてこのサイクルのブランチを切り、**そのうえで**集約スクリプトを実行する。出力（fetch 実施有無・base への遅れ・open PR の一覧・着手可能プロセス一覧・best 推薦。集約スクリプトが追加で返す付随情報があればそれも従う対象に含む）に従う。**プリフライトは作業ツリー内のスクリプトなので、遅れたツリーではその古い版が走る** — 出力は「どの判定が存在するか」からして古い版のものになり、上流で追加された判定の不在が「走って異常なし」と区別できない。実際に起きた形は、スクリプトが印字したコマンド行に上流で足されたフラグが無く、そのコマンドをそのまま使った結果、そのフラグでしか有効にならない検査がサイクル全体で一度も走らなかった、というものである。集約スクリプトが base への遅れを検出して実行を拒否する場合はその指示に従い、ツリーを更新してから再実行する。**拒否は拒否する版へ更新されて初めて効く**ので、古い版のツリーでは自分で `git log --oneline HEAD..origin/<base>` を見る。指していない場合は以下を手動で行う。**以下3項目は「選択判断はすべて origin の現在状態を前提にする」という1原則の各論である** — fetch 漏れ・stale な base・競合しうる未統合の open PR は、いずれも選択判断の前提を確認する対象になる:
     - まず `git fetch origin` でリモートの最新状態を取得する。新規ブランチは `origin/<base>` を起点に作成する — fetch は remote-tracking ref のみ更新し local ブランチは更新しないため、local 経由で切ると stale なまま気づかず作業してしまう
     - **既存ブランチ（前セッションから継続する worktree 等）で作業を再開する場合**、`git log --oneline HEAD..origin/<base>` で base が先行していないか確認し、先行していれば rebase してから続行する。stale なまま進めると無関係な PR diff（他 PR で先行 merge された変更の revert に見える差分）が混入する。**再開時に限らずサイクルの途中でも起こる** — ゲート集約チェッカーやツールが内部で `git fetch` を実行すると、着手時は最新だった base がその場で先行しうる。
差分の混入だけが害ではない。
遅れたツリーから読んだコードは現行の規約の見本として働くため、既に retire された書き方をそこから新規コードへ写してしまう。
判定を読むためだけでなく、実装の前提を作るためにも、進めてから読む。
**この転写がツリーの外へ出た分は rebase では戻らない。** 遅れに気付くまでの窓の中で確定した作業項目・外向きの作業記録・PR 本文は、ツリーを直しても旧規約を抱えたまま残り、以降の検査はいずれもブランチのツリーしか見ないため誰も指さない。rebase の直後に、その窓の間の外向き操作を数え、取り込んだコミットが規約文書を触っていればそれらの内容を読み直す。窓が空だったなら1行そう記録する
     - **自分の変更を確認する差分は三点（`origin/<base>...HEAD`）で取る。** 二点（`origin/<base>..HEAD`）は base 側の先行分も差分に含めるため、他者が追加したファイルが自分のブランチによる削除として現れる。上の遅れが生じている間、二点で見た差分は「身に覚えのない大量削除」の形で出るので、削除を疑う前に差分の取り方を疑う
     - **同一セッションで続けてサイクルを回す場合も、着手時に `origin/<base>` から新しいブランチを切る。** 前サイクルのブランチに続けてコミットすると、前サイクルの差分が次サイクルの PR に混入する。前サイクルの PR が未マージであれば必ずこの形になる。検出は着手時に `git log --oneline origin/<base>..HEAD` が空であることの確認、または終端ゲートのコミット数が想定と合っているかの照合で行う（コミット数はサイクル完了時に初めて見るため、混入に気付くのは PR 作成後になりやすい）
     - **open PR が今回の作業と重なるか、前提を変えるかを確認する。** 競合する作業は、解消方法か影響の扱いを決めてから選択へ進む。リポ固有の判断基準は companion の roadmap.md に記載する
     - `.pfdsl/roadmap.pfdsl` の着手可能プロセスを列挙する。`pfdsl status ready <roadmap.pfdsl> --best --json` で、入力 artifact が全て done のプロセス一覧と `--best` 推薦（合流点を解放するもの＝後続プロセスの最後の未完入力になっているもの）が JSON で得られる。着手可能集合が薄く「何が止めているか」を知りたい場合は `status blocked <roadmap.pfdsl>` で各未着手プロセスの未達入力 artifact を一覧できる（`graph stats` の fan-out と併せればボトルネックの優先度づけもできる）
   - **サイクルの範囲は、選んだ作業項目の設計が確定するまで確定しない。** 複数の作業項目を一度に指定されたとき、着手前の見た目の小ささで1サイクルに畳まない — 設計対話で方針が決まった時点で規模と種類が変わることがあり、そこで初めて別クラスの変更だと分かる。畳んだまま進めると、性質の違う変更が1つの差分に混ざってレビューの信号が埋もれ、片方が他方の前提を動かす（検査を厳しくする変更を同じブランチに入れると、以降のコミットが全てその厳しさを前提にする）。設計確定の直後に範囲を見直し、分けるなら分ける。
   - ユーザー指定があればそれを、なければ `best` の推薦を優先して1つ選ぶ。roadmap 非管理の作業項目（exempt 等）を識別子で指定された場合も本手順で処理する — ready 列挙に出ないことは cycle を通さない理由にならない（プリフライト・終端ゲート・retro は変更内容と独立に有効）。**ユーザー指定で入力 artifact が done でないプロセスを選んだ場合、「前提条件未達で着手する」とその理由を記録してから実行する**
   - **選択後の設計確認**: その作業項目の一次記録と設計判断履歴を確認し、現行のコード・仕様と照合する。取得手段・記録先・再承認参照は roadmap.md が指すバックエンドの L3 reference に従う。記録が無いことは未記録を意味し、追加承認が必要かは依頼内容から別に判断する。方式が確定した小さな修正や既に許可された作業は、必要な記録を整えて進める。結果を大きく変える未決事項、実質的な前提の不一致、ユーザーが明示した設計レビュー待機点がある場合だけ、具体案を示して確認する。記録の不足を理由に既存の承認を取り直さず、機械検査の PASS を設計の妥当性の証明にもしない。公開記録への書込みには既存の承認範囲を適用する。
     プリフライトが設計未確定を報告した場合は、終了コードが成功でも、その理由・作業項目の一次記録・現行のコードと仕様を照合し、未決定の設計や記録の不足を着手前に解消する。
     既存の設計記録を再利用する場合も、採用案と競合する別クラスの実装案が含まれるか、着手前に本文を目視で確認する。「何もしない」「現状維持」だけが比較対象なら、下の適用点1に戻って競合実装案を加え、処分を再検討する。
   - **適用点1 — 作業項目が列挙する案の集合を、設計空間とみなさない。** 起票者が挙げた案は入力の一部であり、網羅性は保証されていない。設計を確定させる前に次を行う。
     **ユーザーへの設計提示と着手前の公開記録は、今回確定する全軸の決定と理由から始める。** 公開記録は `設計記録形式: 3` を宣言し、`決定:`、`理由:`、`案の処分:`、必要数の `前提検査 Pn:`、`改訂履歴:` の順で書く。対話では各トークンを逐語的に読ませる必要はないが、承認された内容と公開記録の意味を一致させる。
     `決定:` の直下には `- <軸名>（<実装 | 調査のみ | 待機 | 実装しない>）: <今回確定した範囲>` を全軸分並べ、ここだけを今回確定した内容の正文とする。`理由:`、`案の処分:`、`前提検査 Pn:` は正文の根拠と検査記録であり、別の決定を宣言しない。
     `理由:` の直下には `- <軸名>: <目的との対応>` を置く。軸名は `決定:` と一致させる。
     `案の処分:` には issue が列挙した元候補を `- <採用 | 部分採用 | 保留 | 却下> — 元候補「<候補名>」— <理由または条件>` の形で直接書く。部分採用は `- 部分採用 — 元候補「<候補名>」— 採用部分: <範囲>; 残部: <却下 | 保留> — <理由または再検討条件>` の形で採用部分と残部を併記する。保留は再検討条件を、却下は規律を満たす理由を併記する。
     前提検査は `P1` から欠番なく連番で書く。各 `前提検査 Pn:` には `対象:`、`前提:`、`前提を外した案:`、`既存候補との差分:`、`検査案の処分 Pn:` をこの順で置く。前提検査で生成した案は対応する `検査案の処分 Pn:` だけに書き、`案の処分:` に重複させない。
     `改訂履歴:` は決定の実質を変更した場合に、改訂行を `-`、旧決定、`→`、新決定、`—`、変更理由、`— 再承認:`、再承認参照の順で書く。決定の変更がなければ `- なし` と書く。再承認参照の具体的な形と解決規則は、採用するバックエンドの L3 reference が定義する。移行境界は各バックエンドの L3 reference が定める。以降の新規記録は完全な Format 3 とする。
     表示種別は読者向けの分類であり、ファイル変更、外部書き込み、認証情報の利用、費用発生の権限を付与しない。`調査のみ` は導入や実装の許可を表さず、`待機` は再検討条件が成立するまで実行へ進まないことを表す。
     1. **前提を1文で書く。** 書式は「本案は〈○○という状態が存在し続けること〉を前提にする」。列挙された全案が共有している前提を書く（案が1つしかない場合はその案の前提を書く）。この書式に嵌らない場合、案が複数ある意味を説明できていないので書き直す。
     2. **その前提を否定した案を1つ作り、同じ粒度で集合に加える。** 起票者が挙げていなくても作る。**作った否定案が列挙済みの案のいずれかと一致したら、集合の外へ出られたことの証拠にはならない** — 否定したのが全案の共有前提でなく採用しかけていた1案の前提だった場合と、起票者の列挙がもともと網羅的だった場合の両方がこの形になる。列挙と読み比べて一致に気付いたら、どちらなのかを `既存候補との差分:` に書く。**後者だと述べる場合は、もう一段上の前提を否定した案も既に列挙内にあることを示す。示せなければ前者として扱い、もう一段上の前提へ遡ってやり直す** — 網羅性は機械照合できない側の性質なので、自己申告だけで免除にすると、遡り直しを避けたい回が必ず後者を名乗る。前提検査の構造だけからはこの一致は見えないので、機械照合は通ってしまう。
     **前提を否定した結果が「何もしない」「現状維持」に帰着する場合、それは前提を試す案として残してよいが、採用案と競合する別クラスの実装案をもう1つ加える。** 対策の有無だけでは採用した手段の対立仮説にならないため、設計記録を確定する前に両案の処分を明示する。
     3. 否定案または追加した競合実装案を却下する場合、却下理由を外部制約か所有者に帰着させる。**「手間がかかる」「大がかり」「今回のスコープ外」は却下理由として無効。** これらしか書けない場合、その案は生存候補として残す。
        **却下理由が既存の挙動を引用する場合、その挙動を実際に起こしたコマンドと出力を記録に併記する。** 引用先が今回の変更対象そのものであっても免除しない — 変更前の挙動は最もよく知っているつもりの対象であり、ソースを読んだ記憶が実行の代わりになりやすい。併記できない引用は成立していないので、却下理由から外す。
     **理由が自分の変更の外にある機構の振る舞いを名指しする場合、その機構を実際に走らせた出力を理由と一緒に書く。** 関数名・JSDoc・コメントは「何をするつもりか」を述べる器であって「何を返すか」ではないので、それらを読んだだけでは確かめたことにならない。走らせられない機構なら、その振る舞いを決めている呼び出し側の分岐を引用する。どちらも書けない述語は成立していない — その述語の真偽を確かめる材料はどのゲートの入力にも入っておらず、記録は必須行頭も時点照合もテストも通ったまま誤った理由を3箇所（記録・実装のコメント・PR 本文）へ同時に定着させる。
     **名指す機構が却下する案そのものの実装である場合、走らせる対象も引用する呼び出し側も存在しない。** 却下した以上その実装は誰も書かないため、理由が偽でも反証の機会が来ない。この形に限り、走らせる代わりに**両案が取り違える入力を1つ構成する** — 一方だけが捕まえる入力を実際に書いて、両案に当てる。構成できたなら一方が他方を包含するという主張は偽であり、理由を「両案は別の経路を塞ぐ」へ書き換えたうえで、採用案が塞がない経路を成果物に明示する。構成しようとして書けないことを確かめた場合に限り、包含を主張してよい。**包含の主張は却下理由の中で最も検査に掛からない形である** — 採用案が現に動いていることは、それが他案の守備範囲を覆っていることの証拠にならない。
     **却下理由に既存の設計決定・規約・制約を引く場合、その決定が案を禁じる条件と、いま却下する案（否定案または上で加えた競合実装案）がその条件を満たすことを1文で書く。** 条件を確かめる相手は実際に処分する案であって、同じ集合の別の案ではない。「その決定が案に及ぶ範囲」を書いても禁止は立証されない — 条件付きで禁じる規範を範囲だけで引くと、条件を満たさない案が恒久的に落ちる。原則・選好・意図だけを述べていて具体的な禁止条件を持たない決定は、この1文を書けないので却下の根拠にならない。その引用とそれに依存して立てた主張を落とす。有効な禁止述語が1つも残らなければ下の第4段で `保留` になり、所有者が拘束力のある条件を示した時点で再検討する。残る述語があるなら落とすのはその引用だけで、処分はやはり第4段で決める。
     決定の文面そのものは走らせられない — 決定が述べるのは「何を禁じるつもりか」であって「何を返すか」ではなく、その射程は文面からしか読めないので、名前や見出しが示唆する範囲を射程と取り違えても出力のどこにも現れない。実行の代わりに条件と該当箇所の記述で足りるのは、引用先が決定の文面だけの場合に限る — このリポジトリに実装を持たない外部仕様・法規・他者所有の規約もここに入り、再読できる版や出典と、案を禁じている具体的な条項を示す。
     **引いた決定が挙動を主張し、その挙動を実装する機構がある場合は、上の挙動節・機構節も併せて適用する** — JSDoc やコメントに書かれた設計判断はこの形であり、条件を1文書いただけでは、その決定を実装しているはずの機構が実際には別のことをしている状態を見逃す。**判定の単位は独立に観測できる規範述語ごとで、それを含む規定や仕様の全体ではない** — 引用した述語のうちこのリポジトリの機構が実現しているものは機構ありとして実行の出力を書き、実装のないものは条件と該当箇所の記述で扱う。実装のある述語を走らせた結果を、実装のない述語の根拠に流用しない。分解が一意に決まらない述語は未確定と印を付けて第3段で落とす対象にし、ここでは処分を決めない — 読み手によって述語の数が変われば、同じ記録が却下にも保留にもなる。
     **手順は、述語へ分解する・述語ごとに根拠を検証する・根拠を書けない引用とそれに依存して立てた主張を落とす・残った理由だけで却下の可否を決める、の順に固定する。** 順序を決めないと、根拠の欠けた述語を先に見た読み手は `保留` にし、それを削ってから見た読み手は残りだけで却下でき、同じ記録が別の処分を指す。**この項目の各節（挙動の引用・機構の名指し・却下案そのものの実装・上の決定の引用）はいずれも第2段の述語ごとの検査であって、単独で処分を決めない。** ある節が「成立していない」と告げる相手は当の述語であり、却下理由の全体ではない — 告げられた述語は第3段で落とす対象になるだけで、処分が決まるのは第4段だけとする。引用だけを削って結論の文を残すのも第3段の取りこぼしで、外部制約にも所有者にも帰着しない却下理由が残り、この項目の冒頭の要件を満たさないまま案が落ちる。第4段で却下してよいのは、残った述語だけで「その案は採れない」と言える場合に限り、妥当な述語が1つも残らないなら `保留` にする。落とした述語が担っていた対象範囲を残りが覆えないなら、覆えない部分について禁止は言えていない — 案全体を落とさず、禁止が言える部分を外した縮小案を生存候補として残す。縮小案が `部分採用` として確定するのも第4段で、全述語の第3段処理を終えた後に限る — 先に採用部分として書くと、まだ評価していない述語がその部分を禁じても実装が進む。縮小案に新しい記録欄を作らず、縮小元が issue の元候補なら `案の処分:` の `部分採用`、前提検査で生成した案なら対応する `検査案の処分 Pn:` の `部分採用` として、採用部分と残部の処分を書く。`部分採用` にできるのは、採用部分がそれだけで案の目的を単独で満たす成果物として分離でき、かつ残部の却下または保留の理由まで確定している場合に限る — 分割できるファイルや面があることは分離の根拠にならず、どちらかを欠くなら `保留` にして再検討条件を書く。これは適用点2 が既存機構を流用する際に作用域の実測を求めるのと同じ要求を、決定を却下理由として流用する側へ掛けたものである。
     対話の要否は案の本数でなく、ユーザーが判断すべき未決事項が残るかで決める。通常の実装詳細は依頼範囲内で判断し、工程が移るたびに同じ内容の承認を求めない。選択肢を提示する場合は、決定を変えうる前提と理由を併記する。
     **記録先**: Format 3 の決定、理由、候補の処分、前提検査、改訂履歴は、そのサイクルについて後から読み返せる作業記録に残す。頭の中だけで済ませない — 残さないと、後から比較検査を行ったかを第三者が判定できず、原則が効いているかの点検自体ができなくなる。**方針と必要な承認は実装着手前に確定する。** 記録先・確定操作・再承認参照はバックエンドの L3 reference に従う。終端ゲートは記録の実在と有効性を検査し、投稿・編集時刻と初コミットの前後関係は判定しない。記録漏れに気付いたら経緯を補記し、必要な承認が未了なら実装を進めず判断を受ける。
**記録の書式に機械検査がある場合、下書きを投稿前に検査し、投稿・編集後に本文を読み戻す。** 書式の補修は同じ記録で行える。決定の実質を変更する場合は必要な再承認を得て改訂履歴を更新し、既存実装との整合を確認する。記録漏れや書式補修を理由に過去コミットを再作成しない。記録やコミットの日時を動かしても、着手前の判断や承認を証明したことにはならない。
     **機械検査は記録の構造と、バックエンドが定義する時刻の妥当性・再承認参照を blocking にする。** Format 3 の宣言が一度だけあり、`決定:` が最初の内容セクションで全軸を持ち、理由の軸集合、元候補の処分、部分採用の残部、前提検査の連番と必須項目、改訂履歴のいずれも空でないことを検査する。機械検査の PASS は設計判断の妥当性を保証しない。
     **人間レビューは、issue 由来の候補をすべて処分したか、決定と処分が意味的に整合するか、複数採用・部分採用・組合せの境界と軸分割が実際の独立性を反映するかを確認する。** さらに、`調査のみ` と `待機` が実装の黙示的な許可になっていないこと、保留の再検討条件が実行可能か、却下理由、共有前提、前提を外した案の粒度、一致時の上位前提検査、改訂履歴と再承認の正確さを確認する。複数の改訂行が同じ再承認参照を用いた場合に、1つの承認がどの範囲を承認したかの対応関係は機械判定せず、人間レビューの専管とする。
     issue 本文から推定した `optionCount` は候補の完全性を証明しない。候補網羅性を機械的に保証したように見せず、人間レビューの責務として扱う。
   - **適用点2 — 既存の不整合・重複・drift・手作業の機械化を目的とする作業では、着手前に次も確認する。**
     - **導入する新概念を列挙する。** 規則・状態・例外・分岐・向き・停止条件を数える。既存の慣行に対する例外は必ず含める。
     - **同じ形の構造がほかに何個あり、今回のスコープは何個かを数える。** スコープ外に同型が残る場合、それらが使っている機構を1語ずつ書き出す。**数える単位は、対策が作用する単位に合わせる。** 対策が出力単位で効くなら同型も出力単位で数える。スクリプト・ファイル・コンポーネントなど数えやすい単位で代用すると、1単位の内部に同型が複数あってもまとめて1と数えてしまい、スコープ外の残存を過小に見積もる。この誤りは「同型は残らない」という結論の形で出るため、結論だけを見ても検出できない。
     - 今回の案の機構がその語彙に無ければ、**「なぜ今回だけ既存機構が使えないのか」を1文で書く。** その1文に現れる性質を、制約でなく設計変数として扱う案を1つ作る。
     - 新概念ゼロを主張する場合、流用する既存機構の作用域を**実測で**確認した旨を1行添える。名前が示唆する範囲を信じない。**この実測は案をユーザーへ提示する前に済ませる。** 提示は選択を確定させる行為なので、提示の後で実測して前提が崩れれば、確定した決定を差し戻すことになる。既存機構への委譲は「その機構が現に何を拾っているか」で成否が決まり、規約や README が述べる範囲とは別物である — 委譲先を実データに当てて、いま拾えているものが拾えなくなる件数を数えてから提示する。適用点1 が記録の時点を着手前に固定しているのと同じ理由で、この実測にも時点がある。
**この実測は、既存機構を受け入れ基準として名指しするときにも要る。** 案の一部として流用する場合だけでなく、「この検査が緑なら目的の性質は保たれている」と宣言する場合が同じ形であり、こちらのほうが誤りが露見しにくい — 流用した機構が拾い漏らせば実装が壊れて見えるが、受け入れ基準が性質を見ていない場合は緑が返るだけで、壊れたことは出力のどこにも現れない。判定したい性質を1つ挙げ、その機構の入力にその性質が入っているかを、機構を実際に走らせた出力の上で確かめる。実装を委譲する回はこの確認を委譲先に任せられない — 委譲先は与えられた基準が緑になったことしか見えず、基準が見ていない範囲の食い違いを正常な完了と区別できない。
     判定物は新概念の数ではなく、この1文の質である。数が多い案を採ってもよいが、その場合は理由を書く。「もう実装したから」は理由にならない。概念数は生成器の内部へ押し込めば操作できるため、数そのものを勝敗判定に使わない。
2. **実行**: 作業項目の一次情報は roadmap.md が指すバックエンド。ブランチを切って作業する（main 直コミットしない）。`.pfdsl/pipeline.pfdsl` が存在する場合は着手前に変換境界を確認し、実装スコープが境界を越えないか確かめる。PFD の読み書きは pfdsl スキルの品質ガイドに従う。ビルド・生成・全量 check 系のコマンドは出力が数百行に及ぶことがある — 結果確認は `git status --short <対象パス>` / `git diff --stat` で変更有無を先に見る（詳細ログが要る場合のみファイルにリダイレクトして絞る）。**その出力が、いま実装しているツリーのものかを毎回確かめる。** worktree で作業していても、実行環境がコマンドの作業ディレクトリをセッション既定の場所へ戻すことがあり、そうなるとビルドもテストも別ツリー（多くの場合 base ブランチ）で走る。そこは変更前の状態なので緑になり、緑は「自分の変更が通った」証拠として読まれる — 実際にはこのサイクルの差分は一度も検査されていない。実測すべきは出力でなく実行場所で、コマンドの冒頭に `pwd` を置くか、ディレクトリ変更を別の呼び出しに分けて確定させてから測る（同じ理由で、`cd <dir> && <cmd>` の形はツール呼び出し前に発火する検査の目には `cd` 前のディレクトリしか見えない）。**この確認は1回では持続しない** — 戻りはサイクルの途中で起きるので、前の呼び出しで確かめた実行場所は次の呼び出しの根拠にならない。測るたびに確かめるか、そもそも対象ツリーの絶対パスを毎回書く。戻った状態は緑としてだけでなく「自分の変更が消えた」形でも出る（テスト件数が減る・作業ツリーが clean に見える・変更したはずのファイルが変更前の内容を返す）ため、消失を疑う前に実行場所を疑う。**GUI・エディタ拡張等の UI 変更は、ビルド後にユーザーと実際に操作して動作確認する。verify が BLOCKED になった場合も「確認手順をユーザーに渡す」で終わらず、ユーザーの確認結果を受け取るまで完了とみなさない。**
**変更前後を報告する作業では、変更前に比較対象と測り方を決める。** 基準は作業開始前の版を commit ID 等で固定し、測定対象・条件と一緒に既存の作業記録へ残す。ブランチ内で自分が作った不具合とその修正幅を、基準からの改善幅にしない。
履歴から同じ条件で復元できる静的な指標は、固定した版から後で測ってよい。未コミットの状態・外部データ・実行時の性能など、後から復元できない対象は変更前に取得する。取得を逃したら比較不能の理由と確認できる範囲を報告し、現在値を before として補わない。
after も測った版と条件に結び付ける。計測後に HEAD・未コミット差分・入力・設定が変わったら、その変更が指標へ影響するかを確認し、影響する測定だけをやり直す。影響しない根拠があれば既存結果を再利用できる。履歴のない実行時指標の代わりに静的な件数を示す場合は代理指標と明記し、効果の実証と区別する。比較を目的にしない通常作業へ新しい計測や報告書を課さない。
**そのサイクルで新設した agent が同じセッションから起動できるかは、確かめるまで分からない。** harness が定義の追加を検出して即座に使える場合と、セッションを開き直すまで見えない場合があり、どちらになるかは追加のしかた（既存のディレクトリへ足したか、ディレクトリごと新設したか）や起動時の設定で変わる。
**「できない」を前提に検証を次セッションへ送る前に、実際に1回呼んでみる** — 呼べないことを前提にすると、呼べる回でも検証が先送りされ、そのサイクルは自分の成果物を一度も動かさずに閉じる。
呼べなかった場合は、壊した状態を作って呼び報告を生ログと照合する型の受け入れ基準はそのサイクル内では満たせない — 検証を次セッションへ渡し、未了である旨を作業記録に明示して閉じる。
別 agent に同じ指示を与えて代用しない。検証対象は agent 定義そのものであり、別の定義の挙動はその代理にならない。
**渡す検証手順には、壊れたことの確認を手順そのものに含める。** 作業ツリーの差分を前提にする壊し方（`git stash push -- <file>` 等）は、その差分をコミットした後は空振りし、以降の検査は健全なツリーに対して走って緑を返す。
空振りは失敗でなく緑として出るため、確認を挟まない限り検証者からは成功と区別できない。
   - **適用点3 — 実装を別エージェント・別セッションへ渡す場合、前提の1文・却下した案とその理由・新概念の列挙、の3点をブリーフに含める。** 差し戻し条件を列挙型で明記する。列挙に無い概念が実装に必要になった場合、前提が事実でないと判明した場合、却下理由に事実誤認があった場合、**仕様が作業項目の目的に反する例外を含んでいる場合**（設計者が書いた仕様そのものの誤りは、実装者が忠実であるほど検出されない）は、実装を止めて設計者へ返す。**無条件の「決定済み・再設計禁止」は書かない。** 凍結してよいのは実装詳細であり、前提ではない。実装者に自由な代案探索をさせることは要求しない（二重設計になりコストが合わない） — 差し戻し条件を列挙型に限定することで churn を抑えつつ、最後の検出機会だけを開けておく。委譲先が留保作業（push・PR 作成・作業項目バックエンドへの書き込み）を実行していないかの戻り時照合は本原則の管轄外であり、委譲の範囲制御として次項で別に扱う。
     **手書きの成果物を生成へ置き換える委譲では、渡す前にその生成器が書き込む先を全部列挙し、受け入れ基準がその全部を固定しているかを確かめる。** 列挙の単位は生成器の出力先であって、ブリーフが名前を挙げた出力ではない。一部だけを固定した受け入れ基準は、固定した出力については最後まで緑を返すため、同じ宣言から作られる他の出力が崩れても委譲先からも呼び出し元からも正常な完了と区別できない。
     **生成物が適合すべき既存構造は、実物から読んで入力に明示する。** 出力が既存の構造（設定ファイルのキー・仕様の節番号・データの形）へ適合しなければならない委譲では、その構造を委譲先に読ませるか、抽出した現物をブリーフへ書く。渡さないと委譲先は存在しない構造を捏造し、戻り後のレビューでしか検出できない — 入力として渡せば捏造そのものが起きない。前提の1文と違いこれは実物を読む工程であり、構造の名前が示唆する形からの推測では代用できない。
     **先例を使う委譲では、先例と今回の入出力を実物で比べる。** 呼び出し元は目的・編集範囲・先例の版と入口・今回の期待結果を渡し、正常系に加えて不正入力、対象不在、権限等の失敗時の扱いを示す。先例の前処理・除外・別枠の分岐のうち、引き継ぐものと今回には当てはまらないものを区別する。「同じ形で」の一言や、パターン名を渡すだけでは入力にならない。
     ブリーフが足りなければ、委譲先は一次資料を読んで補い、目的や権限に関わる未決事項だけを呼び出し元へ返す。調べられる内容の再承認は求めない。先例を使わない単独作業にはこの比較を課さない。
     戻りのレビューにも目的・最終差分・一次資料への入口を渡す。reviewer は依頼に列挙された条件を探索の上限にせず、先例と実消費者から今回の scope を点検し、正常・失敗時の期待結果を実物へ当てる。既に検証した結果は、対象版・条件が今回も一致すると確認できれば再利用し、変更で根拠が崩れる範囲だけ再確認する。
     **必要な作業順と記録形式を分ける。** 承認やレビューなど、委譲の前後で誰が何を確認するかをブリーフに明示する。記録をコミットへ載せる都合だけで実施時点を縛らない。戻り後のレビューで見つけた問題は通常の追加コミットで直し、記録漏れの補修に過去コミットの再作成を要求しない。
     **記録の存在や時刻だけでは、承認・レビューの実施を証明できない。** 内容と対象差分の対応は人間レビューで確認する。未実施の確認は実施し、判断が変わった場合は必要な承認を得てから反映する。
   - **委譲先の外向き操作の制御 — 3層で機構化する。** 実装を委譲するとき、push・PR 作成・作業項目バックエンドへの書き込みは呼び出し元が持つ。ブリーフに「push するな」と明示しても破られることが実測されているため、指示でなく機構で制御する（同一サイクルで範囲指定が2回破られ、2回目は明示的な禁止に反して PR が作成された事例がある）。
     1. **agent の選択。** 外向きツール面（GitHub 連携等）を `tools:` に持たない実装専用 agent を使う。全ツールを持つ汎用 agent は実装委譲に使わない。本スキルに同梱の `pfd-implementer` がこれに当たる（worktree 作成から PR 作成までを一気通貫でやらせる場合は、その範囲を持つ別の agent を使う）。
        委譲先のセッションは呼び出し元のその時点の作業ディレクトリを継ぐ。
        別のツリーへ移動した直後に委譲すると、委譲先は対象ツリーへ書けずに停止するか、書き込みガードが無ければ誤ったツリーへ書く。
        委譲前に作業ディレクトリを確認し、ブリーフには対象ツリーの絶対パスを書く。
        委譲するフローが worktree の作成を含む場合、「既存の分離ワークスペースがあれば再利用する」型の手順を素通しにしない。
        委譲先は呼び出し元が使用中の worktree の中で起動されることがあり、その場合その手順は共有中の worktree を既存の分離ワークスペースと誤認識して乗っ取る。
        agent 定義側に、その再利用判定を迂回して常に新規 worktree を作る旨を明記する。
     2. **PreToolUse ガード。** allowlist 外の subagent による `git push` と変更系コマンドを、ツール呼び出しの時点で拒否する。subagent の hook payload には `agent_id` が入り呼び出し元の payload には入らない — この差が判別子になる。**agent 名を運ぶフィールド（`agent_type` 等）を判別子に流用しないこと** — harness の契約はそれを「subagent 内で発火したとき」に加えて「セッションが `--agent` を使うとき」にも入れると定めており、後者に当たる呼び出し元が subagent と誤判定されて自分の push を止められる。`agent_id` の側にこの追加条件は無い。`session_id` / `transcript_path` は親子で共通のため使えない。デフォルト拒否にすれば、agent を新設しても黙って push 権を得ることはない。プロジェクト全体に効く permission deny を使わないのは、呼び出し元と一気通貫型 agent まで巻き込むためである。実装はリポ固有のため本スキルは配布しない — 置き場は companion に書く。
     3. **戻り時の検出。** 委譲から戻ったら `git log origin/<branch>..HEAD` と open PR 一覧を確認する。上2層をすり抜ける経路（生 `curl`・スクリプト経由の間接実行）は塞げないため、この層が最後の網になる。将来ツール面が増えても効き続けるのはここだけである。
3. **反映 — 終端ゲート（全項目を明示的に確認する。「該当なし」も判断として確認の対象に入る）**:
   - **記録を要求するのは行頭に `**記録先: …**` または `**PR 作成後**` を持つ項目だけで、印の無い項目は確認で足りる。** 線引きは行頭の印だけで決まる — 本文が記録先らしき語に触れていても印が無ければ確認で足り、逆に印のある項目は本文を読まずに記録要求と分かる。項目ごとに本文を読んで記録先の有無を判定する形にしないのは、その照合コストが読み手側にしか現れず、迷った回と迷わなかった回が記録から区別できないためである。記録先を持たない項目の確認結果には読み手がいない — 人間レビューが読むのは差分と PR 本文であり、機械結果に含まれない判断は実行主体がこの正本の節を直接確認する。読まれない書き込み先を全項目に用意しても書き捨てになる。判別せずに「該当なし」と書いた回の検出は、下の「機械が守らない範囲」が人間レビューへ割り当てている
   - **companion がゲート集約チェッカーを指す場合**、まずそれを実行する。PASS/FAIL 判定が出た項目はその結果に従い、それ以外はこの正本の節を直接読んで個別に確認する。集約チェッカーは本文を解析・再印字せず、PR 作成前にこの節を確認する案内と、PR 作成後に `PR 作成後` 項目を確認する案内だけを固定表示する。**companion に到達できない場合は「チェッカーなし」へ倒し、以下を全項目個別に確認する。** companion は採用リポの `.pfdsl/` 配下に置かれた sibling の `.md` なので、そこが見えない読み手（配布バンドルだけを渡された等）は指しているかどうかを確かめる手段を持たない — その状態がこの既定に当たる。倒す向きが非対称なのは、冗長な個別確認は結論を変えないが、PASS を仮定して飛ばした項目は誰も見ないためである

   - [ ] 実行中に発見した新プロセス・成果物を `.pfdsl/roadmap.pfdsl` に追記した（消費者を明示できないものは作らない）

   - [ ] 変換コンポーネントを追加・変更・削除した場合、または成果物の格納先・生成方式・配送経路を変えた場合、それをモデル化している採用済み PFD（`.pfdsl/pipeline.pfdsl` または `.pfdsl/workflow.pfdsl` の該当箇所）へ同一 PR で反映した（該当なしもここでの確認に含める。pipeline.pfdsl 未採用は自動的に N/A にならない — workflow.pfdsl 側を確認）。**「どの PFD もモデル化していない領域を触った」という N/A と、「見て判断した結果の」N/A は、どちらも同じ「該当なし」として記録されるため、記録からは区別できない** — 変更したパスが採用済み PFD の `location:` に載っているかを先に見て、どちらの N/A かを言えるようにする。
**その突合には process の `location:` も入れる** — 成果物の実体が外部（レジストリ・別リポ・外部サービス）にある場合、artifact の `location:` はその外部を指すため、生産・配送を実装しているファイルはどの artifact の `location:` にも載りえない。
artifact 側だけで突合すると、その実装を変えた回が「どの PFD もモデル化していない領域」の N/A として通過し、実際には description・criteria・location が揃って陳腐化する。companion がゲート集約チェッカーを指す場合はその突合材料を使ってよい。影響範囲の特定には `pfdsl graph impact <file> <id>`（下流の消費者全て）・`graph depends-on <file> <id>`（上流の生産者全て）が使える — 変更対象ノードを grep で手繰るより網羅的

   - [ ] 適用点1の方針と必要な承認が確定され、設計選択記録がバックエンドの移行契約が選択する形式を完全に満たす。移行境界は各バックエンドの L3 reference が定め、境界以後の新規記録は完全な Format 3 とし、`決定:`、`理由:`、`案の処分:`、前提検査、`改訂履歴:` を順に持つ。既存の有効な旧形式記録を書き換えないが、人間による意味的な再検査で issue が列挙した元候補の処分、採用案と競合する別クラスの実装案、却下した前提を外した案と競合実装案の理由規律を確認する。「何もしない」「現状維持」に帰着する前提否定案しか無い場合、または無効な理由で前提を外した案か競合実装案を除外している場合は、適用点1から設計検討をやり直した
   - [ ] 手順2で変更前後の比較が対象となる作業では、固定した基準・対象版・条件に対応する結果を確認した。測れない範囲は理由と確認できる範囲を残し、代理指標を示す場合は効果の実証と区別した。比較を目的にしない通常作業はこの項目の対象外。数値の書き込み先は下の「PR 作成後」の項目

   - [ ] コミット粒度（論理単位ごとの分割）が規約（CLAUDE.md または companion で定義）に従っている。**生成元と生成物は同一コミットに入れる** — 作業ツリー全体から再生成して staged 分と突き合わせる型の drift 検査を持つリポでは、両者を別コミットに割ると生成元だけを staged にした時点で不一致になり弾かれる。論理単位が2つ以上あってもこの境界では割れない — 割れない理由の書き込み先は下の「PR 作成後」の項目

   - [ ] **記録先: PR 本文**: 利用中のハーネス・モデルと companion の規約に従って最終差分をレビューし、確認した影響先と検証根拠、未確認範囲、未解決の指摘をまとめた（レビューコマンド・チェックリスト等の具体的な手段は companion で定義。定まっていなければ最低限、差分を自分で読み直す。省略する場合はその理由を PR 本文に書く）。**レビューの重さは diff の規模に合わせる** — 数十行・1〜2ファイル中心の scoped な修正に多角度 finder × 候補ごと検証 agent のような高効度設定をかけると diff に対して過剰になる。角度を絞るか、そもそも委譲せず自分で読む。重量級の構成は大規模 diff 向け。
レビューを取りまとめる実行主体（委譲した場合は呼び出し元）は、今回影響する経路とレビューの確認範囲・根拠を照合し、追加確認の結果または不要と判断した根拠、残る未確認範囲を PR 本文へまとめてから終了を判断する。レビューの実行回数、指摘なし、CI 成功から未確認範囲まで問題なしと推定しない。必要な経路が未確認なら、その経路を追加確認する。
**ただし担保の中核が委譲でしか作れない観点は、重さを落とす対象に入らない。** 独立性（解答を知らない主体が解くこと）や多重性のように、別主体を立てることでしか成立しない性質を自分で回すのは、軽量な実施ではなく不実施である。
その委譲を起動できない回は、記録して閉じずにユーザーへ返す。
**起動できないというその判断も、指示の文面を確かめてから下す** — 「禁止されている」と「まだ求められていない」は実行主体からは同じ形に見え、後者を前者と読めば作業が減る側に倒れる。根拠として引ける文面が無いなら、確かめていない。
**起動可否は harness と plugin の版に依存することがあり、規約に書かれた「起動できない」はそれを書いた時点の観測でしかない。** 過去にそう記録された手段でも、その記録に従う前にその回の実体（コマンド定義の起動可否フィールド）を確認する。逆向きの陳腐化（起動できるようになったのに規約が禁止のまま残る）は、規約を満たせない形ではなく選択肢を1つ失ったまま気付かない形で出るため、失敗としては観測されない
   - [ ] レビューの menu を「どの手段を選ぶか」の優先順ではなく「どの観点が担保されたか」で組んだ。手段を1つに固定すると、その手段が探さない型の欠陥だけが常に無担当になる — 簡素化のみを見るレビューが findings なしを返した回に、別観点のレビューが採用案の成立根拠の不備と JSDoc の事実誤認を検出した実測がある。観点ごとにブリーフ要件を課し、その観点をどの手段で満たすかは companion が定める。
最終差分のレビューでは、変更目的・差分・変更対象の成果物を渡し、reviewer が影響先を自分でも探す。実装がある場合はその入口も渡すが、文書・設定だけの変更でも、その読み手や参照先を調べる。指定ファイル一覧を探索範囲の上限にしない。条件や機能を撤去する場合は、旧識別子・出力文言・条件を手掛かりに、未変更の利用側コードと説明・回復手順を確認し、過去の事例と現行の指示を区別する。探索は今回変えた契約に依存する経路に絞る。
機械が読む文書・設定の抽出対象を変える場合は、編集した実ファイルを読み手の処理に渡し、期待する内容が最終出力へ届くか確認する。構造検査や見本データのテストだけを、この経路の確認済みという根拠にしない。
   - [ ] finding には具体的な failure scenario（入力・状態 → 誤出力・誤誘導）を伴わせ、構成できない指摘は報告しない。敵対的な指示は「何か見つけねば」という圧で false positive を量産するため、scenario を構成できることを報告の条件にする
   - [ ] **記録先: PR 本文**: 発火した観点を軽くしてよいが、消してはならない。 観点の発火条件（何を担保するか）と、その観点にかける重さ（別主体へ委譲するか自分で読むか）は別軸である。規約が両方を1つの文で決めていると、重さを落とす判断が観点そのものを消す判断に化ける — 「小さい回は軽くてよい」と「この条件を満たす回は対象」が同時に成立する回に優先関係が書かれていないと、実行主体は軽いほうへ畳んで観点を1つも回さずに終わり、その事実はどこにも残らない。重さを落とした回は、落とした観点の名前と落とした理由を成果物（PR 本文等）へ書く — 名前を書かせない限り、軽く回した回と一度も回さなかった回は記録から区別できない
   - [ ] 変更束を PR にまとめた（PR 作成後にローカルで追加コミットした場合、push し忘れていないか `git log origin/<branch>..<branch>` で確認する — CI は push 済みの内容にしか反応しない）
   - [ ] バックエンドの L3 が完了契約を定義する場合、その契約と終端ゲート証拠を満たした
   - [ ] **PR 作成後**: 手順2で変更前後の比較が対象となる作業では、固定した基準・対象版・条件と結果を PR 本文に書いた。測れない範囲は理由を示し、代理指標を使った場合はその旨を書いた。比較を目的にしない通常作業に、数値や代理指標の記載を要求しない
   - [ ] **PR 作成後**: 生成元と生成物を同一コミットに入れたために論理単位が割れなかった場合、割れない理由を PR 本文に書いた
   - [ ] **PR 作成後**: サイクルの途中で前提が変わった箇所を、PR 本文（最初に読まれる正本）にも書き戻した。訂正を別の記録媒体へ書いた回は、その場で正本の該当箇所も直す — 正本だけを読む人は訂正の存在を知る手がかりを持たないため、両方を読んだ者にしか食い違いが見えない。サイクルの終わりにまとめて見直す形にしない（その時点では、どの文がいつ書かれたかがもう分からない）。**この項目だけは実施の時点がここではない** — 実施は訂正を書いた各時点であり、ここで確認するのはその実施の有無である。ここへ来て初めて全訂正を見直す運用にすると、項目文自身が禁じている形になる
   - 上3項目がここに置かれているのは、書き込み先が PR 本文だからである。**書いた内容そのもの**（指標の数値・割れない理由・書き戻した訂正）を読むのは PR をレビューする人間だけで、それを判定に使う機械は無い — したがって PR 本文が置き場として適格であり、誤っていたのは確認を求める時点のほうだった（チェックリストの上の方に置くと、書き込み先がまだ存在しない時点で確認を求めることになる）。並べ替えないこと。ゲート集約チェッカーはこの正本の本文や印を解析せず、PR 作成前後の固定案内だけを出す。実行主体は PR 作成後にこの位置へ戻り、行頭に `**PR 作成後**` を持つ項目を直接確認する。`**記録先: …**` は時点でなく記録先を宣言する別の印である
4. **報告**: 完了したプロセス、それにより解放された後続プロセス、更新後の着手可能集合。特定 status の全体像（例: 残 wip 一覧）が要る場合は都度 `status list <roadmap.pfdsl> --status wip,waiting --json` 等で機械的に絞り込む — 全文 Read や個別 `meta get` の積み上げに頼らない
5. **retro**: 上の「定期監査」に従い、done 付与時とサイクル終結時をそれぞれ確認する。報告を出して終わりにしない。hook の通知や事例の一覧を、この実行の代わりにしない。採用リポ独自の reminder があれば、その到達範囲は companion で確認する。

## 機械が守らない範囲

機械検査は、設計記録の実在・形式・正本の一意性と、バックエンドが定義する再承認参照を確認する。委譲先の外向き操作は手順2の3層ガードで制御する。人間レビューとマージ判断は、これらの検査で判断できない内容を確認する。
記録の内容が実質を伴うか、案を網羅しているか、必要な承認が実在し対象の変更を覆うか、最終差分をレビューしたかは人間レビューの責務である。
投稿・編集時刻と初コミットの比較では、判断やレビューの実施を証明できない。記録補修を理由に履歴を作り直すことも、その代わりにはならない。

## 比較対象生成の非免除条件

適用点1〜3 に共通する、比較対象生成を省略しない条件。各バックエンドの L3 reference が定める移行境界以後に確定する設計選択記録は、状況を問わず Format 3 の決定、理由、元候補の処分、前提検査、改訂履歴をこの順で持つ。

- 同型の先例が0件と確認できた場合は、その0件を1行記録する。0件は比較対象を生成しない根拠にせず、前提を外した案とその検査案の処分を前提検査に含める。
- 前提が他者所有・後方互換・法規等の外部制約に帰着する場合も、前提を外した案を先に生成する。外部制約または所有者名は、生成後にその案を採らない検査案の処分として記録する根拠であり、対案生成の免除にはならない。
- 緊急修正でも Format 3 の比較記録を省略しない。新規 Format 3 記録には、緊急性だけを理由に旧形式や記録なしを選ばない。
