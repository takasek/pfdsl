# PFD 種別タクソノミー（ADR-0017 / ADR-0035）

種別は「このPFDが答える問い」で区別する。**この節が種別選定の一次情報**（pfd-ops はここを参照する）。

| 種別 | 答える問い | statusを使うか |
|---|---|---|
| **roadmap** | 何を何の前に作る必要があるか。今着手できる作業はどれか | 使う（todo→wip→done） |
| **workflow** | この作業はどう繰り返されるか。誰が何をトリガーに何を行うか | 通常書かない |
| **runtime-pipeline** | システムが動くとき、データは何に変換されるか。変換の境界はどこか | 通常書かない |

以下の問診リストでユーザーに確認する（YesならそのぶんPFDを作る）:

| 問い | 種別 |
|---|---|
| 実装すべき作業に依存関係があり、着手順を管理したいか？ | roadmap |
| 定常的に繰り返す作業サイクルがあるか？ | workflow |
| システムがデータを受け取り変換して出力するパイプラインがあるか？ | runtime-pipeline |

同一ドメインに複数種別が存在してよい。

## workflow か runtime-pipeline かの判定（ADR-0035）

**判断・承認・裁量が変換の一部なら workflow。入力が揃えば判断なしに出力が決まるなら runtime-pipeline。**

判定に使うのは**判断の有無だけ**である。
実行主体（人・LLMエージェント・機械）や出力の決定性は判定に使わない。
「人が主役か機械が主役か」で切ると、次の2つの境界事例で誤った側に落ちる。

### 判断を含むが担当が LLM エージェント

**workflow に置く。**
LLM が担当していても判断を含むなら workflow である。

runtime-pipeline に置くと、その成果物が人のレビューと承認を経る必要があるという構造が図から消える。
workflow に置けばレビュープロセスと承認済み成果物がグラフに現れ、未承認のものが下流へ流れないことを図が保証する。

実行主体は `owner` フィールドで表す（例: `owner: ドキュメントLLMエージェント`）。
種別で表現しない。

### 判断は不要だが人が手で行う

**runtime-pipeline に置く。**
判断がないため。
2つのシステムが繋がっていないなど、境界の問題だけを理由に人手になっている変換がこれに当たる。

runtime-pipeline に置くと、機械の変換チェーンの中で人手ノードが1つだけ浮く構図になり、自動化候補がそのまま図から読める。
workflow に追い出すと人の営みの中に埋没してこの価値が失われる。
`owner` で担当者を明示し、必要なら人手であることを `tags` で示す。

### 判定の副産物

第3種別を持たないプロジェクトは「判断が営みの本体であるプロジェクト」として説明できる。
選考・審査・合意形成が中心のドメイン（採用フロー・カンファレンス運営・契約交渉など）は workflow だけで足りることが多い。

## ファイル分割

**1種別1ファイルを原則とする。**
同一種別内の細分は group で行う。

同一種別を複数ファイルに分ける動機がない限り分割しない。
分割してよい動機は次の2つである。

- **読み手が完全に別**
- ファイルが実用上の限界を超える

**「読み手が完全に別」による分割は積極的に使ってよい。**
供給側と消費側で読み手が分かれる場合、両者を1ファイルに収めると、一方の読み手にとって無関係なノードが半分を占める図になる。
分割すればそれぞれが単体で筋の通った図になり、片方だけを読んで用が足りる。

どの種別のどこに切れ目が入るかはプロジェクトごとに違う。

- 供給チームと消費チームが分かれるプロジェクトでは、**workflow** を提供側と利用側に割るのが効く
- 自分たちが自分たちのツールを使うプロジェクト（開発者と利用者が同一）では、**runtime-pipeline** を処理系と配布系に割るほうが効く

判定は「この図を読む人は誰か」を両方のファイルについて言えるかで行う。
言えないなら分割の動機が実は薄い。

**読み手を種別の軸にはしない。**
「開発者向けの図 / 利用者向けの図」を独立種別にすると、変換チェーンの終端が意味の切れ目でなくファイル境界になり、実行主体と読み手が分裂するノード（供給側が実行し消費側が読む変換）の置き場が決まらなくなる。
読み手はファイル分割の軸であって、種別の軸ではない。
