# 知識成果物のライフサイクル監査（付属機能）

PFD 運用が生む知識成果物（roadmap の criteria・companion・決定記録・効果ログ）のライフサイクルを監査する選択項目。`.pfdsl/config.json` のキー `knowledgeLifecycleAudit` が `mode: adopt` と空でない `targets` を宣言したときだけ適用し、対象はその `targets` が名指した成果物に限る。
`targets` が無い・空・不正な場合は、binding の散文や成果物の所在を説明する文、将来の予定や候補を述べる文から対象を補わず、監査対象を推測せず、不備を報告して 本監査を適用しない — 推測で広げると、PFD 運用が生む成果物の外にある一般の文書管理へ及ぶ。

- **スケール監査**: 増え続ける成果物の消費方法は全読を要求していないか（例: 設計決定記録（ADR 等）の知見をガイド1行に蒸留して全読不要にする）
- **同期在庫**: 知見の複数経路（ガイド蒸留・設計決定記録・issue）で、片方にだけ届いて滞留している在庫はないか（例: 知見が設計決定記録にはあるがガイドに未反映の状態、lint 候補が issue に未同期の状態 — いずれも監査質問で検出できる）
- **列挙ドリフト**: 同じリストが2箇所に存在しないか。一次情報を1つに定め、他はポインタにする。**ポインタが成立するのは、その読み手が一次情報を引ける場合だけである** — 外部の読み手に向けた成果物（公開ドキュメント・パッケージページ等）は一次情報を実行も参照もできないので、そこではコピーを残したうえで人手を外し、生成物にして機械が書く形にする。突合検査を既定にしない: コピーを人手で維持する義務が残り、drift を検出しても解消は毎回手作業になる
- **改訂規約**: 増え続ける成果物に改訂・廃止の規約があるか（例: 設計決定記録の一覧の改訂・廃止規約）
- **持ち越し状態の可視化**: サイクルをまたいで持ち越す項目に、消化済みかどうかを判別する手段があるか。次サイクル送りの項目を並べた節はあるが消化を記録する場所が無い、という形で欠ける — 複数サイクル分が溜まると何が生きているのか読めなくなる。読み手に全読を強いる点は「スケール監査」と同じだが、あちらは成果物が増えること自体を、こちらは死んだ項目が生きた項目と区別できないことを問う。消化の記録が元の項目へ返る経路（項目の見出しに状態の印を付けて元ファイルを書き換える等）を持たせる
