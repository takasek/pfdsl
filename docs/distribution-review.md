# 配布プロンプトのレビュー観点

配布 bundle（`plugin/pfdsl/`）に入る散文を、**利用側リポの読み手として**問い詰めるための観点カタログ。
手順は `/distribution-review` スキル、承認済み commit hash と回ごとの実行記録は `docs/distribution-review/` にある。

## このファイルがここにある理由

`docs/review-perspectives.md` には置かない。
あれは配布レンズであり、利用側リポにも同梱される。
「自分の配布物をレビューする観点」は上流リポにしか実施先がないので、そこへ置くこと自体が本カタログの観点2に違反する。

## 解いている問題

配布される散文には、上流リポの文脈でしか意味を持たない記述が混入する。
利用側で読むと意味不明になるか、実行不能な指示になる。
このクラスは自分自身の修正を通じて再発している — #340（配布 SKILL.md への上流専用指示の混入）を直した PR #374 が、#674 で問題になる「非配布」という文言を新規に持ち込んだ。
散文の規約は既に存在し、それだけでは効いていない。

決定可能な部分は `scripts/check-distributed-prose.mjs` が毎 CI で機械検査する。
本カタログが扱うのはその上の層 — 語彙でなく**主語**の問題で、機械が判定できないもの。

## 観点

1. **解決不能なパス**: 配布物内のパスが `.claude/` 形だけで書かれていないか。plugin ロードと repo-local ロードで解決先が変わるパスは、両方の分岐を書くか `${CLAUDE_PLUGIN_ROOT}` を使う。決定可能なので `bundle-path` ルールが機械検査する — 本カタログでは、ルールをすり抜ける形（パスを書かず散文で場所を指す等）を見る
2. **実施先の違う行為**: 上流でしか実行できない行為（配布層への昇格・蒸留・生成コマンドの実行）に、利用側で取れる代替アクションが書かれているか。記述ごと剥がすのは誤り — 各項目は「利用側で無意味」なのではなく「実施先が違う」ので、剥がすと利用側が取れる代替行動ごと消えて別の行き止まりを作る
3. **上流にしか存在しない概念語**: 「配布 / 非配布」のように、利用側に対比軸が存在しない語で説明していないか。スコープ（このリポ限定 / 全リポ横断）のように、読み手の側に実在する軸で言い直す
4. **裸の参照**: issue 番号・PR 番号・このリポ固有の固有名詞が、解決注記なしに現れていないか。`issue-ref` ルールが機械検査する範囲を超えるもの（リポ名・パッケージ名・人名・このリポにしかないファイル名）を見る
5. **非パス形の上流前提**: Makefile ターゲット名・リポ内 CLI の叩き方など、上流でしか実行できないコマンド。パスの形をしていないため機械検査が原理的に届かない
6. **否定的能力記述の陳腐化**: 「〜は検出しない」「〜に対応していない」が現行実装と一致しているか。否定形は機能追加時に grep 同期されず一方的に偽になる（`docs/review-perspectives.md` の C 観点を配布物本文へ適用したもの）
7. **生成物の由来ヘッダ**: 読み手が「これは何から生成され、直すならどこか」に到達できるか。上流の読み手と利用側の読み手が必要とする情報は別なので、1本の文字列で両立させようとしない

## 教訓

回ごとの実行記録から蒸留したもの。
一般化できた型だけをここへ昇格させ、具体例は記録側に残す。

- **見せる範囲が測れるものを決める**: 文脈を持たない executor に配布物だけを見せた probe と、リポ全体を見せた probe は違う欠陥を検出する。前者は利用側の行き止まりを、後者は上流の退行を見つける。同じ材料を全員に見せると片方が測れない（2026-08-01、#675 の write-probe 3体）
- **摩擦が偶然のガードになっていることがある**: pfd-retro の昇格経路は宛先が解決しないまま行き止まりだったが、その壊れ方が「誰も配布層に書けない」というガードとして働いていた。行き止まりを直すときは、同時にそこへ検査を足す（同上）
- **複数の probe が別々の課題から同じ行に到達したものを優先する**: 単発の指摘は課題設計の癖を拾っていることがあるが、独立した経路からの収束は配布物側の問題であることの強い証拠になる。初回レビューでは20件中5件がこれに当たった（2026-08-02）
- **課題文はスキルの述語をそのまま使う**: 課題側で言い換えると、probe はその差を配布物の矛盾と誤認して判断に時間を使う。初回レビューで「固有名詞」を "project-specific proper nouns" と書いたために起きた（同上）
- **課題の前提を sandbox の初期状態と突き合わせてから投入する**: 「〜が1つある」と前提を与える課題は、sandbox にそれが実在しなければ probe を空回りさせる（同上）
- **1 probe = 1 sandbox**: probe は実際にファイルを書くので、共有すると互いの編集が相手の入力になり、詰まりの帰属が切り分けられなくなる（同上）
- **散文が未公開の実装挙動を前提にしうる**: 上流の作業ツリーで検証すると通るが、利用側が入れるのは公開版なので通らない。公開版と手元のビルドが同じバージョン番号を名乗る間は、バージョンが判別子にならず、読み手は自分の CLI が古いことにも気付けない。probe には公開版を握らせ、散文は「別枠を返す版と返さない版のどちらでも成立する」書き方にする（2026-08-04、`graph io` の `externalTerminals` と `status gaps` のゼロ件メッセージ）
- **probe の環境に上流への経路が残る**: ブリーフで「利用側の読み手として振る舞え」と書いても、シェルの別名・グローバル導入・PATH は残る。越境マーカーはブリーフでは塞げないので、実体を調べる操作自体を禁じたうえで、報告に出た痕跡で事後判定する（同上、`pfdsl` の別名が上流のビルドを指していた）
- **初回（base = 空ツリー）の指摘は1サイクルで直しきれない**: 実質全文レビューになるため指摘が大量に出る。修正を別サイクルへ切り出すのは正当だが、**その場合 hash は進めない**。未レビューのまま `make release` がブロックし続ける状態が正であり、指摘を残したまま hash を進めると記録そのものが嘘になる（同上）

## 残余（意図して塞いでいないもの）

- **公開と公開の間に混入した欠陥**: レビューは公開境界でしか走らないため、次の公開まで検出されない
- **公開経路の迂回**: `git tag && git push --tags` は `release.mjs` を通らない。ただし marketplace の `ref` pin を動かさない限り利用側の受け取り内容は変わらない
