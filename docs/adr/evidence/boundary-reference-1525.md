### R1: 完了根拠とcommit同期の混合文

原文（W:13）: 「作業完了時の status 更新は完了コミットと同時に行い、done の根拠が言えない場合は出力成果物の定義を疑う。」

保持条件: criteria未達はwipを維持する。PR運用の段落には同一PRに含められない別リポ成果物の例外がある。基準の差替えも無条件ではなく、原理的不能の実測、元の意図を満たす代替、人間の承認が条件。
一般化可能部分: criteriaに対する受入根拠とartifactの定義の点検。書込み先はstatus・criteria・artifact。
期待配置: 完了根拠は中核。commit・PRに結び付いた更新時点は採用先の実行規律（A:50,76）。この原文は外部イベントを中核操作へ写す実装部品を指定していないため、単に「VCS」というだけでアダプタにしない。
独立判定: PFD対象は明示。完了根拠は業種・主体・バックエンド中立。commit同期はPFD語を一般の記録に置き換えても成立し、業種/VCS非中立。書込み先がstatusであるだけでは後半との一括中核化を正当化しない。

### R2: 道具の参加者性

原文（W:23）: 「hook、guard、agent、script 等の道具は、図の process がその道具を要求するか、図の artifact を生産または消費する場合だけ参加者として登録する。」

保持条件: 配布物への包含、同種の道具をまとめて生成すること、規約からの参照は代理であり、参加者性の根拠にしない。
一般化可能部分: 道具の種類を問わず、モデル中のprocess/artifactとの関係で参加を決める。
期待配置: 中核（protocol）。PFD内の要素と関係の判定で、書込み先はモデルの参加者記述。主体・バックエンドに依存しない。
対照上の狙い: hook/agentという語があっても実行主体の編成・動作を規定していない。語彙による区分iii送りは偽陰性。

### R3: 採用済みPFDに対する変換変更の同期

原文（W:25）: 「その変換をモデル化する採用済み PFD の description、criteria、edge、location を同じ変更束で更新する。」

保持条件: componentの追加変更削除または格納先・生成方式・配送経路の変更。pipeline不在だけで非適用にせず、別PFDが同じ変換を表すかを調べる。W:72–74ではartifactだけでなくprocessのlocationも突合する。
一般化可能部分: 現実の変換変更と、それを表すモデルの整合。対象モデルと書込み要素を名指せる。製造・採用等にも適用可能で、主体/バックエンド中立。
期待配置: この同期関係は中核。W:72の「同一PR」は実行規律へ分離し、「同じ変更束」というモデルの整合条件まで失わない。
情報不足ケース: 変更パスだけ渡され、対象PFDの採用状態やprocess/artifactのlocationを読めない場合は「適用判定不能」。中核規則という分類はできても、その変更への非適用は断定できない。

### R4: 知見の宛先と一般的な再発防止

原文（W:29–30）: 「構造的事実は対応する PFD の node、edge、description、criteria に、グラフで運べない手続き散文は sibling companion に置く。」「再発防止の反映先・機械化の判定・hook の決定軸は、リポ固有の規律として `.pfdsl/bindings/pfd-ops.md` 等の binding が持つ。」

保持条件: 両方に該当する変更は両方を更新する。ただしA:50の書込み先制限とA:51の実行側失敗/モデル改訂候補/変更不要の区別を維持し、全ての知見をモデル修正へ変換しない。
一般化可能部分: モデルの構造的事実の修正と、モデルを説明するcompanionへの反映。任意の手続き散文全部をcompanionへ流す一般化は不可。
期待配置: モデル側は中核。一般的な再発防止・機械化・hookの運用は採用先規律で、bindingへのポインタを中核に残して必須実行させない（A:91、S:88）。
独立判定: `.pfdsl/`配下が宛先でも中核とは限らない。後半の判定論理はPFDなしで成立する。

### R5: done契機と会話の締めの監査

原文（W:35–37）: 「前者は対象 process の出力 artifact に done を付けた時点で実行し、直接 pfd-ops を呼んで done event がない回には適用しない。」「サイクルを終える前に、ユーザーに締めてよいか能動的に確認する。」「ユーザーが締めに同意した返答を受けたら、その同じターンで pfd-retro を起動する。」

保持条件: 現行文ではdone契機と締め契機は独立で、一方の非適用が他方の免除ではない。元の意味の記録ではこれを保持するが、配置変更後も両方を中核から強制する意味ではない。
一般化可能部分: artifactの受入を契機とするモデルの再整合。
期待配置: モデル側の監査契約は中核。締めの確認・同じターンでの起動は採用先のdriver規律（A:76、S:87）。
独立判定: 前者はstatusを名指し、業種/主体/バックエンド中立。後者はpfd-retroを名指しても会話のタイミング制御であり、PFDなしに成立する。具体的な書込み先が未指定でも実行規律の判定を保留する必要はない。

### R6: 1サイクル1プロセス

原文（W:54）: 「範囲規則: **1サイクル = 1プロセス**。」

保持条件: 元文には大きすぎる場合に分割をroadmapへ反映してから着手する条件がある。数の既定変更と、モデルの分割の妥当性は分ける。
一般化可能部分: processとrunの対応を保つこと。これは単に数を自由化して消してよい契約ではない。
期待配置: 1という数は既定プリセット。変更可能であり強制規則ではない。process/run対応は中核（A:73,102）。
独立判定: processを名指し、特定業種やbackendにも依存しないが、そのことだけで1という数が中核規則になるわけではない。原文の数の制限自体はPFD書込み操作でもない。

### R7: bindingの追加手順を毎段実行するスロット

原文（W:55）: 「binding（`.pfdsl/bindings/pfd-ops.md`）に『ワークサイクルの追加手順』節がある場合、手順 1〜3 の各段でその追加手順に従う。無ければ本文の手順だけで足りる。」

保持条件: 追加手順の存在による条件分岐。追加手順の中身はこの文だけでは不明。
一般化可能部分: 追加手順のうち特定PFD要素の整合検査は中核候補だが、内容を読んで独立に分類する必要がある。
期待配置: 汎用の実行規律をPFD driverから必須化するスロットは採用先のroot指示へ切り離す（A:91）。
情報不足ケース: binding未提示ではその中身を中核/アダプタ/実行規律のいずれかへ一括分類できない。スロット自身の配置と参照先の個々の配置を区別する。
独立判定: `.pfdsl`のパスは名指しているが、PFD要素/問い合わせの名指しではない。従うという制御はPFD意味論を必要としない。

### R8: バックエンドL3の完了契約

原文（W:76）: 「バックエンドの L3 が完了契約を定義する場合、その契約と終端ゲート証拠を満たした」

保持条件: L3が契約を定義している場合だけ適用。参照された契約の実体はこの抜粋に無い。
一般化可能部分: 受入根拠とモデルのstatus遷移の契約は中核。外部イベントから既存PFD操作への写像はアダプタ。実行者の記録書式/PR手順なら採用先規律。
期待配置: この1行だけからL3契約の分類を断定しない。アダプタが独自のdone/回収意味論を定義するのは不可（A:65）。参照先の判定論理、書込み主体と書込み先、採用用途を追加取得して判断する。
狙い: backendという語だけで区分iiに分類する誤りと、情報不足を「該当なし」にする誤りを検出する。

## Wを補う主要分類の対照例

### C1: アダプタと外部書込み規律

原文（A:74）: 「外部の出来事（既定ブランチへの push など）を契機に中核の操作を起動する部品は、CI のワークフロー定義の形を取っていても区分 ii である。」
期待: 採用用途を持ち、中核の意味論を再定義しない起動部品はアダプタ。CIというファイル種別で採用先規律へ送らない。
対照: 人/agentが行う外部書込みの手順は採用先規律。アダプタ自身が書いた内容の読み戻しはD2の限定例外としてアダプタ。書込み主体が不明なら両者を決めない。本文へデータを載せる場合と固定説明だけの場合についてA:101の条件も保持する。
意味論/中立性: 起動イベントはbackend固有でよい。読み戻し比較はPFD意味論を要さず、PFD対象の名指しも無いが明示例外。一般の読み戻し規則全部へ拡張しない。

### C2: 付属機能と新しい汎用規則

原文（A:75）: 「所有者の決定（D1）により、PFD 運用の付属機能として同じ core plugin で配布する。」
期待: 知識成果物ライフサイクル監査は中核/アダプタでなく付属機能。対象はPFD運用が生む知識成果物、knowledgeLifecycleAuditの採用宣言を維持。一般の文書管理と同じ判定であるためPFD語を足して中核化しない。
対照: 新しい汎用チェックは「役立つ」「任意」を理由にここへ追加できない。新しい所有者決定が必要。休眠能力/停止しない機構はPFDの語彙で判定を書き直せる範囲を中核へ分離する。

### C3: 配布機構

原文（A:66）: 「配布ファイルの鮮度照合（install-sync）、移行状態の記録（`appliedMigration`）、plugin の版照合」等を「PFDSL の責務ではなく配布のコストとして別枠で管理する」。
期待: 配布機構。配布ファイルやmigrationの状態を読む/書くことと、PFDモデルの状態の意味論は別。配布継続に必要でも中核やアダプタへの昇格の根拠にしない。
対照: R3のモデルと実体の整合を、どちらも「同期」と呼べることだけで配布機構へ送らない。
