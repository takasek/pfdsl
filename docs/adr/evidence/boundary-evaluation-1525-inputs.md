# 判定対象

以下の各項目を、rule.md の判定器だけで分類してください。混合文は分離し、残す条件・一般化・判定根拠・不足情報を記述してください。既存のファイルの置き場所を正解ラベルとして使わないでください。

## R1

「作業完了時の status 更新は完了コミットと同時に行い、done の根拠が言えない場合は出力成果物の定義を疑う。」
条件：criteria未達はwipを維持する。別リポ成果物を同一PRへ含められない場合の例外がある。基準の差替えは、原理的不能の実測、元の意図を満たす代替、人間の承認を条件とする。

## R2

「hook、guard、agent、script 等の道具は、図の process がその道具を要求するか、図の artifact を生産または消費する場合だけ参加者として登録する。」
条件：配布物への包含、同種の道具をまとめて生成すること、規約からの参照は参加者性の根拠にしない。

## R3

「その変換をモデル化する採用済み PFD の description、criteria、edge、location を同じ変更束で更新する。」
条件：componentの追加変更削除、格納先・生成方式・配送経路の変更が対象。pipeline不在だけで非適用にせず、別PFDが同じ変換を表すか調べる。artifactだけでなくprocessのlocationも突合する。別の箇所には「同一PRで反映」とある。
追加ケース：変更パスだけが与えられ、対象PFDの採用状態やlocationを読めない。

## R4

「構造的事実は対応する PFD の node、edge、description、criteria に、グラフで運べない手続き散文は sibling companion に置く。」「再発防止の反映先・機械化の判定・hook の決定軸は、リポ固有の規律として `.pfdsl/bindings/pfd-ops.md` 等の binding が持つ。」
条件：両方に該当する変更は両方を更新する。実行側の失敗、モデル改訂候補、変更不要を区別し、全ての知見をモデル改訂へ変換しない。

## R5

「前者は対象 process の出力 artifact に done を付けた時点で実行し、直接 pfd-ops を呼んで done event がない回には適用しない。」「サイクルを終える前に、ユーザーに締めてよいか能動的に確認する。」「ユーザーが締めに同意した返答を受けたら、その同じターンで pfd-retro を起動する。」
条件：前者はdone契機のモデル監査、後者は会話の締め契機。現行文では両契機は独立で、一方の非適用が他方の免除ではない。

## R6

「範囲規則: 1サイクル = 1プロセス。」
条件：大きすぎる場合は分割をroadmapへ反映してから着手する。

## R7

「binding（`.pfdsl/bindings/pfd-ops.md`）に『ワークサイクルの追加手順』節がある場合、手順 1〜3 の各段でその追加手順に従う。無ければ本文の手順だけで足りる。」
追加手順の中身は未提示。

## R8

「バックエンドの L3 が完了契約を定義する場合、その契約と終端ゲート証拠を満たした」
参照された契約の実体は未提示。

## C1

「外部の出来事（既定ブランチへの push など）を契機に中核の操作を起動する部品は、CI のワークフロー定義の形を取っていても区分 ii である。」
関連して比較するケース：部品自身が外部へ書く場合と、人／agentが外部へ書く場合。それぞれの読み戻し。書込み主体が不明な場合。本文へデータを載せる場合と固定説明のみの場合。

## C2

「所有者の決定（D1）により、PFD 運用の付属機能として同じ core plugin で配布する。」
対象：PFD運用が生む知識成果物のライフサイクル監査。knowledgeLifecycleAuditの採用宣言がある。
比較ケース：新しい汎用チェックを「役立つ」「任意」を理由に追加すること。能力成果物を使うprocessへのedgeの有無を判定する観点。

## C3

「配布ファイルの鮮度照合（install-sync）、移行状態の記録（appliedMigration）、plugin の版照合」等を「PFDSL の責務ではなく配布のコストとして別枠で管理する」。
比較ケース：採用モデルと実際の変換の整合も「同期」と呼べる。
