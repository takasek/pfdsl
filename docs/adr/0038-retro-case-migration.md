# ADR-0038: retro-patterns を事例記録へ移し、再発防止を操作の適用点で所有する

Status: Accepted（#1175 の承認済み方針。実装と初期検証を同じ変更束でレビューする）

## 決定と理由

retro-patterns の本文から対策を抽出し、タグ・phase・検索語で選択して通常作業へ配る依存を終了する。
再発防止は、既存の操作手順、その操作に渡す入力、道具・テスト、独立レビューが所有する。
事例の保存は、毎回読む規約や検査を増やす契機にはしない。
当時の観測、原因の仮説、採用済みの現行規約を区別する。

一次資料は [#1175](https://github.com/takasek/pfdsl/issues/1175)。移行前の照合基準は `33878aebdaae1c69fda95bd4aea5bf2ba0b321e3` で、旧事例87ファイル・255,848 bytes、`phase: pre-artifact` は40ファイルだった。
これは構成の基準値であり、再発率や読解費用の測定値ではない。
#1169 の未適用は、委譲や報告で必要な入力と期待結果を渡す責任へ移す。
#1171 の軸と最初の対策行の不一致は、行抽出とファイル単位の適用判定を終了して解消する。
複数軸を含む旧事例は当時の証拠として保持し、誤った抽出値を現行の対策として再配信しない。
#1172 の選択は、現行性の維持責任自体を減らすための置換である。
元 issue の close は責任移管であり、当時の不具合が修正済みだったことは意味しない。

## 比較した案

| 案 | 処遇と根拠 |
|---|---|
| 対策を構造化フィールドに移し、軸ごとに選択・配信する | 不採用。抽出の曖昧さは減らせるが、適用選択と配信、各対策の現行性の保守を続ける。所有者が承認した目的はこの運用責任を減らすことなので、今回の目的には合わない。 |
| カタログを直して従来の抽出と通知を続ける | 不採用。第1軸の対策を第3軸へ送る例や、表示済みでも実作業の入力が不足する例を、表示の成功だけでは区別できない。 |
| 事例と毎回の retro も廃止する | 不採用。未コミットの失敗や未知の問題を拾う入力が失われ、検索できる証拠と毎サイクルの retro を維持するという所有者の要件を満たさない。 |
| 既存の操作へ入力・検証を移し、事例を保存する | 採用。現在の実物と期待結果を効く時点で使い、過去事例の保守と日常の実行を切り離す。全87件の文章を手順へ転記しない。 |

前提を外した案は「通常作業に過去カタログを配る必要はない」であり、最後の案がこれを実装する。
読了証明、パターン名の出現ゲート、自然言語判定器、新しいルール台帳、巨大な総合手順書は追加しない。
既存の各操作が所有する責任を以下で照合したうえで、旧配線を撤去する。
この表は本移行時点の照合記録であり、毎サイクル更新するルール登録簿ではない。

## 操作が所有する入力と検証

既存の work-cycle と companion の規約を対象に照合した。
委譲は先例・対象データ・全出力の実物、正常・失敗時の期待結果を渡し、レビューは一次資料から依頼の外側も調べる。
before/after は変更前の版・条件を固定し、復元できない状態を先に保存する。
計測後に変更があれば影響する範囲だけ再計測し、無関係な変更で全件検証を繰り返さない。

それ以外の事例群も代表2操作の成功から移管済みとは推定しない。
環境・worktree・古い版の問題は work-cycle 手順1〜2、setup・実行場所・dist 鮮度確認が引き続き担当する。
生成物・全出力・二重配置の問題は正準生成器、harness inventory、生成整合検査、workflow companion の生成手順が担当する。
判定範囲・集合・例外・入力 schema の問題は、受入条件と実消費者の照合、反例を使う correctness レビュー、対象機能のテストが担当する。
案の比較・却下理由・目的との食い違いは既存の設計選択手順が、承認と外部書込み・保存済み本文の確認は既存の GitHub 操作と承認境界が担当する。
PR の正本訂正・scope・未確認の報告は終端ゲートが、知見の保存と保留事項は毎サイクルの retro が担当する。
これらは全事例の危険を機械的に防ぐという主張ではなく、現在の適用点と残る人の判断を明示したものである。

横断的レビューでは、目的と一次資料から scope を確かめること、正常・失敗・非該当の入力で主張の反証を試みること、測った版と範囲を超えて結論しないことを維持する。
各事例を毎回のチェック項目へ転記しない。
#1173 の引用した決定の作用域、#1174 の範囲依存の検査結果の陳腐化は独立した未解決事項として残る。
#1075・#1123・#1124・#1051 は制約として扱い、それぞれの問題全体を本移行の完了へ吸収しない。

## 短い試作と初期検証

旧 work-cycle と、既存の委譲・報告手順を直した候補を、互いの文脈を渡さない2人の読み手へ渡した。
同じ小さな JSON 検査器と呼出側、意図的に不足した依頼、性能比較の入力を使った模擬作業である。
読み手は一次資料からブリーフ・最終レビュー・報告を作成し、検査器の契約差は実際に入力して検証した。

| 入力 | 旧手順の結果 | 候補の結果 |
|---|---|---|
| 先例と同じ契約の検査器を委譲する | 正常・除外・例外・reader 差替えをブリーフ化 | 同じ範囲に加え、権限失敗と固定した先例の内容を明示 |
| title の0/1だけを確認してほしいという不十分なレビュー依頼 | 未捕捉例外、archive 除外漏れ、reader 差替えの欠落を検出 | 同じ3種を一次資料から検出し、実 EACCES も再現 |
| 通常の誤字修正 | 修正・読戻しだけで報告 | 修正・読戻しだけで報告 |
| 未コミット実装と再取得不能な API 応答で着手前比較 | 実装と入力の保存、先行計測を要求 | 同じ条件を要求し、対象と条件を固定 |
| 変更前の実装・入力が失われ、after が80msのみ | 改善幅は不明と報告 | 比較不能とし、80msを before や代表値へ流用しない |
| 基準1回→途中2回→1回、計測後HEADでretry追加 | 50%改善を訂正し、現行版の追加確認を要求 | 固定基準から通常時0%と訂正し、影響経路の再計測と非影響範囲の再利用を区別 |

旧手順でも反例を扱えたので、候補の優位性や再発率低下はこの試行では示していない。
比較の性能値は fixture の提供値であり、実環境の性能を計測したものではない。
新手順がカタログ抽出なしで反例を扱えることと、模擬した誤字修正に追加計測を要求しなかったことが初期の確認範囲である。
誤字修正の読み手は通常サイクルを起動しておらず、その試作だけでは終端ゲートを含む通常作業全体を検証していない。
最終独立レビューが、終端ゲートに残った全サイクル向けの before/after 要求と、手順2の通常作業への非適用との競合を検出した。
終端ゲートと PR 記載の条件を同じ手順2へ揃え、代理指標を必ず追加する義務も外した。
構造・参照・生成・動作の検査結果と最終独立レビューは PR の検証記録へまとめる。

## 運用責任の終了と保存

所有者は、機械化だけでなく、移管と到達の確認、原因消滅、規則の置換、費用判断を根拠に現行責任を終了できる。
古さや無再発だけは根拠にしない。
判断と未解決事項を既存記録へ残し、責任の終了と事例の削除を同一視しない。
今回の87件は原文と根拠を残して歴史資料と明示し、旧 phase は現在の制御値として維持しない。

## 採用と4週間の観察

移行担当は #1175 を完了する担当、評価担当は同じ所有者のもとで #1176 を担当する Codex とする。
所有者が新手順を使う環境で採用を確認した際に、移行担当が commit と実際の bundle・指示の版、対象環境、証拠への可視範囲を既存作業記録へ固定する。
PR の作成・merge・配布物の生成だけでは時計を開始しない。
適用未確認の採用先は成功例に数えず、その採用先の作業担当が確認した時点を開始の契機とする。

基準資料は本 ADR の固定版・既知反例と、開始時点で取得できる直近の比較可能な既存作業記録である。
開始担当は比較対象の選び方と欠落を残し、旧事例が取得できなければ改善率の比較には使わない。
適用確認日 T0 を記録してから、既存スケジュール機能で週1回の読取観察を4週間設定し、対象・次回時刻・停止条件を読み戻す。
観察は [#1176](https://github.com/takasek/pfdsl/issues/1176) の標本抽出、追加確認、証拠不足、通知規約に従う。
T0+28日の最終評価を実行した回に同じ観察予定を停止し、停止状態を読み戻す。
人の判断待ち・件数不足・証拠不足でも自動延長しない。
採用前の現在は開始待ちで、観察 automation を作成しない。

配布先向け案内は [#1177](https://github.com/takasek/pfdsl/issues/1177) を唯一の入口とする。
移行担当が利用可能な commit と正準パス、既存の更新手順、固有 bindings・未コミット事例・未解決事項の保持方法、旧経路と現行手順の確認方法を実装完了時に具体化する。
公開の承認後に同 issue 本文へ反映して読み戻す。
専用のガイド skill・移行器・配布基盤は作らず、別リポの移行実行と publish はこの変更に含めない。

品質ガイドへの蒸留は不要である。図の記法でなく運用上の責任を変える判断なので、適用点は work-cycle と pfd-retro の既存手順である。
