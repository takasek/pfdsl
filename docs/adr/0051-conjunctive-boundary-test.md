# ADR-0051: 中核の境界を4条件の AND とし、判定前に規則を分割する

- Status: Accepted
- Date: 2026-10-24
- Partially supersedes: ADR-0048 の契約1、D3 の対応記録の運び手、companion の構造的事実の未決事項

## Context

ADR-0048 の契約1は、PFD の意味論の要否と書込み先を中核の判定条件にした。
一方で配布正本の0段目には「作業項目の管理先に依存しない規則」も中核に置く説明があり、条件の関係が明示されていなかった。
原文に含まれるモデルの条件と実行主体の規律を一括して判定すると、片方を残すために他方を中核へ入れる、または両方を外す誤りも起こり得る。

#1525 の起票時に参照された6規則の完全な原表は取得できていない。
新しい0段目の文案を見る前に、独立 reviewer が既存資料から抽出した11件を、所有者の承認で受入集合へ差し替えた。
元の6規則との同一性や網羅性は主張しない。
判断と対案の処分は [#1525 の設計選択記録](https://github.com/takasek/pfdsl/issues/1525#issuecomment-6370691695)を参照する。

## Decision

### 判定単位と中核の4条件

独立した意味を持つ規則を分割し、対象・適用条件・例外を保って一般化してから判定する。
語彙を PFD の語へ置き換える際に、元の業種固有の条件や例外を削除してはならない。
規則の分類と、その規則が特定の変更に適用されるかは別の判断とする。
参照先の規則やモデルの採用状態・criteria を取得できない場合は、必要な情報を明示して保留し、非該当と同一視しない。

中核の規則は、次の4つの必要条件をすべて満たす。

1. **意味論**: PFD の意味論を除くと判断の意味を失う。
2. **対象**: 判定・更新の対象を PFD 要素、companion の構造的事実、`.pfdsl/config.json` の宣言、CLI が導出する状態に限る。読取だけなら判定対象を、書込みがあれば全書込み先も確認する。他の道具の設定・定義や作業記録の書式を書き換える規則は中核に入れない。
3. **中立性**: 同じ適用条件と判断が、実行主体・業種・作業項目 backend に依存しない。採用工程等の別業種の artifact・process・criteria に対応付けて確かめるが、そのモデルの criteria が未提示なら情報不足とする。
4. **名指し**: 読む・書く PFD 要素または判定に使う CLI 問い合わせを名指し、判断との関係を説明できる。PFD 配下のパスやスキル名だけでは足りない。

名指しは必要条件であり、語の検索は意味論・中立性の証明にならない。
AND による入口の縮小から、偽陽性と偽陰性の同時減少は導けない。
混合文の分割、中核の正例、情報不足の扱いをそれぞれ受入で確認する。
中立性だけの判定経路は廃し、既存の完了チェーン回収や作業項目対応も同じ4条件へ統合する。
数を変更できる既定プリセットは強制規則とは区別し、process を名指しているだけで「1サイクル1プロセス」を中核の義務にはしない。

### companion の構造的事実

名指した PFD 要素・境界・宣言と対応し、モデルから確かめられる構造上の関係、または単一ファイルのグラフでは表しきれないモデル間の関係を説明する事実を指す。
たとえば、ある PFD の artifact を別 PFD のどの process が消費するかと、その対応の根拠が該当する。
node・edge・description・criteria で表せる事実は図を正本とし、companion を二重の status 台帳にしない。
一般的な実行手順・再発防止・実行者への命令は、companion に書かれていても構造的事実にならない。
両方に該当する変更では、モデルの改訂と採用先の実行規律を分けて扱う。

### process と run の対応

ADR-0048 D3 が必須とする対応は、契約3で受け取る証拠の process ID により運ぶ。
証拠はどの実行がどの process を進めたかを対応付ける必要があるが、保存方式・run ID 形式は決めない。
`location:` は既存仕様どおり実体へのポインタであり、作業項目との対応にも使えるが、実行履歴の代替にはしない。
仕様全体を作業項目URLだけへ限定せず、新しいフィールドも追加しない。
PR 本文の書式・記録時点は採用先の実行規律が決める。

### 正本と変更しない範囲

配置判定の正本は `pfd-ops/references/architecture.md` の0段目とし、この判断をその場で完結して読めるように記述する。
本 ADR の番号や経緯を知らなくても判定できることを受入条件とする。
アダプタの要件と自身の書込みの読み戻し例外、D1 の付属機能、配布機構、D5 の plugin 分割の方針は変更しない。
work-cycle・pfd-retro・backend の規律の移管そのものは既存の後続工程に残す。

## Alternatives

- 現行2条件だけを維持する案は、中立性と名指しを独立に確認する所有者の目的を満たさないため採らない。
- 実行主体の語彙を含む規則を全て除く案は、道具の process／artifact への参加判定等の中核規則まで除くため採らない。
- 原文全体へ分割せず AND を当てる案は、モデルの完了根拠と commit 同期等の混合文から中核部分も失うため採らない。
- 実行の対応を PR 本文だけに置く案は、GitHub 以外の driver の証拠を受け取る契約3を満たさないため採らない。

## Validation

評価前に固定した[独立参照集合11件](evidence/boundary-reference-1525.md)を使う。
評価者には正解表や本 ADR を渡さず、変更後の0段目と原文・適用条件だけを渡す。
配置ラベルだけでなく、混合文の分割、保持条件、一般化の限界、追加で必要な情報を照合する。
結果は [受入評価記録](evidence/boundary-evaluation-1525.md)へ記録する。

E0 の成功は本 ADR の受入ゲートにしない。
E0 は実行前に固定した現行契約に基づく別の実験であり、この4条件を既存の実行契約として扱わない。
観測された証拠の不足や誤読は後続の protocol 改訂へ返す。

## Consequences

0段目は管理先中立だけの別経路を失い、各規則の意味と対象を説明する必要が生じる。
判定には人の判断が残り、11件の一致から一般的な誤分類率や網羅性は保証しない。
起票時の6規則との比較は未実施であり、この変更の改善率の根拠にはしない。
移行注記と各リリースの配布レビュー・移行案内は、既存の公開工程に従う。
