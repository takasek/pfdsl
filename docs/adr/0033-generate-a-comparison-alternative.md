# ADR-0033: 作業項目が列挙する案の集合を設計空間とみなさない

- Status: Accepted
- Date: 2026-07-26

## Context

#547 のサイクルで、実装・レビュー・検証・PR まで完了した設計が、ふりかえりで出たより単純な代案に置き換えられ PR #549 が close された。
損失は1サイクル分の実装・レビュー・検証である。

原因を追うと、個別の判断ミスではなく work-cycle 手順1 の条文自体がこの失敗を誘導していた。

> ただし列挙された案のうち一方が本文中で未解決の付随課題を自認している（対称な選択でなく事実上1案に絞られている）場合は、残る案を採用して対話を省略してよい

この条文は「作業項目が列挙した案の集合 = 設計空間」を暗黙に承認し、さらに集合が実質1点なら対話を省けと言う。
**集合の網羅性を誰も問わない構造がプロトコル側にあった。**

### #547 で実際に起きたこと

作業項目は3案（同期コマンド + pre-commit 警告 / pre-commit 自動修正 / 現状維持）を列挙していた。
エージェントがユーザーに提示した3択も、すべて「乖離をどう捌くか」の変種だった（どちらを正とするか、どちら向きに同期するか、いつ強制するか）。
「乖離という状態が構造的に発生しない形にする」という別クラスの案は、一度も選択肢に載らなかった。

判断材料は最初から手元にあった。
作業項目の本文には3箇所を並べた比較表があり、そのうち1行（配布パッケージ内のミラー）は既に生成物として自動化・強制済みと書かれていた。
エージェントはその表を読み、当該生成器の仕組みまで調べたうえで、「なぜ3つ目だけ生成物ではないのか」を問わなかった。

### 「気づいていたのに止まらなかった」ではない

エージェントは実装前・実装中に信号を3回自分で言語化し、記録に残していた（既存の同種チェックと流儀が違うこと、両側編集時の曖昧ケース、2方向のうち片方だけ挙動が違うこと）。
3回とも検出されたうえで、**受容すべきコストとして分類された**。

当時の記録を精査した結果、代案を思いついて捨てた形跡は一切ない。
反転案はユーザーに「もっと良いアプローチはないか」と問われた瞬間に初めて出た。

したがって分岐点は「受容の判断が甘かった」ことではなく、**受容の判断を下す相手（比較対象 = 別解）がその場に存在しなかった**ことである。

## Decision

**「比較対象を生成する」を1原則とし、`references/work-cycle.md` の3箇所に適用点として置く。**
独立した3規則としては書かない。

1. 手順1 の免除条項（上記引用の1文）を削除する。
2. **適用点1（手順1）**: 作業項目が列挙する案の集合を設計空間とみなさない。
   前提を1文（「本案は〈○○という状態が存在し続けること〉を前提にする」）で書き、それを否定した案を1つ作って同じ粒度で集合に加え、否定案を却下する場合は却下理由を外部制約か所有者に帰着させる。
   「手間がかかる」「大がかり」「今回のスコープ外」は却下理由として無効とし、それしか書けない場合は否定案を生存候補として残す。
3. **適用点2（手順1）**: 既存の不整合・重複・drift・手作業の機械化を目的とする作業では、導入する新概念を列挙し、同型の構造がほかに何個ありスコープが何個かを数え、既存機構が使えない理由を1文で書く。
   新概念ゼロを主張する場合は流用する機構の作用域を実測で確認する。
4. **適用点3（手順2）**: 実装を別エージェント・別セッションへ渡す場合、前提の1文・却下した案とその理由・新概念の列挙をブリーフに含め、差し戻し条件を列挙型で明記する。
   無条件の「決定済み・再設計禁止」は書かない。
5. **免除条項**（同型の先例0件 / 前提が外部制約に帰着 / 緊急修正）を末尾に共通節としてまとめる。

### 追補: 手続きの実行時点も検査対象である（#669）

適用点1 が要求する3要素（前提の1文・否定案・却下理由）は、外形として揃っているかだけでは実質を判定できない。
#659 / PR #663 の transcript 検証で、3要素が揃った記録が issue に存在しながら、実際には実装とコミットの後に書かれ、否定案が採用案の対立仮説になっておらず、列挙された案の1つが処分されないまま残っていた事例が確認された。
記録を書く側は常に「これは正当な記録だ」と考えるため、区別は自己申告でなく手続きに担保させる必要がある。

判定に使える情報はすでに存在していた（issue コメントの `createdAt` とコミットの `authorDate`）。
使っていなかっただけである。
したがって適用点1 の判定に次の3つを加える。

1. **実行時点**: 選択記録の投稿時刻がブランチ初コミットより後なら不合格とする。事後に書かれた記録は選択を導いた形跡ではない。
2. **構造**: 行頭 `前提:` / `否定案:` / `却下理由:` を必須とし、列挙された案の数と記録内の処分（採用・却下・保留）の数を突き合わせる。処分されずに残った案は却下理由テストの対象外へ逃げた案である。
3. **否定案の競合性**: 「何もしない」「現状維持」に帰着する否定案は、前提の否定ではなく対策の有無を分けているにすぎない。採用案と別クラスの実装案に置き換える（この判定は機械化せずゲートの MANUAL 項目に残す）。

1・2 は機械照合、3 は人間の判断として分ける。
「もっと慎重に確認する」型の追記を選ばないのは、本 ADR の Rationale 1 と同じ理由による — #669 の3欠陥はいずれも規則を読んだ上で通過しており、読まれて解釈で回避された規則をもう1本増やしても再発しない。

## Rationale

1. **「立ち止まれ」型の規則は原理的に効かない。** #547 では信号が3回とも検出されていた。
   検出を増やしても結果は変わらない。
   規則は「比較対象を1個生成させる」形でなければならない。
   コストは単独では評価できず、常に対案との差でしか評価できないためである。
2. **却下理由の語彙制限が単体で最も効く。** #547 で反転案を却下するとしたら「大がかりだから」としか書けず、語彙制限に引っかかって生存候補に残る。
   前提欄と否定案の生成は入口であり、生存判定の栓はここにある。
3. **新概念の「数」を勝敗判定に使わない。** 概念数は生成器の内部へ押し込めば操作できるため、数で決めると隠蔽を報酬してしまう。
   判定物は「なぜ既存機構が使えないのか」の1文の質であり、数は比較の入口にすぎない。
4. **1原則3適用点として書く。** 独立3規則だと3つとも忘れられるが、1原則なら残る。
5. **実装者に自由な代案探索は要求しない。** 二重設計になりコストが合わない。
   差し戻し条件を列挙型に限定することで churn を抑えつつ、最後の検出機会だけを開けておく。
   #547 でユーザーの選択を「決定済み・再設計禁止」として実装担当へ渡したことは、検出漏れではなく**検出機会の意図的な閉鎖**であり、最後の検出者の口を塞いだ。

### 一般性の検証（過去に記録された別の失敗5件への適用）

過剰適合を避けるため、`.pfdsl/bindings/pfd-retro.md` に記録済みの他の失敗に当てた。

| 過去の失敗 | 判定 |
|---|---|
| 並行リファクタの死角（互いのスコープ外に同型の重複を残した） | 強く発火（同型カウントとスコープの真部分集合判定が正面から当たる） |
| フラグの意味範囲 trap | 部分発火（新概念ゼロ主張時の実測義務が、フラグが束ねる検査群の展開を強制する） |
| メタ項目が下位十数項目を隠す trap | 部分発火（同上。名前が束ねるものの展開） |
| 検査の自己参照 trap（生成器の入力が古いと素通し） | 管轄外 |
| 実行環境の暗黙前提 trap（`gh` 不在で停止） | 管轄外 |

管轄外の2件は「検査や前提が実は成立していない」という別ファミリで、ADR-0014（反実仮想テスト）が上位原則を持つ領域である。
本 ADR は設計フレームのファミリのみを担当する。
**5件中2件が管轄外**である点を、過剰適合していないことの根拠として扱う。

### 初回適用の実測（#553）

#553 が本原則の最初の適用対象であり、結果が issue に記録されている。

- トリガーは**発火して提案を追認した**（覆さなかった）。
  覆すだけでなく追認もするなら空振りとは言えない、という点は誤検出見積もりにとって有利な材料である。
- 一方、案を1つしか生成しなかったため「選択肢がすべて同じクラスでないか」の点検は働かなかった。
  集合としての比較は列挙して初めて働くという限界が初回適用で露見した。
  これを受け、適用点1 の条文には「案が1つしかない場合はその案の前提を書く」を明記し、案が1つでも前提の否定は機能することを担保した。

## Consequences

- `references/work-cycle.md` を改訂した（冒頭に原則の段落、手順1 に適用点1・2、手順2 に適用点3、末尾に免除条項の節。旧免除条項1文は削除）。
- 同ファイルは plugin 同梱の配布物のため `make gen-plugin` で `plugin/pfdsl/` のミラーを再生成した。
- 適用点3 は #554 の「委譲先の外向き操作の制御（3層）」とは別レイヤである。
  本 ADR が扱うのは**設計の凍結が強すぎる**方向の失敗（無条件の再設計禁止で実装者の口を塞ぐ）で、#554 が扱うのは**ブリーフの範囲指定が守られない**方向の失敗である。
  同じ「委譲の制御」だが管轄が異なるため、work-cycle.md 側からは workflow companion へのポインタのみを置いた。
- 前提欄・否定案欄の見出し存在を `gate-check.mjs` が機械検査する案は、本 ADR の設計時に適用点1 が生成した否定案である。
  #552 本文が所有者判断を保留しているため却下せず、生存候補として #556 に分離した。

## 既知の粗（運用しながら埋める前提）

- **新概念の数え方が境界事例で割れる。** 設定項目1個は概念か、既存パターンのN個目のインスタンスは概念か。
  数を勝敗判定に使わない建て付けにしたのはこのためだが、数サイクル回して定義を締める必要がある。
- **誤検出見積もりが実測でない。** 発火頻度・空振り率の見積もりはコミット履歴からの外挿であり、設計対話の頻度は履歴から見えない。
- **形骸化リスク。** 前提欄に「特になし」と書かれたら死ぬ。
  書式強制と却下理由の語彙制限が栓になっているが、有効性は未検証である（#556 の判断材料）。
- **事例が少ない。** 「前提を否定すれば別解に到達する」ことは #547 で確認でき #553 で追認側の発火を1件観測したが、再現性はまだ薄い。
  否定案の併記でユーザーの認知負荷が上がり選択の質が落ちる副作用も測っていない。
