# ADR-0035: 種別を分ける軸は判断の有無、読み手はファイル分割の軸

- Status: Accepted
- Date: 2026-07-30

## Context

ADR-0017 は種別を「答える問い」で切り、workflow と runtime-pipeline の判定を「人・チームの判断やトリガーが主役 → workflow / データの変換経路が主役 → runtime-pipeline」と書いた。
この「主役」表現は運用上2つの穴を持っていた。

第一に、**判断を含むが担当が LLM エージェントである変換**の置き場が決まらない。
実装・起草・蒸留を LLM に委譲する運用では、主体は人でないが判断は含む変換が多数生じる。
「人が主役か」で判定すると機械側に落ちる。

第二に、**判断は不要だが境界の問題で人が手で行う変換**も判定できない。
2つのシステムが繋がっていないという理由だけで人手になっている転記がこれに当たる。
「人が主役か」で判定すると人側に落ちる。

さらに「開発者向けの図と利用者向けの図に分けたほうが価値があるのではないか」という仮説が繰り返し浮上した。
この読み手軸を種別軸として採用すべきかを判定する必要があった。

## Decision

### 1. workflow と runtime-pipeline を分ける軸は判断の有無のみとする

> 判断・承認・裁量が変換の一部なら workflow。入力が揃えば判断なしに出力が決まるなら runtime-pipeline。

実行主体（人・LLM エージェント・機械）と出力の決定性は判定に使わない。

- **判断を含むが担当が LLM** → workflow。実行主体は `owner` フィールドで表す
- **判断は不要だが人が手で行う** → runtime-pipeline。`owner` で担当者を明示する

### 2. 読み手は種別の軸にせず、ファイル分割の軸とする

「開発者向け / 利用者向け」を独立種別にしない。
ADR-0017 が既に認めているファイル分割の例外（「読み手が完全に別」）を、消極的な例外から積極的な推奨へ格上げする。

切れ目が入る種別はプロジェクトごとに違う。
供給チームと消費チームが分かれるプロジェクトでは workflow を割るのが効き、開発者と利用者が同一のプロジェクトでは runtime-pipeline を処理系と配布系に割るほうが効く。

## Rationale

### 判断軸は既存の分類をすべて再現する

ADR-0017 の検討で使った仮想プロジェクト5件に適用し、審査を通った分類と一致することを確認した。

| プロジェクト | workflow 側 | runtime-pipeline 側 |
|---|---|---|
| Polaris（社内SDK提供） | Go/No-go 判断・草稿レビュー・採用判断 | 生成・テスト・パッケージング・公開・依存解決 |
| Zenith（車両管理） | 月次レポートの承認・提出 | GPS生データ→月次レポート |
| Noodle（レシピ共有） | スプリント・API合意 | レシピ投稿→検索・お気に入り |
| FleetOps（カンファレンス） | CFP選考・当日運営・事後振り返り（全件） | なし |
| Mentori（AIスキル開発） | 改善サイクル | なし |

第3種別を持たない2件について、持たない理由（判断が営みの本体である）まで説明できる。
「主役」表現ではこの説明ができなかった。

### 境界事例は図の情報量で決まる

2つの境界事例をどちらに置くべきかは、図として何が見えるかで判定した。

**LLM 担当の判断を runtime-pipeline に置くと、成果物が消費者のない終端として浮く。**
草稿には人のレビューと承認が必要だという構造が図から消える。
workflow に置けばレビュープロセスと承認済み成果物が現れ、未承認のものが下流へ流れないことをグラフが保証する。

**判断のない人手を runtime-pipeline に置くと、機械チェーンの中で1ノードだけ浮いて自動化候補になる。**
workflow に追い出すと人の営みに埋没してこの価値が消える。
このリポの `.pfdsl` に適用したところ、判断のない人手は marketplace への `.vsix` 手動アップロード1件だけであることが判明した。
従来は process の description 中の一文に埋もれており、図としては存在していなかった。

### 読み手軸を種別軸にすると図が壊れる

Polaris を題材に、同一のノード在庫（process 17個）を判断軸・読み手軸・両者の併用で3通りに分割して比較した。

| 変種 | 分割軸 | ファイル数 | 境界再宣言 |
|---|---|---|---|
| A | 判断の有無 | 2 | 3 |
| B | 読み手 | 4 | 8 |
| C | 種別は判断、ファイル分割は読み手 | 3 | 8 |

読み手軸は判断軸の 2.7 倍の縫い代（他ファイルが生産する artifact の再宣言）を要した。
さらに変種Bでは次の破綻が生じた。

- **開発者側 workflow が判断の受信箱になる。** 生産者のない境界スタブが5枚並び、変換の筋がない。リリース判断が後続を持たない終端になるため、判断が何を引き起こすのかを図が示せない
- **変換チェーンの終端がファイル境界になる。** 開発者側 pipeline の終端が誰も欲しがらない中間物（パッケージング直後の配布単位）になり、「何のための変換か」が消える
- **実行主体と読み手が分裂するノードを収容できない。** レジストリ公開・ポータル転記は供給側が実行し消費側が読むため、「利用者側」というファイル名が内容の一部について嘘になる

一方で、変種Bで唯一よく読めた図（消費チームの営み）は3種別のままファイル分割で書ける。
読み手軸が生む価値はファイル分割で回収でき、種別軸にする必要がない。

### 「利用者⇒外部」は成り立たない

読み手軸を種別軸にできない理由の一つは、読み手と所在が独立の軸であることにある。
このリポは自分自身の採用リポであり、`install/` 由来の配置ファイルは canonical とバイト同一で repo ルートに実在する。
「採用リポ」group の成果物が物理的にこのリポの中にある。
ドッグフーディングするツールでは「誰がユーザーか」が判定不能になる一方、「判断を含むか」は常に判定できる。

## Consequences

- `.claude/skills/pfd-ecosystem/references/kind-taxonomy.md` の判定基準を判断軸に書き換える（種別選定の一次情報）
- ADR-0017 の「主役」表現は本 ADR の判定基準に置き換わる。種別の定義表・問診リスト・1種別1ファイル原則は有効なまま
- このリポの `.pfdsl/workflow.pfdsl` と `.pfdsl/runtime-pipeline.pfdsl` を判断軸で描き直す。生成系4プロセスと公開の自動部分が runtime-pipeline 側へ移り、`make gen-plugin` の二重モデル化が解消される
- 種別名 `runtime-pipeline` の `runtime` は判断軸と整合しない（ビルド時・導入時の変換を含むため）。改名は `type:` 列挙値の破壊的変更であり #670 として独立に扱う
