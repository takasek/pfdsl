# ADR-0040: 監査の対象についての契約と、1回の監査の実行管理を別の区分に置く

- Status: Accepted
- Date: 2026-09-26

## Context

ADR-0039 は配布層の所有範囲を3区分で定め、その live な一次情報を `pfd-ops/references/architecture.md`「昇格先の判定ルール」の0段目に置いた。
同 ADR は「配布層の判定が配布されない文書に依存しないため、そこで定義が閉じている」と主張した。

#1229 の事後レビュー（観点3(b)、F4）がこの主張の反例を示した。
0段目は区分 i に「着手可能性と終端監査の契約」を挙げるが、これは監査の対象がどの状態なら着手可能・完了かについての契約である。
一方、ADR-0039 が pfd-retro から binding へ移した「1 回の実行契約」は、実行 ID・cutoff・必須情報源集合の凍結・並行実行や引継ぎ時の checkpoint といった、1回の監査をどう実行として固定するかの規律である。
後者は0段目のどの区分の文言にも当たらず、ADR-0039 が binding へ移したという判断は0段目だけからは再現できなかった。

採用リポが pfd-retro を拡張し、実行の凍結規律の置き場を0段目で判定すると、区分 i の「終端監査の契約」に引き寄せて配布層の責務と読み得る。
そうなると自リポの binding には書かれず、配布物にも無いので、凍結規律を持たないまま運用される。
pfd-retro SKILL.md は契約を持たない binding でも適用単位の判断で実行するため、サイクルは止まらず、昇格先の誤判定として静かに残る。

同じ判定経路を持つ自リポの文書にも食い違いがあった。
`.pfdsl/bindings/pfd-ops.md` の冒頭は、新しい指示が「配布先リポでも一般に有効なら」配布 reference へ追記するよう指示しており、ADR-0039 が十分条件でないとした汎用性をそのまま昇格の根拠にしていた。
同じ箇所は、既に存在しない pfd-ops SKILL.md の節を参照していた。

## Decision

0段目の区分の境界を、監査の対象と監査の実行管理で分けて明記する。

- 監査に関わる区分 i・ii の項目が定めるのは、監査の対象について何を判定するかである。着手可能性・終端監査の契約は区分 i、知識成果物のライフサイクル監査の項目は区分 ii に入る。区分 ii の作業項目バックエンド連携は監査ではないので、この区別の対象にしない。
- その判定を1回の実行としてどう凍結し、記録し、引き継ぐか（実行 ID、cutoff、情報源集合の凍結、並行実行や引継ぎの checkpoint）は区分 iii とし、採用リポの binding に置く。

実行管理を区分 iii とする理由は、それが PFD の意味論から導けず、実行環境・並行性・証拠の可視性によって決まることである。
同じ監査観点を配布していても、どのホストがどの記録を保持し、誰に checkpoint を見せてよいかは採用リポごとに異なる。

区分の数と、区分 i・ii が提供すると決めた用途は変えない。
この ADR は定義の境界を明確化するもので、新しい用途を配布へ加えたり、既存の配布物を移したりしない。

自リポの判定経路を0段目に揃える。

- `.pfdsl/bindings/pfd-ops.md` の冒頭は、昇格の可否を「昇格先の判定ルール」で判定し、候補は0段目の区分 i・ii に入るものだけとする。存在しない節への参照は、宛先を定める「companion への書き分けルール」表への参照に替える。
- `.pfdsl/workflow.md`「知見の振り分け（3経路）」の経路1も同じ判定を通すと明記する。
- `.pfdsl/bindings/pfd-retro.md`「1 回の実行契約」は、区分 iii に当たるため binding が持つことを節の冒頭で示す。

## 検討した対案

**監査実行の契約を配布側の共通プリセットへ戻す。**
成立する案だが、ADR-0039 が自リポへ移した実行管理を、再び全採用者向けの保守責務（distribution-review・生成同一性・Codex ミラー・scaffold）にする。
実行管理の中身は採用リポの環境に依存するため、共通化しても採用リポ側の調整は残る。
既決の提供範囲を広げる変更になるので採らない。

**実行管理のための区分を新設する（3区分という前提を外す案）。**
区分を増やせば、区分 iii の「有用だが利用者の環境に任せるもの」と語の上で重ならずに済む。
しかし新区分の扱いは「配布せず採用リポの binding に置く」で区分 iii と同じになり、判定の結果を変えない。
扱いが同じ区分を増やすと、0段目の読み手が確かめる境界だけが1つ増えるので採らない。

**現状の文言のまま曖昧さを受容する。**
今回の分類を採用リポが上流の非配布文書なしに再現できる、という ADR-0039 の前提を満たさないため採らない。

## Consequences

採用リポは、pfd-retro の監査観点（A・B・C・D）と、その監査を1回の実行として固定する規律とを、0段目の文言だけで別の置き場へ振り分けられる。
配布 scaffold の `bindings/pfd-retro.md` は既に「1 回の実行契約」を採用リポが記入する節として持つので、scaffold の変更は要らない。

ADR-0039 の「0段目で定義が閉じている」という主張は、この明確化を経て成り立つ。
ADR-0039 の本文は書き換えず、Status 行に本 ADR による明確化を注記する。

自リポの運用負担は変わらない。
「1 回の実行契約」の内容と、それが binding にあることは以前と同じで、変わるのは置き場の判定が文言から再現できるようになる点である。

採用リポ側でこの区分を判別できるかは、変更後の bundle だけを渡す採用側プローブで確認する（#1208 R6b）。
この ADR の採用は、そのプローブの実施を意味しない。
