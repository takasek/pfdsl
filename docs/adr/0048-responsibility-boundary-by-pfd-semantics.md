# ADR-0048: PFDSL の責務を、PFD の意味論なしには成立しない判断に限る

- Status: Accepted
- Date: 2026-10-21

## Context

ADR-0039 は配布層の所有範囲を「提供すると決めた用途」で定め、3区分を置いた。
ADR-0040 は、監査の対象についての契約と1回の監査の実行管理を別の区分に分けた。
ADR-0039 の変更で配布物の散文は大きく縮み、`pfd-ops/references/work-cycle.md` は ADR-0039 が記録した 64,958 バイトから、2026-10-21 時点で 17,100 バイトになっている。

所有者が依頼した外部のセカンドオピニオン（2026-10-17、リポジトリ外の文書）は、ADR-0039 の線のまま残る漏れを3つ指摘した。

1. **判定が動機で書かれている。** PFD 運用に帰着するか、工程から呼ばれるか、という形の判定は、ほぼ何でも通す。委譲の失敗も、プロセスの入力不足の発見なので再整合に帰着する、と言えてしまう。ADR-0039 の「提供すると決めた用途」も同じ形をしている。ADR-0039 の Context は、D 層を「採用者にも役立つ」という理由で残すなら同じ理由が git 衛生にも成立する、という所有者レビューの指摘を記録している。それでも D 層は用途の宣言と任意化で残された。用途の宣言は、どの規律にも付けられる。
2. **ループを持つことと、ループを回すことが混同されている。** `work-cycle.md` は、binding の「ワークサイクルの追加手順」節を手順1〜3の各段で読ませる。このスロットを通じて、配布物が持たない git 衛生・委譲・レビューの規律が PFD のサイクルの内側で実行され、retro の findings もそこへ還流する。肥大化の主な経路は散文の置き場所ではなく、この主従の向きにある。
3. **実行の証拠に形式が無い。** retro はセッションの記録を非形式的に読む。そのため配布物が特定のハーネスの記録に結合し、外部の実行主体が出す記録を入力にできない。

同じレビューは、実行主体の方法論や制御フローを持つ外部の道具を確認した（pstack は `cursor/plugins` `101b274`、TAKT は `nrslib/takt` `c87caab`）。
確認した範囲では、どちらも成果物の依存関係から着手可能性を計算しない。
TAKT のタスク定義に依存のフィールドは無く、pstack の作業単位の表にも依存の列は無い。
着手可能性は宣言された成果物グラフから導出されず、coordinator の判断に委ねられている。
したがって、サイクルの選択・状態・終端監査を外部へ出すと、その責務の持ち主がいなくなる。
外へ出せるのは、ループを回す主体（driver）までである。

ADR-0039 の Consequences は、このリポの作業規律を将来 `takasek/common` へ抽出したときに自リポの負担が減る、と書いた。
しかし `takasek/common` は private である（2026-10-21 に GitHub の visibility で確認）。
公開リポの運用規約を、貢献者・Codex・クラウドのセッション・CI が読めない場所には置けない。

所有者は 2026-10-21 に、このレビューと再編の計画を受けて判断点 D1〜D6 を決めた。

## Decision

### 境界原則

PFDSL は、成果物の生成・依存・受入条件を表すモデルと、版の対応した実行証拠に照らしてその状態と構造を維持する契約を所有し、PFD の意味論なしには成立しない判断だけを担う。
誰がどの手法・制御手順・資源で実行するかは外部に委ね、retro は実行の失敗とモデルの欠陥を区別して、後者の場合だけモデルを改める。

ここで中核とは、言語・意味論・検証・問い合わせ・変更を担う CLI とライブラリ、およびモデルに対する手続き（選択・着手の宣言・完了・終端ゲート・報告・model retro）を指す。
後者を以下では protocol と呼ぶ。

この原則から導かれないまま配布するものが3つある。
所有者の決定（D1）で配布する付属機能、配布を続けるための配布機構（契約7）、アダプタ自身が外部へ書いた内容の読み戻し（D2）である。
どれも以下の区分の改訂でその扱いを定め、ほかの規則を配布層へ載せる先例にしない。

### 新しく導入する契約

この ADR の中心は次の7つの契約である。
後で述べる区分の改訂や配布物の整理は、上の3つの扱いを除き、これらから導かれる。

1. **中核に入れる判定。** PFD の意味論を取り除いても同じ意味で成り立つ規則は、中核に入れない。たとえば「作業完了の commit と同時に done にする」は、PFD を除いても commit と記録の同期という VCS の規則として成り立つので中核ではない。「done にするには criteria を満たした根拠を言えること」は、PFD を除くと意味を失うので中核に入る。あわせて、中核の規則が書き換える対象を、PFD の要素（artifact・process・edge・feedback・criteria・status・kind・boundary）、companion の構造的事実、`.pfdsl/config.json` の宣言、CLI が導出できる状態に限る。他の道具の skill・hook・CI 設定・agent 定義・作業記録の書式を書き換える規則は持たない。
2. **retro の結論は3値。** retro の各 finding の結論は「実行側の失敗」「モデルの改訂候補」「変更不要」のいずれかで、どれも根拠を伴う。観測をすべてモデルの欠陥へ翻訳しない。「変更不要」は、照合したモデルの要素と証拠を名指すことを要件にする。これは、何でも「変更不要」で閉じる逆向きの失敗を防ぐためである。「モデルの改訂候補」は次の6型の乖離として出し、右列の修正に落ちる場合だけ PFDSL の finding とする。右列に落ちない finding は、それを生んだ実行主体の側の宛先へ渡し、pfd-ops・pfd-retro の新しい規則に翻訳しない。「忘れ物 = 構造の欠落」は無条件の読み替えでなく、「構造の欠落という仮説を検査する」に改める。

   | 観測された乖離 | PFD への修正 |
   |---|---|
   | 追加の入力が必要だった | 入力 edge の追加（必要ならその入力の producer も） |
   | 想定した process の分割が成立しなかった | process の統合・分割（ADR-0004 の粒度基準） |
   | 本当は feedback loop が必要だった | `>>?` edge、または版 artifact（ADR-0002・ADR-0011） |
   | artifact の定義が曖昧だった | artifact の分割・改名、description・criteria の具体化 |
   | criteria が観測不能だった | 観測できる形への criteria の書き換え |
   | 下流で必要な判断を上流の process が実質的に行っていた | 出力の付け替え、または境界の再モデル化（決定の先取り） |

3. **証拠は版と対応する。** 受入の証拠は、どのモデル版・成果物版・criteria に対するものかを示す。retro と終端ゲートが入力にする証拠の最小の形は、変更されたパスの一覧、行った status の遷移、作業項目の id、型付きの乖離報告であり、それらが上の3つの版に対応付けられていることである。保存方式や run ID の形式は決めない。実行管理の凍結（実行 ID・cutoff・checkpoint）が区分 iii であることは ADR-0040 のとおりで、証拠の形が決まれば、それは証拠を出す実行主体の側の問題になる。
4. **run の成功と artifact の受入を分ける。** 外部の実行主体の完了（例: TAKT の `COMPLETE`）を、無条件に `done` へ変換しない。`done` は criteria に照らした受入の後に付ける。
5. **同じ作業の spawn・retry・stop を制御する主体は1つ。** `/pfd-cycle` は protocol の参照 driver であり、外部の orchestrator と同じ process に重ねて使わない。外部の orchestrator を使う場合、PFDSL はその orchestrator へ着手可能集合と process の入出力・criteria を渡し、証拠を受け取る。
6. **アダプタは意味論を定義しない。** 作業項目バックエンド・VCS・orchestrator との連携は、外部の出来事を PFD の操作へ写すだけである。完了と回収の規則は中核に1つだけ置き、アダプタは「いつ実行するか」だけを決める。この帰結として、完了チェーン回収の保持規則（done でない artifact を出力する process と、その入出力 artifact を残す）は CLI に置く。作業項目 id と process id の対応（恒久の prefix、複数対応の連結、起票前の plain な id）、managed / exempt の判定基準、作業項目の close が status を動かさないこと、process と run の対応は、バックエンドに依存しない protocol の契約として1つだけ置く。
7. **配布機構は責務の根拠にしない。** 配布ファイルの鮮度照合（install-sync）、移行状態の記録（`appliedMigration`）、plugin の版照合、環境の採取、上流への報告（pfd-upstream-report）、配布前のレビュー（distribution-review）、生成（gen-plugin）、Codex のミラー、配布層への還流の監査（L4 滞留監査）は、PFDSL の責務ではなく配布のコストとして別枠で管理する。配布を続ける限りこれらは必要だが、その必要性を責務の範囲を広げる根拠にしない。

### 区分の改訂（ADR-0039 の一部上書き）

ADR-0039 の3区分の骨格と、区分 iii を採用リポへ移した判断は維持する。
次の点を改める。

- **区分 i** は上の中核であり、契約1がその判定である。記法・種別・後ろ向き導出による執筆・図の監査観点に加え、protocol の各段と契約2〜6を含む。契約5は、実行主体がどう spawn・retry・stop するかを定めるものではない。同じ process の着手・状態・証拠を書き込む経路を1つに保ち、PFD 側が外部の orchestrator へ渡すものと受け取る証拠を定める protocol 側の規則なので、区分 i に入る。実行主体が変えてよい既定値（1サイクルで進める process の数など）は規則にせず既定のプリセットとして区分 i と一緒に配布し、どの既定値でも残す PFD 側の記録（process と run の対応）だけを規則にする（D3）。
- **区分 ii** の要件に「判定の論理が PFD の語彙で書ける」を加える。ADR-0039 の区分 ii は、提供すると決めた用途ごとに理由と範囲を持つことを求めていた。この要件は残すが、用途はどの規律にも宣言できるので、それだけでは入口が閉じない。対象が PFD 運用に関わり用途が決まっていても、判定の論理が PFD の要素で書けなければ区分 ii に入らない。区分 ii のアダプタは契約6に従う。外部の出来事（既定ブランチへの push など）を契機に中核の操作を起動する部品は、CI のワークフロー定義の形を取っていても区分 ii である。実行主体（agent・人）が行う外部への書込みの手順は書き込む主体に属するので区分 iii とし、アダプタ自身が外部へ書く場合の読み戻しだけを区分 ii に残す（D2）。読み戻しの比較は PFD の語彙で書けないが、書いた部品自身の責任なので区分 ii に置く。現時点の用途は、作業項目バックエンドとの連携である。ADR-0039 が区分 ii (1) に挙げた「設計記録の配置」は、記録を作る実行主体の実践なので区分 iii に移す。ADR-0039 が再承認参照について区分 ii とした backend の事実（コメントは編集できるので URL 文字列では自己参照を判定できない等）も、設計記録の再承認のためだけに使われるので、同じく区分 iii とする。これは、GitHub Issues プリセットから実行主体の書込み規律と PR 運用（設計確定の証拠を含む）を外す後続の変更と同じ判断である。
- **区分 ii (2) の知識成果物ライフサイクル監査（pfd-retro D 層）は、区分 ii から外す。** 判定の論理は一般の文書管理と同じで、上の要件を満たさない。そのうえで所有者の決定（D1）により、PFD 運用の付属機能として同じ core plugin で配布する。対象は PFD 運用が生む知識成果物に限り、採用の宣言（`knowledgeLifecycleAudit`、ADR-0041・ADR-0042）は変えない。任意で無効化できても、配布側の保守責務は残る。この付属機能は区分の判定から導いたものではなく、他の汎用規則を配布層へ昇格させる先例にしない。付属機能に項目を加えるには、昇格の判定ではなく新しい所有者の決定（ADR）を要する。D 層の項目のうち PFD の語彙で書き直せるもの（休眠能力、停止しない機構）は、区分 i の図の監査レンズへ移す。
- **区分 iii** に、実行主体を主語にする規則を明示的に加える。セッション・ターンの構造（締めの確認、同じターンでの起動など）、commit・PR・branch・worktree と結び付けた時点や手順、委譲とその worker（実装 agent を含む）、レビューの組み方、実行主体が行う外部書込みの手順と本文の規約、設計記録の置き場所・書式と再承認がこれに当たる。retro で実行主体の振る舞い（委譲の失敗、選択前の着手など）を点検する観点も同じである。
- **配布機構**（契約7）は区分の外の別枠とする。配布物に含まれるものもあるが、区分 i・ii の判定の根拠にも、昇格の候補にもしない。既に配布している付属機能と配布機構の記述を直すことは昇格ではなく、上流がそれぞれの正本で行う。

live な一次情報は ADR-0039 と同じく `pfd-ops/references/architecture.md`「昇格先の判定ルール」の0段目であり、本 ADR に合わせて書き換える。
0段目は配置の判定器なので、上の改訂のうち配置の判定に要るもの（契約1、区分 ii の要件と契約6、区分 iii の範囲、付属機能と配布機構の扱い、既定値をプリセットとして示すこと）だけを入れる。
契約2〜5は protocol と retro の中身であり、0段目には入れない。
ただし契約3・5の置き場が区分 iii と読まれないよう、PFD 側と外部の実行主体との受け渡し（渡すもの、受け取った証拠の扱い、書き込む経路を1つに保つこと）が区分 i に入ることだけは0段目に書く。
0段目では、ADR 番号に依存せずに判定が閉じるよう、規則をその場で述べる。

ADR-0039 と ADR-0040 の本文は書き換えない。

### `takasek/common` を移設先とした記述の訂正

ADR-0039 の Consequences が `takasek/common` を将来の抽出先としたことを訂正する。
`takasek/common` は private なので、公開リポの運用規約の置き場にしない。
このリポの開発規律はこのリポに残し、PFD protocol のフック（binding の「ワークサイクルの追加手順」スロット）から切り離して、root の指示から読ませる。
所有者個人のリポ横断の規律は、所有者の global 設定が持つ。
同じ開発規律を別のリポでも使いたくなった場合は、2つめの利用者が現れた時点で公開の plugin として抽出し、抽出先を private リポにしない。
新しいリポジトリは今は作らない。

### 判断点 D1〜D6

| ID | 問い | 決定 | 根拠・条件 |
|---|---|---|---|
| D1 | D 層を配布に残すか | 同じ core plugin 内の独立した skill にする。休眠能力と停止しない機構は PFD の語彙で書き直し、図の監査の A・B レンズへ移す | 採用先が D 層を adopt しており、binding と companion を運用から乖離させないための仕組みとして所有者が必要と判断した。別の plugin にすると採用先に追加の導入が要り、導入するまで能力を失うので、同じ plugin に置く。宣言のキー `knowledgeLifecycleAudit` は変えない。配布側の保守責務は残る |
| D2 | 複数行本文の exact readback をどこに置くか | 規約の本文はこのリポの binding へ移し、アダプタには「自ら外部へ書く場合は読み戻す」原則の1文を残す | 完了チェーン回収の bot PR は第三者の action が作り、読み戻していない。その本文は固定の説明と実行条件（PR を開いた token の種類、検査に使った CLI の版）だけで、正しさの根拠は diff にあり、人がマージするので信頼してよい。本文に削除する id や証拠などのデータを載せ始めたら、その時点で読み戻しを足す |
| D3 | 「1サイクル1プロセス」を protocol に残すか | 既定のプリセットに下げ、process と run の対応の記録を必須にする | 複数の process をまとめて進める状況が実際に頻繁にある。対応の記録は既存の process の `location:` と PR 本文で足り、新しいフィールドは作らない |
| D4 | 完了チェーン回収の CLI の形 | トップレベル動詞 `prune`。意味論は GitHub Issues 版の保持規則を正とし、ファイルベース版はそれを参照する。出力モデルは ADR-0022（既定は stdout、`--write`、`--check`、`--json`） | ADR-0030 は `graph` を読み取り専用の問い合わせ、`status` を status から導出される計画クエリとしている。書き換えを伴うトップレベル動詞 `delete`・`rename` の先例に揃える |
| D5 | plugin を core とアダプタに分けるか | 分ける方針で設計仕様を作る | 設計仕様で費用が過大と分かった場合は、1つの plugin のまま `.pfdsl/config.json` の宣言で絞る案へ切り替える。plugin 間の依存宣言の可否を最初に確認する。marketplace の `plugins` は配列で、同じ marketplace に2つめの plugin を置ける |
| D6 | 実行主体との往復をどう検証するか | pstack で試す実験 E1 を先に行い、TAKT で試す実験 E2 は条件付きにする | 配布物の protocol の縮小は D6 に依存しない。縮小の効果が大きいこのリポの作業規律を、導入の軽い道具で先に測る。E1 ではマージを伴う playbook を使わない（このリポではマージは人が行う）。E2 は、外部からの強制や無人実行を検討するとき、または claim / complete のような CLI 動詞を足す前に行う |

### 非目標

- TAKT の workflow を生成する compiler や、汎用の実行スキーマ・イベント基盤は作らない。
- 実行主体との往復を1回確かめるまで、claim / complete のような CLI 動詞は作らない。
- spec §2.7.1 の PR・merge のタイミングを述べる段落は、この再編では変えない。変える場合は issue を経る（ADR-0010）。
- このリポの開発規律そのものの見直し（内容の削減・言い換え）はしない。扱うのは置き場所と読み込みの経路だけである。
- workflow PFD と TAKT の workflow の整合検査、process から委譲 brief への射影は、需要が出るまで作らない。

## 検討した対案

**PFDSL を静的なモデル・問い合わせ・検証だけに限る（H1）。**
一部を採る。
中核は agent なしで完結し、決定的で、業種に依存しないべきだという点はそのとおりで、protocol を散文ではなく CLI と短い文書にする方向はこの仮説から来ている。
しかし全面的には採らない。
status の意味、done の根拠、版と feedback の意味、ready / blocked はすでに動的な意味論である。
証拠からモデルを直す側のループは、モデルの所有者以外には正しく持てない。

**サイクルを完全に外部の orchestrator へ出す（H2）。**
driver については採り、protocol については採らない（契約5）。
Context で述べたとおり、選択・状態・終端監査を成果物グラフから担う仕組みは、確認した外部の道具に無い。

**retro は PFDSL ではなく一般の agent・プロセス改善の道具である（H3）。**
半分を採る。
セッションの retro（委譲の失敗、流した違和感、選択前の着手）と知識管理の大半は一般の道具の領分である（契約2、区分 iii、D 層の扱い）。
しかし忘れ物を欠けた edge として読むことや、決定の先取りを境界の再モデル化として読むことは、PFD の意味論なしにはできないので PFDSL に残す。

**現在の線引きで十分であり、大きく削る必要はない（H4）。**
規模については採る。
ADR-0039 で大きな削減は済んでおり、書き直しは要らない。
構造については採らない。
binding のスロットを通じた主従の逆転、証拠の入口の未定義、protocol が散文にしか無いことは、今の線引きのままでは残り続ける。

**PFD の再整合に帰着するかどうかで判定する（再編の暫定案）。**
採らない。
判定が動機で書かれており、委譲の失敗のような実行主体の問題も「入力不足の発見」として通る。
契約1は、判定を書き換え先と意味論の要否で行う形に置き換えたものである。

**ADR-0039 の区分 ii を現状のまま維持する。**
採らない。
用途の宣言は任意の規律に付けられるので、区分 ii の入口が閉じない。
D 層は区分 ii の新しい要件を満たさないが、それを区分 ii に残したまま要件を足すと、要件と例外が同じ区分に同居し、読み手が例外を先例として読む。
付属機能として区分の外に置き、先例にしないと明記するほうが入口を閉じられる。

**D 層を配布から外す、または別の plugin にする。**
セカンドオピニオンは、休眠能力と停止しない機構を除く D 層を利用者の環境へ出すよう勧めた。
所有者が採らなかった（D1）。
採用先が実際に D 層を adopt しており、外すか別の plugin にすると、採用先は導入し直すまで能力を失う。

**exact readback をアダプタから完全に外す、または配布層に全文を残す。**
前者はセカンドオピニオンの案で、後者は ADR-0039 の判断である。
所有者はどちらも採らず、規約の本文を binding へ移して原則の1文を残した（D2）。
アダプタ自身が書く本文の正しさを人が確認できる限り読み戻しは不要で、データを載せ始めた時点で要る、という条件で両案の間を切った。

**外した責務のために新しいリポジトリを作る。**
今は採らない。
pfdsl は公開 OSS であり、Claude Code・Codex・クラウドのセッション・CI がこのリポのチェックアウトだけから規律を読めなければならない。
GitHub アダプタは、CLI の版・生成器・テスト・distribution-review を共有しているので、別のリポにすると版の固定をリポ間で合わせる必要が生じる。
同じ marketplace の2つめの plugin として分ける（D5）。

**外した開発規律を `takasek/common` へ移す（ADR-0039 の記述）。**
採らない。
`takasek/common` は private で、公開リポの貢献者や CI が読めない。

**「1サイクル1プロセス」を protocol の規則として残す（セカンドオピニオンの案）。**
採らない（D3）。
複数の process をまとめて進める運用が実際に頻繁にあり、規則として残すと記録と実態が食い違う。
代わりに process と run の対応の記録を必須にして、追跡可能性を保つ。

**完了チェーン回収を `graph` か `status` のサブコマンドにする、または配置スクリプトのまま残す。**
前者は、ADR-0030 がこの2グループを問い合わせとして定めたことと衝突する。
後者は契約6に反し、ファイルベース版との意味論の重複が残る（D4）。

## Consequences

`pfd-ops/references/architecture.md` の0段目を、本 ADR に合わせてこの変更で書き換える。
0段目の中で D 層を区分 ii と述べていた説明は付属機能の説明に改め、`pfd-retro/references/knowledge-lifecycle.md` が監査範囲の根拠として区分 ii を名指していた語も、同じ変更で区分名に依存しない言い方に改める。
採用先から見える変化は、0段目の判定と、L4 滞留監査がそれに従って昇格候補を選ぶ範囲である。
実行主体を主語にする汎用の規則は、昇格候補ではなく利用者環境への移設候補として報告される。

既存の配布物には、この判定に合わない記述が残る。
本 ADR は決定を記録するだけで、それらの手順の挙動は後続の変更が改めるまで現行のまま有効である。
後続の変更は次のとおりで、それぞれ別の変更束にする。

- このリポの作業規律を、binding の「ワークサイクルの追加手順」スロットではなく root の指示から読ませる。配布物の整理より先に統合し、移行の途中でこのリポのセッションが規律を読まなくなる状態を作らない。
- `work-cycle.md` を実行主体に依存しない protocol に絞る（定期監査の同ターン起動、「知見と機械化」の後半、D3、契約4・5、スロットの縮小）。
- pfd-retro を3値の model retro と証拠の契約に絞り、C 層の汎用項目を外し、D 層を D1 のとおり独立した skill とレンズへ分ける。L4 滞留監査は配布層への還流として別の節にする。
- 配布物の中に消費者のいない実装 agent（pfd-implementer）を配布から外し、このリポでは生成し続ける。
- GitHub Issues プリセットから、実行主体の書込み規律と PR 運用を外す（D2）。
- バックエンドに依存しない作業項目の対応契約を1つにする（契約6）。
- 完了チェーン回収を CLI の動詞にする（D4）。
- core plugin と GitHub アダプタ plugin を分ける（D5）。
- protocol に指定したファイルの実行主体の語彙を、報告から始めて検査にする。
- 実行主体との往復の実験（D6）。

採用先への移行案内は、これらの変更が公開される時点で `.pfdsl/workflow.md`「採用先への移行案内」に従って扱う。
plugin の更新だけで手順が配布物から消える採用先のために、各変更の案内には手元に残す方法を含める。

このリポの運用負担は内容の点では変わらない。
変わるのは規律の置き場所と読み込みの経路である。
配布側の保守責務は、D 層と配布機構について残る。

ADR-0039 の Status に `Superseded in part by ADR-0048` を加え、本文は書き換えない。
上書きするのは、区分 ii の要件、D 層の区分、設計記録の配置と再承認参照の backend の事実の区分、複数行本文の readback の置き場所、`takasek/common` を移設先とした記述である。
ADR-0040 も一部を上書きする。
監査の対象と実行管理の区別は維持し、知識成果物のライフサイクル監査の項目を区分 ii に入るとした記述だけを、付属機能の項目に改める。
ADR-0040 の Status にもその旨を加え、本文は書き換えない。
ADR-0041・ADR-0042 の宣言のキーと置き場所は変えない。

本 ADR の規則は配布範囲の判定であり、PFD の執筆と点検の規則を含まないので、品質ガイド（pfdsl スキル）への蒸留は要らない。
