# ADR-0053: 仕様 ID の永続性を main の履歴から適用し、1つのブロックに1つの ID だけを許す

- Status: Accepted
- Date: 2026-11-08
- Partially supersedes: ADR-0027「ID の性質」のうち、削除した ID を tombstone に記録する対象を、main の履歴に入った ID に限る部分

## Context

ADR-0027 は、仕様 ID を不透明で永続なものとし、削除した ID の再利用を禁じた。
ただし、永続性がどの時点から ID に掛かるのかと、1つのブロックに複数の ID を付けてよいのかは定めていなかった。

#542 の段階移行では、Stage 1 を統合ブランチの上で進めた。
その間に main 側の作業が、同じ §15.1 に別の ID を付けた（`3ac0190a`）。
採番前の確認（`mint-check`）はそれぞれの作業ツリーの中しか見ないので、main 側と統合ブランチは互いの ID を見られなかった。
加えて `mint-check` の既定の走査範囲は spec.md だけで、ADR-0027 自身が定義する `SPEC_id_syntax` も既出として見つけられなかった。
両者を統合する最初の変更（PR #1588 の初版）は、§15.1 に2つの ID を残した。
さらに、main で削除済みの節の ID を、廃止の経緯を書いた別のブロックへ付け替えた。
既存の検査は、どちらも通した。

## Decision

### 永続性の境界

- ID の永続性（ADR-0027「ID の性質」）は、その ID が main の履歴に入った時点から掛かる。
- main に入る前のブランチや PR の中で付けた ID は、改名しても削除してもよく、tombstone も要らない。
- main の履歴にある ID を削除する場合は、ADR-0027 のとおり tombstone に記録する。tombstone の実体は、最初にそのような削除を行う変更で導入する。

### 1つのブロックに1つの ID

- 1つのブロックが持てる ID は1つだけとし、別名は認めない。
- `check-spec-ids` は、同じブロックに2つ以上の ID があればエラーにする。ブロックは、ADR-0027 のレンジ規則で決まる範囲の開始行で識別する。
- 統合の際に同じブロックへ2つの ID が付いた場合は、main の履歴にある方を残す。どちらも main の履歴に無ければ、一方を選ぶ。
- 定義を別のブロックへ移してよいのは、ブロックの内容ごと移し、同じ ID が同じ内容を指し続ける場合に限る。マーカーだけを別の内容のブロックへ付け替えることは、ID の削除として扱う。

### ID を持つ節への節番号参照

- 同じファイルの中で、ID を持つ番号付きの節を素の `§N.M` で参照することはエラーにする。参照は `[[SPEC_xxx]]` で書く。
- この規則は同じファイルの中の参照に限る。spec.md の節を当時の番号で書いた版履歴（`docs/spec/spec-history.md`）は、対象に入らない。

### 採番前の確認の範囲

- `mint-check` の既定の走査範囲は、`check-spec-ids` と同じ `docs/**/*.md` とする。

### リスト項目の範囲

- ADR-0027 のレンジ規則にあるリスト項目の範囲は、CommonMark（GFM）の list item の範囲とする。
- リストの最後の項目は、リストの終わりで終わる。

## Alternatives

- **別名を許可リストで認める案。** 外部に出た旧 ID を、現存する同じ規範へ解決し続けられる。所有者の判断（2026-11-08）で採らない。境界を main の履歴に置くと、統合ブランチにしかなかった ID は保護の対象から外れるので、別名が要る場面がなくなる。
- **永続性の境界を origin への push に置く案。** PR の中で付けた仮の ID を改名するたびに、tombstone が要る。所有者の判断で採らない。
- **永続性の境界をリリースに置く案。** 外部の PR や issue での引用が保護されない。所有者の判断で採らない。
- **`mint-check` で remote の全ブランチを走査する案。** 実際に起きた事故は、同じ節に別の slug が付いたものだった。slug ごとに走査しても見つからず、push していないブランチも見えない。1つのブロックに1つの ID だけを許す検査なら、統合の時点で決定的に落とせる。
- **統合ブランチで段階移行を続ける案。** 部分移行の状態は lint を通り、roadmap の wip で表せる。統合ブランチの進捗は main の roadmap から見えず、二重採番の原因になった。

## Consequences

- ADR-0027 の「ID の性質」は、削除した ID をすべて tombstone に記録するよう求めていた。本 ADR はその対象を main の履歴に入った ID に限るので、この部分を部分置換する。
- そのほかの ADR-0027 の決定は保たれる。本 ADR は、ADR-0027 が決めていなかった次の4点を足す。ADR-0027 の Status には、部分置換と改訂の両方を注記する。
  - 1つのブロックに1つの ID
  - ID を持つ節への節番号参照の禁止
  - 採番前の確認の範囲
  - リスト項目の範囲
- `check-spec-ids` は、重複と dangling に加えて、複数の ID を持つブロックと、ID を持つ節への節番号参照を検出する。
- 検査が見るのは1つのブロックの中の複数 ID である。見出しとその直後の段落に別々の ID を付けると、同じ規範に事実上の別名が付いても検査は通る。入れ子の ID は正当な使い方と区別できないので、この形はレビューで確かめる。
- 1つのブロックに1つの ID だけを許す検査はレンジ規則を使うので、ADR-0027 の Consequences にある「レンジ規則は当面の lint には未実装」は当てはまらなくなる。
- spec.md の外にある節番号参照（コード・テスト名・ADR）は、本 ADR の対象外である。
