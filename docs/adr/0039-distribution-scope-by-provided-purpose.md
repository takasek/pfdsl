# ADR-0039: 配布層の所有範囲を提供すると決めた用途で定め、汎用性では定めない

- Status: Accepted
- Date: 2026-09-19

## Context

配布物の散文は、汎用性だけを基準に増え続けていた。
ADR-0023 が定めた昇格基準は「固有名詞を含まず、そのスキルの全利用者に無条件で効く」であり、PFD 運用と無関係な規律でもこの条件を満たせば配布層へ昇格できた。
その結果、git 衛生・委譲規律・設計記録の書式・レビュー menu・commit 粒度といった、PFD 運用に固有の用途を持たない規律が bundle の大部分を占めた。

#1208 の責務境界の監査が、配布物と自リポ運用文書の14ファイル・275,670 バイトを節単位で分類した。
配布側の最大ファイルである `references/work-cycle.md`（64,958 バイト）のうち、PFD 固有でない節が大半を占めることが分かった。
これらの散文は配布層に置かれている限り、distribution-review・`check-distributed-prose`・gen-plugin の生成同一性・Codex ミラー・scaffold の5機構に保守義務を生み、さらに pfd-retro の L4 滞留監査の対象として「昇格候補」に戻り続ける。

所有者レビューは2回入り、「配布物に残す」基準の不整合を指摘した。
知識成果物ライフサイクル監査（pfd-retro D 層）を「採用者にも役立つ」で残すなら、同じ理由が git 衛生にも成立する。
また「工程から呼ばれる」ことや「binding で有効化できる」ことを所有の理由にすると、同じ基準で git 衛生や委譲規律も配布層へ戻れてしまう。

## Decision

配布物の所有範囲を、PFDSL が提供すると決めた用途で定める。
3つの区分を置く。

- **区分 i — PFD 固有の意味論・活用法。** 記法、kind taxonomy、grill、ready/blocked・終端監査・status 更新の契約、図の監査観点。既定で提供する。
- **区分 ii — 提供すると決めた用途に基づく連携・運用プリセット。** 用途ごとに提供する理由と範囲を書く。現時点で提供すると決める用途は2つ。(1) 作業項目バックエンドとの連携（GitHub Issues と file-based tracker）: 作業項目と roadmap の対応、完了チェーンの回収、設計記録の配置。(2) 知識成果物ライフサイクルの監査（pfd-retro D 層）: 範囲は PFD 運用が生む成果物に限り、一般の文書管理には広げない。
- **区分 iii — 有用だが利用者の環境に任せるもの。** git 衛生、委譲規律、設計記録の書式と再承認、レビュー menu、commit 粒度。配布しない。

昇格基準にこの区分を0段目として置く。
昇格候補になるのは区分 i か区分 ii に属するルールだけで、固有名詞を含まず全利用者に効くことは必要条件であって十分条件ではない。
工程から呼ばれることや binding で有効化できることは所有の根拠にしない。
区分 ii の項目を任意で無効化できても、配布側の保守責務（distribution-review・生成同一性・Codex ミラー・scaffold）は残る。

区分 ii (2) の知識成果物ライフサイクル監査は選択項目にする。
D 層7項目を `pfd-retro/references/knowledge-lifecycle.md` へ分け、`.pfdsl/bindings/pfd-retro.md` が `知識成果物ライフサイクル監査: 採用する` を宣言したときだけ読む。
宣言が無ければ、対象の知識成果物が実在しても監査しない。

区分 iii の移設先は採用リポの binding である。
このリポでは `work-cycle.md` の区分 iii を `.pfdsl/bindings/pfd-ops.md`「ワークサイクルの追加手順」へ、`github-issues-backend.md`「設計確定の証拠」の書式・再承認部分を同 binding の「GitHub Issues バックエンドの設計記録」へ、pfd-retro の「1 回の実行契約」と上流専用2項目を `.pfdsl/bindings/pfd-retro.md` へ移した。
`work-cycle.md` に残るのは運用契約・定期監査・前提条件・4手順の骨格・PFD 固有の終端ゲート項目で、binding に「ワークサイクルの追加手順」節があれば手順1〜3の各段でそれに従う旨だけを本文が指す。

`github-issues-backend.md`「規約」節の「複数行本文の外部書込み」は配布層に残す。
成功表示や返却 URL が persisted body の証拠にならないのは GitHub API の性質であり、保存内容の一致確認は連携プリセット固有の配布契約（区分 ii）である。
binding へ委ねるのは Format 3 の書式と再承認参照の検査に限る。

## Consequences

採用リポは git 衛生・委譲・設計記録の書式・レビュー menu の手順を bundle から受け取らなくなる。
必要なら自リポの binding か利用者環境（global 設定・共通リポ）で持つ。

この線引きの最も鋭い帰結は、GitHub Issues バックエンドを採用するリポが、canonical comment URL の文法・node ID による自己参照判定・`lastEditedAt` の時間窓を自分の binding で書くことになる点である。
これらは GitHub の object model に由来する事実（コメントは編集可能なので URL 文字列では自己参照を判定できない等）を符号化しており、書式の好みではない。
独立レビューはこの性質を根拠に、機構は連携プリセット側（区分 ii (1)）に残すべきだと結論した。
それでも移設する理由は、#1208 の処遇表 A が「Format-3 の書式・再承認の時間窓・移行履歴の cutoff・構造 parser の意味論は区分 iii」と所有者の判断として定めたことである。
採るのは所有者の線であって、独立レビューの線を無効と示せたからではない。
この分担が採用リポに過大だと判明した場合、動かすのは区分の定義でなく処遇表の該当行になる。
`work-cycle.md` が binding の追加手順を指す一文を残すため、採用リポは移設先を自分で用意できる。
`check-companion-bindings` は `.pfdsl/bindings/pfd-ops.md` が存在するとき「ワークサイクルの追加手順」見出しを必須にするので、節を置いたリポでは見出しの消失が検出される。

自リポの運用負担は減らない。
移設した手順は binding で引き続き必須であり、内容も変えていない。
減るのは配布側の保守義務だけで、自リポの負担が減るのは将来この規律を `takasek/common` へ抽出したときである。

distribution-review と `check-distributed-prose` の対象が縮む。
機械検査は1つも撤去していない。
pfd-retro の L4 滞留監査は、0段目に入らない汎用ルールを昇格候補にせず、利用者環境への移設候補として報告する形に変わる。

ADR-0023 の昇格経路は存続し、その判定条件だけが本 ADR で改訂される。
