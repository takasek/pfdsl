# ADR-0036: 配布プロンプトは公開境界でレビューし、承認済み commit を記録する

- Status: Accepted
- Date: 2026-08-01

## Context

配布 bundle に入る散文には、上流リポの文脈でしか意味を持たない記述が混入する。
利用側で読むと意味不明になるか、実行不能な指示になる。

このクラスは自分自身の修正を通じて再発している。
#340（配布 SKILL.md への上流専用指示の混入）を直した PR #374 が、#674 で問題になる「非配布」という文言を新規に持ち込んだ。
「配布層に固有名詞・issue 番号・パスを書かない」という散文の規約は既に存在し、それだけでは効いていない。

同時に、この欠陥クラスを検出する手法自体は ADR-0029 が既に定めていた。
定めたうえで、起動条件がどこにも書かれていなかったため作成時の1回で休眠した（#680）。
スキル・companion・スクリプト・CI・Makefile のいずれからも参照ゼロだった。

つまり不足していたのは手法ではなく、**手法が必ず走る瞬間**である。

## Decision

### 1. 決定可能な部分は機械が、残りはレビューが見る

語彙で判定できる違反（`.claude/` 形だけで書かれた bundle パス、裸の issue 番号）は `scripts/check-distributed-prose.mjs` が毎 CI で検査する。
より広いクラス — 散文の**主語**が上流の作業机であるもの — は語彙では判定できない。
実測で棄却している: 「リポルート」は bundle 中に7回出現し、うち6回は利用側リポのルートを正しく指す。
ここに規則を置くと正しい散文の上で鳴り続け、定常的な偽陽性が検査全体を沈黙させる。

カバレッジより信号対雑音比を優先し、決定可能な部分集合だけを機械化する。

### 2. レビューは利用側の読み手を実際に走らせる

観点を机上で当てるのではなく、sandbox に隔離した subagent に「利用側リポのメンテナがやる作業」をさせ、詰まりを観測する。
渡すのは課題であって観点ではない。
観点カタログを渡せばチェックリスト照合になり、それは3回続けてこのクラスを見逃した机上レビューそのものになる。

sandbox はディレクトリとして実体化する。
ADR-0029 の Limitations が記録したとおり、fresh subagent は skill の解決先が呼び出し元 worktree に紐づくため、指示だけでは「plugin だけを渡された読者」を再現できない。
sandbox 外を読んだ痕跡が報告に出た probe は無効として回し直す — 越境した probe は上流の読み手として答えており、その報告で pass を出すと検出力が落ちたことに気付けない。

### 3. 承認は commit hash として記録し、`make release` が齟齬でブロックする

`docs/distribution-review/reviewed.json` が承認済み commit を持つ。
記録と HEAD の間に配布 `.md` の差分があれば、`make release` の pre-tag checks が tag を打つ前に落ちる。
逃げ道は用意しない — 緊急時に一度使われた escape hatch は、以後そのゲートの通り方になる。

**hash を進めるのは差分モードだけとする。**
全文モード（手動起動）は実行記録と修正を残すが hash は進めない。
全体を見る分ひとつの変更に対する解像度が差分モードに劣るため、これで承認済みとすると差分観点の穴を見逃したまま記録だけが進む。
全文モードの修正は未レビュー差分として残り、次の差分モードが必ず拾う。

記録の初期値は `null` とし、diff base を git の空ツリーに落とす。
最初の差分モード実行が構造上そのまま全文レビューになり、「誰も読んでいない内容を承認済みとして記録する」プレースホルダが要らなくなる。

### 4. 起動条件は公開境界の希少性そのものに置く

配布層に触れるコミットは全マージの約2割ある。
その頻度でレビューを義務化すると、軽い課題で素早く記録を埋める方向に劣化する。
公開は稀で、かつ利用側が実際にその散文を渡される唯一の瞬間なので、そこに置く。

## Rationale

1. **散文の規約は同型の再発を止めなかった**: #340 → PR #374 → #674 が実測。規約でなく機構が要る
2. **手法があっても起動条件がなければ休眠する**: ADR-0029 が1回で止まった（#680）。本 ADR は手法を作り直すのではなく、既にある手法に起動条件を与えるものである
3. **ノイズを含む検査は読まれなくなる**: このリポ自身が「定常的な偽陽性が検査を沈黙させる trap」として記録している型
4. **レビュー対象は利用側が受け取る現物にする**: 判定は組み上がった bundle に対して行う。canonical との一致は gen-plugin identity が担保しているので、現物を見ても編集先は一意に決まる

## Consequences

- レビュー対象は `plugin/pfdsl/**/*.md` から生成物3本（`spec.md` / `examples.md` / `samples.md`）を除いた22ファイル・約1,000行。除外分は DSL の言語仕様と実例集であり、上流の作業机について語る文書ではない
- 除外の帰結として、`references/spec.md` の変更履歴節にある裸 issue 番号8件は検査対象外のまま残る
- 公開と公開の間に混入した欠陥は、次の公開まで検出されない
- `git tag && git push --tags` は `release.mjs` を通らない。ただし marketplace の `ref` pin を動かさない限り利用側の受け取り内容は変わらないため、prompt 配布に対する実害は限定的
- commit hash 方式は、記録が指す commit に到達できない clone（浅い clone・squash merge）で判定不能になる。その場合は黙って通さず fetch を促して落とす
- ADR-0029 は廃止しない。4観点のうち観点1（同梱物の妥当性）に起動条件と自動検査を与えたのが本 ADR であり、観点2・4 の自動化は未着手のまま残る
