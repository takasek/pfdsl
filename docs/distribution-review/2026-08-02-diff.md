### (a) 配布プロンプトの欠陥

1. **`pfd-ops/references/work-cycle.md:49` が上流リポを主語にしている。**
   「**バックストップ**（(a) について、**このリポでは**）: … `scripts/lib/retro-reminder-check.mjs`」。
   利用側は「このリポ」を自分のリポと読み、存在しないパスを指されて止まる。
   bundle は同じ役割の `hooks/retro-reminder-post-tool-use.mjs` を同梱しているのに、この文はそれに触れていない。
   機械検査の2ルールはどちらも踏まないため素通りしていた（観点5「非パス形の上流前提」と観点2「実施先の違う行為」の複合）。

2. **`pfd-retro/SKILL.md:70` の起票が、issue バックエンドを持たない採用リポで実行不能になる。**
   「上流リポへの変更提案として起票する — 検出結果を捨てない」に対し、バックエンド未採用のリポには起票先が無い（probe の環境では remote も `gh` も無かった）。
   出力表の「未着手作業の発見 | issue 起票 + roadmap.pfdsl に依存チェーン追加」も同じ穴を持つ。

3. **`pfd-retro/SKILL.md:64` の宛先上書き経路が未記入プレースホルダで行き止まる。**
   「宛先の上書き・追加は pfd-ops の workflow companion に従う」→ scaffold の companion は「(経路を記載する。)」のまま。
   未記入だったときに基本表へ戻れという指示が無い。

4. **pfd-retro に前提条件が無い。**

### (a) だが判断を要するため今回は記録に留めたもの

- **L4 滞留監査に scaffold 除外が無い。** 「companion（L4）は配布されないため」という根拠は、採用直後の companion が scaffold そのままである間は成り立たない（scaffold は配布されている）。検出器の判別軸が「固有名詞を含まない」という構文だけなので、未記入の採用リポでは候補が全件偽陽性になる。
- **固有名詞の列挙が2箇所で違う。** `pfd-retro/SKILL.md:47` は「リポ名・パッケージ名・ツール名・パス」、`architecture.md:52` は「リポ名・パッケージ名・ツール名・パス・issue 番号・ADR 番号」。同じ概念の列挙が2箇所にあり、スキル自身が禁じている列挙ドリフトの形。
- **companion に書く言語の規約が無い。** scaffold は日本語、採用リポは英語のことがある。
