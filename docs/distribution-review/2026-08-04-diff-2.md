## (a) 配布プロンプトの欠陥 — 直したもの

### 版下限の根拠が実測と食い違っていた

pin を 0.0.25 へ動かした一方、その**理由**の記述が古いままだった。
「古い版は grouped `graph`/`meta`/`status` surface を持たず `unknown command` になる」と書いてあったが、実測すると 0.0.24 の `help` は3群すべてを列挙する。

```
$ npx pfdsl help   # 0.0.24
  graph summary|io|stats|neighbors|impact|depends-on|path|edges|orphans
  meta get|set|sort|reindex|check-links
  status ready|blocked|list|gaps
```

実際の理由は逆の形で、しかも質が悪い。
古い版はコマンドを**受け付けたうえで答えが少ない**。

```
### 0.0.24 graph io ###
external inputs: response_csv
terminal artifacts: digest_delivery
### 0.0.25 graph io ###
external inputs: response_csv
terminal artifacts: digest_delivery
external-stakeholder terminals:
```

エラーにならないので、版落ちは「監査したつもりで対象が減っている」という形でしか表に出ない。
記述をこの形に直した。
`unknown command` に言及する後段も、preflight が守っている失敗とは別物であることを明記した。

これは観点6「否定的能力記述の陳腐化」の型。
リリースで pin を動かすと、pin の数値は自動で追随するが**理由の散文は追随しない**。

### preflight の脱出経路が読み手に届かない順序だった

版下限未満のとき、箇条書きは「ユーザーに更新を頼み、確認が取れてから続行」を先に置き、pin 付き `npx` を「グローバル導入できない場合」として後ろに置いていた。
無人の読み手は前者で必ず止まる。
2本の probe が同じ順序で読み、同じ場所で止まってから後者へ回避した。
pin 付き `npx` を「常に使えて誰の許可も要らない経路」として先に置き、正規の導入依頼は「挙げてよいが待つ理由にはならない」と位置づけ直した。

### そのほか

- `iN_` prefix は恒久だが、成果物の門番はプレースホルダ後続プロセスを**起票より先に**グラフへ入れる。番号を採番できないこの状態の id 規約が無かった。plain で置き起票時にリネームする、`check` は通ってしまうので逸脱を `roadmap.md` に書き残す、と定義した
- プロトコル5の「新しい種類の成果物は `workflow.pfdsl` に登録してから作る」に、`workflow.pfdsl` が未採用・scaffold のままのリポ向けの分岐が無かった。あわせて**前提条件の scaffold 判定は `roadmap.pfdsl` しか読まない**ため、roadmap だけ実データで他が雛形という状態が判定をすり抜けることを明記した

理由文そのものは残した。

**指示の追加ではなく削除のため probe の再走はしていない。**
