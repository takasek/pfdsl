## 評価役に渡した課題

契約レビューには、会話を引き継がない agent を使用した。
匿名ケースごとに両 backend と architecture を渡し、正本・識別子・分類・記録の要求と配置・更新と完了を照合し、欠落・矛盾・責任逸脱を file:line と理由付きで報告させた。
維持すべき差と、参照先未確認のため判断できないものも分けるよう求めた。
ケースの出典と期待する判定は渡さなかった。

GitHub 採用側には、別の会話を引き継がない agent を使用した。
GitHub 本文だけを渡し、各ケースで次の4状況の要求・任意・未規定と次の操作を回答させた。
file 採用側にも同じ状況を file 本文だけで問うたが、agent 数の上限により、旧欠陥を既に知る agent を使ったため非盲検の補助確認とした。
W9 は契約レビューだけで評価した。

- A: roadmap 採用済みで、binding が設計記録を定めない。一次情報は読取済み、承認された小修正へ着手する。
- B: binding は設計記録を所定の場所へ残すと定めるが、commit 粒度・互換書式を定めない。記録して実装へ進む。
- C: 無関係な既存バグを直さないと今回のテストが通らない。同じ変更束で直すかを判断する。
- D: managed 分類の表示場所、記録先、完了反映の次の操作を説明する。

読み手は他方の backend、上流 repo、履歴、ネットワークを読まないよう指示した。
これは指示による範囲制限で、OS の隔離環境ではない。
返却結果は指定資料の行を根拠とし、越境した資料の引用はなかったが、操作履歴全体からのアクセス監査はしていない。
各役が複数ケースを読む1回の試行なので、ケース間学習や結果の再現性は測れていない。

## 追加所見と証拠の限界

全6ケースの file:22 にある「GitHub Issues 版がこれをマージ時点とクローズ時点に分けている」という比較説明が P3 として指摘された。
比較対象の GitHub:37 はマージ時の自動 close、:12 と :59 は完了状態の更新と push 後の回収を説明しており、主担当も原文の内部不整合を確認した。
同じ所見が6ケースに現れたのであり、6件の新規欠陥ではない。
既知3件の修正後であることを「指摘0件」の根拠にせず、追加所見として扱う。
この説明の修正は今回の方式反映に含めず、未解決として残す。
GitHub 自体の外部挙動を実験したわけではない。

採用側の回答は操作の判断であり、実際の投稿、保存、commit、ゲート実行ではない。
file 採用側の結果は独立検出実績に含めない。
参照先の work-cycle・binding・実装を与えていない範囲では、完了経路全体の実行可能性や実装との整合は未評価。
集約報告は別 agent が入力・原回答・hash と照合し、判断を変える誇張や実行検証との混同はないと確認した。

## 採用した反映と保留した案

前提は、両 backend を別々の reference として提供し続けること。
この前提を外す共通契約一本化は、片側更新漏れを減らしうるが、F1/F2 のような不要な規律の残留を防ぐこととは別であり、この実験では直接比較していない。
共通化が必要な重複を具体化したときの再検討候補として保留する。
構造に限定した機械検査も、機械判定できる参照欠落等が具体化したときの候補として保留する。
両案の費用や検出能力が劣ると確定したわけではない。
見出し差分を主な合否判定にする案は、上の取り逃がしを理由に採らない。

採用するのは、既存の変更レビューで契約と責任範囲を比較し、条件・操作順序の変更は採用側シナリオで影響を確認する方式。
通常レビューの入口を `.pfdsl/workflow.md`、比較の問いを `docs/distribution-review.md` に反映する。
比較対象は提供する2つの backend と、それらの契約を変える共有 reference。
新しい確認条件は backend 契約変更時の両版照合と、条件・操作順序変更時の採用側判断の確認であり、新しい機械状態・allowlist・合否ゲートは作らない。
確認結果は既存の PR 本文へ含める。
この評価例の全件再実施を毎回の変更へ課さず、方式変更時の評価材料とする。
静的レビューと実動作の証拠を区別し、配布レビューの承認 hash を進める根拠にはしない。
