## (a) 配布プロンプトの欠陥 — 直したもの

### 公開済み CLI に無い挙動を前提にしていた（複数 probe が到達）

`graph io` の終端一覧と `status gaps` のゼロ件メッセージについて、配布散文は #686・#687 で入った挙動を前提にしていた。
だが npm 公開版 `@pfdsl/cli@0.0.24` にその挙動は無い。
このリポの作業ツリーのビルドも `0.0.24` を名乗るため、**バージョン番号が判別子にならない**。

実測（同一ファイルに対して）:

```
公開 0.0.24: {"ok":true,"externalInputs":["a"],"terminals":[]}
作業ツリー:  {"ok":true,"externalInputs":["a"],"terminals":[],"externalTerminals":["b"]}
```

`externalStakeholders` を最終納品物に付けると `terminal artifacts:` が空になるため、ecosystem と grill の probe はどちらもグラフ破損を疑って手を止めた。
散文側をどちらの版でも成立する書き方に直し、別枠を返さない CLI 向けに `meta get` での代替手順を明示した。
CLI のリリース（`make release-status` は「2 commit 先行、要 version bump」と報告する）は次サイクルの先頭タスクとして記録する。

### 配布 scaffold が、スキル自身の指定するゲートを落とす

3つの scaffold `.pfdsl` すべてが `check --strict` で W002（criteria 欠落）になっていた。
pfd-grill は `--strict` をゲートに置き、pfd-ecosystem も `check` を要求するので、採用リポはコピーした時点でゲートを落とすファイルを持つ。
初回の #685 は同じ scaffold の `fmt` を直しており、`--strict` は残っていた。
あわせて `workflow.pfdsl` の出力 artifact が `status: done` を持っており、kind-taxonomy の「workflow は status を通常書かない」と食い違っていた。

### 配布 hook の起点判定が symlink 経路で無言に無効化される

`import.meta.url === \`file://${process.argv[1]}\`` は、Node が `import.meta.url` の側だけ symlink を解決するため、経路に symlink が挟まると常に false になる。
macOS の `/tmp` がそれに当たる。
work-cycle が「(a) 用の唯一の安全網」と書いている retro リマインダが、何も言わずに止まる形。
`isCliEntrypoint` を切り出して realpath 比較にし、テストを追加した。
同型の記述は上流スクリプト4箇所に残るが、いずれも symlink を挟まない経路で起動されるため今回のスコープ外とし、別途起票した。

### バックエンド非対称

- `file-based-tracker-backend.md` に `決定: 案N` の記法が無い。work-cycle は記法の定義をバックエンドの L3 reference に委ねているので、ファイルベースを選んだリポには定義が存在しなかった。markdown には行ごとの author が無いため、GitHub Issues 版の「起票者本人か」に相当する判別子をコミット author へ置き換えて定義した
- 同ファイルの完了規則が、`status: done` 更新とチェーン削除を同じ瞬間に置いていた。終端 artifact ではゲートが削除済みノードを指すことになり、原理的に確認できない。GitHub Issues 版と同じく2段に分けた
- pfd-retro の「起票 issue の roadmap 未追加スキャン」が `gh` のみを列挙元にしていた。初回の #683 は findings の宛先を直したが、このスキャンは残っていた

### 指示どうしの衝突・欠落

- pfd-retro「未着手作業の発見 → roadmap に依存チェーン追加」と pfd-ops プロトコル2「ゲートしない作業は roadmap に載せない」が衝突。probe は書かれていない第三の経路を自分で発明した
- pfd-retro の委譲判断が「大きい図・複数図」対「小さい図1枚のみ」で、小さい図が複数枚のとき両方に当たる
- 「監査の新パターン」の具体例の宛先が、bindings と instance カタログの2箇所に割れていた
- pfd-grill の検証ゲートが `check --strict` だけで `fmt` を含まず、通ったまま未整形のファイルが残る。companion を埋める手順も無く、図だけ完成して雛形が残る
- pfdsl SKILL.md の frontmatter 例のインライン配列（`[tag1, tag2]`）が `fmt` の正準形（`[ tag1, tag2 ]`）でない。例のとおり書くと `fmt --check` が落ちる
- 同 SKILL.md の preflight が、グローバル導入とバージョン固定 `npx` の2経路しか認めていなかった。`@pfdsl/cli` を依存に持つリポの `npx pfdsl` が想定に無い
- 同 SKILL.md の process 欄に `location:` が無い（spec は artifact と process の共有フィールドとして定義しており、V013 は #310 で撤廃済み）
- `graph orphans` は宣言済み group を必ず全件返す。group はエッジに参加しないためだが、「配線忘れの検出」としか書かれておらず偽陽性の種類が読めない
- `${CLAUDE_PLUGIN_ROOT}` のフォールバックが2分岐しかなく、どちらも解決しない読み手（skill 本文をファイルとして直接読んだ場合）に行き先が無い。のべ5本の probe が同じ場所で時間を使った。ファイル自身の所在を使う3つ目の分岐を足した
- `check-install-sync --deploy` が、出力に出さないファイル（`.claude/pfd-ops-install-manifest.json`）を書く。非採用時のメッセージも `node check-install-sync.mjs --deploy` とパスなしの裸のファイル名で、リポのルートからは実行できない
- pfd-retro の前提条件が参照先のファイル名を出していない
- architecture.md の書き分け表は `develop` 由来のゲート項目を `workflow.md` へ送るが、scaffold で「終端ゲート追加項目」の節を持つのは `roadmap.md` だけだった

## (c) 環境制約 — 配布物は直していない

- `${CLAUDE_PLUGIN_ROOT}` は probe のシェルで展開されない。plugin ホスト下では置換されるので probe 固有。ただし「解決しない読み手に行き先が無い」部分は上記のとおり (a) として手当てした
- 対話相手が居ない。pfd-ecosystem の問診、pfd-grill の後ろ向き対話はいずれも設計どおり人間を要する。probe は自分で答えを埋めたと明示して進んだ
- remote と `gh` が無いため `git fetch origin` 起点のプリフライトと PR 関連のゲートが実行不能
- サブエージェントを起動できないため pfd-lens への委譲が実行できない（委譲ブリーフの作成までで確認した）
- ops probe の `gh pr create` はハーネスのガードが拒否した

## (b) 課題設計の不備

- ecosystem と grill の sandbox で、README が実在しないファイル（`src/*.mjs` 等）を名乗っていた。quality-guide の「実装が実在するならエッジは実装で裏取り」が原理的に実行できず、2本の probe がそこで時間を使った。既存の教訓「課題の前提を sandbox の初期状態と突き合わせてから投入する」の再発で、今回は前提が課題文でなく sandbox 内の README にあった。再走では README が名指しするファイルを実際に置いた
- 初回走の ecosystem probe は上記の越境により無効
