# Reader-first 設計選択記録

## 目的

pfd-ops が要求する比較検査と着手前の公開記録を維持しながら、読者が今回確定した範囲を先に把握できる設計選択記録へ変更する。
記録は、単一案の採用と単一対案の却下だけでなく、複数軸、部分採用、保留、調査のみ、待機、実装しない決定を表現できなければならない。

## 変更前の観測

同じ bounded change のシナリオを変更前の `work-cycle.md` だけを読む fresh-context agent 5件に与えた。
4件は `前提:` を採用案より前に提示し、1件だけが採用案を先に提示した。
変更前の規則は必須情報を運ぶが、対話の出力順を契約しないため、検査手順が読者向け説明の主役になる。

最初の reader-first 案は、`提案:`、`理由:`、`前提を外した対案:`、`対案を採らない理由:` の4行を要求した。
この案は読み順を改善する一方、単一の採用案と却下済みの対案を前提にするため、保留や部分採用を記録すると必須行と処分が矛盾する。

## 公開記録契約

移行後の設計選択記録は `設計記録形式: 3` で版を宣言し、次の構造を持つ。

```text
設計記録形式: 3

決定:
- <軸名>（<実装 | 調査のみ | 待機 | 実装しない>）: <今回確定した範囲>

理由:
- <軸名>: <目的との対応>

案の処分:
- 採用 — 元候補「A」— <理由>
- 部分採用 — 元候補「B」— 採用部分: <範囲>; 残部: <却下 | 保留> — <理由または再検討条件>
- 保留 — 元候補「C」— <再検討条件>
- 却下 — 元候補「D」— <理由>

前提検査 P1:
対象: <軸名、決定、または元候補名>
前提: <候補群が共有する前提>
前提を外した案: <前提が成立しない場合の検査案>
既存候補との差分: <一致、包含、組合せを含む具体的な差分>
検査案の処分 P1: <採用 | 部分採用 | 保留 | 却下> — <理由または条件>

改訂履歴:
- なし
```

`決定:` 配下だけを今回確定した内容の正文とする。
`理由:`、`案の処分:`、`前提検査 Pn:` は正文の根拠と検査記録であり、別の決定を宣言しない。

複数の独立した設計軸がある場合は、全軸の決定を `決定:` の直下へ列挙してから根拠を記録する。
軸が一つの場合も同じ構造を使い、単一軸用の別形式は設けない。

表示種別は読者向けの分類であり、ファイル変更、外部書き込み、認証情報の利用、費用発生などの権限を付与しない。
`調査のみ` は導入や実装の許可を表さず、`待機` は再検討条件が成立するまで実行へ進まないことを表す。

`部分採用` は採用部分と残部の両方を記録する。
残部を `保留` とする場合は再検討条件を、`却下` とする場合は却下理由を書く。

issue が列挙した元候補は `案の処分:` に書き、前提検査で生成した案は対応する `検査案の処分 Pn:` だけに書く。
同じ検査案を両方へ重複させない。

前提検査は必要な数だけ `P1` から連番で繰り返す。
`既存候補との差分:` は `集合外` と `一致` の二択へ縮約せず、既存候補との一致、包含、具体化、組合せを記述する。
既存候補と一致する場合は一致先を示し、現行規則が要求する上位前提の検査結果も同じ欄へ書く。

## 改訂契約

最初の実装コミットより前に決定を変更する場合だけ、同じコメントを編集してよい。
編集後は `改訂履歴:` の `- なし` を、旧決定、新決定、変更理由、再承認URLを持つ行へ置き換える。

```text
改訂履歴:
- <旧決定> → <新決定> — <変更理由> — 再承認: <URL>
```

完全な形式3コメントを別コメントとして追加して既存記録を置換してはならない。
完全な形式3コメントが複数存在する場合は正本を推測せず fail-close とする。

最初の実装コミット後に設計変更が必要になった場合は、既存記録を着手前の決定だったように編集しない。
現サイクルを停止し、変更後の設計を別の作業単位として扱う。

## 機械検査の境界

機械検査は、自然言語の意味を推測せずに判定できる構造だけを blocking にする。

- `設計記録形式: 3` が一度だけ存在する。
- `決定:` が最初の内容セクションであり、一件以上の決定行を持つ。
- 決定行の軸名、表示種別、本文が空でなく、軸名が重複しない。
- `理由:` の軸名集合が `決定:` の軸名集合と一致し、各理由が空でない。
- `案の処分:` が一件以上あり、処分語、案名、後続本文が空でない。
- `部分採用` が採用部分と残部の処分を持つ。
- `P1` から始まる前提検査番号が重複や欠番のない連番である。
- 各前提検査が `対象:`、`前提:`、`前提を外した案:`、`既存候補との差分:`、`検査案の処分 Pn:` をこの順で一件ずつ持ち、各値が空でない。
- 処分語が `採用`、`部分採用`、`保留`、`却下` のいずれかである。
- 雛形文字列が残っていない。
- `改訂履歴:` が存在し、`- なし` と改訂項目を同時に持たない。
- 改訂項目が旧決定、新決定、変更理由、再承認参照を持つ。
- コメントの作成時刻と最終編集時刻が有効であり、遅い方の時刻が最初の実装コミットより前である。
- 完全な形式3コメントが一件だけ存在する。

ゲートの成功表示は設計記録の構造適合を表す。
設計判断の妥当性を機械的に保証したとは表示しない。

次の内容は人間がレビューする。

- issue 由来の候補をすべて処分したか。
- `決定:` と各処分が意味的に整合するか。
- 複数採用、部分採用、組合せの境界が明確か。
- 軸分割が実際の独立性を反映しているか。
- `調査のみ` や `待機` が実装の黙示的な許可として使われていないか。
- 保留に実行可能な再検討条件があるか。
- 却下理由が規律を満たすか。
- 前提が検査対象の候補群で共有されているか。
- 前提を外した案が元候補と同じ粒度か。
- 既存候補と一致する場合の上位前提検査が十分か。
- 改訂履歴が変更を正確に説明し、実際に再承認されているか。

issue 本文の Markdown 構造から推定した `optionCount` は候補の同一性を証明しないため、形式3の blocking 判定には使わない。
候補網羅性を機械的に保証したように見せず、人間レビューの責務として明示する。

## 対話契約

ユーザーへの設計提示は、今回確定する全軸の決定と理由から始める。
候補の処分と前提検査は決定の後へ置くが、bounded change でも省略しない。
対話で公開記録のトークンを逐語的に読み上げる必要はないが、承認された内容と公開記録の意味を一致させる。

## 移行互換

形式1の cutoff は `2026-08-30T09:32:50Z` とする。
この時刻より前に作成されたコメントは、旧 `前提:`、`否定案:`、`却下理由:` 形式でも有効とする。

形式2は、`2026-08-30T09:32:50Z` 以上 `2026-08-31T01:30:24Z` 未満に作成されたコメントに限り、`提案:`、`理由:`、`前提を外した対案:`、`対案を採らない理由:` の4行形式を有効とする。
形式2の既存コメントを書き換えない。

形式3の cutoff は `2026-08-31T01:30:24Z` とする。
この時刻以降に作成されたコメントは `設計記録形式: 3` と形式3の完全な構造を要求する。
形式1、形式2、形式3の候補が共存する場合は、形式3、形式2、形式1の順に優先する。
不完全な新形式の断片や不正なtimestampは、完全な旧形式記録を隠してはならない。

## 実装境界

`scripts/lib/gate-check.mjs` は形式ごとの必須構造、cutoff、record selection、content verdict を一次情報として持つ。
`scripts/lib/cycle-status.mjs` は gate-check の定数と構造定義から形式3テンプレートを組み立てる。
`work-cycle.md` は比較検査の意味、対話順、人間レビュー境界を定義し、tracker backend references は記録先と時系列契約を定義する。
canonical source を編集した後に生成コマンドを実行し、`.agents/` と Claude/Codex plugin の mirror を同じコミットに含める。

## 検証

変更前に使った bounded-change scenario を新しい `work-cycle.md` で fresh-context agent 5件に再実行し、5件すべてが決定から始まることを確認する。
複数軸、部分採用、保留、調査のみ、実装しない決定を形式3のfixtureで表現し、決定正文が先に読めることを確認する。
unit test は形式1と形式2のcutoff境界、形式3の受理、複数の完全な形式3コメントの拒否、不完全な形式3断片による旧記録のshadow防止、軸と理由の不一致、部分採用の残部欠落、前提検査番号の欠番、改訂履歴、最終編集時刻を覆う。
repository gate は skillとplugin生成物のidentity、review record、PFD snapshot、issue-flowを確認する。
