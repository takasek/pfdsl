# モデル既定と artifact 上書きの参照先 (#1542)

## 対象仕様バージョン

v0.0.29 → v0.0.30。
2026-10-26、所有者が「推奨案の3点で進めて。#1542の仕様を確定してPRにまとめたら、#1519の切替前準備も続けよう」と承認した。
採用は `baseRef` / `ref`、`{ source, revision }`、Artifact のみへの適用である。
本 proposal は spec へ統合する設計記録であり、参照解決の実装・公開の完了を表さない。

## 概要

モデル既定と artifact ごとの上書きで、成果物の場所を解決・照合する参照先を指定する。
`location` は場所、参照先はその場所が属する写し・版を表す。
Issue 本文と [決定記録](https://github.com/takasek/pfdsl/issues/1542#issuecomment-6400284280) の方向を入力とし、今回の所有者承認で名称・型・適用範囲を確定した。

## 仕様変更

### §2.2・§2.3: モデル既定と artifact 上書き

採用案Bは、モデルの `baseRef` と artifact の `ref` に `{ source: <string>, revision: <string> }` を指定する。
`source` はリソース集合を一意に識別し、`revision` はその集合内の写し・版を選択する。
どちらも空白だけではない文字列とし、Git branch の構文には限定しない。
`revision` は `main`、`approved`、`edition-2026-10` のような可変名・発行版名、または固定版を表せる。
`source` の取得方式と `revision` の解釈は利用側が供給する。
数値・真偽値・null・配列・スカラー・空mapping・片方だけの指定・未知のメンバー・空文字列・空白だけの文字列は不正である。
文字列を暗黙に trim・数値変換しない。
取得元識別子には認証情報を埋め込まず、取得側が認証を担う。

```pfdsl
---
title: Document editions
basePath: ..
baseRef: { source: document-store-A, revision: approved }
artifact:
  approved_plan:
    location: docs/plan.md
    status: done
  working_plan:
    location: docs/plan.md
    ref: { source: document-store-A, revision: working }
    status: wip
---
approved_plan >> revise -> working_plan
```

artifact の有効参照先は `artifact.<id>.ref`、モデルの `baseRef`、既存の暗黙の参照先の順で決定する。
artifact の上書きはモデル既定を丸ごと置換し、`location` の全要素と、その artifact の受入を判断する参照先に適用する。
参照先だけを指定し `location` を省略してもよい。
上書きが不正・解決不能でもモデル既定や手元のツリーへ戻さない。

### §2.3・§15.8: 場所と参照先の直交

解決入力を「有効参照先、モデルの論理ファイル位置、basePath、location」とする。
解決コンテキストは、source と revision の組を固定版・その固定版のルートへ対応付け、モデルの論理ファイル位置を明示する。
外部保管モデルでは物理的な抽出先の一時パスを論理位置として推測しない。
たとえば `.pfdsl/roadmap.pfdsl` と `basePath: ..` と `location: docs/plan.md` は、どの固定版でもルート内の `docs/plan.md` を指す。
PFD自身がその固定版に存在することは要求しない。
論理位置や取得元を一意に確定できなければ解決不能とする。
明示参照先では、論理ファイル位置と basePath と相対 location を正規化した結果が、その参照先のリソース集合内に収まることを要求する。
`..` によりルート外へ出るパスは error とし、取得側はシンボリックリンク等の解決後にも集合外の実体を代用しない。
この集合境界の条件は明示参照先にだけ適用し、無宣言の旧モデルの解決契約を変更しない。

明示参照先がある artifact は、リポ内モデルでも明示先を優先する。
絶対ファイルパスは明示参照先に対して移植可能に解釈できないため、明示参照先との併用を error とする。
両フィールドを省略する既存ファイルの絶対パス解決は変更しない。
URL は自己完結した場所として扱い、参照先で書き換えない。
glob は既存の分類を維持し、列挙を実装する利用側だけが選択先の固定版で展開する。
URLやglobの既存のリンク検査免除を、成果物の受入済みの証拠とは解釈しない。

### §2.7.1: status の意味

status は成果物の進捗・受入を述べる宣言であり、参照先の指定だけで変化しない。
場所・版の条件を criteria に明記した場合は、その条件を満たすことが done の前提となる。
記載がなければ、明示参照先がある artifact の done の既定の統合先はその有効参照先となる。
criteria は ref の値や location の解決式を自動的に書き換えない。
条件が別の場所・版を要求する場合は、その条件と宣言されたポインタを区別して根拠を示す。

§2.7.1 の「値はそのファイルを含むツリー」の規則は、明示参照先を持たない artifact に限って維持する。
PFDを含むツリーは状態宣言の版を識別し、成果物の有効参照先は照合対象の版を識別する。
同じ成果物について矛盾する状態宣言がある場合、どのモデル版を正本にするかは採用先が定める。
このフィールドから正本モデルを自動選択しない。

### process・複数ファイルへの適用範囲

採用案Bでは `baseRef` は artifact の既定だけに効き、process の `location` と `command.cwd` は変更しない。
process への `ref` 指定は error とし、§15 と §16 の両方に対称に記載する。
複数出力が異なる参照先を持つ場合も、コマンド実行先を出力から推測しない。
実行側が作業先を明示し、出力を各参照先の受入条件と照合する。
`basePath` は従来どおり process の場所と cwd にも効く。

`subflow` と `extends` の基準は従来どおりモデルファイルの位置であり、新フィールドでは切り替えない。
子PFDの artifact は子自身の宣言から有効参照先を決め、親の参照先は暗黙継承しない。
`baseRef` は表示用プリセットの継承対象に加えない。
`revises` とファイル内 ID スコープを変更せず、location による他PFD内部のノード参照も定義しない。

### 取得責務・解決不能・固定版の証拠

構文・型検査はネットワーク取得なしで行う。
参照先解決を要求する操作では、未対応の解決機能、取得元不明、版選択子不明、論理位置欠落、版不明、取得失敗、対象パス欠落を区別して失敗を報告する。
解決できなかったことと、成果物が未受入であることを同一視しない。
認証・取得・キャッシュ・作業ディレクトリの準備は利用側の責務とし、解析や描画が暗黙に取得・checkoutしない。
静的描画では宣言値を表示できるが、未解決のファイルパスを手元のファイルへのリンクとして出力しない。
URL の既存リンク表示は維持する。

可変参照は1回の検証で固定版に解決し、その検証の間は同じ固定版を使う。
証拠には対象モデルの固定版と論理ファイル位置、artifact ID、宣言した有効参照先、その取得元、解決した固定版、解決後の場所、確認結果を対応付ける。
モデル自身の取得元内の文書識別子・抽出箇所も記録し、成果物解決用の論理ファイル位置とは区別する。
同じWiki固定版の異なるページやブロックを同じ論理位置へ抽出した場合でも、証拠から元モデルを一意に識別できなければならない。
取得時刻だけでは固定版を代替しない。
版管理のない写しは内容hash等で固定する。

```text
model source: wiki-source / snapshot W / page Roadmap / block roadmap
logical model path: .pfdsl/roadmap.pfdsl
artifact: approved_plan
declared: { source: document-store-A, revision: approved }
resolved source: document-store-A
resolved snapshot: sha256:<content digest A>
resolved path: docs/plan.md
result: present; acceptance evidence recorded separately

artifact: working_plan
declared: { source: document-store-A, revision: working }
resolved source: document-store-A
resolved snapshot: sha256:<content digest B>
resolved path: docs/plan.md
result: present; still wip
```

Git 利用例では `source` を同じrepoの識別子とし、`revision` に `main` と `develop` を指定して、それぞれ取得した完全commit SHAを証拠に残す。
上記のhash表記は記録形の説明であり、実検証の証拠ではない。
source と revision をモデルに残しても、取得アダプタや論理位置は自動的には決まらない。
再現にはその解決コンテキストも識別可能に保存し、証拠から対応を確認できる必要がある。

### ADR-0051 の process/run 識別との関係

ADR-0051 の対象モデル版・PFDファイル・process ID は「どの工程を実行したか」を識別する。
新フィールドは「どの写しで成果物を解決・照合するか」を示す。
同じrunが異なる参照先の出力を生成でき、モデル版と成果物版が別の取得元に属する場合もあるため、片方だけで両方を一意に表せない。
単一ファイル・同一版の運用では取得元・固定版の情報を共用できるが、process ID と artifact ID の役割は分ける。
証拠形式やrun IDは新設せず、既存の証拠が両方の対応を運べることを求める。
ADR-0051 の「新しいPFDフィールドを追加しない」はprocess IDのグローバル化を避ける決定であり、今回の成果物参照先の禁止としては扱わない。

### 互換性・移行と診断契約

両フィールドを省略したファイルは、場所・status・cwd・複数ファイル参照とも現行契約を維持する。
新規宣言を解決できない旧実装でも未知キーが無視されるため、check成功だけでは移行成功としない。
参照先対応版を採用条件として固定し、その同じ版でモデル既定・artifact上書き・解決失敗を検証してからWiki正本を切り替える。
仕様統合、実装、採用版収録、Wiki切替は既存roadmapの別成果物を維持する。

§15に型・空値・process指定・明示参照先と絶対パスの併用・正規化後の集合外パスをerrorとして追加し、§16にも列挙する。
現行レジストリは実際に発行できるコードと照合されるため、未実装のコードを登録して実装済みと見せない。
spec §16に未実装の診断契約を別表として置き、新コードの割当・登録は後続の実装時に行う。
型違反には既存のFM004を用い、逆型指定・不正値・集合外パスのerrorと解決操作の失敗理由は仕様として確定する。
解決機能を持たない構文checkerが静的検査のみ成功した場合、参照解決の検証を行っていないことを利用側に明示する。

## 設計判断

所有者が案Bを採用した。
他の名称と文字列キー案は不採用とし、意味や取得方式の要件が変わった場合に再検討する。
process適用案は不採用とし、成果物の受入先と実行文脈を別々に指定する必要が生じた場合に独立した提案として再検討する。

| 軸 | 採用案B | 対案と扱い |
| --- | --- | --- |
| 名前 | モデル `baseRef` / artifact `ref` | `baseBranch` は版をbranchに限定すると誤読される。他の名称案も比較したうえで、所有者が既定と上書きの対応を示す採用名を選んだ。 |
| 値の型 | `{ source, revision }` | 候補Aは参照先識別子の文字列。簡潔だが取得元と版を外部束縛だけから読むことになる。所有者がモデル内で両方を読めるBを選んだため不採用。 |
| 解決の共有前提 | 宣言と取得処理を分離する | 全取得規則を言語に内蔵する案も可能だが、必要な業種・取得方式の集合は未確定なので保留。必要な共通プロトコルが判明したら再検討する。 |
| 適用対象 | artifact のみ | process locationへの適用案は、成果物の照合先と実行文脈を分ける所有者判断により不採用。command.cwdも切り替える案では、実行可能な参照先と複数出力の扱いを別途設計する必要がある。 |
| 言語外に置く案 | 比較として残す | 全情報を設定・証拠に置く案は、Issue本文の「言語フィールドとする」という所有者決定と矛盾するため今回の採用候補から除く。取得を設定側が担う部分は両案に利用できる。 |

候補A/Bに共通する前提は「参照先を場所と独立した宣言としてモデルに持つ」である。
その前提を外す言語外設定案を上記の所有者決定と比較した。
候補Aは単なる現状維持ではない競合案として比較した。
たとえば複数repoの同じ `main` を扱う場合、Aは名前ごとの外部束縛を要し、Bは `source` の違いをモデル内に示せる。
Bでも取得・論理位置のコンテキストは必要なので、Bが外部設定を完全に不要にするとは主張しない。
Bは取得元と版の両方をモデル内で読める利点から採用した。
2026-10-26の所有者判断に基づき、仕様本文へ統合する。

## 影響範囲

- spec §2.2、§2.3、§2.7.1、§15.8、§15.18、§16とspec-historyへ統合する。§2.9のファイルローカルID・subflow・extendsの契約は変更しない。
- core: 型、frontmatter保持、schema、正準化、メタデータ編集・差分・export、診断の対応を実装工程で行う。
- CLI・リンク検査・エディタ・renderer: 参照先を無視したローカル解決を防ぎ、解決済みか未解決かを区別する。
- sample・fixture・生成スキル: 仕様例と参照を更新し、未実装の現時点では対応済みと表示しない。
- Wiki取得アダプタ: 参照先ごとの固定版と論理位置のコンテキストを供給し、証拠との対応を検証する。
- 独立レビュー・仕様本文・履歴・後続依存の整合確認を経て#1542を完了する。実装・採用版検証・Wiki切替は別成果物として維持する。

### 起草チェックと後続の検証ケース

- 型専用指定: processへのref指定のerrorを§15と§16の両方へ追加する。
- 例示: artifactとprocessは本文のedgeに参加し、2つのartifactが同じパスを異なる参照先で指す。
- 分類境界: URL・glob・相対パス・絶対パス・空値・型違反・部分mappingを扱う。
- 互換性: 無宣言の旧モデルでパス・status・cwdの意味を維持する。
- 取得失敗: 宣言した版に対象パスがなく、手元に同名ファイルがある場合でも代用しない。
- 可変参照: 検証中にbranchが進んでも同じ固定版を利用し、別の検証では新しい固定版を証拠に残す。
- 上書き: モデルsource Aとartifact source Bを部分合成せず、artifactのmappingを丸ごと使う。
- 複数ファイル: 親の参照先でsubflowやextendsの解決先を変えない。
- 複数出力: 異なる参照先のartifactを生成してもcommand.cwdを自動選択しない。
- 証拠: Wikiモデル版Wと成果物版C、同名processを含む2つのPFDを区別する。
- 集合境界: basePathとlocationの組合せによるルート外参照と、集合外へ到達するリンクを代用しない。
- モデル識別: 同じWiki版の異なるページを同じ論理位置に抽出しても、元の文書と抽出箇所を証拠から区別する。

これらは後続実装に渡す検証契約であり、現行CLIで新フィールドを解決できたという結果ではない。
