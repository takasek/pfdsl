# Standalone レビューの比較と課題分析

両評価は、ソースと図の同期や標準的な編集能力を長所としつつ、診断への入口と狭幅 Connections の読みづらさを共通して指摘した。
Astra は表示領域の切替、Sol はエラー修正中の図の参照を重点的に検討している。
この二つは別の課題であり、片方への対応だけで両方が解消するとは限らない。
同じ製品版を対象とした2026年10月28日の Claude 評価を追加した。
診断位置と typo の見落とし、大きい図の探索、文書操作のメニュー、状態表示と衝突確認、Finder との統合は、従来の分析を補う論点である。
以下は報告と保存した証拠を照合した分析であり、保存担当による製品の再操作評価ではない。

## 課題ごとの事実と未決事項

### 診断の認知と移動

両者は件数表示から問題箇所へ進む入口を見いだせず、エディタの F8 では説明と場所へ移動できた。
Sol は F8 を既知の Monaco 操作として試したと明記している。
課題の仮説は「問題へ移動する能力が利用者の知識に依存している」であり、移動機能が存在しないことではない。

件数から次の問題へ移る案、短い一覧を開く案、メニューとショートカットを案内する案がある。
件数の少ない文書と複数警告のある文書で、どの入口なら場所と内容を把握できるかが判断材料になる。
実際の初見利用者の発見率・修正時間は今回測定していないため、一覧パネルの新設を必須条件にはできない。

[Claude の A1](claude/review.md)では、V003 の marker が typo のある行ではなく先頭行に現れる例をブラウザで観察した。
一方、Astra・Sol が F8 で確認した W002 には実際の場所が示されている。
したがって、問題へ移る入口の発見性と、移動先が修正対象を指すかは別の課題である。
[静的集計](claude/evidence/diagnostic-ranges.txt)には zeroRange を使う出力箇所を持つ41コードと、実位置を持つ出力箇所の6コードがある。
分類は重複し、全ての経路やグラフ診断が常に先頭行になるという意味ではない。

また、`venue_contract` を `venue_contractX` に変えた[前後の CLI 診断](claude/evidence/typo-before-check.txt)と[変更後の診断](claude/evidence/typo-after-check.txt)では、警告が8件から7件に減っている。
原報告では、元の成果物の W002 が消え、別の未定義 ID が新ノードとして扱われたと説明している。
警告数の減少だけを修正成功と解釈できず、未知の ID が意図した追加か誤記かを利用者が確かめる手掛かりも検討対象になる。
未定義 ID を許す言語の性質を維持し、近い ID の案内や Quick Fix の候補は、似た正当な ID を誤って誘導しないか比較する必要がある。

Claude の M2・M3 は、提案モデルの問題一覧について得た条件である。
問題解消後の選択先と、衝突確認中に一覧から許す操作を定義する問いとして残す。
現行アプリに問題一覧の選択残存や modal 越しの操作という不具合を観察したものではなく、ペインへの配置や全面的な無効化を採用済みとも扱わない。

### 狭い領域での関係の読取り

両者がブラウザ幅600px・左右50%で、Connections の三列内の文字分断を観察した。
[Astra の R2](astra/review.md)の画面観察でも、中心ノードと入力・出力ラベルの途中折返しを確認できる。
これは関係の向きと名前を一緒に読む課題であり、三列という表示形式そのものの廃止を導く根拠ではない。
Sol は十分な幅では形状と前後関係を保つ三列表示を長所とした。

狭幅で縦並びにする案と詳細領域へ切り出す案がある。
名前の長さ、隣接ノード数、日本語、ソース側の必要幅、popup とキーボード操作の保持が判断条件になる。
ネイティブの最小幅・境界値・折返し条件は未実測で、600pxをそのまま実装の閾値にはできない。

### 編集と図の確認に必要な面積

Astra の R3 は、狭幅でソース行と図の文字を同時に読むことの難しさを扱う。
Sol の13ノードで Fit が21%となった記録は、図全体を収めることと文字を読むことが異なるという観察である。
両者の倍率や図のサイズを横並びの性能指標にしてはいけない。

ソースのみ／図のみへの切替は一案だが、図の読取りには既存の Focus selected node と Connections も使える。
表示モード、拡大率、全体から対象への移動を一つの解決策として混ぜず、どの作業がどの状態で詰まるのかを分けて検討する必要がある。
表示切替で狭幅の可読性が改善するかは、実画面では検証していない。

[Astra の R3](astra/review.md)が挙げた案の条件には、切替時の選択・カーソル・未保存状態の保持と、図側で問題を選んだ際にソースを見せることがある。
図のみの表示でも未保存状態を識別できること、非表示のエディタへの操作をどう扱うかも、表示切替案を検討する条件になる。
これらは提案の条件であり、現在の製品でその切替や実フォーカス移動を受入済みという意味ではない。

また、[Sol の D4 と幅変更の操作記録](sol/design-review.md)では、幅を変えると図の一部が領域外へ出て、Fit で戻せることも観察されている。
この対策を検討する場合は、手で調整したパンや倍率を毎回奪わず、注目点を新しい領域内に保つ案を比較する。
全体を収めるための自動 Fit と、読んでいる対象を保つことは同じではない。

Claude の A2 は、約750行の図をネイティブで開き、Fit が11.6%、表示領域を広げても17.1%となった観察を加えている。
editor 検索で対象を選択・パンしても倍率は小さいままで、Focus selected node を別途使うと100%で読めたと記録している。
図内の検索、group 単位の概観、選択時の自動拡大は異なる案であり、対象を探す作業と全体の関係を読む作業のどちらを助けるかで比較する。
Claude は直前が Fit 状態の場合だけ幅変更時に Fit をやり直す案を挙げており、手動の倍率を常に初期化する案とは区別する。
Connections の高さや caret 追従のパンが読取り領域を変える観察もあり、領域を広げるだけで解消すると決めない。

Claude の A5 では、ネイティブの縮小ウィンドウで sidebar を出すと editor と Find 欄が狭まり、ファイル名も省略で見えなくなると報告している。
sidebar の収納、両ペインの最小幅、表示切替、ファイル名を残す表示は比較候補である。
この追加観察によって Astra・Sol のネイティブ狭幅が確認済みになるわけではなく、OS と操作条件の差も残る。

### エラー時の参照と編集の整合

Sol は循環エラー V010 で図・操作が無効になり、Connections が閉じることを記録した。
[Sol の操作記録](sol/task-log.md)と[AX 記録](sol/evidence/native-cycle.ax.txt)がその状態を示す。
不正な現在ソースに対する図編集を止めることと、以前の関係を参照できなくなることは分けて評価する。

旧図を残す案には、版の表示、参照専用化、初回から不正な場合、非同期解析、複数文書ごとの版の対応という設計論点がある。
さらに [Sol の D2](sol/design-review.md)は、保存成功や通知の取消によって、現在ソースのエラーと旧図の鮮度表示を消さないことを案の条件にしている。
鮮度表示を一時通知だけに置くと、保存メッセージへの置換や通知取消で旧図を現在版と取り違える余地が残る。
旧図と現在ソースの対応を保証できない場合は、編集だけでなく、旧ノードから現在ソースへの無条件な移動も許さないという条件がある。
一方で診断と移動を充実させ、旧図を残さない案も Sol 自身が挙げている。
現時点の課題は「修正に必要な参照をどこで確保するか」であり、「図キャッシュを追加すること」を要件として確定する段階ではない。

### 操作の階層と書体

両者は、拡大縮小・対象への移動・Connections・Help が同じ強さで連続する点を指摘した。
一方でパン・ズーム・Fit は実際に動き、Sol は選択対象を100%へ戻せた。
機能を追加する話と、既存操作の役割を見分ける話を分ける必要がある。

[Astra の R4](astra/review.md)には、Help を開くと説明の段落が図の高さを減らすという観察もある。
ボタンのグループ化や折返しだけでは、操作を調べながら図を見る際の領域不足は解消しないため、補助説明の提示方法も検討対象になる。

書体の違いは両者の第一印象に現れるが、serif 自体が不適切という結論ではない。
21%での読みにくさを、100%での書体選択の欠陥へ転写しない。
画面用の変更が出力図にも影響するか、日本語 fallback やラベルと ID の役割をどう扱うかが別の判断条件になる。

Claude の A7 は ID を上段、label を下段に置く現在の表示と、空状態・sidebar の枠付きボタンの主従も検討対象にしている。
label を強調すると source の ID と照合する作業が難しくならないかを確かめ、書体の変更だけでこの役割分担まで解決したと扱わない。

### 文書と参照操作の入口

Claude の A3 では、書き出し、Go to Line、構造比較などの既存機能を、README とブラウザのパレット・右クリックを調べてから発見した。
評価対象版のネイティブメニューにも Find・Create Definition・図の Fit 等はあるため、全機能がメニューにないという指摘ではない。
メニューバーとパレットの役割、標準と PFDSL 専用の定義移動が並ぶ場合の名前の区別、実行環境で使えないコマンドの見せ方を検討する論点である。
具体的なメニュー名とキー割当は提案に留め、ブラウザの F1・F8 の成功をネイティブのショートカット受入へ広げない。

### 文書識別と衝突確認の結果

Claude の A4 では、パスの反復、通知による下端の高さ変化、衝突確認の語彙と最初の差分への移動を課題に挙げた。
通知を短くする案は、保存失敗や未解決状態を見逃させない条件と合わせて検討する。
前述のエラー・鮮度表示まで一時通知とともに消す案ではない。

M1 は、保存から開いた衝突確認と、閉じる途中で開いた確認の見た目が同じでも、決定後は前者が保存して残り、後者が保存して閉じるという観察である。
確認の起点と結果を文言でどう示すかを検討する材料になる。
観測した editor・ディスクの版にだけ決定が効くこと、編集内容と閉じる意図を保持することを、表示変更でも維持する。

### Finder と Recent の境界

Claude の A6 では、Recent のパス全文・整理手段の不足と、平坦な sidebar 表示を観察した。
Finder 連携の不足は document type と open event のコード探索からの推測で、Finder から開く操作は未確認である。
表示や履歴の整理と OS 経由のファイル受取を分け、後者は既存の選択フォルダ単位の権限境界との整合を確認する。
Claude は Recent 一覧を事前に用意してファイルを開いており、通常の初回 Open の動線を成功した証拠にはしない。

### 保存と読込の結果差

| 操作経路 | Astra | Sol |
| --- | --- | --- |
| Save As | 無効状態から完了せず | 初回は無効。ウィンドウを Raise して開き直すと成功 |
| 保存後の再編集と Command-S | 保存完了の検証なし | ファイル内容と表示の更新を確認 |
| Recent からの再読込 | 未確認 | 文書・ラベルの復帰を確認 |
| Open ダイアログから確定 | Open が無効で完了せず | 行選択後も Open が無効で完了せず |
| ビルド条件 | dev／debug、評価専用識別子等 | release、評価専用識別子 |

Sol の成功は保存全般が常に壊れるという説明への反例だが、Astra の観察を取り消す根拠ではない。
両者の Open の詰まりは共通した観測であり、原因は製品・OS・操作ツールの前面状態のどこにあるか未分離である。
通常の配布構成、人の操作、前面状態を揃えた場合を比べるまで、製品バグの確定や重大度の決定は保留する。
今回の記録にはデータ消失の観測はないが、競合や破損からの復旧全般の受入を示すものでもない。

Claude は File › Save のディスク反映、外部変更、衝突確認、閉じる確認で編集が保持される経路を操作したと記録している。
Save As と Open/Save パネルでの選択は未確認であり、既存二者の経路表を全て成功へ更新する根拠にはならない。

## 現段階の課題構造

分析上は、診断と図操作の発見、必要な領域の確保、エラー中の参照と整合、ファイル操作の検証条件、という四つの問いに分けられる。
Claude の追加評価により、診断の位置と誤記の識別、文書コマンドの発見、状態表示と確認結果、OS とのファイル受取境界も個別に検討する問いとなった。
診断への入口を改善しても狭幅の文字分断は残り、表示切替を設けても旧図と現在ソースの版の問題は残る。
ツールバー、表示モード、Connections は同じ画面領域を使うため、個別案が互いに領域を奪う可能性もある。
これは記録から立てた仮説で、採用する構成を決めたものではない。

既存の同期、F8、キャンセル時の保持、Fit、対象への拡大、十分な幅での Connections の役割は、変更を検討する際にも残したい観測済みの性質である。
不足情報は各課題の判断材料であり、対応範囲や案の採否を左右する不確実性を課題ごとに確認する。
調査・比較を始める範囲の判断と、解決案の採用判断は分ける。
